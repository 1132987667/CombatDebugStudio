**Step 1: BuffConfigResolver.buildEffectPlan — 删除 4 个旧格式兼容块**

文件: `src/domain/buff/atomic/BuffConfigResolver.ts`

改动: 删除第 69–117 行全部 4 个 `// 兼容旧格式` 代码段。`effects[]` 为空且非 trigger-only 时返回空 plan。

额外: 未知原子效果类型从 `console.warn + continue` 改为 `throw new Error`。

```typescript
private buildEffectPlan(raw: Record<string, any>): ResolvedEffectPlan[] {
  const plan: ResolvedEffectPlan[] = []
  const rawEffects = raw.effects ?? []
  for (const rawEffect of rawEffects) {
    const handler = this.registry.get(rawEffect.type as AtomicEffectType)
    if (!handler) {
      throw new Error(
        `[BuffConfigResolver] ${raw.id}: 未知原子效果类型 "${rawEffect.type}"`
      )
    }
    plan.push({
      type: rawEffect.type as AtomicEffectType,
      handler,
      params: rawEffect.params ?? {},
    })
  }
  // 不兼容旧格式——没有 effects[] 就是空 plan，让调用方决定如何处理
  return plan
}
```

验证: `npm run typecheck` → 检查是否有调用方依赖返回的 plan 包含旧格式派生项。

## 风险与注意事项

1. **Step 1 会崩启动**：删除旧格式兼容后，任何还在用 `attributes`/`controlType` 的 JSON buff 都会在解析时得到空 plan。需要评估 `configs/buffs/buffs.json` 中有多少 buff 还没迁移到 `effects[]`。如果数量多，可能需要在执行 Step 1 前先迁移一批 JSON。

2. **Step 2 合并 Path C→B 需要确认**：Path C 目前的调用方——`removeBuff`、`refreshBuff`、`updatePerTurn`——对 Path C 都只是"无操作"，所以合并是安全的。但 `applyBuffImmunities` 的副作用（`characterImmunities` 集合）需要确认 Path B 的 immunity handler 是否已经替代了这个职责。

3. **Step 4 的调用链影响**：`evaluateCondition` 的调用方在 `PassiveSkillManager.ts` 内部 `evaluateConditions` 方法（第 498 行），需要确认调用处是否传递了 `conditionParams`。

## 验证方案

```bash
npx vue-tsc --noEmit          # 类型检查
```

- Step 1/2 后：大量 buff 配置相关测试可能因 `effects[]` 缺失而失败

- 最终运行 `npm run dev` 确认启动无异常
