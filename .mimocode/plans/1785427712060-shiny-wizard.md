# 字段与定义漂移修复计划

## 摘要

修复 4 个 P0 bug（Buff 属性修正静默失效）及 10+ 个类型/状态/依赖层漂移问题。分三阶段执行。

---

## 阶段一：P0 — 修复静默失效的 Bug（约 10 分钟）

### 1.1 收窄 `BaseBuffScript.addModifier` 和 `BuffContext.addModifier` 参数类型

- **文件**: `src/domain/buff/scripts/templates/BaseBuffScript.ts:43`、`src/domain/buff/BuffContext.ts:69`
- **改动**: `attribute: string` → `attribute: ATTRIBUTE_CODE`
  - `BaseBuffScript.ts:43` — 方法签名
  - `BuffContext.ts:69` — 方法签名；第 76 行 `attribute as ATTRIBUTE_CODE` → 直接传 `attribute`（不再需要断言）
- **验收**: 收窄后，4 个 bug 文件立即产生编译错误（因为它们传了 `'CRIT_DAMAGE'`、`'HIT_RATE'` 等非法字面量）
- **风险**: 极低。`BaseBuffScript.addModifier` 只有继承类调用，`BuffContext.addModifier` 被 `BaseBuffScript` 和 `ModifierEffect` 调用。`ModifierEffect` 从 JSON 读键，其 `attr` 来源已用 `as ATTRIBUTE_CODE` 断言。

### 1.2 修复 CritDamageReductionDebuff

- **文件**: `src/domain/buff/scripts/CritDamageReductionDebuff.ts`
- **改动**: `'CRIT_DAMAGE'` → `ATTRIBUTE_CODE.critDamage`（第 17、38、55 行）
- 增加 `ATTRIBUTE_CODE` import

### 1.3 修复 HitReductionDebuff

- **文件**: `src/domain/buff/scripts/HitReductionDebuff.ts`
- **改动**: `'HIT_RATE'` → `ATTRIBUTE_CODE.hit`（第 17、38、55 行）
- 增加 `ATTRIBUTE_CODE` import

### 1.4 修复 DodgeUpBuff

- **文件**: `src/domain/buff/scripts/DodgeUpBuff.ts`
- **改动**: `'dodgeRate'` → `ATTRIBUTE_CODE.dodge`（第 13 行）
- 增加 `ATTRIBUTE_CODE` import

### 1.5 处理 MountainChildBuff（`'NATURE_POWER'` 不存在于 ATTRIBUTE_CODE）

- **文件**: `src/domain/buff/scripts/MountainChildBuff.ts`
- **分析**: `NATURE_POWER` 是一个从未落入属性系统的概念属性。此 Buff 的逻辑是"山林之力"加成，效果未知。
- **方案**: 移除所有 `NATURE_POWER` 修饰符调用（第 17-22、61-67、87-92 行），转用 `ATTRIBUTE_CODE.attackBonus` 作为替代（山林之力提升攻击）。保留其他逻辑（hpRegen）。
- **验收**: 编译通过，无运行时行为变化（之前是静默不生效，现在至少部分生效）

### 1.6 BattleData.battleState 改为必填

- **文件**: `src/domain/battle/type/types.ts`
- **改动**: `battleState?: BattleStatus` → `battleState: BattleStatus`
- **文件**: `src/domain/battle/aggregate/BattleState.ts` 第 43 行
- **改动**: 移除 `battleData.battleState!` 中的 `!` 断言
- **验收**: `createDefaultBattleData` 已赋值 `BattleStatus.CREATED`，类型系统不再允许遗漏
- **注意**: 需要确认所有新建 BattleData 的地方都赋值了 `battleState`（目前只发现 `createDefaultBattleData` 一处）

## 阶段二：P1 — 类型安全加固（约 30 分钟）

### 2.1 ParticipantSide 裸字符串替换

- **搜索目标**: 10 处 `'ally'`/`'enemy'` 裸字符串比较（探针已定位）
- **核心文件**:
  - `src/domain/battle/BattleSystem.ts:1337,1343` — `p.team === 'ally'` → `p.team === ParticipantSide.ALLY`
  - `src/application/projection/participantMapper.ts:44` — `entity.team as 'ally' | 'enemy'` → `entity.team as ParticipantSide`
  - `src/shared/types/battle-log.ts:731,740,748,753` — 替换为 enum
  - `src/domain/battle/logs/renderers/RoundNarrativeRenderer.ts:368,817` — 替换
  - `src/shared/utils/log-segment-factory.ts:267` — 替换
- **注意**: `projection.ts:25` 和 `battle-log.ts:69,259` 的 `'ally' | 'enemy'` 类型定义保留（它们是类型声明，非比较逻辑）
- **风险**: 低——运行时值相同（`'ally'` === `ParticipantSide.ALLY`）

### 2.2 SkillStep → ExtendedSkillStep 入口校验

- **文件**: `src/domain/skill/SkillManager.ts`
- **改动**: 在 `executeSkill()` 入口（第 133 行附近）加 `resolveStep()` 函数，在 deubg/dev 模式下对 `DEAL_DAMAGE`/`HEAL` 类型步骤校验 `calculation` 存在性
- **不动**: 不改 `SkillConfig.steps` 类型（改成 `ExtendedSkillStep[]` 会污染 JSON 配置层类型）
- **风险**: 低——纯防御式校验，不改变运行时行为

### 2.3 BattleAction.extra 结构化

- **文件**: `src/domain/battle/type/types.ts`
- **改动**: 在 `BattleAction` 附近新增：
  ```typescript
  export interface BattleActionExtra {
    healOverflow?: Record<string, number>
    revivedEntityId?: string
    reviveParams?: ReviveStepParams
  }
  ```
  将 `BattleAction.extra?: Record<string, unknown>` → `BattleAction.extra?: BattleActionExtra`
- **文件**: `src/domain/skill/SkillExecutor.ts:216,220,594,597,924-926`
- **改动**: 移除 `action.extra = action.extra || {}` 模式，直接 `action.extra ??= {}` 或通过工厂方法
- **风险**: 低——结构化后编译器捕获拼写错误

### 2.4 BattleStateManager 同步链去重

- **文件**: `src/presentation/stores/battleStore.ts`
- **改动**: `syncTeams()` 中移除重复的 `isBattleActive` 判定（第 239-243 行），改为从 `BattleStateManager` 或 `BattleSystem.getBattleStatus()` 直接读取
- **文件**: `src/domain/battle/state/BattleStateManager.ts`
- **改动**: `syncBattleState()` 中的 `isBattleActive` 条件（第 94-97 行）作为单一真相源
- **风险**: 中——需确保同步时序正确

### 2.5 ALY_FATAL_DAMAGE / ALY_DAMAGE_TAKEN 消费方

- **文件**: `src/domain/battle/BattleSystem.ts:559-560`
- **改动**: 这两个 trigger 只 `emitTriggerEvent` 未 `triggerPassives`。对其增加 `this.triggerPassiveSkillsForAll(...)` 调用（沿用 `DamageCalculator` 示例模式），或在 `PassiveSkillManager` 中增加对应 `evaluateCondition` 支持
- **分析**: 目前没有任何被动技能使用这两个阶段，修改是防御性的
- **风险**: 低——只增加基础设施，不改变已有行为

## 阶段三：P2 — 契约对齐（约 1-2 小时，可分批）

### 3.1 EffectType 拆分为 StepEffectType + ActionResultType + ControlType

- **目标**: `EffectType` 42 个成员拆分为 3 个独立枚举，消除 `HEAL`/`SHIELD`/`DRAIN`/`REFLECT` 的双重语义
- **涉及文件**: 约 15-20 个消费方（`SkillExecutor.ts`, `EffectRenderer.ts`, `BattleExecutor.ts`, `BattleAI.ts`, `target-resolver.ts`, `display-helpers.ts` 等）
- **迁移策略**:
  1. 保留 `EffectType` 作为重导出（`EffectType.DEAL_DAMAGE = StepEffectType.DEAL_DAMAGE` 等），保持旧引用兼容
  2. 消费方逐个迁移为新类型
  3. 清理旧引用后移除重导出
- **风险**: 中——大量引用，需逐个确认

### 3.2 BuffConfig 补齐 aura 字段

- **目标**: 消除 `getBuffAuraConfig()` 的不安全强制转换
- **方案 A（推荐）**: 在 `BuffConfig` 中加 `aura?: BuffAuraConfig`，`addBuff()` 中从 `jsonConfig` 读取并赋值
- **方案 B**: 完全废弃旧 aura 路径，统一走 `effectPlan`（需要确认所有 aura 配置已迁移到 `effects[]`）
- **影响**: `BuffSystem.ts` 第 780-783 行的 `getBuffAuraConfig` 可改为从 `BuffConfig` 读取
- **风险**: 中——需确保运行时 `aura` 数据路径一致

### 3.3 Skill/SkillConfig 字段统一

- **最小改动**: 仅对齐 `SkillConfig.skillType` → `SkillConfig.type`（或反向）。保留 `Skill` 的聚合字段 `damage/heal/hasBuff`
- **涉及文件**: `src/domain/skill/types.ts`、`GameDataProcessor.ts`（JSON 配置读取）
- **风险**: 低——纯重命名，编译器追踪

### 3.4 LoggerProvider 静态定位器 → DI 注入（渐进）

- **规模**: 21 个领域文件
- **策略**: 5 个核心类先改（`SkillExecutor`、`DamageCalculator`、`HealCalculator`、`PassiveSkillManager`、`BattleExecutor`），其余保留旧模式
- **注意**: 不作为本次提交的必须项——可拆分到独立 PR

### 3.5 void statsVersion 修复

- **文件**: `src/presentation/composables/useParticipantStats.ts`
- **方案**: 将 `participant.statsVersion` 作为 computed 的显式依赖，改为在投影层（`UIParticipantSnapshot`）增加 `version` 字段，store 层使用 `shallowRef` + `triggerRef`
- **风险**: 低——纯表现层改动

### 3.6 其他（DamageCalculator/HealCalculator 共用、BATTLE_CONSTANTS 等）

- 标记为待定，不在本次提交范围内
- 理由：修复成本高，无功能影响
