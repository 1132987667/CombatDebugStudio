# BattleExecutor 数据流重塑 — 修复三个风险点

## 背景

上一轮评审识别出 BattleExecutor 的三个风险点，用户提交了最终修改方案（5 个步骤）。逐行核对后，方案中的部分代码与现有实现有接口偏差（虚构 API、硬编码错误、日志顺序/类别回归风险），本计划在忠实落地用户意图的前提下修正这些偏差，并保持重构前后行为一致。

**三个风险点**：
1. **状态泄漏（P0）**：`pendingDeaths` / `currentActionOrder` 是实例级可变状态，`BattleSystem.resetBattle()` 未重置，跨战斗残留。
2. **DTO 职责混淆**：`targetResults` 是内联匿名对象（BattleExecutor.ts:405-412），无类型契约。
3. **God Method + 异常路径**：`selectAndExecuteSkill`（332-753）内联全部日志；catch（706-721）静默降级为随机普攻，无用户可见警告日志。

## 涉及文件

| 文件 | 改动 |
|---|---|
| `src/domain/battle/service/BattleExecutor.ts` | 主改动（reset / DTO / helper / 日志发射器） |
| `src/domain/battle/BattleSystem.ts` | `resetBattle()` 加一行 `this.executor.reset()` |

## 改动 1：`BattleExecutor.ts` — reset()（风险点 1）

在 `drainPendingDeaths()`（110-118）附近新增：

```ts
/** 重置跨回合/跨战斗的可变状态。由 BattleSystem.resetBattle() 调用。 */
reset(): void {
  this.pendingDeaths = []
  this.currentActionOrder = 0
}
```

`traceCounter` 不重置（trace id 带 `Date.now()`，单调递增无害，重置反而引入同毫秒冲突）。

## 改动 2：`BattleSystem.ts` — resetBattle() 接线

`resetBattle()`（1228-1244）开头新增 `this.executor.reset()`（executor 字段在 :115）。

## 改动 3：`BattleExecutor.ts` — 局部 DTO（风险点 2）

类外部（import 之后）新增两个 interface：

```ts
/** 目标结算结果 —— 仅用于日志渲染的局部视图模型，随方法作用域结束销毁 */
interface TargetResult {
  target: BattleEntity
  hpBefore: number
  hpAfter: number
  damage: number      // token 记录值（= 现有 targetResults.finalDamage，settleDamage 返回值只进 overkill）
  heal: number
  rawDamage: number   // 保留：action 日志"造成 X 点伤害"用 rawDamage（现有 496/1172 行）
}

/** 行动表现清单 —— 伤害结算与日志拼装之间的局部数据契约，仅在方法内流转 */
interface ActionManifest {
  type: 'skill' | 'attack'
  source: BattleEntity
  targets: BattleEntity[]
  skillName: string
  skillId?: string
  isMiss: boolean
  isCrit: boolean     // 提级到 manifest：现有 isCrit 是全局判定（allEffects.some，501-503），非 per-target
  results: TargetResult[]
}
```

需确认 `LogSegment` 类型已导入（文件已导入 `skillSegment` 等，缺则补 `import type { LogSegment } from '@/shared/types/battle-log'`）。

## 改动 4：`BattleExecutor.ts` — helper 提取（风险点 2 配套）

新增两个 private 方法（实现按用户方案）：

- `buildEntitySegment(entity, isSelf = false): LogSegment` — `[阵营前缀]名`，classStr 按 `entity.team === ALLY ? 'log-friendly' : 'log-hostile'`，`kind: 'entity'` + `faction`。
- `buildValueSegment(value, type: 'damage' | 'heal'): LogSegment` — classStr `log-damage`/`log-heal`，kind 同 type。

## 改动 5：`BattleExecutor.ts` — 重构 selectAndExecuteSkill（风险点 3）

**保持不变的部分**（严格保留，动画时序不动）：
- 方法签名、技能可用性校验、`getSkillTargets`、BEFORE_ATTACK 被动缓冲、`executeSkill` 循环 + `recordCombatRecord` 循环（含 TraceDamageLogger try/catch）。
- 动画三分支结构：伤害路径（511-565，flight → resultMap 聚合 → settleDamage/overkill → impact）、治疗路径（566-577，`damageToken.applyAll()` + `triggerDirectImpactAndWait`，**不填 targetResults**）、零值路径。
- `isCrit` 计算（501-503）、`overkillMap`（548-549）。
- 复活结算（724-737）、AFTER_ATTACK 被动（739-749）、`recordBattleAction`（751）。

**替换的部分**：
1. `targetResults`（405-412 内联匿名类型）→ `const manifest: ActionManifest`（`results` 初始为 `[]`），结算循环（545-556）填充 `manifest.results`（元素按 TargetResult 结构，damage/heal 用 token 记录值，hpAfter 为扣血后快照）。
2. 内联 action 日志 + sub 日志块（604-677）→ `this.emitSkillLog(battleData, manifest)`。
3. 零值分支内联日志（680-705）→ 同样 `this.emitSkillLog(battleData, manifest)`（results 为空 → category STATUS）。
4. catch（706-721）新增降级警告日志（风险点 3 修复目标），其余保留：

```ts
LoggerProvider.logger.addBattleLog({
  turn: battleData.currentTurn,
  message: `${source.name} 尝试使用 ${skill.name} 时发生异常，降级为普通攻击`,
  segments: [
    this.buildEntitySegment(source),
    { text: ' 尝试使用 ' },
    { text: `【${skill.name}】`, classStr: 'log-skill' },
    { text: ' 时发生异常，降级为普通攻击', classStr: 'log-info' },
  ],
  category: BATTLE_LOG_CATEGORIES.STATUS,
  meta: { role: 'action', skillName: skill.name, error: true },
})
```

## 改动 6：`BattleExecutor.ts` — 新增 emitSkillLog / emitAttackLog，删除 generateAttackLogParams

**新增 `private emitSkillLog(battle: BattleData, m: ActionManifest)`**，按用户方案结构，但修正 4 点（均与现有行为对齐）：

1. **日志顺序**：action header → `LoggerProvider.logger.flushBufferedSubLogs()` → results sub。现有顺序即 action(604) → flush(641) → sub(644-677)，BEFORE_ATTACK 被动 sub 日志必须保持在 action 与 result 之间（RoundNarrativeRenderer 按序挂 subs）。
2. **category**：`totalDmg > 0 ? DAMAGE : totalHeal > 0 ? HEAL : STATUS`（用户方案漏 STATUS 分支，零值时会错误输出 HEAL）。
3. **meta 补全**：`role: 'action'`、`entityId`/`hpBefore`/`hpAfter`（取 `results[0]`，≈ 现有 `logTarget` = pendingDamages[0].target）、`damage: totalDmg`、`crit: m.isCrit`、`kill: results[0]?.target 未存活`（缺失会导致 RoundNarrativeRenderer 的回合"击杀!"标签与 ✦ 高亮丢失）、`skillName`。
4. **文本口径**：header 的"造成 X 点伤害"用 rawDamage 总和（现有 496 行用 `totalRawDamage`），"恢复 X 点气血"用 heal 总和；技能段复用现有 `skillSegment(skillId, this.skillManager)` + try/catch 回退（不手写 hover 段）。
5. targets 段按用户方案逐个 `buildEntitySegment`（含 `t.id === source.id ? '自身'` 判断）并用 ', ' 连接。

**新增 `private emitAttackLog(battle: BattleData, m: ActionManifest)`**，按用户方案结构，修正 3 点：

1. **miss 分支**：category STATUS；action meta 用现有字段 `{ role, entityId, miss: true, skillName }`；"被闪避!" sub 保留现有 classStr `'log-heal'`（现存样式，勿改）。
2. **hit 分支**：category `m.isCrit ? CRIT : DAMAGE`（现有 generateAttackLogParams 967-969 逻辑）；message 由 segments join 生成（用户方案漏了 `[友方]/[敌方]` 前缀）；"造成 X 点伤害"用 rawDamage（现有 1172 行）；action meta.damage 用 rawDamage、sub meta.damage 用 finalDamage（现有 1186/1204 口径）；meta 含 `kill: !target.isAlive()`。
3. 纯治疗技能不产出 sub 日志是现有行为（治疗分支不填 results），emitSkillLog 的 heal sub 分支仅为"伤害+治疗混合技能"服务，保持。

**删除 `generateAttackLogParams`（895-971）**：被 emitAttackLog 取代，调用方仅 handleMissAttack(1071)/handleHitAttack(1163)，无外部引用（BattleExecutor 仅被 BattleSystem 引用，后者不调它）。

**替换调用点**（动画/结算/被动逻辑保留在 handle 方法内，仅日志块替换）：
- `handleMissAttack`：1071-1097 两个 addBattleLog → `this.emitAttackLog(battle, { type: 'attack', source, targets: [target], skillName: '普通攻击', isMiss: true, isCrit: false, results: [] })`
- `handleHitAttack`：1163-1205 两个 addBattleLog → `this.emitAttackLog(battle, { type: 'attack', source, targets: [target], skillName: '普通攻击', isMiss: false, isCrit: isCritical, results: [{ target, hpBefore, hpAfter, damage, heal: 0, rawDamage }] })`

**`executeAction` 技能路径（1465-1702）不动**：独立入口（预构建 action 执行），日志结构不同（单目标、action.turn、isCrit 来自 skillAction），用户方案未覆盖，保持最小 diff。

## 用户方案修正点汇总（为什么偏离用户给的代码）

| # | 用户方案 | 实际修正 |
|---|---|---|
| 1 | `playFlightAnimation/playImpactAnimation` | 不存在；用 `animationManager.triggerFlightPhaseAndWait/triggerImpactPhaseAndWait`，参数与现有 513-519/559-565 完全一致 |
| 2 | `TargetResult.isCrit` 硬编码 false | isCrit 提级到 manifest，全局判定（现有 501-503） |
| 3 | emitSkillLog 在 flush 之前输出 results | 保持 action → flush → results 顺序 |
| 4 | category `totalDmg>0 ? DAMAGE : HEAL` | 补 STATUS 分支 |
| 5 | meta 缺 kill/entityId/hpBefore/hpAfter | 补全（kill 影响回合标签） |
| 6 | catch 用 `log-warning` | 样式不存在，改用 `log-info`（_battle-log.scss:307 有样式） |
| 7 | emitAttackLog message 无前缀、用 finalDamage | segments join 生成（带前缀）；rawSuffix 用 rawDamage |
| 8 | TargetResult 无 rawDamage、damage 用 settleDamage 返回值 | 保留 rawDamage；damage/heal 用 token 记录值（护盾吸收时数值与现有一致） |
| 9 | 手写技能 hover 段 | 复用现有 `skillSegment()`（含 try/catch 回退） |

**已知的有意行为变化**（可接受，执行时验证）：
- 多目标混合阵营时，action header 目标名从"整段统一色"变为"按目标独立着色"（更精确；单目标/同阵营场景零差异）。
- 零值分支技能名获得悬浮提示（复用 skillSegment 后），现有无 hover。

**范围外发现（不做）**：TraceLogCollector 跨战斗累积 — `exportAll()`（BattleSystem.ts:1178）自带清空（TraceLogCollector.ts:189-190），泄漏面小且用户方案未要求。

1. **类型检查**：`npm run typecheck`（ActionManifest/TargetResult/LogSegment 无报错）。
2. **现有测试无回归**：`npm run test`（8 个 unit + e2e；reset() 为两行赋值属琐碎逻辑，按 AGENTS.md 不新增测试）。
3. **手动验证**（`npm run dev`）：
