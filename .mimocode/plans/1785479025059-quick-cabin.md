# 消灭 20 处启发式猜测反模式 — 实施计划

## 一、目标与原则

**目标**：数据生产者（配置层/领域层）显式声明业务语义；契约在唯一边界 `BuffConfigResolver.resolve()` 强制；下游删除全部猜测代码（正则/阈值/ID 前缀/字段存在性/鸭子类型/翻译表）。

**三条原则**：
1. 语义由生产者声明，消费者只读取
2. 契约在唯一边界强制执行，而非消费点各自防御
3. 命名约定升级为显式字段（`polarity`/`executionMode`/`{value,type}`/`category`/`severity`/`conditionLabel`）

**已确认决策**（用户）：
- 属性值**全量迁移为 `{ value: number, type: 'PERCENTAGE'|'ADDITIVE' }` 对象格式**
- severity **按显式动作类型判定**（录制时写入）
- 回放时序**统一到单一时间源**（接受回放速度变化，属预期行为修正）
- 每完成 5 项汇报一次进度（按 #1-5 → #6-10 → #11-15 → #16-20 编号顺序）

## 三、契约边界设计（BuffConfigResolver.resolve() 增强）

`ResolvedBuffConfig` 新增/修改：
- `polarity: 'positive'|'negative'|'neutral'` — 缺失时按 controlType(非NONE→negative)/tags(dot|poison|debuff→negative)/facet 推导，推导失败 `throw`
- `description: string` — 缺失时用 effectSummary 自动生成（不再依赖 LogTooltipResolver 三级回退）
- `effectSummary: string` — 从 effectPlan(MODIFIER attributes 用 getAttrName+{value,type} 格式化"攻击↑20%")/duration("2回合"/"永久")/maxStacks 派生**静态部分**（层数/剩余回合是运行时数据，不进 resolve）
- `executionMode: 'script'|'effectPlan'|'triggerOnly'|'marker'` — 推导：registry.has→script（由 BuffScriptRegistry.getResolvedBuffConfig 补充）；effectPlan.length>0→effectPlan；triggers.length>0→triggerOnly；否则→marker
- `triggers[].phase` — 用 OLD_PHASE_NAME_MAP 归一化为 BattleTriggerPhase 枚举，未知值 `throw`
- `attributes` 值类型 → `{ value: number, type: 'PERCENTAGE'|'ADDITIVE' }`

## 七、风险清单

1. **phase 归一化**：BuffSystem 现消费 raw triggers（addBuff :441-483 手动拼的 resolvedConfig.triggers），必须改为读 resolve 输出的归一化 triggers，否则 eventBus.on 用旧名静默失效——测试守护
2. **classifyBuff 必填 polarity**：BuffSystem:710、SkillExecutor:460 两处先改读 resolved.polarity，编译器强制
3. **aura value ×100 迁移**：0.1→10 后必须同步删除三处 `<1` 修正，否则 double-scale
4. **#13 签名变更**：BattleAI createAIWithSkills 调用方（BattleSystem 初始化）需注入 registry，编译期强制
5. **`this.speed`（播放倍率）与行动者 speed（属性）语义区分**：时序公式必须显式分流
6. **effects.json 迁移**：19 条逐个核对，`defenseReduction: 0.7 → -30%` 语义在迁移时固化（写为 `{ value: -30, type: "PERCENTAGE" }`），不得依赖原量级规则
