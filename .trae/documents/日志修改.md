战斗日志系统优化改造计划
一、目标概述
精简 BattleLogEntry 类型：移除冗余字段，仅保留核心数据，降低内存占用与传输开销。

统一转换逻辑：实现 BattleAction → BattleLogEntry 专用转换方法，确保日志生成准确、可复用。

全面采用 LogSegment[]：所有日志的渲染均基于结构化片段，支持更丰富的色彩与样式，同时移除对 htmlResult 等字符串格式的依赖。

二、当前类型分析与精简方案
现有 BattleLogEntry 字段（src/types/battle-log.ts）
```
export interface BattleLogEntry {
  turn: string          // 必需
  source: string        // 必需
  action: string        // 必需
  target: string        // 必需
  result: string        // 可被 segments 替代
  level: BattleLogMessageType   // 必需
  category: BattleLogCategory   // 必需
  htmlResult?: string   // 冗余，由 segments 动态渲染
  type?: BattleLogType  // 可推导，移除
  isHit?: boolean       // 可嵌入 segments 元数据
  isCrit?: boolean      // 同上
  skillName?: string    // 同上
  subEffects?: string[] // 可转为多个 segment
  segments?: LogSegment[]  // 新结构，将成为主要载体
}
```
精简后类型定义
```
export interface BattleLogEntry {
  turn: string          // 回合标识（如 "回合1"）
  source: string        // 动作发起者名称
  action: string        // 动作描述（如 "攻击"）
  target: string        // 目标名称（可能为空）
  level: BattleLogMessageType   // 日志级别（info/warning/error）
  category: BattleLogCategory   // 业务分类（damage/heal/status等）
  segments: LogSegment[]        // 结构化日志片段（必需）
}
```
说明：

移除 result、htmlResult、type、isHit、isCrit、skillName、subEffects，所有展示信息均通过 segments 表达。

segments 成为必需字段，渲染时完全依赖该数组生成显示内容。

LogSegment 接口保持不变（包含 text 和 color 字段）。

三、核心转换方法设计
3.1 函数签名
ts
function battleActionToLogEntry(
  action: BattleAction,
  battleState: BattleState,
  options?: {
    turnNumber?: number;          // 可指定回合号，否则从 action.turn 或 battleState 推导
    sourceIsAlly?: boolean;       // 可预计算，避免重复查询
    targetIsAlly?: boolean;
  }
): BattleLogEntry;
3.2 转换逻辑步骤
提取基本信息

turn：优先使用 action.turn，若不存在则取 battleState.currentTurn + 1 或 1。

source：根据 action.sourceId 从 battleState.participants 获取角色名，若为 'system' 则设为 '系统'。

target：根据 action.targetId 获取角色名，若无则为空字符串。

action 字段：固定为 "对" 或由动作类型决定（如 "攻击"、"施放"），可简化为固定值或省略，因为片段会详细描述。

确定分类与级别

category：根据 action.type 和 effects 决定（damage / heal / crit / status / system）。

level：默认 'info'，错误日志标记为 'error'。

生成片段数组

调用现有 BattleLogFormatter 中的 formatXXXHTML 系列函数，将其返回的 htmlResult 解析为片段数组，或直接复用内部的片段生成逻辑。

若无法复用，则重新实现一套基于 LogSegment 的构造器。

组装最终对象

返回包含 turn, source, action, target, level, category, segments 的对象。

注意：此方法应集中处理所有动作类型（普通攻击、技能、治疗、buff、系统消息等），确保类型安全且无遗漏。

四、现有代码调整范围
4.1 类型定义修改（src/types/battle-log.ts）
按上述精简方案修改 BattleLogEntry 接口。

同步更新 LogSegment 相关工具函数（如 getSegmentClass），确保颜色映射正确。

4.2 日志生成方法重构
battleStore.ts

修改 addLog 方法，移除 result 和 htmlResult 参数，改为接收 segments: LogSegment[]。

重构 parseBattleAction 方法，内部调用 battleActionToLogEntry 获取完整日志对象。

调整 syncBattleLogs 中的日志添加逻辑，直接使用 addLog 传入 segments。

BattleLogManager.ts

修改 addLog、addSystemBattleLog 等方法，统一使用 segments 结构。

移除内部对 htmlResult 的处理，日志存储仅保留 segments。

4.3 日志渲染组件修改（src/views/BattleLog.vue）
模板中保留 v-if="log.segments" 分支，直接遍历 segments 生成带样式的文本。

移除对 log.htmlResult 和 log.result 的渲染，确保所有日志均通过 segments 展示。

更新 getSegmentClass 映射，若颜色映射不存在则使用默认样式。

4.4 其他依赖调整
搜索项目中对 BattleLogEntry 的引用，确保所有创建日志的地方都改为使用 segments。

检查 DebugLogDialog 等调试组件，若展示原始日志需适配新结构。

五、验收标准
BattleLogEntry 类型已精简，仅包含必要字段。

所有战斗日志均通过 segments 数组渲染，无 htmlResult 或 result 的使用。

新增的 battleActionToLogEntry 方法能准确转换所有动作类型，并通过单元测试。

战斗日志在 UI 中显示正确，颜色分类符合设计规范。

无编译错误，且运行性能未下降。
