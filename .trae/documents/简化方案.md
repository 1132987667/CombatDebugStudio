针对您提出的问题——职责过细、同步复杂、多层嵌套，确实是当前战斗系统设计中需要优先解决的核心痛点。一个良好的设计应当既保持模块的清晰边界，又避免不必要的间接通信，同时让数据流向一目了然。下面我将分享一套旨在简化这些问题的设计思路，供您参考。

设计目标
职责聚合而非碎片化：将紧密相关的功能合并到同一模块，减少跨模块通信。

单向数据流：状态变化可预测，数据流向单一，易于追踪。

UI与核心的轻量同步：消除手动同步层，利用框架的响应式能力自动反映状态变化。

核心业务逻辑独立：核心战斗逻辑仍应保持与UI框架无关，便于测试和复用。

1. 核心状态管理：单一数据源
   问题：当前 BattleData 散布在多个管理器（TurnManager、ActionExecutor 等）中，需要维护多个映射，且 BattleStateManager 负责手动同步到UI。

思路：将战斗状态封装为单一的、可观察的“战斗上下文”对象，该对象包含战斗所需的所有可变数据（参与者、回合信息、行动记录等）。所有战斗核心组件（回合管理、动作执行、AI）都直接操作这个上下文，而不是各自持有部分数据的副本。

typescript
// 简化的战斗上下文
class BattleContext {
// 使用普通的 JavaScript 对象，但在 Vue 中可以通过 shallowReactive 使其响应式
public state = {
battleId: string,
participants: Map<string, BattleParticipant>,
turnOrder: string[],
currentTurnIndex: number,
currentRound: number,
isActive: boolean,
winner?: ParticipantSide,
actions: BattleAction[],
// ... 其他状态
};

// 提供修改状态的方法，方便在内部逻辑中直接修改，但所有修改都会触发通知
public update(partial: Partial<BattleContext['state']>) {
Object.assign(this.state, partial);
this.notifyChange(); // 内部触发 UI 更新
}

// 观察者模式：UI 可以订阅变化
private listeners = new Set<() => void>();
public subscribe(listener: () => void) { this.listeners.add(listener); }
public unsubscribe(listener: () => void) { this.listeners.delete(listener); }
private notifyChange() { this.listeners.forEach(fn => fn()); }
}
优点：

所有战斗逻辑共享同一个状态源，无需多处同步。

状态变化通过 update 方法集中管理，便于追踪（可加入日志）。

为 UI 同步提供了天然的观察者接口。

2. 职责合并：将控制类整合为“战斗控制器”
   问题：自动战斗、手动干预、回放等功能各自有独立管理器，它们都需要访问战斗核心，导致通信开销和类数量爆炸。

思路：创建一个统一的 BattleController（或 BattleOrchestrator），将战斗的控制逻辑（自动、手动、回放）集中在一起。控制器内部可以包含不同的“模式”策略，但对外只提供一组简单的接口。

typescript
class BattleController {
constructor(private context: BattleContext) {}

// 自动战斗模式
private autoMode = false;
private autoTimer?: any;

startAuto(speed: number) {
if (this.autoMode) return;
this.autoMode = true;
this.runAutoLoop(speed);
}

stopAuto() { this.autoMode = false; clearTimeout(this.autoTimer); }

// 手动干预：直接执行动作
executeManualAction(action: BattleAction) {
// 验证动作合法性，然后调用战斗系统的动作执行器
new ActionExecutor(this.context).execute(action);
}

// 回放模式：接管控制权
startReplay(events: BattleEvent[]) {
// 暂停自动战斗，进入回放状态
this.stopAuto();
// 逐帧播放事件...
}

// ... 其他控制方法
}
优点：

将分散的控制逻辑整合到一个类中，外部只需与 BattleController 交互。

内部可以灵活切换模式，但对外隐藏复杂性。

减少了跨模块通信，因为所有控制逻辑都直接操作同一个上下文。

3. 消除手动同步层：利用响应式系统
   问题：BattleStateManager 需要监听事件、维护映射、手动更新 UI 角色，导致复杂且易错。

思路：放弃“纯核心不与UI通信”的约束，让 UI 直接订阅核心状态的变化，并利用 Vue 的响应式系统自动更新。具体做法：

将 BattleContext 的状态对象设计为 Vue 的响应式对象（例如使用 shallowReactive 包装其 state 属性）。

UI 组件可以直接导入并使用这个响应式状态，无需任何同步层。

当核心逻辑通过 context.update(...) 修改状态时，由于状态是响应式的，所有依赖它的 Vue 组件会自动重新渲染。

typescript
// 在 Vue 组件中
import { battleContext } from '@/core/battle/context';

const participants = computed(() => battleContext.state.participants);
const turnOrder = computed(() => battleContext.state.turnOrder);
// 模板中直接使用 participants、turnOrder 等
优点：

彻底消除 BattleStateManager 及其映射关系、事件监听等复杂性。

数据流变成单向：核心修改状态 → 响应式系统 → UI 更新。

调试时只需关注核心状态的变化，UI 自动反映。

注意：这要求核心状态对象本身必须是响应式的（Vue 的 reactive），或者我们采用“状态容器 + 发布订阅”的方式，然后在 UI 层将其转换为响应式（如使用 ref(battleContext.state)）。为了保持核心的框架无关性，可以让核心提供一个普通的对象，由 UI 层在初始化时将其包装为响应式。

4. 简化事件通信：用直接调用替代事件总线
   问题：当前使用 eventBus 在核心与 UI 之间传递日志、动画事件等，导致数据流向难以追踪。

思路：对于同步需求（如状态更新），采用上述的“响应式状态直接绑定”；对于异步事件（如日志、动画），可以使用简单的回调或 Promise，而不是全局事件总线。

例如，当核心需要记录一条日志时，可以直接调用一个注入的日志处理器：

typescript
// 在 BattleContext 中注入日志处理器
class BattleContext {
constructor(private logger: (log: BattleLogEntry) => void) {}

private recordAction(action: BattleAction) {
this.actions.push(action);
this.logger(createLogFromAction(action));
}
}
在 UI 层初始化核心时，传入一个将日志添加到 UI Store 的函数：

typescript
// 在 Vue 组件或启动文件中
const battleContext = new BattleContext((log) => {
battleStore.addLog(log); // 直接调用 store action
});
对于动画事件，可以采用类似的方式，通过回调触发 UI 动画。

优点：

消除了全局事件总线的模糊性，调用关系显式化。

数据和事件流变得可预测，易于调试。

核心仍然不依赖 UI 框架，只依赖简单的函数接口。

5. 模块内部保持内聚，但减少外部暴露
   虽然我们合并了控制类，但战斗核心内部的模块（如 TurnManager、ActionExecutor）仍可保留，但应作为内部实现细节，不对外暴露。它们可以直接操作 BattleContext，通过构造函数注入。

typescript
class BattleEngine {
private turnManager: TurnManager;
private actionExecutor: ActionExecutor;
private aiSystem: AISystem;

constructor(context: BattleContext) {
this.turnManager = new TurnManager(context);
this.actionExecutor = new ActionExecutor(context);
this.aiSystem = new AISystem(context);
}

// 对外只暴露一个执行回合的方法
public async processTurn() {
const actorId = this.turnManager.getCurrentActor();
const action = await this.aiSystem.decide(actorId);
await this.actionExecutor.execute(action);
this.turnManager.advance();
}
}
优点：

内部职责仍然清晰，但外部只看到 BattleEngine 一个入口。

减少了外部直接与多个管理器交互的复杂性。

总结
通过上述设计思路，我们可以：

合并控制类，减少跨模块通信和类数量。

利用响应式状态，消除手动同步层，让 UI 自动更新。

用直接调用替代事件总线，使数据流向清晰可追踪。

保持核心内部模块化，但通过一个统一的引擎暴露必要功能。

这样的架构既简化了外部使用，又保持了内部的可维护性，同时也满足了调试工具需要的高透明度和可干预性。希望这些思路能对您的重构工作有所帮助，我们可以进一步讨论具体的实现细节。

1. 构建单一可观察的战斗上下文（BattleContext）
   目标：将战斗所有可变状态（参与者、回合信息、行动记录等）集中到一个对象中，作为整个战斗系统的“唯一事实来源”。

操作：

创建一个 BattleContext 类，内部维护一个普通 JavaScript 对象 state（包含 participants、turnOrder、currentTurn 等）。

提供 update(partialState) 方法统一修改状态，并在方法内部触发变更通知（观察者模式或直接依赖 Vue 响应式）。

移除 BattleData 在多个管理器中的分散存储，所有管理器（TurnManager、ActionExecutor 等）在构造时注入 BattleContext，直接读取和更新 context.state。

2. 合并控制逻辑为 BattleController
   目标：将自动战斗、手动干预、回放等控制功能从多个独立管理器集中到一个类中，减少跨模块通信和类数量。

操作：

创建 BattleController，构造函数接收 BattleContext。

将原 AutoBattleManager、InterventionManager、BattleReplayManager 的功能内聚到 BattleController 的不同方法或内部策略中。

对外仅暴露一组简洁的控制接口（如 startAuto(speed)、executeManualAction(action)、startReplay(events) 等），内部根据模式切换逻辑。

3. UI 直接订阅核心状态，消除 BattleStateManager
   目标：利用 Vue 的响应式系统，让 UI 组件自动反映核心状态的变化，彻底移除手动同步层 BattleStateManager。

操作：

将 BattleContext 的 state 设计为响应式对象。有两种实现方式：

方案 A：在核心层使用 Vue 的 shallowReactive 包装 state，但核心层会依赖 Vue（可接受则选此）。

方案 B：核心层保持普通对象，在 UI 层（如 Pinia store 或组件）中将其包装为 reactive 或 ref，并订阅 BattleContext 的变更通知（例如通过 watch 或自定义订阅）。

移除 BattleStateManager 及其事件监听、映射关系维护等代码。UI 组件直接通过 import { battleContext } from '@/core/battle/context' 读取状态并渲染。

4. 用回调替代事件总线处理日志/动画等异步事件
   目标：将模糊的全局事件通信改为显式的回调注入，让数据流向更清晰。

操作：

在 BattleContext 构造函数中接受日志处理器函数（如 (log: BattleLogEntry) => void）和动画触发器函数（如 (animationData: AnimationData) => void）。

核心内部在需要记录日志或触发动画时，直接调用这些回调函数，将数据传递给 UI。

UI 层在初始化核心时传入这些回调，回调内部直接操作 UI 的 Store 或触发动画组件的方法。

移除所有对 eventBus 的依赖，事件总线在重构后可彻底废弃。

5. 内部模块保留但对外隐藏
   目标：保持内部职责清晰（如 TurnManager、ActionExecutor 等），但对外部（UI 层）仅暴露 BattleEngine 或 BattleController 一个入口。

操作：

将 TurnManager、ActionExecutor、AISystem 等设计为 BattleEngine 的内部依赖，由 BattleEngine 在构造时实例化并传入 BattleContext。

对外只提供 BattleEngine.processTurn()、BattleEngine.getContext() 等必要方法，外部不直接与内部管理器交互。

这样既保证了模块的可测试性和可维护性，又简化了外部使用。

6. 实施顺序建议
   第一步：创建 BattleContext 类，将现有 BattleData 迁移进去，并逐步改造现有管理器，让它们接收 BattleContext 并直接操作其 state。

第二步：合并控制类为 BattleController，将 AutoBattleManager 等逻辑内聚，并调整调用方（如 Vue 组件）使用新的控制器。

第三步：实现 UI 对核心状态的直接订阅。先选择一种响应式方案（建议方案 B，保持核心独立），然后移除 BattleStateManager。

第四步：用回调替换事件总线。在 BattleContext 构造函数中增加回调参数，并逐步替换原有 eventBus.emit 调用。

第五步：最后将 BattleEngine 作为对外统一入口，隐藏内部管理器。

7. 注意事项
   渐进式重构：每一步完成后进行充分测试，确保战斗逻辑和 UI 交互不受影响。

依赖注入简化：由于类数量减少，可以简化甚至移除原有的复杂 DI 容器，改用简单的构造函数参数传递。

类型安全：利用 TypeScript 严格定义 BattleContext 的 state 类型，以及回调函数的类型。

性能考量：状态更新频繁时，避免在 update 中触发大量不必要的 UI 渲染。Vue 的响应式系统已足够高效，但需注意合理使用 shallowReactive 或细粒度的计算属性。
