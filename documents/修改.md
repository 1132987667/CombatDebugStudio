## 优先级 P0 — 功能性 Bug（必须修复）

### P0-1. ShieldBuff._onApply 写入错误变量值（第 39 行）

**文件**: `src/domain/buff/scripts/ShieldBuff.ts:14-39`

**严重程度**: 严重

**问题描述**: 第 14 行 `const shieldValue = this.getConfigValue(context, 'shieldValue', -1)` 声明了一个局部 `const` 变量。当进入 `else` 分支（第 19-35 行，处理 `shieldPercent` 或公式计算分支）时，`shieldValue` 仍然是 `-1`。但第 39 行：

```typescript
context.getBuffSystem()?.setShieldValue(context.characterId, shieldValue)
```

使用了原始 `shieldValue`（即 `-1`），而非计算得到的实际护盾值。影响路径：

- **`applyShield` 触发器**（`triggers/index.ts:220-232`）传入 `{ shieldPercent: 0.1 }`，不传入 `shieldValue` → 进入 `shieldPercent` 分支 → 计算出 `computed = Math.floor(maxHP * 0.1)` → `context.setVariable('shieldValue', computed)` → 但第 39 行仍用 `-1` → **shieldValues 被设置为 -1**
- **`executeShield`**（`SkillExecutor.ts:803-843`）传入 `{ shieldValue: 100 }` → 进入第 15 行 `shieldValue >= 0` 分支 → `context.setVariable('shieldValue', 100)` → 第 39 行正确设置 `100`。**这条路径侥幸正确。**

**建议修复**: 第 39 行使用已写入 context 变量的值（三个分支都调用了 `context.setVariable('shieldValue', ...)`）：

```typescript
const actualShield = context.getVariable<number>('shieldValue') ?? 0
context.getBuffSystem()?.setShieldValue(context.characterId, actualShield)
```

### P0-2. BuffSystem.addBuff 护盾后处理导致双倍累加（第 713-718 行）

**文件**: `src/domain/buff/BuffSystem.ts:713-718`

**严重程度**: 严重

**问题描述**: `addBuff` 在脚本 `onApply` 和 effectPlan 执行完毕后，**无条件**从 `resolvedConfig.parameters?.shieldValue` 读取值并累加到全局 `shieldValues`：

```typescript
const shieldValue = (resolvedConfig.parameters?.shieldValue as number) ?? 0
if (shieldValue > 0) {
    const current = this.getShieldValue(characterId)
    this.setShieldValue(characterId, current + shieldValue)
}
```

**触发条件**: 此问题仅在 `parameters.shieldValue > 0` 时触发。影响以下路径：

| 路径 | ShieldBuff/Script 已设置 | 此代码再累加 | 结果 |
|------|------------------------|-------------|------|
| `executeShield` 传 `shieldValue: 100` | `_onApply` 设 shieldValues=100 ✅ | `current+100=200` | **双倍** ❌ |
| `applyShield` 传 `shieldPercent` | `_onApply` 设 shieldValues=-1(P0-1) | `shieldValue=0` 不执行 | 值=-1 ❌ |
| effectPlan 有 ShieldEffect 无 `parameters.shieldValue` | `ShieldEffect.onApply` ✅ | `shieldValue=0` 不执行 | 正确 ✅ |
| effectPlan 有 ShieldEffect 同时有 `parameters.shieldValue` | 两者都设 | **双倍** ❌ |

对于 `buff_shield` 脚本，`ShieldBuff._onApply` 已经设置了 shieldValues，此后的累加导致双倍（100 → 100 + 100 = 200）。

**建议修复**: 此段代码应与 effectPlan/旧脚本路径二择一。`ShieldEffect` 和 `ShieldBuff` 都已各自管理 `shieldValues`，**删除此段代码**是最干净的方案。保留它仅适用于"纯 JSON 配置的无脚本/无 effectPlan 护盾 Buff"这种边缘场景，即使如此也应为**覆盖而非累加**。

### P0-3. BuffSystem.removeBuff 护盾回收使用静态原始值（第 929-938 行）

**文件**: `src/domain/buff/BuffSystem.ts:929-938`

**严重程度**: 严重

**问题描述**:

### P0-5. ShieldBuff._onUpdate 用本地变量覆盖 BuffSystem.shieldValues（第 59-61 行）

**文件**: `src/domain/buff/scripts/ShieldBuff.ts:59-61` + `src/domain/battle/entity/BattleParticipantImpl.ts:619-624`

**严重程度**: 严重

**问题描述**: 护盾值存在两个"副本"：

1. `BuffSystem.shieldValues` — 全局聚合值，由 `takeDamage`（`BattleParticipantImpl.ts:624`）直接消耗
2. `BuffContext` 变量 `'shieldValue'` — ShieldBuff 的本地视图，不反映吸收

当 `ShieldBuff._onUpdate` 的 shieldRegen 触发时：
```typescript
const newShield = Math.min(currentShield + shieldRegen, maxShield)
context.setVariable('shieldValue', newShield)
context.getBuffSystem()?.setShieldValue(context.characterId, newShield)  // ← 覆盖全局值
```

如果 `takeDamage` 在两次 `_onUpdate` 之间消耗了护盾，shieldRegen **不是"恢复"** 而是**覆盖**——它用本地变量中的旧值加恢复量，写回全局，**擦除了 takeDamage 的吸收效果**。

**建议修复**: shieldRegen 应从 `BuffSystem.getShieldValue()` 读取当前值做增量恢复：

```typescript
const currentGlobal = context.getBuffSystem()?.getShieldValue(context.characterId) ?? 0
const regened = Math.min(currentGlobal + shieldRegen, maxShield)
context.setVariable('shieldValue', regened)
context.getBuffSystem()?.setShieldValue(context.characterId, regened)
```

## 优先级 P1 — 逻辑缺陷

### P1-1. effectPlan 原语的 onRemove 未受错误边界保护

**文件**: `src/domain/buff/BuffSystem.ts:905-910`

**严重程度**: 严重

**问题描述**: 脚本 `onRemove`（经 `BuffErrorBoundary.wrap`）和 effectPlan 的 `onRemove`（裸调用）的安全级别不同。若任意原子效果的 `onRemove` 抛出异常，后续的 `isActive = false`、`buffInstances.delete`、修饰符清理、触发器反注册均不会执行 → **内存泄漏**。

```typescript
BuffErrorBoundary.wrap(() => {
    instance.script.onRemove(instance.context)      // 有保护
})
// ★ 数据驱动：执行 effectPlan 中各原语的 onRemove 清理
const buffResolved = this.scriptRegistry.getResolvedBuffConfig(instance.buffId)
if (buffResolved?.effectPlan) {
    for (const effect of buffResolved.effectPlan) {
        effect.handler.onRemove(instance.context, effect.params)  // ← 无保护
    }
}
```

**建议修复**: 将 effectPlan 的 `onRemove` 循环移入 `BuffErrorBoundary.wrap`，或逐元素加 try-catch。

### P1-3. addBuff 中 BuffErrorBoundary 返回值未检查——onApply 失败不回滚

**文件**: `src/domain/buff/BuffSystem.ts:630-677`

**严重程度**: 严重

**问题描述**: `BuffErrorBoundary.wrap(() => { script.onApply(buffContext) })` 的返回值（可能为 null）完全被忽略。如果 `onApply` 抛出，代码继续执行 effectPlan 原语、注册触发器、触发属性变更。结果是 Buff 实例被部分初始化地存入 `buffInstances`，没有回滚。当后续 `removeBuff` 被调用时，`onRemove` 会在部分初始化状态上执行。

### P1-8. `addBuff` 免疫检查中 `immuneTagMatch` 语义错误

**文件**: `src/domain/buff/BuffSystem.ts:500-507`

**严重程度**: 中等

**问题描述**:

```typescript
const immuneTagMatch = resolvedConfig.immunities?.some((tag) =>
    targetImmunities.has(tag.toLowerCase()),
)
```

`resolvedConfig.immunities` 是此 Buff **授予目标**的免疫标签（如"获得眩晕免疫"），`targetImmunities` 是角色已有的免疫集。这里检查的是"Buff 授予的免疫标签是否与角色已有免疫重叠"——即"这个 Buff 的增益是否冗余"，而非"角色是否对该 Buff 免疫"。

前两个检查（`controlTag`、`buffTag`）是正确的角色免疫检查。`immuneTagMatch` 的方向不对——应检查的是 **buff 自身的标签**（如 `'burn'`、`'slow'`）是否在角色免疫集中，而非检查 buff 授予的免疫标签。

**建议修复**: 根据 `resolvedConfig.tags` 检查（区分授予的免疫与自身的标签），或移除 `immuneTagMatch` 分支只保留 `controlTag`/`buffTag`。

## 优先级 P3 — 代码质量/可维护性

### P3-1. 多条护盾路径并存，职责边界模糊

**文件**: 跨文件

**严重程度**: 设计

**问题描述**: 当前系统中有三条护盾值管理路径：

1. **旧脚本路径**（`ShieldBuff.ts`）：`_onApply` → `setShieldValue`，`_onRemove` → `setShieldValue(0)`，`_onUpdate` → 每秒恢复
2. **新原子效果路径**（`ShieldEffect.ts`）：`onApply` → `getShieldValue + setShieldValue`，`onRemove` → `Math.min` 扣减

**建议修复方向**: 
- 删除 `BuffSystem.ts:713-718` 和 `929-938` 的硬编码逻辑
- `ShieldEffect` 和 `ShieldBuff` 二择一保留（迁移到 effectPlan）
- 显式守卫：effectPlan 含 `shield` 类型时跳过旧脚本路径

## 附录：第一性原理架构审查

> 以下分析从架构根基出发，不修具体 Bug，而是指出导致这些 Bug 的系统性设计问题。

### 原理 1：单一数据源（SSOT）

> 每份数据应该只有一个权威存储位置。

**违反**: 护盾值有三个"权威"——`BuffSystem.shieldValues` Map、`BuffContext.variables['shieldValue']`、`resolvedConfig.parameters.shieldValue`。三者各自写入，互不同步。

**直接后果**: 6 个 P0 中有 4 个源于三重存储：
- P0-1 写入 `-1`（读到错误的数据源）
- P0-2 `addBuff` 后处理在已设值之上再累加
- P0-3 `removeBuff` 后处理在已扣减之上再扣减
- P0-5 shieldRegen 用本地副本覆盖全局值

**修正方向**: 
- `BuffSystem.shieldValues` 是唯一的运行时护盾值存储
- `config.parameters.shieldValue` 只在 `addBuff` 入口读取一次转交 ShieldEffect/ShieldBuff，之后不再引用
- `BuffContext.variables` 不存护盾值副本，只存计算因子

---

### 原理 2：单一路径生命周期

> 一个 Buff 从生到死应该走一条清晰路径。

**违反**: `addBuff` 同时执行三条路径——`script.onApply`、`effectPlan` 原语、`addBuff` 后处理硬编码。`removeBuff` 同理。`isSelfContained` 试图区分，但实现有 bug（P1-4）。

**直接后果**: 路径叠加产生双倍操作（P0-2/P0-3）。新旧效果的交互由 `isSelfContained` × `effectPlan` 存在性的组合决定，逻辑难以追踪。

**修正方向**: 二者择一：
- `selfContained === true` **且** 无 `effectPlan` → 走旧路径
- 有效 `effectPlan` → 走新路径，**不执行** `script.onApply/onRemove/onUpdate`
- 不允许同时走两条路。`isSelfContained` 严格只检查 `selfContained === true`，去除 `registry.has(scriptId)` 的宽泛匹配

---

### 原理 3：接口语义与调用环境匹配

> `IBuffScript.onUpdate(context, deltaTime: number)` 的 `deltaTime` 文档为"帧间隔（毫秒）"（`types.ts:66`）。

**违反**: `BuffSystem.updatePerTurn` 调用 `onUpdate(ctx, 0)`——回合制引擎没有"帧"概念，`deltaTime` 恒为 0。

**直接后果**:
- P0-4: `ShieldBuff._onUpdate` 的 shieldRegen 永不可达
- P3-2: `PoisonDebuff`、`HealOverTime` 基于 `context.getElapsedTime()` 的实时计时在快速战斗中失效——2 秒实时可能横跨多回合，DOT/HOT 不触发或延迟

**修正方向**: 
- `IBuffScript.onUpdate` 接口本身不适合回合制。可以废弃，或增加 `onTurnTick(ctx, currentTurn)` 
- 所有旧脚本迁移到 effectPlan（`IAtomicEffect.onTick` 接收 `turn` 参数，语义正确）
- 短期：`onUpdate(ctx, 0)` 加注释说明"回合制传 0，实时模式才用 deltaTime"

---

### 原理 4：操作幂等 + 重入防护

> 同一个操作不能被第二次调用产生不同效果，且必须防御自身重入。

**违反**: `removeBuff` 的序列是 回调 → 标记删除 → 清理。标记（`isActive = false`）在回调执行完后才设置（第 912 行）。回调可能触发事件 → 其他 Buff 移除 → 重入当前 `removeBuff`。

**直接后果**: 
- P1-3: `onApply` 失败不回滚，部分初始化实例残留
- P3-8: `isActive` 置 false 过晚，异常路径下永久泄漏
- 当前 isActive 检查（第 887 行）规避了最直接的重入，但异常路径无保护

**修正方向**: 重写 `removeBuff` 序列为：

```
removeBuff(id):
  instance = map.get(id)
  if !instance || !instance.isActive: return false
  instance.isActive = false           // 第一步就标记
  try:
    script.onRemove(ctx)
    effectPlan.onRemove(ctx)          // 统一 error boundary
  finally:
    map.delete(id)
    modifierStack.remove(id)
    cleanup()
    pool.return(ctx)
```

---

### 原理 5：错误隔离（Fail-safe）

> 一个效果处理失败不应影响其他效果或整个 Buff 生命周期。

**违反**: 
- effectPlan 的 `onRemove` 无 `BuffErrorBoundary` 保护（P1-1）
- `addBuff` 中 `onApply` 失败后继续执行 effectPlan、注册触发器（P1-3）
- `updatePerTurn` 中脚本 `onUpdate` 有保护，effectPlan `onTick` 无保护

**直接后果**: 原子效果抛异常 → `isActive` 不置 false、`buffInstances.delete` 不执行、修饰符不清除 → 内存泄漏 + 状态残留。

**修正方向**: 
- 所有外部可触发的回调（`onApply`、`onRemove`、`onTick`、`onStackChange`）统一用 error boundary 包裹
- `addBuff` 中任何步骤失败 → 完整回滚（删 instance、还 context、向上抛）
- `removeBuff` 用 `finally` 保证 `isActive = false` 和 `buffInstances.delete` 一定执行

---

### 原理 6：数据模型反映业务语义

> 聚合值如果丢失了分账信息，后续操作就无法精确。

**违反**: `shieldValues` 是每个角色一个 `number`。多护盾叠加后无法区分每个护盾贡献了多少。

**直接后果**: P0-3 的护盾扣减不精确。`Math.min` 修复保证"不崩溃"但"不精确"——移除护盾 A 时无法知道 A 还剩多少，只能用 `Math.min(A_原始值, 全局剩余)` 估算。

**修正方向**（两个选项）:
- **方向 A（精确，推荐）**: `shieldValues` 改为有序列表 `{instanceId, amount}[]`。`takeDamage` 按 FIFO 逐个消耗。`onRemove` 只移除自己的条目。
- **方向 B（承认近似）**: 保留全局值，`onRemove` **不做扣减**（护盾已被 `takeDamage` 消耗）。移除时若 `shieldValues` 有余额才调平。当前 `Math.min` 是方向 B 的折中。

---

### 根因映射表

| 架构根因 | 直接影响 | 关联报告条目 |
|---------|---------|------------|
| 三重护盾存储（SSOT 违反） | 双倍累加/扣减、覆盖吸收 | P0-1/2/3/5、P2-5、P3-1 |
| 两条并行执行路径 | 叠加操作、路径选择错误 | P0-2/3、P1-4/5、P3-1/7/9 |

| 全局聚合值丢失分账信息 | 护盾扣减不精确 | P0-3、P2-5 |

### 三个架构决策建议

1. **废弃 `IBuffScript`，统一到 `IAtomicEffect`**。所有旧脚本（ShieldBuff、PoisonDebuff、HealOverTime 等）迁移到 effectPlan。删除 `BuffInstance.script` 字段和后向兼容的 `isSelfContained` 逻辑。

2. **护盾值管理收缩到两个操作点**：`ShieldEffect.onApply` 负责加，`takeDamage` 负责消耗，`ShieldEffect.onRemove` 负责减。删除 `addBuff`/`removeBuff` 中的硬编码护盾处理（第 713-718 行、第 929-938 行）和独立维护的 `ShieldBuff` 脚本。

3. **`removeBuff` 执行序列重写**：`isActive = false` 移到第一行 → 统一 error boundary 包裹回调 → `finally` 保证 `map.delete` 和 `pool.return` 一定执行。
