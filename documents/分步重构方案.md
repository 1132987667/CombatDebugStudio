# 战斗系统增量重构方案

> 本方案是在 `整体重构.md`（目标架构）基础上的**执行方案**。核心策略：**每一步都可编译、可运行、可验证**，通过兼容层保持项目始终处于可用状态。

---

## 核心原则

| 原则 | 说明 |
|------|------|
| **每步可编译** | 每完成一个 Phase，`pnpm build` 必须通过 |
| **先测试后重构** | 移动/拆分代码前，先写测试锁定当前行为 |
| **兼容层模式** | 旧路径保留 re-export，不阻塞旧引用；全部完成后集中清理 |
| **巨石拆分优先** | 先拆大文件（不改变架构），再移动目录位置 |
| **strict mode 渐进** | 逐目录启用 strict 检查，不一次性全开 |
| **验证先行** | 每个阶段结束有明确的验证命令和通过标准 |

## Phase 1：TypeScript strict mode 渐进启用（1 周）

> 目标：在不改变业务逻辑的前提下，逐步收紧类型检查。

### P1.1 先开 `noImplicitAny`

```jsonc
// tsconfig.json
"noImplicitAny": true,
```

修复所有隐式 `any` 错误。策略：
- 能推断出具体类型的 → 补类型
- 确实不确定的 → 显式 `any`（暂时）
- `types/` 中的类型优先补全

### P1.2 再开 `strictNullChecks`

```jsonc
"strictNullChecks": true,
```

修复所有潜在的 null/undefined 问题。

### P1.3 最后开 `strictFunctionTypes` + `strictBindCallApply`

```jsonc
"strict": true,
```

如果 P1.3 错误太多（预计 100+），改为逐目录启用（`@ts-check` 或 `include` 范围控制）。

### ✅ Phase 1 验收标准

```
pnpm build   → 通过（strict mode 全开）
pnpm test    → 10+ 测试，全部通过
```

## Phase 2：巨石文件内部分解（3 周）

> 目标：将超大文件拆分为职责单一的小文件，**保持旧目录结构不变**，不引入新架构。

### P2.1 拆分 `core/BattleSystem.ts`（2130 行）→ 4 个文件

当前 `BattleSystem.ts` 中混合了：战斗流程编排 + 回合管理 + 动作执行 + 状态管理。

**拆分方案（保持 `core/` 目录）：**

```
src/core/
├── BattleSystem.ts          # 瘦身后的门面（协调者）~300行
├── battle/
│   ├── BattleState.ts       # [新增] 状态管理（从 BattleSystem 提取）~200行
│   ├── TurnManager.ts       # [已有] 回合管理（已有，检查是否被 BattleSystem 内联）
│   └── ActionExecutor.ts    # [已有] 动作执行（已有）
```

**做法**：
1. 先为 `BattleSystem.ts` 的每个 public 方法写测试（测试当前行为）
2. 将状态管理逻辑提取到 `BattleState.ts`，`BattleSystem` 委托给它
3. 将回合流程提取到 `TurnManager`，`BattleSystem` 委托给它
4. `BattleSystem.ts` 只保留协调逻辑

### P2.2 拆分 `core/battle/BattleParticipantImpl.ts`（932 行）

### P2.3 拆分 `core/skill/SkillManager.ts`（854 行）

**拆分方案**：

## Phase 3：值对象与领域内核迁移（2 周）

> 目标：将共享值对象和基础类型迁移到 `domain/kernel/`，同时保留旧路径兼容层。

### P3.1 创建兼容层策略

在新目录创建文件，旧文件保留为 re-export：

```typescript
// OLD: src/types/attribute.ts → 按职责保留或拆分
// NEW: src/domain/kernel/value-objects/Health.ts

// OLD 文件末尾保留（不删除）：
// src/types/attribute.ts
export { Health } from '@/domain/kernel/value-objects/Health'
```

这样旧 `import { Health } from '@/types/attribute'` 仍然可用。

### P3.2 值对象迁移

| 原位置 | 目标位置 | 文件 |
|--------|---------|------|
| `types/attribute.ts` 中的 Health | `domain/kernel/value-objects/Health.ts` | Health |
| `types/attribute.ts` 中的 Energy | `domain/kernel/value-objects/Energy.ts` | Energy |
| `types/attribute.ts` 中的 Speed | `domain/kernel/value-objects/Speed.ts` | Speed |
| `types/attribute.ts` 中的 Side | `domain/kernel/value-objects/Side.ts` | Side |
| `core/errors/BattleErrors.ts` | `domain/kernel/exceptions/` | 领域异常 |

迁移时转为不可变类（带私有构造 + 工厂方法）。

### P3.3 属性引擎迁移

| 原位置 | 目标位置 |
|--------|---------|
| `core/AttributeEngine.ts` | `domain/attribute/AttributeEngine.ts` |
| `core/AttributeEngine.ts`（辅助类型） | `domain/attribute/AttributeValue.ts` |

| 风险 | 概率 | 影响 | 应对 |

## 每个开发日的标准流程

```
1. git pull
2. pnpm build          # 确认当前可编译
3. pnpm test           # 确认当前测试全部通过
4. 开始当天工作
5. pnpm build          # 确认工作后可编译
6. pnpm test           # 确认测试全部通过
7. git commit          # 小步提交，每完成一个功能点就提交
```

这条流程确保：**你永远不会在"项目坏掉了"的状态下收工。**
