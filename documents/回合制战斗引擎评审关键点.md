> 状态效果管理的关键评审点（核心关键点）

1. 状态叠加机制
   叠加规则：相同状态是替换还是叠加？
   层数限制：是否有最大叠加层数？
   效果合并：不同层数的效果如何计算？
2. 状态优先级系统
   优先级定义：状态生效的顺序如何确定？
   冲突解决：高优先级状态如何影响低优先级状态？
   特殊状态：眩晕、沉默等控制状态的处理优先级
3. 时间计算精度
   时间单位：使用回合制还是帧率制？
   时间漂移：长时间战斗的时间累积误差处理
   暂停处理：战斗暂停时状态的计时逻辑
4. 状态清除机制
   清除条件：自然过期、主动清除、条件清除
   清除优先级：多个清除条件同时存在时的处理顺序
   状态免疫：某些角色对特定状态的免疫机制
5. 状态相互影响
   状态增强/削弱：一个状态如何影响其他状态的持续时间或效果
   状态连锁反应：状态触发的连锁效果
   状态组合策略：不同状态之间的组合效果
6. 性能优化
   状态数量限制：同时存在的最大状态数量
   更新频率：每回合/每帧的状态更新效率
   内存管理：状态对象的创建和销毁机制
7. UI/UX设计
   状态可视化：当前状态的清晰展示
   时间显示：剩余时间的准确显示
   状态冲突提示：状态冲突时的玩家提示

> 评审建议
> 当您用这些关键点评审AI框架时，重点关注：
> 逻辑完整性：每个关键点是否都有明确的实现？
> 扩展性：是否容易添加新的状态效果？
> 性能：在大量状态存在时是否仍然高效？
> 可调试性：是否容易追踪状态的变化和问题？
> 平衡性：状态系统的设计是否符合游戏平衡需求？

## 一、战斗流程与回合管理（BattleSystem / TurnManager / BattleExecutor / BattleRuleManager）

- **初始化链路**：`BattleSystem.initialize()` 是否依次完成：参与者 Map 建立 → 确定性随机源 `battleData.rng` 重建并注入各消费方 → AI 实例创建 → `BattleRecorder.startRecording` → 规则桥接（暴击/闪避开关、仇恨配置）→ 被动注册 + BATTLE_START 触发 → 出手顺序（`TurnManager.createTurnOrder`）→ 光环分发 → 场地效果 → 阵型 Buff → 属性重算。
- **回合流程**：`processTurnInternal()` 是否按顺序完成：TURN_START 事件 → 被动触发 → 复活冷却递减 / 场地周期 → `reduceSkillCooldowns` → 受击能量计数重置 → 回合能量发放 → 批量 `recalcAll` → `recalculateTurnOrder` → 逐个行动（`executeParticipantAction`）→ 行动后钩子 ACTION_END → 结束条件检查 → TURN_END buff 统一结算（`updatePerTurn`）→ TURN_END 事件 → 场地周期 / 仇恨衰减 → 额外行动消费 → 态势快照日志 → 回合递增。
- **额外行动**：`extra_action`（时之沙）是否在 TURN_END 后消费，且每回合上限（`MAX_EXTRA_ACTIONS = 3`）防死循环；`SkillExecutor.drainExtraActions()` 是否在战斗重置时清空。
- **行动决策三路径**：`executeParticipantAction` 是否按 `controlMode` 分流——`AI`（BattleAI 决策）/ `AUTO`（权重策略选技能）/ `MANUAL`（玩家手操）；被控制角色是否直接产出"无法行动"日志。
- **结束判定**：`BattleRuleManager.checkBattleEndCondition` 是否覆盖"一方全灭"与"超过最大回合按血量比例判胜"；死亡被动（ON_DEATH/ON_KILL）是否在 `runEndConditionCheck` 延迟结算，且已被复活的角色跳过。
- **重置隔离**：`resetBattle()` 是否清理被动注册、连击/轮转状态、待处理额外行动、仇恨、场地/阵型、复活追踪、事件总线残留监听、TraceCollector，防止跨战斗污染。

## 二、技能配置与数据结构（JSON → 运行时）

- **配置完整性**：`SkillConfig` 是否包含 `id`、`name`、`description`、`energyCost`、`cooldown`、`maxUses`、`selector`、`steps`、`condition`、`skillType`、`isNormalAttack`、`triggerTimes`、`triggerProbability`、`passiveCategory`、`parameters` 等字段且类型严格。
- **步骤结构**：`StepEffectType` 是否覆盖全部支持的操作——`deal_damage`、`heal`、`apply_buff`、`modify_attribute`、`gain_energy`、`remove_debuff`、`cleanse`、`shield`、`reflect`、`drain`、`revive`、`custom`、`stun`、`silence`；对应参数（`calculation`、`buffId`、`modifiers`、`duration`、`stacks`、`targetConfig`、`targetType`、`parameters`）是否完整。
- **目标选择器**：`SkillTargetConfig` 是否支持 `faction`（`self/ally/enemy/all`）、`strategy`（`first/lowest_hp/highest_hp/random/all/front/back/adjacent/random_adjacent`）、`count`，并在 `target-resolver.ts` 中正确实现。
- **被动技能标识**：被动技能的 `skillType: 'passive'` + `triggerTimes` 是否明确；无 `triggerTimes` 时默认 `battle_start` 的补全逻辑是否正确（`GameDataProcessor.registerParticipantPassives`）。

## 三、技能执行管道（SkillManager → SkillExecutor → 具体计算器）

- **执行入口**：`SkillManager.executeSkill()` 是否依次完成：配置查找 → 统一可执行性检查（`participant.canExecuteSkill`：被控制/沉默 → 冷却 → 能量）→ 无有效目标检查 → 施法者被控制检查 → 目标被控制检查 → 消耗能量 → 创建 `BattleAction` → 发射 SKILL_USE 事件 → 校验 DEAL_DAMAGE/HEAL 步骤 calculation 配置 → 循环执行 `steps`（含步骤级 `targetType` 额外目标）→ 设置冷却 → 返回。
- **步骤分发**：`SkillExecutor.executeStep()` 是否根据 `step.type` 正确路由到 `executeDamage`、`executeHeal`、`executeBuff`、`executeModifyAttribute`、`executeShield`、`executeGainEnergy`、`executeControl`、`executeCleanse`、`executeReflect`、`executeDrain`、`executeCustom`、`executeRevive`，未知类型是否抛错。
- **延迟伤害模式**：是否用 `DeferredDamageToken`（替代旧的全局 `deferDamage` 标志）——技能执行只记录数值不扣血，动画结束后由 `BattleExecutor` 按目标聚合调用 `settleDamage` 统一结算，异常路径漏调用最多丢单次伤害、不污染全局状态。
- **失败语义**：技能不可用/无目标/被控制时是否返回 `success: false` 的 `BattleAction` 且不消耗能量、不触发冷却。

## 四、伤害/治疗计算（DamageCalculator / HealCalculator）

- **基础伤害来源**：`calculateBaseDamage` 是否正确处理：有 `calculation` → 取 `baseValue`；无 `calculation` → 回退 `attack + level * 2`（旧版 `formula` 表达式已移除）。
- **额外加成**：`extraValues` 是否通过 `resolveAttributeValue` 从 `source`（攻击者）或 `target`（目标）读取属性（如 `maxHealth` 从目标取），并乘以 `ratio`。
- **暴击/闪避**：暴击判定使用 `critRate`（受 `enableCrit` 开关与必暴标记 `buff_guaranteed_crit` 控制），闪避判定使用 `clamp(hitValue/(hitValue+dodgeValue)×100 + hit − dodge, 10, 95)`（受 `enableDodge` 开关控制），并正确记录 `isMiss` 与 `isCritical`。
- **伤害链路顺序**（与代码逐项核对）：基础 → extraValues → 暴击倍率 → 来源方加成（`damageBoost` / 火系技能加成 / 物理技能加成 / 低血量加成）→ 捕获 `rawDamage`（减免前）→ 暴伤减免 → 防御值减法（TRUE 跳过）→ 普攻/技能减免（TRUE 跳过）→ 元素抗性 + 场地元素修正（仅 ELEMENTAL）→ 通用减免（TRUE 跳过）→ 易伤（`damageTakenIncrease`）→ 目标修正（`targetModifiers`）→ 阵营元素克制（elementMatrix）→ 阈值裁剪（`minDamageThreshold` / `maxDamageThreshold`）。
- **治疗上限**：`HealCalculator` 是否限制治疗量不超过 `maxHealth - currentHealth`，单独记录溢出量 `overflow`（供 `overflow_shield` 转盾），并考虑减治疗效果（`STATUS_CODE.HEAL_REDUCTION` 标签，每层 20%、上限 80%）。

## 五、技能目标选择与动态解析（target-resolver）

- **技能级 selector**：`resolveSkillTargets` 是否按 `faction` 过滤存活目标，再依次应用：嘲讽优先（`taunt` 标签回调）→ 仇恨优先（`ThreatManager`）→ 策略排序/选择；`front`/`back` 是否结合阵型行查询，`FIRST` 策略是否支持前排保护过滤后排。
- **步骤级目标覆盖**：当 `step.targetType` 有值时（`adjacent` / `random_adjacent`），是否通过 `resolveStepTargets` 重新解析额外目标并应用。
- **AI 建议目标验证**：`validateTargetAgainstSelector` 是否校验建议目标满足阵营与位置策略约束，不满足则回退自动解析。
- **边界条件**：无有效目标时返回失败动作且不消耗能量/触发冷却；`faction === 'self'` 时直接返回施法者，忽略 `strategy`。
- **确定性**：随机选择（`RANDOM`/`RANDOM_ADJACENT`）是否走 `battleData.rng`（`SeededRandom`），未注入时回退 `Math.random`。

## 六、技能冷却与能量管理（ParticipantSkills / canExecuteSkill）

- **冷却存储**：`ParticipantSkills.skillCooldowns` Map 是否正确记录每个技能的剩余冷却回合，并在每回合 `reduceSkillCooldowns()` 递减。
- **冷却生效时机**：技能执行成功后是否立即设置冷却（`setSkillCooldown`），冷却回合数来自 `config.cooldown`。
- **统一可执行性检查**：`canExecuteSkill` 是否合并控制（CONTROLLED/SILENCED）→ 冷却 → 能量三级检查，并返回可读的 `SkillBlockReason`。
- **能量消耗**：执行前通过 `canExecuteSkill` 保证能量充足，开始执行时 `spendEnergy` 立即扣除；失败时（如能量不足）返回失败动作且不消耗。
- **被动技能**：`energyCost` 应为 0，不消耗能量，冷却由 `PassiveSkillManager` 自行管理（不依赖 `ParticipantSkills` 冷却）。

## 七、被动技能触发与执行（PassiveSkillManager）

- **注册机制**：`GameDataProcessor.registerParticipantPassives` 是否将 `triggerTimes` 通过 `TRIGGER_TIME_MAP` 映射到 `BattleTriggerPhase`，并补全默认值（无 `triggerTimes` → `battle_start`；`battle_start` 默认 `maxTriggerCount = 1`，其余时机默认不限次）。
- **倒排索引**：是否维护 `indexByPhase` 按触发时机索引，`triggerPassiveSkillsForAll` 只遍历注册了该时机的被动，且注册/移除/清空均同步维护索引。
- **触发条件检查**：`triggerPassives` 是否依次检查：触发时机匹配 → 冷却（`lastTriggeredTurn`）→ 最大触发次数 → 触发概率（走确定性 rng）→ 气血阈值（HP_LOWER_THAN）→ 自定义 `condition`（参数化条件 `conditionParams`）。
- **目标解析**：是否优先使用技能 `selector` 从 `context.participants` 中解析目标，若无则回退到 `context.target` 或自身。
- **执行管道**：`executePassiveSkill` 是否走独立管道——跳过能量/眩晕/冷却检查、共享 `SkillExecutor`、每步独立 try-catch 单步失败不中断、跳过已死亡目标、通过 `EffectRenderer` + `BattleLogProjector` 统一渲染日志、headless/快速模式抑制动画事件。
- **跨战斗清理**：`clearAll()` 是否在战斗重置时清除所有注册的被动与索引，防止污染下一场战斗。

## 八、Buff 系统与原子效果（BuffSystem / ModifierStack / atomic effects）

- **原子效果原语**：`AtomicEffectType` 是否覆盖 `modifier / dot / heal / control / shield / trigger / aura / immunity / summon / thorns`；各效果（`ModifierEffect`、`DotEffect`、`HotEffect`、`ControlEffect`、`ShieldEffect`、`TriggerEffect`、`AuraEffect`、`ImmunityEffect`）是否实现 `onApply / onRemove / onTick / onStackChange / onRefresh / getEffectLines` 统一生命周期。
- **配置解析**：`BuffConfigResolver` 是否将 `buffs.json` 解析为带 `polarity`、`effectSummary`、原子效果组合的 `ResolvedBuffConfig`，极性判定不再靠 ID 前缀猜测。
- **修饰符堆叠**：`ModifierStack` 是否正确按 `sourceKey` 管理修饰符（同源去重、移除时清理跨角色修饰符），并通过脏标记缓存（`recalcAll`）与加成属性同步（`attributeSync`）保持一致。
- **叠加与刷新**：`StackRule`（LIMITED/REFRESH 等）与 `maxStacks` 是否正确决定叠加行为；`currentStacks` 是否反映真实层数并用于效果计算与 UI 显示。
- **控制优先级**：`getHighestPriorityControlEffect` 是否返回最高优先级控制效果；控制类 Buff（STUN/SILENCE）是否阻断行动/技能，且被控角色不触发多余结算。
- **触发器脚本**：触发器类 Buff（反伤/荆棘/击杀回血等）是否通过 `TriggerEventBus` 监听阶段事件执行，并用深度计数器（上限 3）防止反伤→反伤无限递归。
- **免疫机制**：`registerCharacterImmunities` 是否在初始化时注册角色免疫，`addBuff` 时按免疫标签正确跳过。
- **级联移除**：父→子 Buff 反向索引（`parentToChildren`）是否正确支撑 buff 移除时的级联清理。
- **性能与隔离**：`BuffContextPool` 对象池复用、`BuffErrorBoundary` 异常隔离、`updatePerTurn` 回合末统一结算。

## 九、触发器事件系统（BattleTriggerPhase / TriggerEventBus）

- **阶段完整性**：`BattleTriggerPhase` 是否覆盖 `battle_start / battle_end / turn_start / turn_end / before_attack / on_hit / after_attack / action_end / damage_taken / on_kill / on_death / heal_received / energy_gained / skill_use / hp_lower_than / ally_fatal_damage / ally_damage_taken / on_apply / condition_changed / dodge / on_revive`，作为 Buff 触发、被动技能、回放、事件总线的唯一气血周期来源。
- **事件桥接**：被动技能与 Buff 触发器是否共用 `TriggerEventBus`（mitt 实例），`DAMAGE_TAKEN` 等关键阶段是否在 `settleDamage` 中统一发射，避免路径重复/遗漏。
- **旧名兼容**：`OLD_PHASE_NAME_MAP` 是否将旧式 `ON_TURN_START` 等配置名映射到标准化阶段名，保证 JSON 配置向后兼容。

## 十、AI 技能选择与资源权衡（AISystem / AIPriorityStrategy）

- **技能可用性检查**：AI 决策前是否校验冷却（`isSkillAvailable`）与能量充足性。
- **优先级策略**：`AIPriorityStrategy` 是否按基础权重（终结技/小技能/被动）+ 战场形势（治疗需求、高威胁目标）+ 角色状态（能量不足 -50、低血优先治疗）计算技能权重，并输出可审计的 `breakdown` 贡献项；是否支持 `Aggressive / Defensive / Balanced` 三种策略。
- **资源权衡**：AI 是否在能量低时倾向低消耗技能或普通攻击，避免能量耗尽后无法释放关键技能。
- **随机性**：`BATTLE_CONSTANTS.SKILL_USE_CHANCE`（0.4）是否控制 AI 使用技能的概率，避免完全可预测；随机判定走确定性 rng。

## 十一、确定性、回放与日志（SeededRandom / BattleRecorder / TraceEventCollector / 投影层）

- **确定性随机**：`battleData.rng`（`SeededRandom`）是否在 `initialize` 时按 seed 重建，并注入 `DamageCalculator` / `BuffSystem` / `PassiveSkillManager` / `AISystem`，使命中/暴击/目标/概率等全部随机判定可复现。
- **战斗录制**：`BattleRecorder` 是否记录回合开始/结束、行动、CombatRecord（含伤害拆分 `DamageBreakdown`）、TraceEvent，支持从 seed 复现与统一归档（unified archive）。
- **结构化追踪**：`TraceEventCollector`（IDebugTracePort）是否发射 `TURN_FLOW` / `ACTION_EXECUTION` / `PASSIVE_TRIGGER`（含跳过取证）/ `AI_DECISION` / `DAMAGE_CALCULATION` / `HEAL_CALCULATION` 等 TraceEvent，并以因果链 scope（`corr_${turn}_${seq}`）贯穿一次行动。
- **日志系统**：`BattleLogManager`（`LoggerProvider.logger`）是否统一战斗/系统/调试日志；攻击、技能、被动、回合态势快照等日志拼装是否委托 `BattleLogProjector` 单一实现（SSOT）。
- **投影层**：`BattleProjection` 调度器 + `participantMapper` 是否将领域实体映射为 `UIParticipantSnapshot` 纯数据快照，Vue 组件统一从快照读取而非直接绑定领域实体。

## 评审建议

- **逻辑完整性**：逐条对照以上关键点，检查现有代码（尤其 `BattleSystem.processTurnInternal`、`SkillManager.executeSkill`、`SkillExecutor.executeStep`、`DamageCalculator.calculateDamage`、`PassiveSkillManager.triggerPassives`、`BuffSystem`）是否全部覆盖，无遗漏或矛盾。
- **可扩展性**：评估添加新技能效果（如"嘲讽"、"变形"）所需的改动范围——是否只需新增 `StepEffectType` 与 `SkillExecutor` 中的对应 `execute` 方法；新增 Buff 效果是否只需新增原子效果实现。
- **平衡性**：通过实际战斗测试，验证高耗技能（如终极技）的伤害/效果是否与消耗和冷却匹配，避免出现"最优解"技能。
- **可调试性**：检查是否可通过战斗日志、CombatRecord 伤害拆分、TraceEvent 因果链，定位技能释放、计算步骤、能量变化、冷却更新、被动跳过等关键信息。
- **确定性**：同一 seed 下回放是否完全一致，随机源是否在重置后重新注入，避免引用漂移。

这些关键点完全基于本项目的代码结构，可直接用于代码审查和架构评审。
