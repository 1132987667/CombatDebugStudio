## D1 五行攻击是否拆 5 个属性

> ✅ **状态：已拍板（归并）** —— 删除五行攻击 ×5，伤害统一走 `attack`，五行差异由"技能 elementType + 元素加成% + 克制矩阵"表达。

### 背景

现有 `attributes.json` 同时存在：
- 五行攻击 ×5：`waterAtk` `fireAtk` `metalAtk` `woodAtk` `earthAtk`
- 五行抗性 ×5：`metalRes` `woodRes` `waterRes` `fireRes` `earthRes`
- 元素技能加成：`fireSkillDmgBonus` `physicalSkillDmgBonus`

技能本身带 `elementType`（JIN/MU/SHU/HUO/TU），伤害大类 `damageCategory` 分 physical/elemental/true。

**问题**：伤害计算只有一个 `attack` 基线（`DamageCalculator` 基础伤害走 `attack × (1±15%)`）。
五行攻击如果真拆开，必须定义"技能用哪个攻击"，否则它们不参与任何公式，只是装饰属性。

### 选项

| 选项 | 含义 |
| ---- | ---- |
| **a. 拆 5 个** | 保留 `waterAtk`~`earthAtk`，技能按 elementType 取对应攻击参与伤害 |
| **b. 归并** | 删掉 5 个五行攻击，伤害一律走 `attack`；元素克制用"元素加成%"（如 `fireSkillDmgBonus`）+ 克制矩阵实现 |
| **c. 中间态** | 只拆 2 个：物理攻击 + 元素攻击（五元素归并为 1），技能按 physical/elemental 大类取用 |

### 利弊对比

| 维度 | a 拆 5 个 | b 归并 | c 拆 2 个 |
| ---- | ---- | ---- | ---- |
| 公式改动 | **大**：需新增"技能绑定攻击值"逻辑；elemental 技能伤害 = 攻击×ratio 与 fireAtk 叠加需定义，计算链拉长 | **零**：完全复用现有环节（来源方加成 + 目标方抗性 + 克制系数） | 中：需定义元素攻击的来源与成长 |
| 面板认知负担 | 高：玩家要理解 5 种攻击各自打什么 | 低：攻击一个，元素差异看"加成%" | 中：物理/元素双轨 |
| 角色差异化 | 高：可做"物理+火系双修"、词条丰富 | 中：靠技能带元素 + 百分比加成表达 | 中高 |
| 平衡难度 | **高**：物理 vs 元素各占多少要反复调；抗性 5 个 vs 攻击 5 个数量对等但减免维度翻倍 | 低：克制 = 系数 × 百分比，单一减免维度 | 中 |
| 数据维护 | 每个角色要配 5 个攻击位，中小型内容大量闲置 | 一个攻击，配置最少 | 两个攻击 |
| 与现有数值匹配 | 与"伤害 = 攻击×ratio"模型冲突 | 与现有公式与 guardian 数值完全兼容 | 与现有公式部分兼容 |

### 推荐：b（归并），c 留作扩展

**理由**（按强度排序）：

1. **零公式改动**：b 方案下 `DamageCalculator` 每个环节都不用动——元素技能已走 `fireSkillDmgBonus`（来源方加成环节，`DamageCalculator.ts:278`）、目标五行抗性（目标方环节，`:435`）、五行克制系数（`elementMatrix`，`:544`）。全部现成，只需把克制表/加成数据填上。
2. **属性收敛是框架主线**：D1 与 §1.3 的收敛清单同源。拆 5 个属性 = 面板再加 5 个数字，违背"属性可见即所用"。
3. **双修不需要双攻击**：角色想"物理+火系"，靠**带多个元素技能**即可（技能自带 elementType），攻击统一，元素差异由技能与加成表达。这是卡牌游戏最常用的做法。
4. **平衡成本最低**：单一攻击 + 单一防御 → 破防约束只盯一对数（现有 `balance-check.cjs` 的断言直接适用）；拆开后"物伤段 vs 火伤段"各过各的减免，TTK 模拟要重写。

**c 的适用情形**：未来出现"法系职业与物理职业区分度不足"时，再拆一个元素攻击即可，不推翻 b 的结构（b → c 是平滑演进）。

> **拍板后修订**：从 `attributes.json` 删除五行攻击 ×5；面板元素区只保留"五行抗性 ×5 + 所属元素加成"。克制公式 = `attack × ratio × (1 + 元素加成%) × 克制系数`，全部走现有环节。

### 完整对拍示例（同一个战斗场景，两套方案分别怎么算）

> 用同一组数字跑完整伤害流程，直观对比"归并"与"拆 5"的实际差异。可复核：每一步都对应 `DamageCalculator` 的现有环节（`:185 基础 → :343 捕获原始 → :369 防御 → :435 元素抗性 → :544 克制`）。

**战斗场景**（固定输入）：
- 我方「炎姬」：火属性，`attack = 200`
- 拆 5 方案额外有 `fireAtk = 80`
- 技能「烈焰掌」：`elementType = HUO`，倍率 `ratio = 0.9`，`baseValue = 0`
- 敌方「木灵卫」：`defense = 60`，`fireRes = 20%`
- 五行克制：火克木，`coefficient = 1.2`
- 不暴击，无伤害提升/易伤等其他加成

**① 归并（方案 b）：只有一个 attack，全程一条路径**

```
基础伤害    = attack × ratio             = 200 × 0.9 = 180
来源方加成  = 180 × (1 + fireSkillDmgBonus/100)
            = 180 × 1.0                  = 180        （炎姬无火系加成）
防御        = 180 − 60                   = 120
目标火抗    = 120 × (1 − 20%)            = 96
五行克制    = 96 × 1.2                   = 115.2 → floor 115
最终伤害    = 115
```

面板上炎姬只有"攻击 200"一个数字。火元素差异完全由**技能自带 elementType** 表达：同一个炎姬，打木（被克）是 115，打金（克制火）则是 96 × 0.8 = 77——**不需要第二套攻击数值，克制照样生效**。

**② 拆 5（方案 a）：必须先回答"技能用哪个攻击"，且不止一种合法实现**

合法实现至少有两种，结果天差地别：

| 实现 | 定义 | 伤害计算 | 最终伤害 |
| ---- | ---- | ---- | ---- |
| A1 叠加 | 火技能 = (attack + fireAtk) × ratio | 280×0.9−60=192 → 192×0.8=153.6 → ×1.2=184.3 | **184** |
| A2 替代 | 火技能只看 fireAtk | 80×0.9−60=12 → 12×0.8=9.6 → ×1.2=11.5 | **11** |

**同一场战斗，同一个炎姬，两个"合法"实现打出 184 或 11——相差 17 倍。** 归并方案只有 115 一条结果，拆 5 方案在写第一行代码前就要先立法选 A1 还是 A2，而 A2 下火攻 80 减去防御 60 后只剩 12，火系角色直接废掉。

**③ 拆 5 让"减法防御"出现连环坑**

防御是减法公式（`damage − defense`），拆开后每个攻击维度都要单独过防：

- 归并：只要保证 `attack > defense`，全部技能都能破防——**一条破防约束**（现有 `balance-check.cjs` 断言直接适用）；
- 拆 5：`fireAtk` 若小于 target 防御，火伤段被清成 1 点。要维护 **5 条破防约束**（每种攻击 vs 每种敌人的 defense），且"火攻堆到多少才能打高防坦克"成为常态调参话题。

**④ 玩家视角的三个差异**

| 视角 | 归并 b | 拆 5 a |
| ---- | ---- | ---- |
| 面板 | 攻击 200，一个数字 | 攻击 200 + 火攻 80 +（其他五行攻击）……6 个数字 |
| 养成 | 堆攻击 → 所有技能等比变强，直觉清晰 | 堆攻击还是堆火攻？要理解"每种攻击打谁用" |
| 装备词条 | 攻击/火系技能伤害+%，简单 | 攻击/火攻/金攻/木攻……词条池膨胀，每种攻击都有专属词条 |

**⑤ 双修怎么表达（归并方案下的答案）**

"物理+火系双修"角色在归并方案下 = **带 2 个不同 elementType 的技能**：
- 烈焰掌（HUO）对木 115、对金 77；
- 猛击（physical）走物理减免路径，数值独立于火伤。

元素差异化在"技能"层完成，而不是"属性"层——这是卡牌游戏最常用、平衡成本最低的形态。

## D1b 五行抗性是否归并（补充决策）

> ✅ **状态：已拍板（保留 5 个，不归并）** —— `metalRes`~`earthRes` 五行抗性保留。

### 为什么攻击删、抗性留

五行攻击删除、五行抗性保留，看起来不对称，但本质区别在于：

| 维度 | 五行攻击（已删） | 五行抗性（保留） |
| ---- | ---- | ---- |
| 参与环节 | 基础伤害的**输入值**，走减法防御 | 目标方**减免百分比**，乘法区 |
| 破防风险 | `fireAtk` < 防御 → 火伤清成 1 点，破防约束×5 | 无破防概念，纯百分比，不会崩 |
| 归并的最强论据 | 正打在它身上（减法悬崖） | **不适用** |
| 玩家负担 | 6 个攻击数字，要理解"堆哪个" | 5 个抗性是防御向，可折叠显示 |
| 词条 | 攻击词条池 5 选 1，闲置 4 个 | 抗性词条"选 1~2 个防特定的"，有策略 |

**结论**：抗性是乘法减免，"归并砍维度"的最强理由（减法破防悬崖）对它不成立。
保留 5 个五行抗性没有成本，删掉反而丢失五行闭环的防御侧差异。

### 抗性与克制矩阵的分工（避免两套五行重叠）

```
克制矩阵（elementMatrix）：阵营相性 —— 火阵营 打 木阵营 ×1.2    ← 单位级，由 faction 决定
五行抗性（fireRes…）：属性减免   —— 目标堆火抗 20% → 火伤害 ×0.8   ← 属性级，可培养
```

分工不同：
- **克制矩阵** = 阵营出生自带，表达"火克木"的天理；
- **五行抗性** = 可堆叠的防御策略。

两者并存产生策略深度：火克木，但木阵营角色可以堆 `fireRes` 反制——"克制是天赋，抗性是修行"。

### 面板与词条策略

- 面板：五行抗性折叠成一组"五行抗性"，展开看 5 个，不占主面板行数；
- 词条：抗性词条 5 种，玩家通常堆 1~2 种针对特定敌人（配克制打本），不会全堆；
- 上限沿用 80%（保留 20% 克制穿透空间）。

## D2 是否做等级压制

> ✅ **状态：已拍板（a 不做）** —— 不引入等级差修正环节，等级差完全由减法公式与成长曲线体现。
> 软替代：关卡显示"推荐等级"，战斗前提示"敌方等级高于我方"。

### 背景

等级压制 = 根据攻防双方等级差修正伤害/命中（常见：`f(Δlevel) = clamp(1 + Δ×0.05, 0.5, 1.5)`）。

本游戏的防御是**减法公式**（`damage - defense`），这是判断 D2 的决定性前提。

### 选项

| 选项 | 含义 |
| ---- | ---- |
| **a. 不做** | 等级差完全由数值曲线体现，不加额外修正环节 |
| **b. 做** | 等级差以乘法系数修正伤害 |

### 利弊对比

| 维度 | a 不做 | b 做 |
| ---- | ---- | ---- |
| 公式复杂度 | 低：不加环节，调试链不变 | 高：新增乘区、系数表、上下限，多一套参数 |
| 越级体验 | 减法公式天然惩罚越级（打 1 点），**等级差已是硬约束** | 乘法惩罚叠加在减法上，越级从"困难"变"不可能" |
| 碾压体验 | 高等级 vs 低级敌人自然秒杀（攻远大于防） | 同样秒杀，且还有修正叠加 |
| 破防风险 | 无额外风险 | **叠加减法双重惩罚**，低等级打高等级更容易卡 1 点，体验崩坏 |
| 平衡工具链 | `balance-check` 现有断言直接可用 | TTK 模拟必须带等级差修正，重写 |
| 玩家理解 | 靠数值差距自然理解 | "等级不足伤害-30%"更直白 |

### 推荐：a（不做），等级差交给减法公式与曲线

**理由**：

1. **减法公式已经内建了等级压制**：攻-防的差值随等级差自然放大。高等级打低级 = 碾压；低等级打高级 = 打 1 点。等级差效应不是缺，而是已有——再加乘法修正是**双重复利/双重惩罚**。
2. **破防约束不容叠加**：现有平衡断言"任何敌人 def < 我方最低攻 × 0.85"保障的是"同级可破防"。若再加等级压制，低级挑战高级时 `damage` 先被乘法削、再被防御减，极易跌破 1 点悬崖。
3. **中小型内容没有大等级差**：玩家按关卡推进，关卡推荐等级与队伍等级基本同步，等级差修正没有用武之地。

**软替代**：不做战斗修正，但做 UI 引导——关卡显示"推荐等级"，战斗前提示"敌方等级高于我方"。既给玩家预期，又不污染公式。

> **拍板后修订**：框架不引入等级差修正环节；玩家曲线与敌人曲线的关系（§2.4）作为唯一的等级差来源，维持 TTK 断言不变。

## D3 玩家成长曲线的数据形态

### 背景

角色 `growth` 字段引用曲线定义，曲线决定"每升 1 级白板加多少"。
现有状态：角色编辑器的"均衡/攻击/防御/速度"是硬编码枚举文本，无独立数据（规格说明书 §3.8）。

### 选项

| 选项 | 含义 |
| ---- | ---- |
| **a. 职业模板系数表** | 曲线 = 职业模板的一组每级系数，任意等级属性可推导（`base + Σ系数`） |
| **b. 逐级手工表** | 每个等级一个确定值，50 级 × 4 属性 = 一张完整表 |
| **c. 混合** | 模板系数（连续成长）+ 里程碑表（5/10/20/30/40/50 级离散奖励） |

### 利弊对比

| 维度 | a 模板系数 | b 逐级表 | c 混合 |
| ---- | ---- | ---- | ---- |
| 数据量 | **极小**：5 职业 × 4 系数 | **爆炸**：30 角色 × 50 级 × 4 = 6000 个数 | 极小：模板 + 1 组里程碑 |
| 调参便利 | 调一个系数，整个职业全局生效 | 改一处成长要改 50 行 | 连续成长调系数、特殊等级调里程碑 |
| 角色差异化 | 同职业曲线一致，个性靠 base 与里程碑 | 可做到逐级独有 | base + 里程碑足以差异化 |
| 特殊等级奖励（10/20/30 解锁技能） | 不支持，需另加机制 | 天然支持 | **原生支持** |
| 角色编辑器"45 级预览" | 函数推导，一行算出 | 查表 | 函数 + 里程碑，可推导 |
| 出错风险 | 低 | 高（漏级/不平滑） | 低 |

### 推荐：c（模板系数 + 里程碑），即 a 的增强形态

**理由**：

1. **函数可推导 > 查表**：角色编辑器要预览任意等级属性（规格说明书 §3.8"45 级属性"）、战斗快照要冻结属性，模板系数天然支持任意等级推导；逐级表只能查到已定义等级。
2. **里程碑表达离散奖励**：RPG 常规做法是 10/20/30/40/50 级给一次特殊奖励（解锁技能、+5% 暴击、天赋点）。逐级表能表达但维护沉重，里程碑表一张就能表达全部角色的阶段奖励。
3. **数据量最小 = 改起来最安全**：6000 个手工数值是维护事故源；模板 + 里程碑把"曲线"收敛成"策略"，符合框架"成长有预算"原则。

**落地形态**（示意）：
```jsonc
{
  "id": "growth_attacker",
  "template": "attacker",              // 引用职业系数
  "base": { "hp": 80, "atk": 20, "def": 8, "spd": 15 },
  "milestones": {
    "10": { "unlockSkill": "skill_xxx_2" },
    "20": { "bonus": { "critRate": 5 } },
    "50": { "bonus": { "attackBonus": 20 } }
  }
}
```

> **拍板后修订**：`curves.json` 采用"模板系数 + 里程碑"结构；`growth` 表新增 `template/base/milestones` 字段；`CharacterEditor` 的枚举文本替换为曲线引用。

## D4 各养成子系统的占比

### 背景

框架 §3.1 提出 5 个养成子系统及建议占比：等级 40% / 装备 25% / 技能 15% / 突破 15% / 天赋 5%。

**必须先澄清定义的模糊性**：技能升级不直接加白板（它加 `ratio`），天赋加的是乘区。因此"占比"更准确的定义是：
**玩家养成总投入（时间/资源）的分配节奏**，而非"最终属性的精确构成"。占比决定**玩家每天把精力花在哪**，进而决定**毕业时各系统的产出体感**。

### 可选的分配方案

| 方案 | 等级 | 装备 | 技能 | 突破 | 天赋 | 特点 |
| ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| 等级主导 | 50 | 20 | 15 | 10 | 5 | 重练级，成长感知强，后期等级封顶后无事可做 |
| **均衡（推荐）** | **40** | **25** | **15** | **15** | **5** | 练级始终有用 + 装备提供长期追求 |
| 装备主导 | 30 | 35 | 15 | 15 | 5 | 追掉落/强化，重复可玩强，但单机无重刷场景，方差大 |
| 重养成 | 30 | 20 | 20 | 20 | 10 | 全系统深挖，内容量要求最高 |

### 各子系统的特性约束

| 子系统 | 优势 | 风险 | 占比约束 |
| ---- | ---- | ---- | ---- |
| 等级 | 反馈最直接、内容门槛最低 | 封顶后零产出 | 不能太低（主体验），不宜 >50（后期真空） |
| 装备 | 稳定长期追求、可离线验证 | 单机无重刷，掉落方差伤体验 | 不宜 >30（方差大），≤25 稳妥 |
| 技能 | 强化战斗手感、差异化 | 材料单一易溢出 | 15 左右即可，MVP 必做 |
| 突破 | 角色收集动力、百分比产出直观 | **依赖碎片来源（D6 未定）** | 若 D6=关卡掉落碎片可给 15~20；若仅商店兑换则降 |
| 天赋 | 差异化最深、流派构建 | 天赋点稀缺、内容量最大 | MVP 可后置，保留 5% |

### 推荐：均衡型 40/25/15/15/5，附加"投放阶段模型"

**理由**：

1. **均衡型让 5 个系统都有"存在意义"**：等级锚定主体验（40%），装备提供满级后的长期追求（25%），技能强化每次战斗手感（15%），突破给出角色收集目标（15%），天赋留差异化入口（5%）。
2. **等级 40 是防"后期真空"的关键**：等级主导型（50%）封顶后玩家无事可做；均衡型把后期重心平滑转移到装备/突破。
3. **装备 25 是单机安全线**：卡牌网游常把装备做到 40%+ 靠重刷/付费，单机无重刷场景，装备占比过高会暴露掉落方差。

**配套要求（比数字更重要）**：占比不是"一次性给满"，而是**投放节奏曲线**——

```
前期（1~15级）  等级 60% 装备 10%   —— 没装备可给，升级是唯一主线
中期（16~30级） 等级 40% 装备 30%   —— 装备/技能/突破陆续开放
后期（31~50级） 等级 25% 装备 35%   —— 装备强化与突破收尾，天赋入场
```

这张"资源投放节奏表"才是 D4 的可操作落地物，占比（40/25/15/15/5）只是它的累计形态。

**联动依赖**：突破占比 15% 的前提是 D6（碎片来源）能支撑——若 D6 定"仅商店兑换"，碎片稀缺，突破占比应下调至 10% 并把差额补给技能或天赋。**D4 需在 D6 之后复核**。

> **拍板后修订**：采纳 40/25/15/15/5 + 投放阶段模型；在封神榜新增"资源投放节奏表"数据域（每段等级区间各子系统资源的投放权重）。

## D11 ModifierType 审查（独立乘区连乘化）

> ✅ **状态：已拍板** —— `MULTIPLICATIVE`（独立乘区）改为**每个来源独立连乘**；
> `ADDITIVE`/`PERCENTAGE`/`FINAL` 语义与实现保留。

### 现状：四类修饰符的数学结构

`ParticipantStats.ts:158` 当前实现，四类都是**同类累加**：

```
value = (base + Σ加算) × (1 + Σ百分比/100) × (1 + Σ独立乘/100) × (1 + Σ最终乘/100)
```

**关键发现**：`PERCENTAGE` 与 `MULTIPLICATIVE` 在数学上完全等价——
两者都是"同类修饰符累加成一个乘区再乘"，而乘法可交换，所以这两个类型干的其实是同一件事，只是名字不同。
而业界"独立乘区"通常指**每个来源各自独立相乘**（`×1.3 × 1.5 = 1.95`），当前实现名不副实。

### 累加 vs 连乘的差别（同一个角色两个 +50% 修饰符）

| 实现 | 公式 | 结果 |
| ---- | ---- | ---- |
| 当前（累加） | `(1 + 0.5 + 0.5)` | 最终 ×2.0 |
| 独立连乘（拍板） | `1.5 × 1.5` | 最终 ×2.25 |

若未来某 buff 是"伤害 ×1.3"（真独立乘法），放进当前 `MULTIPLICATIVE` 会与别的累加，数值对不上设计意图。

### 修正后的四类语义（拍板结果）

| 类型 | 语义 | 数学 | 典型用途 |
| ---- | ---- | ---- | ---- |
| `ADDITIVE` | 加算 | `base + Σ加` | 白板成长、装备固定值 |
| `PERCENTAGE` | 百分比（同类累加） | `(1 + Σp/100)` | 攻击%、防御% 等百分比加成 |
| `MULTIPLICATIVE` | **独立乘区（每个来源独立连乘）** | `Π(1 + mᵢ/100)` | 暴伤、天赋 ×1.3、buff "伤害翻倍" |
| `FINAL` | 最终乘区（同类累加） | `(1 + Σf/100)` | 最终兜底修正 |

### 对代码的影响

`ParticipantStats.recalcAttribute` 中 `MULTIPLICATIVE` 分支从 `independentMultiplier += mod.value`
改为 `independentMultiplier *= (1 + mod.value / 100)`（语义变更，见 D13 乘区注册表落地时一并处理）。

## D12 减免乘区收敛 / D13 乘区注册表

> D12 ⏳ 待拍板 / D13 ⏳ 待拍板（推荐采纳）。

### 问题：隐式乘区散落

现有减免/增伤属性不止五行抗性，它们全是"乘区"，但没有统一管理：

```
damageReduction       免伤率           → 目标方通用减免
normalAtkDmgReduction 普攻伤害减免      → 仅普攻
skillDmgReduction     技能伤害减免      → 仅技能
critDmgTakenReduction 暴击承伤减免      → 仅暴击时
damageTakenIncrease   易伤             → 目标方增伤
trueDamageRate        真实伤害率        → 无视防御
damageBoost           伤害提升          → 来源方增伤
```

`DamageCalculator` 里这些是**硬编码顺序的连乘环节**（`:369 → :435 → :487 → :504`），
每加一个新减免属性都要改计算器代码——这正是归并方案要封顶的东西。

### D12 选项

| 选项 | 含义 |
| ---- | ---- |
| a. 维持现状 | 6~7 个隐式乘区，每加一个改 `DamageCalculator` |
| **b. 收敛（推荐）** | 归并为"通用减免 + 定向减免"两类，面板只展示可理解的那几个 |
| c. 全数据化 | 所有减免做成"乘区条目"，由配置声明顺序（即 D13） |

### D13 乘区注册表（配合 D11 落地）

把"乘区有哪些、顺序如何、是否连乘"从代码提升为**配置**：

```jsonc
// configs/params/multiplier-registry.json（示意）
{
  "multipliers": [
    { "id": "damageBoost",          "mode": "multiplicative", "order": 10 },
    { "id": "fireSkillDmgBonus",    "mode": "multiplicative", "order": 20 },
    { "id": "critDmgTakenReduction","mode": "multiplicative", "order": 30 },
    { "id": "elementRes",           "mode": "multiplicative", "order": 40 },
    { "id": "damageReduction",      "mode": "multiplicative", "order": 50 },
    { "id": "damageTakenIncrease",  "mode": "multiplicative", "order": 60 },
    { "id": "elementMatrix",        "mode": "multiplicative", "order": 70 }
  ]
}
```

- **收益**：新增减免乘区只改 JSON 不改公式；昊天镜可按注册表解释每一步伤害链路；
- **代价**：属性重算（`ParticipantStats`）与伤害流程（`DamageCalculator`）需接入同一注册表，属中等重构。

> **拍板后修订**（若 D12/D13 采纳）：减免属性收敛为"通用/定向"两类；新增乘区注册表，
> `ParticipantStats` 与 `DamageCalculator` 共读；TTK 断言扩展覆盖新乘区路径。
