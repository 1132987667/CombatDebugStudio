# 太初道枢 — 资深用户改进建议（QA 主管视角）

> 本报告基于对 CombatDebugStudio 代码库的逐模块核实（证据均带 file:line），以每日 4+ 小时使用昊天镜/唤灵台/封神榜/演劫台的资深战斗系统 QA 主管身份撰写。
> 生成日期：2026-08-04

---

## 0. 先说现状（一句话版）

四大模块里，**唤灵台（阵容战斗）** 和 **昊天镜（战局分析）** 是真实现且相当能打——统一存档带随机种子、双工作台、分支 diff、会话导出导入、Worker 校验都已落地；但**封神榜（数据编定）是占位符（BattleArena.vue:59-66「开发中」）、演劫台（实战对局）是占位符（BattleArena.vue:68-75「规划中」）**。数据闭环"调参 → 验证 → 分析 → 回流"在代码层面断在最两头。以下 8 条建议按切肤之痛排序。

---

## 建议 1【操作效率】事件检索只有关键词，多维过滤缺失

**场景描述**：我在昊天镜调试一份 2000+ 事件的压测存档（CommandBar「压测 · 2000+ 事件」源），最常见的诉求是两类：① "本场所有暴击伤害 > 200 的伤害计算事件"；② "剑士这一整场被施加过哪些 Buff、分别在哪个回合"。这两类我现在都只能**肉眼滚动事件流**，或者在搜索框里赌关键词。

**当前问题**：检索维度只有两个——关键词匹配（`summary + correlationId`，haotianStore.ts:156-164）+ 调试事件显隐开关（showDbg）。而数据本身是结构化的：每个 TraceEvent 都带 `phase / sourceId / targetId / turn / payload`（trace-event.ts），索引里甚至已注入 rolls 索引和 HP/EN 增量 `_delta`（unified-indices.ts:65-97）——这些字段全部**没有暴露成过滤条件**。summary 是中文文本（"伤害计算 剑士→史莱姆 100→85"），数值条件"伤害>200"根本无法表达。

**改进建议**：在 ReplayStream 顶部加一个检索面板：① phase 多选（按 TracePhase 11 类胶囊）；② 参与者过滤（sourceId/targetId 下拉）；③ 数值区间过滤（对 payload 数值字段，如 final>200、roll<0.1）；④ 组合条件 AND/OR。过滤结果在时间轴打点显示、命中数实时统计。常用检索保存为"检索预设"（persistPrefs 已有 localStorage 机制，haotianStore.ts:205-219 直接扩展）。

---

## 建议 2【操作效率】长局回放无"跳转目标"，反复加载同一存档繁琐

**场景描述**：验证第 37 回合结算时，我的操作路径是：播放 → 等它跑到 37 回合 → 暂停，或者点时间轴慢慢找刻度。一天要重复 20 次。而"反复加载同一存档"更是常态——同一份录制在回放/调试工作台间来回切，每次都要从数据源下拉重新选。

**当前问题**：跳转只有三种手段：时间轴点击、回合刻度点击、←/→ 逐事件（ReplayStage.vue:139-143）。**没有"跳到第 N 回合 / 第 N 个事件"的数字输入框**。更可惜的是 `ReplayEngine.seekToTurn/seekToRound/seekToEvent`（ReplayEngine.ts:198-247）存在但昊天镜从不调用——整条 ReplayEngine/BattleReplayManager 链路是无调用方死代码（统一战斗事件流方案 §1.4 事实 2）。录制列表每次要**先手动切"战斗记录"数据源**才出现（CommandBar.vue:22-28），没有"最近打开"记忆。

**改进建议**：① 时间轴旁加跳转输入框（回合号 + 事件号，回车跳转，吃 unified-indices 已有的事件表）；② CommandBar 加"最近打开"（localStorage 记最近 10 个录制 key/深链，复用 #m=&e= 深链机制 haotianStore.ts:537-556）；③ 把 seekToTurn 的按回合定位逻辑移植到统一事件流上，别让它死在旧链路里。

---

## 建议 3【功能缺失】统一存档只导出不导入——跨人 Bug 复现彻底断裂

**场景描述**：这是我最痛的一条。同事在封神榜调了暴击率参数，跑出一场伤害溢出的异常战斗，把存档 JSON 发我，让我复现分析。我拿到文件，**昊天镜没有入口能加载它**。全仓库 grep `importArchive|loadArchiveFromFile` 零匹配。

**当前问题**：存档是完整资产（UnifiedArchive v2.0.0，含 randomSeed/initialState/events/checksum，unified-archive.ts:98-108），导出按钮有（CommandBar.vue:36「⇩ 导出存档」），**导入按钮没有**。数据源只有四个内部来源：演示存档/战斗记录/压测合成/实时流（CommandBar.vue:16-21）。会话导入（:32）只导入"模式+书签+断点+过滤"这类偏好，不含事件数据——同事传的两个文件里，核心的存档反而无处安放。连旧档迁移函数 migrateUnifiedLog（unified-migrate.ts:131）都是死代码，无任何调用者。

**改进建议**：CommandBar 加"⤒ 导入存档"（与"会话导入"并列），file input 读 JSON → 复用 loadArchive 现有校验管线（runValidationPipeline）→ 加载即回放。顺手支持窗口拖拽文件。这会把"发存档 → 拖进昊天镜 → 复现"变成标准工作流，是 Bug 协作闭环的最小必要件。

---

## 建议 4【功能缺失】断点能力太弱：单例、命中必暂停、单步不触发

**场景描述**：单步调试是我每天最常用的操作。设好"伤害 ≥ 300"断点后，我按空格逐事件走，**断点根本不触发**——因为它只在播放循环 tickLoop 里检测（haotianStore.ts:441-451），单步/seek 路径（stepEvent → selectEvent → seekTo，:471-488）不检测。我只能退回播放模式，等它自己撞上断点暂停，再回来单步，来回切。而且同时只能设**一个**断点（BreakpointConfig 单值，unified-breakpoint.ts:10-13），我想同时监视"伤害>100"和"某角色行动"两个条件做不到。

**当前问题**：断点 = 播放模式下的一次性暂停点，不是调试工作台的"监视器"。命中必暂停 + toast + 定位（haotianStore.ts:447），**没有"只记录不暂停"的 watch 模式**——排查"伤害是否异常"这类低置信度怀疑时，我只想标记出来看一眼，不想被反复打断。

**改进建议**：① 断点升级为**列表**（多条件并存，breakpoint ref 改数组）；② 新增 watch 模式（命中不暂停，在 DebugCards 打黄标 + 计数）；③ 把断点检测从 tickLoop 提为公共函数，单步/seek 后统一调用（改一行调用点的量级）；④ 断点按钮上显示累计命中次数——这是建议 7 命中率统计的基础。

---

## 建议 5【功能缺失】录制/阵容/场景没有持久化管理

**场景描述**：回归测试跑 20 场，想删掉调试用的废记录、把"剑士+奶妈+坦克"标准阵容存成模板、把基准场景保存下来下轮回归复用——三件事**全做不到**。录制只能看列表 + 加载（CommandBar.vue:22-28）；"保存场景"点了之后刷新页面就没了。

**当前问题**：① `BattleRecorder.deleteRecording/deleteRecordingByBattleId`（BattleRecorder.ts:498-515）存在，但 presentation 层**零调用**——只能看不能删，50 条上限自动淘汰（BattleRecorder.ts:120）没得选；② 阵容是 18 个硬编码预设（ParticipantPanel.vue:189-318），没有自定义阵容保存；③ "保存场景"只 push 内存数组（BattleArena.vue:481-502），load 也不恢复状态（:488-492 只打日志）。IndexedDbStorage 已有 `keysByField/getStats` 端口（IndexedDbStorage.ts），存什么都能落盘，缺的只是 UI。

**改进建议**：① 录制管理面板：列表 + 删除/重命名/复制 key + 容量统计（直接接上现有删除 API）；② 阵容持久化到 IndexedDB 新增 lineups store（封神榜规格 §2 已规划"预设阵容管理 P0"，数据模型可对齐）；③ 场景管理落地为真实存取（SceneManagementDialog 已有骨架，补持久化即可）。

---

## 建议 6【性能】大存档事件流全量渲染

**场景描述**：切到压测存档（2000+ 事件）的瞬间，回放工作台明显掉帧，滚动事件流时选中/高亮有延迟。同一份数据切到调试工作台的卡片流却很流畅。

**当前问题**：DebugCards 有虚拟滚动（visible/offsetOf/measure，DebugCards.vue:64-143），**ReplayStream 是普通 v-for 全量渲染**（ReplayStream.vue:17，`v-for="ev in shown"`，shown = store.filteredEvents 无上限）。同一个 store、两种性能待遇。另：校验在 Worker 跑但 2s 超时回退主线程（unified-worker.ts:74-97），大档校验一旦超时主线程会同步卡顿且无进度反馈。

**改进建议**：① ReplayStream 复用 DebugCards 的虚拟列表模式（同一份实现，已在仓库内，非新依赖）；② 事件行按需渲染（当前视口 ± 缓冲行）；③ 校验改为带进度的异步反馈（"校验中 62%…"），超时回退前先提示，别让用户以为卡死。

---

## 建议 7【数据与报表】无断言、无断点命中率、无回归沉淀——验证全靠肉眼

**场景描述**：封神榜调完暴击率，我的验收动作是：手动打 10 场 → 一场一场翻事件流 → 心里默算"好像暴击变多了"。想验证"第 3 回合前不应出现伤害>500 的暴击"这种规则在 50 场里是否成立？只能导 JSON 出去写脚本。**昊天镜连一个"断言"概念都没有**（grep assert/hitCount/statistic 在 haotian + unified 目录零实现）。

**当前问题**：唯一的"统计"是校验器的一次性 ValidationStats（事件/因果链/锚点/判定次数，unified-validator.ts:16-30），在 DiagPanel 展示完即弃（DiagPanel.vue:41）——**不累计、不持久化、无历史对比**。断点命中率、断言通过率这些 QA 最需要沉淀的指标全部不存在。

**改进建议**：① 断言规则集：对事件流声明式断言（数值范围/因果链完整性/回合数一致性/缺失 battle_end 等），跑完存档输出断言报告（通过/失败/覆盖数），复用校验器管线的模式（unified-validator 已有骨架）；② 断点命中计数 + 校验统计沉淀为每场存档的"质量记录"存 IndexedDB，支持两场战斗报告对比；③ 报告导出 Markdown/CSV（BattleSummaryDialog 已有导出先例 :127-161，直接沿用）。

---

## 建议 8【易用性】事件字段语义与 phase 分类学习成本高

**场景描述**：新来的战斗策划第一次开调试工作台，看到 11 种 phase（battle_lifecycle / turn_flow / action_execution / damage_calculation / buff_lifecycle…）、四级 level、correlationId 因果链、快照与增量 `_delta` 的读法，第一反应是懵——"我该先看哪？搜索框填什么？"调试工作台默认还关着"调试专属事件"开关（showDbg），第一眼看到的和回放工作台几乎一样，完全不知道调试能力在哪。

**当前问题**：没有字段图例、没有 phase 语义解释、没有引导。样式里的 phase 着色体系很完整（haotian.scss 35KB），但**语义没人解释**，新用户只能靠试错。

**改进建议**：① 事件行 hover 显示字段 tooltip（这个 phase 是什么、level 三级含义、correlationId 是同一因果链分组）；② 顶部加"phase 图例"胶囊条（点击即过滤，与建议 1 的检索面板复用同一状态）；③ 首次进入调试工作台显示一次性三步引导层："选回合 → 点事件 → 沿因果链看数字怎么算出来的"（10 秒可跳过）。

## 杀手级功能：种子驱动的确定性重演 + 一键回归对比台（暂名「照妖镜」）

**场景**：QA 最深的痛一句话——**"这个 Bug 我复现了，但重开一局就没了。"** 实况战斗全程 `Math.random()`（DamageCalculator.ts:129,141,586 / BattleAI.ts:365 / BuffSystem.ts:358 / target-resolver.ts:98 等十几处），随机性不可控；randomSeed 在录制时生成（BattleRecorder.ts:151）、随存档导出（unified-archive.ts:102），但只在 StatusBar 只读展示（StatusBar.vue:13）——**没有任何 UI 能指定种子重跑同一场战斗**。回归验证 = 手工重开对局 + 肉眼对比，误差全看运气。

**为什么是杀手级**：它一次性打通"复现 → 验证 → 回归"三条主线，而且**三块都有现成基础，不是画饼**：

1. **复现**：`SeededRandom`（shared/utils/SeededRandom.ts）已存在，只差把实况随机源从 Math.random 收敛成可注入的 RNG。同一存档 + 同一种子 + 同一操作序列 → 100% 重演。"复现不了"直接消失。
2. **验证**：封神榜调参后，用**同一 seed** 重跑，伤害/暴击/回合数变化是纯参数效应，可量化对比——这正是封神榜→昊天镜回流调参闭环缺的那块计量器。
3. **回归**：批量（如 50 场同种子 × 多配置分支）重演 + 建议 7 的断言集检查 → 输出回归报告（数值分布 diff + 断言通过率），沉淀历史版本。分支 diff 引擎（unified-diff.ts）和校验管线（unified-worker.ts）都是现成的，报告格式沿用 BattleSummaryDialog 的导出先例。

**落地路径**（按依赖排序）：① 战斗引擎随机源注入（把十几处 Math.random 收敛为注入的 RNG，SeededRandom 已就绪）；② 唤灵台/演劫台加"固定种子"开关 + 种子输入框；③ 昊天镜加"回归台"视图：选存档 → 选配置分支 → 批量重演 → diff + 断言报告。①② 是纯基础设施改造不碰玩法逻辑，③ 是纯增量视图。这是我作为 QA 主管最想按住产品经理的手签下来的需求——没有它，其他所有建议都只是让"人工验证"更快，只有它把"人工验证"变成"自动回归"。
