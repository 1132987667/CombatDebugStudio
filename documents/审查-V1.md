## 架构评审报告

基于 `neat-freak` skill 的「代码事实面」审计标准，以下是对 `CombatDebugStudio` 的架构层面深度评审。

---

### 一、DDD 四层架构：名义合规，实质穿透

项目声明采用 DDD 四层架构（domain / application / infrastructure / presentation），但实际依赖关系存在多处**反向穿透**：

| 违规点 | 位置 | 问题 |
|--------|------|------|
| domain → infrastructure | `BuffSystem.ts` 直接 import `battleLogManager` | 领域层不应依赖具体日志实现 |
| domain → infrastructure | `PassiveSkillManager.ts` import `battleLogManager` | 同上 |
| domain → presentation | `BattleAI.ts` import `useBattleStore` | 领域层反向依赖 UI 状态管理 |
| domain → main 入口 | 多处 import `eventBus from '@/main'` | 领域层依赖应用入口文件 |
| infrastructure → domain 具体类 | `Container.ts` 直接 new 所有领域服务 | DI 容器应通过接口注册，而非硬编码具体类 |

**核心矛盾**：`AGENTS.md` 声明「领域层通过端口定义依赖，基础设施层提供适配器实现」，但 `domain/port/` 目录下仅有 `ILogger` 和 `IStorage` 两个端口接口，远未覆盖实际依赖面。`BuffSystem` 对日志、事件总线的依赖完全绕过了端口抽象。

---

### 二、God Class 与职责膨胀

| 类 | 行数 | 承担职责 | 问题 |
|----|------|----------|------|
| `BattleSystem.ts` | ~1000+ | 战斗生命周期、回合流转、被动触发、光环分发、动画回调注册、伤害/治疗回调、触发器脚本注册、AI 实例管理 | 至少 6 个独立关注点混在一个类中 |
| `BattleExecutor.ts` | ~600+ | 参与者行动决策、技能执行、攻击处理、连击追踪、额外行动队列、自定义步骤分发 | 决策逻辑与执行逻辑未分离 |
| `types.ts`（battle/type/） | ~500+ | 枚举、常量、接口、工厂函数（`BattleActionHelper`）、辅助类型 | 类型定义与运行时逻辑混合 |
| `BuffSystem.ts` | ~500+ | Buff 生命周期、修饰符管理、触发器注册/反注册、免疫管理、护盾值管理、控制效果判定、回调桥接 | 至少 4 个子系统 |

**`BattleSystem` 的回调注册问题尤为突出**：在 `initialize()` 方法中，通过闭包注册了 `onAttributeChange`、`onDamageRequest`、`onHealRequest`、`onBuffApplied` 四个回调，且使用 `let _inDamageCallback = false` 做递归守卫——这是典型的「用过程式补丁掩盖架构缺陷」。

---

### 三、事件系统：三套并行，职责模糊

项目中存在**三套独立的事件机制**，彼此无统一契约：

| 事件系统 | 位置 | 用途 | 问题 |
|----------|------|------|------|
| `eventBus`（mitt） | `infrastructure/adapters/event/EventBus.ts` | UI 层动画触发、队伍变更通知 | 从 `@/main` 导出，领域层反向依赖 |
| `TriggerEventBus` | `infrastructure/adapters/event/TriggerEventBus.ts` | Buff 触发器阶段事件 | 与 eventBus 完全独立，无共享类型 |
| `BattleEventManager` | `domain/battle/events/BattleEventManager.ts` | 战斗日志事件处理 | 直接 import `useBattleStore`，领域层依赖 presentation |

`BattleEventCodes` 和 `BattleTriggerPhase` 两套枚举存在语义重叠（如 `TURN_START`、`BATTLE_START` 在两边各定义一次），但无映射关系文档。

---

### 四、DI 容器：注册即硬编码

`Container.ts` 的 `initializeContainer()` 函数是一个 200+ 行的**手动装配清单**：

```typescript
container.register('BuffScriptRegistry', new BuffScriptRegistry())
container.register('BuffSystem', new BuffSystem(buffScriptRegistry))
container.register('SkillManager', new SkillManager(buffSystem))
// ... 20+ 行硬编码
```

问题：
- 无接口绑定——所有注册使用字符串 key（`'BuffSystem'`），无编译期类型安全
- 无模块划分——所有服务在一个函数中平铺注册，无法按特性独立加载
- `BattleSystem.createInstanceWithContainer()` 内部又通过 `container.resolve()` 拉取依赖——**构造器注入与 Service Locator 混用**
- 子管理器（`BattleStateManager`、`AutoBattleManager` 等）通过 `registerFactory` 延迟创建，但工厂内部再次 `container.resolve()`，形成**隐式循环依赖链**

---

### 五、领域模型：贫血 + 过程式

`BattleParticipantImpl` 名义上是「实体」，但：

- 属性通过 `ParticipantStats`（一个 `Map<ATTRIBUTE_CODE, AttributeValue>`）管理，实体本身只是 getter/setter 的代理
- 行为逻辑（伤害计算、治疗、Buff 应用）全部外置到 `DamageCalculator`、`HealCalculator`、`BuffSystem`、`SkillExecutor`
- 实体不持有自己的 `ModifierStack` 引用，而是通过 `setModifierProvider(buffSystem)` 在运行时注入——**实体不知道自己被谁修改**

这是典型的**事务脚本模式**（Transaction Script），而非 DDD 所倡导的富领域模型。`AGENTS.md` 中「DDD 四层架构」的声明与实际代码组织存在显著偏差。

---

### 六、配置驱动 vs 代码驱动的边界模糊

| 数据 | 存储位置 | 问题 |
|------|----------|------|
| Buff 定义 | `buffs.json` + 脚本类 `static CONFIG` + `effects.json` | 三处来源，优先级规则散落在 `BuffScriptRegistry.resolve()` 中 |
| 技能定义 | `skills.json` + `skill_passive.json` + `skills_new.json` + `skill_passive_guardian.json` | 四个文件，`GameDataProcessor.getSkillsData()` 简单拼接，无版本/覆盖语义 |
| 触发器脚本 | `triggers/index.ts` 硬编码 15 个 handler | 与 JSON 中 `triggers[].scriptId` 的映射无 schema 校验 |
| 技能 ID 重复 | `skills.json` 中 `skill_enemy_023_small` 出现 3 次 | JSON 解析静默覆盖，无运行时告警 |

`skills_new.json` 的存在表明曾有过迁移计划，但新旧文件并存且无废弃标记——这是 `neat-freak` skill 中「退役符号的非历史引用未清」的典型案例。

---

### 七、presentation 层对 domain 的过度耦合

`BattleArena.vue`（主视图）直接：
- `container.resolve<BattleService>('BattleService')` — 视图层手动拉取 DI 容器
- `container.resolve<BuffSystem>('BuffSystem')` — 视图层直接操作领域服务
- `container.resolve<PassiveSkillManager>('PassiveSkillManager')` — 视图层注册被动技能
- `GameDataProcessor.enemyToParticipant()` — 视图层执行领域转换逻辑

`BattleDashboard.vue` 直接 import `ATTRIBUTE_CODE`、`ModifierType`、`ModifierTypeNames` 等领域内部类型用于 UI 渲染——表现层与领域层的类型契约未通过 DTO 隔离。

| 优先级 | 建议 | 预期收益 |

| P0 | 消除 `BattleAI.ts` 对 `useBattleStore` 的 import | 解除 domain → presentation 反向依赖 |

## Buff 系统代码级深度评审

> 评审范围：`src/domain/buff/` 全部文件 + `src/domain/buff/scripts/` + `src/domain/buff/triggers/`
> 评审基准：`neat-freak` skill 的代码事实面审计标准

---

### 一、架构层面：职责膨胀与层间穿透

#### 1.1 BuffSystem 是一个 God Class

`BuffSystem.ts` 单文件承担了 **至少 9 个独立职责**：

| # | 职责 | 代码位置 | 行数估算 |
|---|------|---------|---------|
| 1 | Buff 实例生命周期管理（add/remove/update） | `addBuff`, `removeBuff`, `updatePerTurn` | ~180 |
| 2 | 叠加规则引擎（REFRESH/LIMITED/INDEPENDENT） | `addBuff` 内 switch | ~40 |
| 3 | 配置合并（五层优先级） | `addBuff` 内 resolvedConfig | ~25 |
| 4 | 免疫系统（注册/查询/重建） | `registerCharacterImmunities`, `rebuildCharacterImmunities` | ~35 |
| 5 | 光环分发（self 目标） | `applyBuffAuraModifiers` | ~20 |
| 6 | 触发器接线（注册/反注册） | `registerTriggersForInstance`, `unregisterTriggersForInstance` | ~45 |
| 7 | 修饰符栈管理（实现 IModifierProvider） | `getModifierStack`, `applyAttributeModifiers` | ~30 |
| 8 | 控制效果查询（实现 BuffQuery） | `isCharacterControlled`, `canUseSkill`, `canAct` | ~25 |
| 9 | 护盾值管理 | `getShieldValue`, `setShieldValue` | ~10 |

**问题**：`addBuff` 方法体约 **120 行**，是一个典型的"做所有事情"的方法。任何修改（如新增叠加规则、调整配置合并优先级）都需要理解整个方法。

**建议拆分方向**：

```
BuffSystem (协调者，~50行)
├── BuffLifecycleManager    — add/remove/update/refresh
├── BuffStackRuleEngine     — REFRESH/LIMITED/INDEPENDENT 策略
├── BuffConfigResolver      — 五层配置合并
├── ImmunityRegistry        — 免疫标签注册/查询/重建
├── TriggerWiring           — 触发器注册/反注册
└── BuffSystem 保留        — 实例 Map、ModifierStack Map、事件通知
```

#### 1.2 领域层反向依赖基础设施层

```typescript
// BuffSystem.ts — 领域层
import { battleLogManager, LogLevel } from '@/infrastructure/adapters/logging'  // ❌
import { TriggerEventBus, triggerEventBus } from '@/infrastructure/adapters/event/TriggerEventBus'  // ❌
```

`AGENTS.md` 声明「领域层通过端口定义依赖，基础设施层提供适配器实现」，但 BuffSystem 直接 import 了两个基础设施模块。`domain/port/` 下只有 `ILogger` 和 `IStorage`，缺少 `ITriggerEventBus` 端口。

#### 1.3 双接口实现的耦合

```typescript
export class BuffSystem implements IModifierProvider, BuffQuery {
```

`IModifierProvider` 服务于属性系统（`ParticipantStats` 通过它同步修饰符），`BuffQuery` 服务于战斗实体（`BattleParticipantImpl` 通过它查询 buff 状态）。两个接口的消费者完全不同，合并在一个类中意味着：
- 属性系统的变更可能意外影响战斗查询
- 无法独立 mock 其中一个接口进行测试

### 二、`addBuff` 方法：核心路径的 7 个具体问题

#### 2.1 配置合并的 `aura` 字段缺失

```typescript
// addBuff 中的 resolvedConfig 构建
const resolvedConfig: BuffConfig = {
  id: ..., name: ..., description: ..., duration: ...,
  maxStacks: ..., cooldown: ..., stackRule: ...,
  controlType: ..., controlPriority: ..., isPermanent: ...,
  isDebuff: ..., isPositive: ..., iconPath: ...,
  dispellable: ..., immuneTags: ..., tags: ...,
  parameters: ..., attributes: ..., triggers: ...,
  // ❌ 没有 aura 字段
}
```

`BuffConfig` 类型定义中**没有 `aura` 字段**，`ScriptBuffConfig` 也没有。但 JSON 配置（`buffs.json`）中大量 buff 有 `aura` 字段。这意味着：

- 脚本的静态 `CONFIG` **无法定义光环**
- `resolvedConfig` 不携带 `aura`
- `getBuffConfigByInstanceId()` 返回的 config 没有 `aura`
- 光环只能通过 `BuffScriptRegistry.getBuffConfig(buffId)` 从 JSON 原始数据读取
- `BattleSystem.distributeAuras` 使用 `getBuffAuraConfig(buffConfig.id)` 间接读 JSON

**后果**：如果一个 buff 只有脚本静态 CONFIG（自包含模式），没有 JSON 配置，它的光环永远不会被分发。

#### 2.2 LIMITED 叠加的实例选取不确定性

```typescript
case StackRule.LIMITED: {
  const existingBuffs = this.getBuffInstances(characterId).filter(
    (instance) => instance.buffId === buffId,
  )
  if (existingBuffs.length > 0) {
    const target = existingBuffs[0]  // ❌ 取第一个，顺序不确定
```

`getBuffInstances` 遍历 `Map`，`Map` 的迭代顺序是插入顺序。但如果之前有 INDEPENDENT 模式的实例残留（配置热更新场景），`existingBuffs[0]` 可能不是最新的实例。

#### 2.3 LIMITED 叠加时 `onRefresh` 未包裹 ErrorBoundary

```typescript
// LIMITED 分支中：
target.script.onRefresh(target.context)  // ❌ 直接调用，无 ErrorBoundary
```

对比 `addBuff` 中 `onApply` 的调用：

```typescript
BuffErrorBoundary.wrap(() => {
  script.onApply(context)  // ✅ 有 ErrorBoundary
})
```

如果 `onRefresh` 抛异常（如 `BerserkBuff._onRefresh` 中读取了不存在的变量），整个 `addBuff` 方法中断，但实例已经部分修改（`currentStacks` 已递增，`_stacks` 已设置），导致**不一致状态**。

#### 2.4 免疫检查的时序问题

```typescript
// 免疫检查在配置合并之后、实例创建之前
const targetImmunities = this.characterImmunities.get(characterId)
if (targetImmunities && targetImmunities.size > 0) {
  const controlTag = resolvedConfig.controlType && resolvedConfig.controlType !== ControlType.NONE
    ? resolvedConfig.controlType.toLowerCase() : null
  const buffTag = buffId.startsWith(BUFF_ID_PREFIX) ? buffId.slice(BUFF_ID_PREFIX.length) : buffId
  if ((controlTag && targetImmunities.has(controlTag)) || targetImmunities.has(buffTag)) {
    return ''  // 静默跳过
  }
}
```

**问题**：免疫检查只匹配 `controlType` 和 `buffId`（去掉 `buff_` 前缀），但 `immuneTags` 配置中的标签可能是任意字符串（如 `"slow"`, `"stun"`, `"freeze"`）。如果 JSON 中 `immunities: ["slow"]`，而 buff 的 `controlType` 是 `ControlType.NONE`（因为 slow 不是通过 controlType 实现的，而是通过 attributes 中的 `speed: "-10"` 实现），那么免疫检查**不会生效**。

`buff_mountain_child` 的 JSON 配置：
```json
{ "id": "buff_mountain_child", "immunities": ["slow"] }
```

但 `buff_slow_heavy`（减速 buff）没有 `controlType`，它的减速是通过 `attributes: { "speed": "-10" }` 实现的。所以 `buff_mountain_child` 的 `slow` 免疫**实际上无法阻止 `buff_slow_heavy`**。

#### 2.5 `onBuffApplied` 回调与动画重复

```typescript
// addBuff 末尾：
if (this.buffAppliedCallbackEnabled && this.onBuffApplied) {
  this.onBuffApplied(characterId, buffInstance.buffId)
}
```

`BattleSystem.initialize` 中注册了 `setBuffAppliedCallback`，触发 `BUFF_EFFECT` 事件。但 `BattleExecutor.executeBuff` 中也会触发 `BUFF_EFFECT` 动画。`buffAppliedCallbackEnabled` 标志用于在主动技能执行期间禁用回调（避免重复），但这个标志的管理分散在 `BattleExecutor` 中：

```typescript
// BattleExecutor.executeBuff 中：
this.buffSystem.setBuffAppliedCallbackEnabled(false)
// ... 执行技能 ...
this.buffSystem.setBuffAppliedCallbackEnabled(true)
```

如果技能执行中途抛异常（在 `setBuffAppliedCallbackEnabled(false)` 之后、`true` 之前），回调**永久禁用**，后续所有被动触发的 buff 都不会有动画。

#### 2.6 对象池归还时的引用泄漏

```typescript
// BuffContextPool 的 reset：
reset: (context) => context.reset()

// BuffContext.reset：
public reset(): void {
  this.characterId = ''
  this.instanceId = ''
  this.config = {} as BuffConfig
  this.startTime = 0
  this.variables.clear()
  this._buffSystem = null  // ✅ 这里确实清空了
}
```

等等，重新看代码——`reset()` 确实清空了 `_buffSystem`。但 `BuffContextPool` 的 `validate` 函数：

```typescript
validate: (context) => context.characterId === '' && context.instanceId === '' && context.variables.size === 0
```

没有验证 `_buffSystem === null`。如果 `reset()` 因为某种原因没有完全执行（如 `variables.clear()` 抛异常），`_buffSystem` 可能残留。但这是一个极端边界情况。

**真正的问题**是 `BuffContext.getCharacter()` 永远返回 `undefined`：

```typescript
// TODO: 实现从 BuffSystem 或外部注入的 Character 缓存中获取角色实例
public getCharacter(): Character | undefined {
  return undefined
}
```

这意味着 `getAttributeValue()` 永远返回 0。任何依赖此方法的脚本逻辑都会静默失败。

#### 2.7 战斗记录（CombatRecord）集成缺失

`addBuff` 接受 `record?: CombatRecord` 参数，但**从未使用它**。对比 `BattleExecutor.executeBuff`：

```typescript
// BattleExecutor 中：
const instanceId = this.buffSystem.addBuff(buffTarget.id, buffId, buffConfig, 0, record)
```

`record` 被传入但 `addBuff` 内部没有向 `record.effects` 推送任何内容。Buff 的施加/移除不会出现在战斗记录中。

### 三、触发器系统：接线正确但语义断裂

#### 3.1 阶段名映射的脆弱性

```typescript
private static readonly PHASE_NAME_MAP: Record<string, BattleTriggerPhase> = {
  ON_TURN_START: BattleTriggerPhase.TURN_START,
  ON_TURN_END: BattleTriggerPhase.TURN_END,
  // ... 18 个映射
}
```

JSON 配置中使用 `ON_TURN_START` 风格，枚举值是 `turn_start`。这个映射是**运行时字符串匹配**，没有编译期保障。如果 JSON 中写错（如 `ON_TURN_START` 写成 `ON_TURNSTART`），会静默跳过，不报错。

#### 3.2 触发器回调中的概率/冷却/次数检查

```typescript
const callback = (ctx: TriggerEventContext) => {
  if (trigger.probability !== undefined && trigger.probability < 1 && Math.random() > trigger.probability) return
  if (trigger.maxTriggers !== undefined && trigger.maxTriggers >= 0 && triggerCount >= trigger.maxTriggers) return
  const turn = ctx.currentTurn ?? 0
  if (trigger.cooldown && (turn - lastTriggerTurn) < trigger.cooldown) return
  // ...
}
```

**问题**：`triggerCount` 和 `lastTriggerTurn` 是闭包变量，绑定到特定的 `(instanceId, trigger)` 组合。如果 buff 被移除再重新添加，新的闭包会重置计数器——这是正确的。但如果 buff 是 REFRESH 模式（remove + re-add），计数器也会重置——这可能不是期望的行为。

#### 3.3 `healPercentMaxHp` 的多余调用

```typescript
export function healPercentMaxHp(ctx: TriggerExecutionContext): void {
  const percent = (ctx.params?.percent as number) ?? 0.05
  const targetId = ...
  ctx.buffSystem?.requestHeal(targetId, 0)           // ❌ 治疗 0，无意义
  ctx.buffSystem?.requestDamage(targetId, 0, -Math.abs(percent))  // 负百分比 = 治疗
}
```

`requestHeal(targetId, 0)` 会触发 `onHealRequest` 回调，进而触发 `HEAL_RECEIVED` 被动事件——**治疗量为 0 也会触发**。这可能导致无限循环：治疗触发 HEAL_RECEIVED → HEAL_RECEIVED 被动触发治疗 → ...

#### 3.4 `applyShield` 的参数断裂

```typescript
export function applyShield(ctx: TriggerExecutionContext): void {
  const shieldPercent = (ctx.params?.shieldPercent as number) ?? 0.1
  ctx.buffSystem?.addBuff(ctx.targetId ?? '', 'buff_shield', {
    duration: 1,
    parameters: { shieldPercent },  // 传入 shieldPercent
  }, ctx.currentTurn ?? 0)
}
```

但 `ShieldBuff` 脚本读取的是：

```typescript
const baseShield = this.getConfigValue(context, 'baseShield', 100)
const shieldScale = this.getConfigValue(context, 'shieldScale', 1)
```

`shieldPercent` 参数**从未被读取**。护盾值始终是 `baseShield * shieldScale + maxHP * 0.1`，与触发器传入的 `shieldPercent` 无关。

### 四、ModifierStack：接口契约与实现的不一致

#### 4.1 `calculate` 方法是死代码且逻辑不完整

```typescript
/**
* 计算属性最终值
* ponytail: 未被调用（ParticipantStats 自行计算），保留接口契约
*/
public calculate(attribute: ATTRIBUTE_CODE, baseValue: number): number {
  // ...
  for (const modifier of mods) {
    switch (modifier.type) {
      case ModifierType.ADDITIVE: additiveSum += modifier.value; break
      case ModifierType.MULTIPLICATIVE: multiplicativeSum *= 1 + modifier.value; break
      case ModifierType.PERCENTAGE: additiveSum += baseValue * modifier.value; break
      // ❌ 缺少 ModifierType.FINAL 的处理
    }
  }
```

`ParticipantStats.recalcAttribute` 处理了四种类型（ADDITIVE → PERCENTAGE → MULTIPLICATIVE → FINAL），但 `ModifierStack.calculate` 只处理了三种，且 PERCENTAGE 的计算方式不同（`baseValue * modifier.value` vs `percentSum += modifier.value` 然后 `base * (1 + percentSum/100)`）。

如果将来有人调用 `ModifierStack.calculate`（因为它是 `IModifierStack` 接口的一部分），会得到**与 ParticipantStats 不一致的结果**。

#### 4.2 修饰符的 `sourceType` 硬编码

```typescript
public addModifier(buffInstanceId: string, attribute: ATTRIBUTE_CODE, value: number, type: ModifierType): void {
  stack.push({
    sourceKey: buffInstanceId,
    sourceType: ModifierSourceType.BUFF,  // ❌ 硬编码为 BUFF
    attribute, value, type,
  })
}
```

所有通过 `ModifierStack.addModifier` 添加的修饰符都被标记为 `BUFF` 来源。但 `GameDataProcessor.pushModifier` 使用 `ModifierSourceType.SKILL`。这意味着同一个属性下，来自 buff 脚本和来自被动技能的修饰符有不同的 `sourceType`——这是正确的。但 `ModifierStack` 无法表达 `SKILL` 来源，因为它的 API 不接受 `sourceType` 参数。

### 五、脚本层：模板设计的隐患

#### 5.1 `AttributeBuffTemplate` 的 `_onRemove` 是空操作

```typescript
protected _onRemove(context: BuffContext): void {
  // ponytail: 修饰符清理由 BuffSystem.removeBuff → modifierStack.removeModifier(instanceId) 统一处理
}
```

这是正确的设计（集中管理），但 `BerserkBuff` 在 `_onApply` 中通过 `addModifier` 添加了 4 个修饰符（attack, critRate, critDamage, defense）。如果 `BuffSystem.removeBuff` 中的 `modifierStack.removeModifier(instanceId)` 因为某种原因没有执行（如 `removeBuff` 在 `onRemove` 回调之后、`removeModifier` 之前抛异常），修饰符会**永久残留**。

看 `removeBuff` 的执行顺序：

```typescript
public removeBuff(instanceId: string): boolean {
  const instance = this.buffInstances.get(instanceId)
  if (!instance || !instance.isActive) return false
  BuffErrorBoundary.wrap(() => { instance.script.onRemove(instance.context) })  // 1. 脚本回调
  instance.isActive = false                                                      // 2. 标记失活
  this.unregisterTriggersForInstance(instanceId)                                 // 3. 反注册触发器
  this.buffInstances.delete(instanceId)                                          // 4. 删除实例
  const modifierStack = this.getModifierStack(instance.characterId)
  modifierStack.removeModifier(instanceId)                                       // 5. 清除修饰符
  // ...
}
```

步骤 3（`unregisterTriggersForInstance`）如果抛异常（虽然有 try-catch），步骤 4-5 不会执行。但 `unregisterTriggersForInstance` 内部有 `this.eventBus.offByBuffInstance(instanceId)`，这个操作不太可能抛异常。

**真正的风险**是步骤 1：`onRemove` 被 ErrorBoundary 包裹，即使抛异常也会继续。但如果 `onRemove` 中修改了 `modifierStack`（如某个脚本在 `_onRemove` 中手动添加修饰符），步骤 5 的 `removeModifier(instanceId)` 只移除该 instanceId 的修饰符，不会影响新添加的——这是正确的。

#### 5.2 `BerserkBuff` 的 `_onRefresh` 与 LIMITED 叠加的交互

```typescript
// BerserkBuff._onRefresh：
protected _onRefresh(context: BuffContext): void {
  const currentAttack = context.getVariable<number>('currentAttackBonus') ?? params.attackBonus
  const newAttack = currentAttack + params.refreshAttackBonus
  this.addModifier(context, ATTRIBUTE_CODE.attack, params.refreshAttackBonus, ModifierType.ADDITIVE)
  context.setVariable('currentAttackBonus', newAttack)
}
```

在 LIMITED 叠加时，`BuffSystem.addBuff` 调用 `target.script.onRefresh(target.context)`。但 `_onRefresh` 中调用 `this.addModifier`，这会向 `ModifierStack` 添加一个**新的**修饰符（使用相同的 instanceId）。

`ModifierStack.addModifier` 不做去重——它直接 `push`。所以每次 LIMITED 叠加都会添加一个新的修饰符，而不是更新已有的。

但 `ParticipantStats.recalcAttribute` 在重算时会读取 `modifierStack.getModifiers(code)`，返回所有修饰符。所以多个同 instanceId 的修饰符会被**累加**——这是 LIMITED 叠加的预期行为（每层 +20 攻击）。

**但问题是**：`_onApply` 中也调用了 `addModifier`。所以第一次添加时有 1 个修饰符，第一次 LIMITED 叠加后 `onRefresh` 添加第 2 个，第二次叠加后添加第 3 个。总共 3 个修饰符，每个 +20（假设 refreshAttackBonus=20），总加成 60。

但 `_onApply` 中的 `attackBonus` 是 100，`refreshAttackBonus` 是 20。所以：
- 初始：+100（来自 _onApply）
- 第一次叠加：+100 + 20 = +120
- 第二次叠加：+100 + 20 + 20 = +140

这看起来是正确的。但如果 buff 被移除再重新添加（REFRESH 模式），`_onApply` 会重新添加 +100，而旧的修饰符已被 `removeModifier(instanceId)` 清除。新的 instanceId 不同，所以不会冲突。

#### 5.3 `GuardianBuffs.ts` 中的空修饰符列表

```typescript
export class FirmShieldBuff extends AttributeBuffTemplate {
  public static readonly BUFF_ID = 'guardian_buff_firm_shield'
  protected getModifiers(): AttributeModifier[] {
    return []  // 空！
  }
}
```

`FirmShieldBuff`、`StaticReboundBuff`、`EyeForEyeBuff`、`RandomTauntBuff`、`BackwaterArmorBuff` 都返回空修饰符列表。它们的实际效果由 `BattleSystem` 或 `BattleParticipantImpl` 中的硬编码逻辑实现（如 `takeDamage` 中检查 `hasBuff('guardian_buff_backwater_armor')`）。

这意味着这些 buff 的"效果"不在 buff 系统中，而在战斗系统的各处 `hasBuff` 检查中。这违反了 buff 系统的封装原则——buff 的效果应该由 buff 脚本自包含，而不是散落在战斗逻辑中。

### 六、`parseAttributeValue` 的歧义

```typescript
public parseAttributeValue(value: string): { value: number; type: ModifierType } {
  const isPercent = trimmed.includes('%')
  const numValue = parseFloat(numericStr)
  if (isPercent) return { value: numValue, type: ModifierType.PERCENTAGE }
  if (Math.abs(numValue) < 1) return { value: numValue * 100, type: ModifierType.PERCENTAGE }
  return { value: numValue, type: ModifierType.ADDITIVE }
}
```

| 输入 | 解析结果 | 意图 | 是否正确 |
|------|---------|------|---------|
| `"+20%"` | PERCENTAGE, 20 | +20% | ✅ |
| `"+0.1"` | PERCENTAGE, 10 | +10%（0.1×100） | ✅ |
| `"+10"` | ADDITIVE, 10 | +10 固定值 | ✅ |
| `"+1"` | ADDITIVE, 1 | +1 固定值？还是 +1%？ | ⚠️ 歧义 |
| `"-0.5"` | PERCENTAGE, -50 | -50% | ✅ |
| `"0"` | ADDITIVE, 0 | 无效果 | ✅ |

`"+1"` 的歧义：如果 JSON 中写 `"critRate": "+1"`，意图可能是 +1% 暴击率（ADDITIVE 1 个百分点），也可能是 +1 固定值。当前解析为 ADDITIVE 1，这在 `critRate` 的上下文中是合理的（暴击率以百分点计）。但对于 `speed` 属性，`"+1"` 可能是 +1 速度（ADDITIVE）或 +1% 速度（PERCENTAGE）。

### 二、P0 级问题（功能性/架构性错误）

#### 2.1 领域层反向依赖基础设施层（4 处）

| 文件 | 违规 import | 影响 |
|------|------------|------|
| `BattleSystem.ts` | `import { eventBus } from '@/infrastructure/adapters/event/EventBus'` | 领域核心直接耦合基础设施 |
| `BattleLifecycleManager.ts` | 同上 | 战斗生命周期管理耦合 |
| `DebugGate.ts` | 同上 | 调试门控耦合 |

`domain/port/event/` 目录下定义了 `IDomainEventBus` 接口，但 **从未被任何类实现或注入**。这是一个「定义了端口但没有适配器」的典型半成品。

```typescript
// domain/port/event/IDomainEventBus.ts — 存在但从未使用
export interface IDomainEventBus {
  emit(event: string, data?: unknown): void
  on(event: string, handler: (data: unknown) => void): void
```

#### 2.2 BattleEventManager 是死代码

`BattleEventManager` 在 `Container.ts` 中被初始化：

```typescript
// Container.ts
battleEventManager.setBattleSystem(battleSystem, battleStateManager)
```

但 **`startListening()` 从未被调用**。实际的事件订阅由 `battleStore` 通过 `BattleService.on()` 完成。

更严重的是，`BattleEventManager` 存在以下问题：

```typescript
// BattleEventManager.ts — 领域层文件直接 import 表现层
import { useBattleStore } from '@/presentation/stores/battleStore'  // ❌ domain → presentation

// stopListening 会移除所有监听器，不仅仅是自己注册的
stopListening() {
  eventBus.off(BattleEventCodes.BATTLE_LOG)    // ❌ 移除该事件的全部监听器
  eventBus.off(BattleEventCodes.BATTLE_ENDED)  // ❌ 同上
  // ...
}
```

mitt 的 `off(type)` 不传 handler 时移除该事件的 **所有** 监听器。如果 `stopListening` 被调用，`battleStore` 注册的监听器也会被一并移除。

#### 2.3 BattleManager.on 单处理器限制

```typescript
// BattleManager.ts
on<T extends BattleEventName>(event: T, callback: (data: BattleEvents[T]) => void) {
  const existing = this.handlers.get(event)
  if (existing) {
    eventBus.off(event, existing)  // ❌ 移除前一个处理器
  }
  this.handlers.set(event, callback)  // ❌ 每个事件只保留一个处理器
  eventBus.on(event, callback)
}
```

**每个事件只能有一个处理器**。如果两个组件都调用 `BattleService.on('damage-animation', ...)`，第二个会静默覆盖第一个。当前代码中 `battleStore` 是唯一调用者，所以暂未触发此 bug，但这是一个 **架构级定时炸弹**。

#### 2.4 `BattleEvents` 接口中的遗留键

```typescript
export interface BattleEvents {
  // ... 正常的事件定义 ...
  [BattleEventCodes.TEAM_DATA_CHANGED]: TeamDataChangedEventData;  // 'team-data-changed'

  // ❌ 遗留键 — 与 TEAM_DATA_CHANGED 不同
  'teamDataChanged': void;

  // ❌ 不在 BattleEventCodes 中，无类型约束
  'battle-summary': BattleSummary;

  // ❌ 索引签名破坏了类型安全
  [key: string]: unknown;
  [key: symbol]: unknown;
}
```

- `'teamDataChanged'`（驼峰）与 `'team-data-changed'`（kebab）是 **两个不同的事件名**，前者从未被发射或订阅
- `'battle-summary'` 在 `BattleArena.vue` 中被硬编码订阅，绕过了 `BattleEventCodes` 常量
- `[key: string]: unknown` 索引签名使 mitt 的类型约束 **完全失效**——任何字符串都可以作为事件名

### 三、P1 级问题（设计缺陷）

#### 3.1 事件名在两套系统间共享

```typescript
export const BattleEventCodes = {
  BATTLE_START: BattleTriggerPhase.BATTLE_START,  // 'battle_start'
  BATTLE_ENDED: BattleTriggerPhase.BATTLE_END,    // 'battle_end'
  TURN_START: BattleTriggerPhase.TURN_START,      // 'turn_start'
  TURN_END: BattleTriggerPhase.TURN_END,          // 'turn_end'
  // ...
}
```

`BATTLE_START`、`TURN_START` 等同时是 `BattleEventCodes`（全局 eventBus）和 `BattleTriggerPhase`（TriggerEventBus）的值。虽然两套系统独立运行不会互相干扰，但：

- 开发者看到 `'turn_start'` 无法判断它属于哪套系统
- 如果未来合并两套系统，会产生事件名冲突
- `BattleTriggerPhase` 有 18 个值，`BattleEventCodes` 复用了其中 4 个，其余 14 个仅在 TriggerEventBus 中使用

#### 3.2 动画事件与业务事件混在同一总线

全局 `eventBus` 同时承载两类完全不同关注点的事件：

| 类别 | 事件 | 频率 | 消费者 |
|------|------|------|--------|
| **业务事件** | `BATTLE_LOG`, `TURN_START`, `TURN_END`, `BATTLE_ENDED`, `TEAM_DATA_CHANGED` | 每回合 1-2 次 | battleStore |
| **动画事件** | `DAMAGE_ANIMATION`, `MISS_ANIMATION`, `BUFF_EFFECT`, `SKILL_EFFECT` | 每次攻击/技能 | battleStore → BattleField |
| **调试事件** | `DEBUG_PAUSE`, `DEBUG_TOGGLE` | 手动触发 | DebugStepOverlay |
| **属性事件** | `PARTICIPANT_ATTRIBUTE_CHANGED` | 每次 Buff 变更 | battleStore |

没有分离关注点。如果动画事件高频发射（如 AOE 技能同时命中 5 个目标），会阻塞业务事件的处理。

#### 3.3 回调桥接模式脆弱

`BuffSystem` 通过 4 个回调字段与 `BattleSystem` 通信：

```typescript
// BuffSystem.ts
private onAttributeChange?: (characterId: string) => void
private onDamageRequest?: (targetId: string, damage: number, damagePercent?: number) => void
private onHealRequest?: (targetId: string, amount: number) => void
private onBuffApplied?: (characterId: string, buffId: string) => void
```

这些回调在 `BattleSystem.initialize()` 中注册：

```typescript
// BattleSystem.ts — initialize()
this.buffSystem.setAttributeChangeCallback((characterId: string) => {
  eventBus.emit(BattleEventCodes.PARTICIPANT_ATTRIBUTE_CHANGED, { characterId })
})
this.buffSystem.setBuffAppliedCallback((characterId: string, buffId: string) => {
  eventBus.emit(BattleEventCodes.BUFF_EFFECT, {
    targetId: characterId,
    buffName: buffId,
    isPositive: true,  // ❌ 硬编码为 true，debuff 也被标记为正面
  })
})
```

问题：
- **`isPositive: true` 硬编码**——所有通过 `onBuffApplied` 回调触发的 `BUFF_EFFECT` 事件都标记为正面效果，包括 debuff
- 回调是 **单播**（只有一个回调函数），不支持多个消费者
- 回调在 `initialize` 中注册，但 `resetBattle` 不清理回调——如果 `initialize` 被多次调用，回调会被覆盖（不会泄漏，但语义不清晰）
- `onDamageRequest` 和 `onHealRequest` 的命名暗示是「请求」，但实际上是 **同步执行**，没有请求-响应语义

#### 3.4 TriggerEventBus 无容量保护

```typescript
// TriggerEventBus.ts
public on(phase: BattleTriggerPhase, callback: TriggerEventListener, buffInstanceId?: string): string {
  const id = `trigger_listener_${++this.listenerIdCounter}`
  if (!this.listeners.has(phase)) {
    this.listeners.set(phase, new Set())
  }
  this.listeners.get(phase)!.add({ id, callback, buffInstanceId })
  return id
}
```

- 没有最大监听器数量限制
- 如果 Buff 不断添加但 `removeBuff` 未被正确调用（如战斗异常中断），监听器会无限增长
- `listenerIdCounter` 是数字递增，长时间运行后可能溢出（虽然 JS 数字精度足够大）

#### 3.5 `offByBuffInstance` 性能问题

```typescript
public offByBuffInstance(buffInstanceId: string): number {
  let removedCount = 0
  this.listeners.forEach((set) => {        // 遍历所有 phase（18 个）
    const toRemove: ListenerItem[] = []
    for (const item of set) {              // 遍历每个 phase 的所有 listener
      if (item.buffInstanceId === buffInstanceId) {
        toRemove.push(item)
      }
    }
    for (const item of toRemove) {
      set.delete(item)
      removedCount++
    }
  })
  return removedCount
}
```

时间复杂度 O(P × L)，P = phase 数量（18），L = 每个 phase 的 listener 数量。在极端情况下（100 个 Buff 各注册 3 个触发器），每次 `removeBuff` 需要遍历 18 × 300 = 5400 个 listener。

**优化方案**：维护一个 `Map<buffInstanceId, Set<listenerId>>` 的反向索引。

#### 3.6 事件发射无错误隔离（全局 eventBus）

```typescript
// mitt 的 emit 是同步的，不捕获异常
eventBus.emit(BattleEventCodes.TURN_START, { actorId: firstActorId })
```

如果任何 `TURN_START` 的监听器抛异常，后续监听器不会执行。`TriggerEventBus` 有 try-catch 保护，但全局 `eventBus` 没有。

对比：

```typescript
// TriggerEventBus — 有错误隔离 ✅
for (const { callback } of listeners) {
  try {
    callback(context)
  } catch (error) {
    console.error(`[TriggerEventBus] 事件 ${phase} 监听器执行出错:`, error)
  }
}

// 全局 eventBus (mitt) — 无错误隔离 ❌
// 任何监听器抛异常会中断整个 emit 链
```

### 四、P2 级问题（代码卫生/一致性）

#### 4.1 import 路径不一致

同一个 `eventBus` 实例在不同文件中通过不同路径导入：

| 文件 | import 路径 |
|------|------------|
| `BattleSystem.ts` | `@/infrastructure/adapters/event/EventBus` |

`@/main` 中 re-export 了 `eventBus`：

```typescript

export { eventBus }
```

但 `main.ts` 是应用入口，不是模块导出文件。通过 `@/main` 导入 `eventBus` 会导致 **循环依赖风险**（main.ts import 了 BattleArena.vue，BattleArena.vue 又 import main.ts）。

#### 4.2 硬编码事件名字符串

```typescript

  lastSummary.value = summary as BattleSummary       // ❌ any 类型
})
```

```typescript
// BattleSystem.ts — TURN_START 发射

// firstActorId 可能是 null（无存活参与者时）

// battleStore.ts — TURN_START 处理
```

`handleTurnStartEvent` 的参数类型是 `any`，失去了 `BattleEvents` 接口提供的类型约束。

#### 4.4 `TEAM_DATA_CHANGED` 发射空数据


`battleStore.syncTeams()` 收到事件后从 `BattleService` 重新拉取数据，事件中的 `allyTeam`/`enemyTeam` 字段 **从未被使用**。事件仅作为「通知信号」，但携带了无用的空数据。

#### 4.5 `battleLogManager` 也是直接依赖

```typescript
// BattleSystem.ts
import { battleLogManager, LogLevel } from '@/infrastructure/adapters/logging'

// BuffSystem.ts

// TriggerEventBus.ts — 未使用 battleLogManager，但使用 console.error
```

与 `eventBus` 相同的问题——领域层直接依赖基础设施层的日志单例。`domain/port/logging/ILogger` 接口存在但未被注入。

### 五、事件流完整追踪

#### 5.1 一次攻击的完整事件链

```
BattleExecutor.executeParticipantAction()
  │
  ├─→ skillManager.executeSkill()
  │     └─→ SkillExecutor.executeStep()
  │           └─→ damageCalculator.calculateDamage()
  │
  ├─→ animationManager.playAttackAnimation()     [GSAP 动画，无事件]
  │
  ├─→ animationManager.playHitAnimation()        [GSAP 动画，无事件]
  │
  ├─→ buffSystem.setDamageCallback 触发:
  │     └─→ eventBus.emit(DAMAGE_ANIMATION, {...})
  │           └─→ battleStore.handleDamageAnimationEvent()
  │                 └─→ setAnimationState('damage', data)
  │                       └─→ watch(store.animationState) in BattleField.vue
  │                             └─→ visualEffectsRef.playAttackSequence()
  │
  ├─→ buffSystem.setBuffAppliedCallback 触发:
  │     └─→ eventBus.emit(BUFF_EFFECT, {...})
  │           └─→ battleStore.handleBuffEffectEvent()
  │
  ├─→ buffSystem.setAttributeChangeCallback 触发:
  │     └─→ eventBus.emit(PARTICIPANT_ATTRIBUTE_CHANGED, {...})
  │           └─→ battleStore.handleAttributeChanged()
  │                 └─→ proxy.recalculateAll()  [Vue 响应式]
  │
  ├─→ passiveSkillManager.triggerPassives(DAMAGE_TAKEN, ...)
  │     └─→ TriggerEventBus.emit(DAMAGE_TAKEN, ctx)
  │           └─→ Buff 触发器回调（如 reflect_damage）
  │                 └─→ buffSystem.requestDamage()
  │                       └─→ onDamageRequest 回调
  │                             └─→ target.takeDamage()
  │
  └─→ battleRecorder.recordAction()              [无事件，直接记录]
```

**问题**：一次攻击触发了 **至少 4 个 eventBus 事件** + **N 个 TriggerEventBus 事件**。事件链是同步的，任何一个环节抛异常都会中断后续流程。

#### 5.2 回合流转的事件链

```
processTurnInternal()
  │
  ├─→ eventBus.emit(TURN_START, { actorId })
  │     └─→ battleStore.handleTurnStartEvent()
  │           └─→ currentActorId.value = data.actorId
  │           └─→ battleLogManager.addTurnStartLog()
  │
  ├─→ [对每个参与者循环]
  │     ├─→ eventBus.emit(CURRENT_ACTOR_CHANGED, { actorId })
  │     │     └─→ battleStore.handleCurrentActorChanged()
  │     │
  │     ├─→ executor.executeParticipantAction()
  │     │     └─→ [见 5.1 攻击事件链]
  │     │
  │     └─→ buffSystem.updatePerTurn()
  │           └─→ [可能触发 removeBuff → 属性变更事件]
  │
  ├─→ eventBus.emit(TURN_END)
  │     └─→ battleStore.handleTurnEndEvent()
  │           └─→ battleLogManager.addTurnEndLog()
  │
  ├─→ TriggerEventBus.emit(TURN_END, ctx)
  │     └─→ [Buff 触发器：如 heal_percent_max_hp]
  │
  └─→ eventBus.emit(TEAM_DATA_CHANGED, { allyTeam: [], enemyTeam: [] })
        └─→ battleStore.syncTeams()  [全量同步]
```

**问题**：`TURN_START` 和 `CURRENT_ACTOR_CHANGED` 语义重叠。`TURN_START` 的 `actorId` 是第一个行动者，但 `CURRENT_ACTOR_CHANGED` 在每个角色行动前都会发射。`battleStore` 中两个处理器都更新 `currentActorId`，`TURN_START` 的更新会被第一次 `CURRENT_ACTOR_CHANGED` 立即覆盖。

### 一、架构层面：三套执行管道的分裂

技能系统存在 **三条独立的执行路径**，各自跳过不同的检查：

```
路径 A：主动技能（BattleExecutor → SkillManager → SkillExecutor）
  ✅ 能量检查  ✅ 目标眩晕检查  ✅ 冷却设置  ✅ SKILL_USE 事件  ✅ CombatRecord

路径 B：被动技能（PassiveSkillManager → SkillExecutor）
  ❌ 能量检查  ❌ 目标眩晕检查  ❌ 冷却设置  ❌ SKILL_USE 事件  ❌ CombatRecord

路径 C：触发器脚本（BuffSystem.triggerScripts → BuffSystem.requestDamage）
  ❌ 能量检查  ❌ 目标眩晕检查  ❌ 冷却设置  ❌ SKILL_USE 事件  ❌ CombatRecord
```

#### 1.1 路径 B 绕过 SkillManager 的完整检查链

`PassiveSkillManager.executePassiveSkill` 直接调用 `SkillExecutor.executeStep`：

```typescript
// PassiveSkillManager.ts — executePassiveSkill
private executePassiveSkill(
  config: SkillConfig,
  source: BattleEntity,
  targets: BattleEntity[],
  turn: number,
): boolean {
  const executor = this.skillManager.getExecutor()
  // ...
  for (const step of steps) {
    try {
      executor.executeStep(step, action, source, target)  // ← 直接调用
      anyExecuted = true
    } catch (err) { /* ... */ }
  }
  return anyExecuted
}
```

对比路径 A 中 `SkillManager.executeSkill` 的检查链：

```typescript
// SkillManager.ts — executeSkill
// 1. 能量检查
if (source.spendEnergy && config.energyCost) {
  source.spendEnergy(config.energyCost)
}
// 2. 目标控制检查
const targetControl = this.buffSystem.getHighestPriorityControlEffect(target.id)
if (targetControl === ControlType.STUN) { /* 取消 */ }
// 3. 冷却设置
if (config.cooldown && config.cooldown > 0) {
  source.setSkillCooldown(skillId, config.cooldown)
}
// 4. SKILL_USE 事件
this.buffSystem.getEventBus().emit(BattleTriggerPhase.SKILL_USE, { ... })
```

**后果**：
- 被动技能的伤害/治疗 **不会写入 CombatRecord**（`executePassiveSkill` 不传 `record` 参数）
- 被动技能 **不触发 SKILL_USE 事件**，其他依赖此事件的被动无法连锁
- 被动技能的 `apply_buff` 步骤 **不设置冷却**

#### 1.2 SkillManager 与 SkillExecutor 的职责边界模糊

| 职责 | SkillManager | SkillExecutor | 问题 |
|------|-------------|---------------|------|
| 能量检查/消耗 | ✅ | ❌ | 正确分层 |
| 目标控制检查 | ✅（仅 STUN） | ❌ | 不完整 |
| 步骤遍历 | ✅ | ❌ | 正确分层 |
| 具体步骤执行 | ❌ | ✅ | 正确分层 |
| 伤害/治疗计算 | ❌ | ✅（委托 Calculator） | 正确分层 |
| Buff 施加 | ❌ | ✅（委托 BuffSystem） | 正确分层 |
| 连击状态管理 | ❌ | ✅（`comboStates`） | 应在更高层 |
| 额外行动管理 | ❌ | ✅（`pendingExtraActions`） | 应在更高层 |

`SkillExecutor` 同时承担了 **步骤执行** 和 **运行时状态管理**（连击、额外行动），违反了单一职责。

### 二、SkillManager：核心入口的 6 个具体问题

#### 2.1 目标控制检查仅覆盖 STUN

```typescript
// SkillManager.ts — executeSkill
const targetControl = this.buffSystem.getHighestPriorityControlEffect(target.id)
if (targetControl === ControlType.STUN) {
  // 取消技能
}
```

`ControlType` 枚举定义了 6 种控制类型：

```typescript
export enum ControlType {
  NONE = 'none',
  STUN = 'stun',
  SILENCE = 'silence',
  FREEZE = 'freeze',
  SLEEP = 'sleep',
  BIND = 'bind',
}
```

但 `executeSkill` **只检查 STUN**。如果目标被 FREEZE/SLEEP/BIND，技能仍然可以对其释放。

更严重的是：**施法者自身的控制状态完全不检查**。`executeSkill` 是公共 API，如果被直接调用（绕过 `BattleExecutor.isParticipantControlled`），被沉默/眩晕的施法者仍可释放技能。

#### 2.2 能量消耗的鸭子类型检查

```typescript
// SkillManager.ts — executeSkill
if (source.spendEnergy && config.energyCost) {
  source.spendEnergy(config.energyCost)
}
```

- `source.spendEnergy` 是鸭子类型检查——如果 `BattleEntity` 接口没有 `spendEnergy` 方法，TypeScript 不会报错
- `config.energyCost` 为 `0` 时条件为 `false`——正确（0 能量技能不消耗）
- 但 `config.energyCost` 为 `undefined` 时也为 `false`——**配置缺失被静默忽略**

#### 2.3 `loadSkillConfigs` 无验证、无去重

```typescript
// SkillManager.ts
loadSkillConfigs(configs: SkillConfig[]): void {
  for (const config of configs) {
    this.skillConfigs.set(config.id, config)  // ← 重复 ID 静默覆盖
  }
}
```

- 无 schema 验证（`validateSkillConfigs` 存在但未被调用）
- 重复 ID 静默覆盖（`skills.json` 中存在大量重复 ID，见第四节）
- 无日志记录覆盖了哪些技能

#### 2.4 `getSkillConfig` 返回可变引用

```typescript
getSkillConfig(skillId: string): SkillConfig | undefined {
  return this.skillConfigs.get(skillId)  // ← 返回原始引用
}
```

外部代码可以修改返回的对象，影响所有后续使用者。应返回深拷贝或 `Readonly<SkillConfig>`。

#### 2.5 `executeSkill` 不传 `record` 给 `executeStep`

```typescript
// SkillManager.ts — executeSkill
for (const step of steps) {
  const ctx: CalculationContext = {
    skillStep: step,
    action,
    source,
    targets: [target],
    record,       // ← record 传入了 CalculationContext
    token,
  }
  this.executeStep(ctx)  // ← 但 executeStep 内部是否使用了 record？
}
```

`executeStep` 内部：

```typescript
private executeStep(ctx: CalculationContext): void {
  this.executor.executeStep(
    ctx.skillStep,
    ctx.action,
    ctx.source,
    ctx.targets[0],
    ctx.record,    // ← 传给了 executor
    ctx.token,

}
```

`SkillExecutor.executeStep` 确实接收 `record` 参数，但 **只有 `executeDamage` 和 `executeDrain` 使用了它**。`executeHeal`、`executeBuff`、`executeModifyAttribute` 等都不写入 `record`。

#### 2.6 `executeSkill` 中 `targets` 数组只取第一个

```typescript
const ctx: CalculationContext = {
  // ...
  targets: [target],  // ← 只有一个目标
}
```

`SkillManager.executeSkill` 的签名只接受单个 `target`，不支持多目标技能。多目标技能（如 AOE）需要在 `BattleExecutor` 层面循环调用，每次只处理一个目标。

### 三、SkillExecutor：步骤执行的 8 个具体问题

#### 3.1 `executeBuff` 中 `isDebuff` 硬编码为 `false`

```typescript
// SkillExecutor.ts — executeBuff
const buffConfig: Partial<BuffConfig> = {
  id: buffId,
  description: '',
  duration: skillStep.duration ?? -1,
  maxStacks: skillStep.stacks,
  cooldown: 0,
  stackRule: StackRule.LIMITED,
  controlType: ControlType.NONE,
  controlPriority: 0,
  isDebuff: false,  // ← 硬编码！
  parameters: skillStep.parameters || skillStep.effectParams || {},
}
```

所有通过技能施加的 Buff 都标记为 `isDebuff: false`。但 `skills.json` 中大量技能施加的是 debuff（如 `buff_poison`、`buff_stun`、`buff_def_reduction`）。

**后果**：
- `BuffSystem.getBuffInstances` 无法正确区分 buff/debuff
- 驱散逻辑（`removeDispellableBuffs`）可能误删增益或保留减益
- UI 层无法正确着色（增益青色/减益红色）

#### 3.2 `executeModifyAttribute` 绕过 ModifierStack

```typescript
// SkillExecutor.ts — executeModifyAttribute
const attrData = modTarget.getAttrValue(attrCode)
if (!attrData) continue
// 直接操作 attrData.modifiers
attrData.modifiers = attrData.modifiers.filter(m => m.sourceKey !== sourceKey)
attrData.modifiers.push(newMod)
attrData.cachedVersion = -1
```

对比 `BuffSystem.addBuff` 中的修饰符管理：

```typescript
// BuffSystem.ts — addBuff
const modifierStack = this.getModifierStack(characterId)
modifierStack.addModifier(instanceId, normalizedAttr, parsed.value, parsed.type)
```

**两条路径管理同一个 `attrData.modifiers` 数组**，但：
- `BuffSystem` 通过 `ModifierStack` 管理，有 `removeModifier(instanceId)` 清理
- `SkillExecutor` 直接操作数组，用 `sourceKey` 去重
- 如果同一个属性同时被 Buff 和被动技能修改，`removeModifier` 只清理 Buff 的修饰符，被动技能的修饰符残留

#### 3.3 `executeModifyAttribute` 的加成属性同步与 `GameDataProcessor` 重复

```typescript

// ponytail: 与 GameDataProcessor.pushModifier 保持一致的加成属性同步

  }
  // ...
}
```

`GameDataProcessor.pushModifier` 中有完全相同的逻辑。两处代码独立维护，修改一处不会同步另一处。

#### 3.4 `executeCustom` 的分发基于字符串匹配

```typescript
// SkillExecutor.ts — executeCustom
if (customType === 'third_strike' || desc.includes('第三')) {
  this.handleThirdStrike(action, source)
} else if (customType === 'combo_master' || desc.includes('连续攻击')) {
  this.handleComboMaster(action, source, target)
} else if (customType === 'burn_detonate' || customType === 'burn_detonate_full') {
  this.handleBurnDetonate(action, source, target, customType === 'burn_detonate_full', token)
} else if (customType === 'extra_action') {
  // ...
} else if (customType === 'steal_item') {
  // ponytail: PvE 掉落系统，非战斗逻辑
} else if (customType === 'overflow_shield') {
  // ...
} else {
  battleLogManager.addDebugLog(`自定义步骤未实现: ${desc}`, { level: LogLevel.WARN })
}
```

- `desc.includes('第三')` 和 `desc.includes('连续攻击')` 是 **中文文本匹配**——如果配置中的描述文字改变，分发会失败
- `steal_item` 只有日志，没有实现
- 未匹配的 `customType` 只打日志，不抛异常

#### 3.5 `handleBurnDetonate` 硬编码伤害比例

```typescript
// SkillExecutor.ts — handleBurnDetonate
const dmgPerTick = target.getAttribute('maxHealth') * 0.05  // ← 硬编码 5%
```

灼烧伤害应从 Buff 配置中读取（`buff_burn` 的 `baseDamageFormula` 字段），而非硬编码。

#### 3.6 `comboStates` 和 `pendingExtraActions` 无上限保护

```typescript
// SkillExecutor.ts
private comboStates = new Map<string, ComboState>()
private pendingExtraActions: string[] = []
```

- `comboStates` 只在 `cleanupComboState` 和 `clearAllComboStates` 中清理
- 如果战斗异常中断（未调用 `clearAllComboStates`），Map 会持续增长
- `pendingExtraActions` 没有上限——如果 `extra_action` 步骤被无限触发，数组会无限增长

#### 3.7 `executeShield` 委托给 `buff_shield` 但参数不匹配

但 `ShieldBuff` 脚本读取的是：

`shieldValue` 参数 **从未被 ShieldBuff 读取**。护盾值始终是 `baseShield * shieldScale + maxHP * 0.1`。

#### 3.8 13 个步骤类型中只有 12 个有 case 分支

|---------|---------|-------------|

### 五、DamageCalculator：伤害计算的 5 个具体问题

#### 5.1 暴击判定不受 `config.enableCrit` 控制

```typescript
// DamageCalculator.ts — calculateDamage
// 暴击判定
let cr = source.getAttribute(ATTRIBUTE_CODE.critRate)
if (Number.isNaN(cr)) {
  cr = getAttributeDefaultValue(ATTRIBUTE_CODE.critRate)
}
if (Math.random() * 100 < cr) {
  damageResult.isCritical = true
}
```

`config` 中有 `enableCrit: false`，但 **从未被检查**。暴击判定总是执行。

#### 5.2 防御公式是线性减法，注释说"递减公式"

```typescript
// DamageCalculator.ts — calculateDamage
// 防御计算（减法公式：不破防为 0）
breakdown.defenseValue = getAttributeValue(target, ATTRIBUTE_CODE.defense)
breakdown.effectiveDefense = breakdown.defenseValue
breakdown.defenseMultiplier = Math.max(
  0,
  1 - breakdown.defenseValue / Math.max(1, damage),
)
const beforeDef = damage
damage = Math.max(0, damage - breakdown.defenseValue)  // ← 纯减法
```

- `defenseMultiplier` 被计算但 **从未用于最终伤害**
- 最终伤害是 `damage - defense`——线性减法
- 当 `defense >= damage` 时，伤害为 0——"不破防"
- 注释说"递减公式"，但实际是线性减法

#### 5.3 `calculateBaseDamage` 使用不可重放的 `Math.random`

```typescript
// DamageCalculator.ts — calculateBaseDamage
if (skillStep.calculation) {
  baseDamage = skillStep.calculation.baseValue
} else {
  const minAtk = this.getAttributeSafe(source, ATTRIBUTE_CODE.minAttack)
  const maxAtk = this.getAttributeSafe(source, ATTRIBUTE_CODE.maxAttack)
  const levelBonus = (source.level || 1) * 2
  if (skillStep.attackType === AttackType.NORMAL && minAtk > 0 && maxAtk > 0) {
    baseDamage = Math.floor(Math.random() * (maxAtk - minAtk + 1)) + minAtk  // ← 不可重放
  } else {
    const atk = source.getRandomAttackDamage()  // ← 内部也用 Math.random
    baseDamage = Math.floor(atk + levelBonus)
  }
}
```

战斗回放系统（`ReplayEngine`）使用 `SeededRandom` 确保确定性，但 `DamageCalculator` 使用全局 `Math.random`——**回放时伤害值不可重现**。

#### 5.4 伤害大类（DamageCategory）的防御跳过逻辑

```typescript
// DamageCalculator.ts — calculateDamage
if (damageCategory === DamageCategory.TRUE) {
  // 真实伤害：跳过防御计算和攻击类型减免，还原到暴击后伤害
  damage = breakdown.postCritDamage
} else if (damageCategory === DamageCategory.ELEMENTAL) {
  // 元素伤害：根据技能的元素类型查找对应抗性
  // ...
}
// 'physical' 沿用现有防御逻辑
```

- `TRUE` 伤害跳过 **所有** 防御和减免——包括 `damageReduction`（通用减免）
- `ELEMENTAL` 伤害使用元素抗性，但 **仍然受 `damageReduction` 影响**
- `PHYSICAL` 伤害使用防御减法 + 攻击类型减免

问题：`TRUE` 伤害是否应该跳过 `damageReduction`？设计文档未明确。

#### 5.5 `targetModifiers` 的处理在阈值限制之前

```typescript
// DamageCalculator.ts — calculateDamage
// targetModifiers 处理
if (skillStep.targetModifiers) {
  Object.entries(skillStep.targetModifiers).forEach(([attr, modifier]) => {
    // ...
    damage *= 1 + modifierEffect
    damage = Math.floor(damage)
  })
}
// 伤害阈值限制
const minDmg = this.config.minDamageThreshold ?? 1
const maxDmg = this.config.maxDamageThreshold ?? 9999
damage = Math.max(minDmg, Math.min(maxDmg, damage))
```

`targetModifiers` 在阈值限制之前应用——如果 `targetModifiers` 将伤害降到 0 以下，阈值限制会将其拉回 `minDmg`。这是正确的。

但 `targetModifiers` 中的 `modifier` 值没有范围检查——如果配置中 `modifier: -2`，伤害会变成负数（然后被阈值拉回）。

### 六、HealCalculator：治疗计算的 3 个具体问题

#### 6.1 `calculateDebuffEffect` 的减益效果计算

```typescript
// HealCalculator.ts — calculateDebuffEffect
private static readonly HEAL_REDUCTION_PER_DEBUFF = 0.2
private static readonly MAX_HEAL_REDUCTION = 0.8

private calculateDebuffEffect(target: BattleEntity, buffSystem?: BuffSystem): number {
  if (!buffSystem) return 0
  const reductionInstances = buffSystem.getBuffInstancesWithTag(target.id, EffectTag.HEAL_REDUCTION)
  const debuffEffect = reductionInstances.length * HealCalculator.HEAL_REDUCTION_PER_DEBUFF
  return Math.min(debuffEffect, HealCalculator.MAX_HEAL_REDUCTION)
}
```

- 每个带 `heal_reduction` 标签的 Buff 减少 20% 治疗效果
- 最多减少 80%
- 但 `buffSystem` 参数是 **可选的**——如果调用方不传，减益效果完全不生效

`SkillExecutor.executeHeal` 中：

```typescript
const { heal, overflow } = this.healCalculator.calculateHeal(
  skillStep, source, healTarget, record,
  this.buffSystem,  // ← 传入了 buffSystem
)
```

这里传入了 `buffSystem`——正确。但如果其他地方直接调用 `HealCalculator.calculateHeal` 而不传 `buffSystem`，减益效果会被忽略。

#### 6.2 治疗溢出记录到 `action.extra`

```typescript
// SkillExecutor.ts — executeHeal
if (overflow > 0) {
  action.extra = action.extra || {}
  const overflowMap = (action.extra.healOverflow as Record<string, number> | undefined) || {}
  overflowMap[healTarget.id] = (overflowMap[healTarget.id] || 0) + overflow
  action.extra.healOverflow = overflowMap
}
```

`action.extra` 的类型是 `Record<string, unknown>`——`healOverflow` 是动态添加的字段，没有类型安全。

#### 6.3 `isSingleTurnEffect` 的判断逻辑

```typescript
// HealCalculator.ts
isSingleTurnEffect(skillStep: ExtendedSkillStep): boolean {
  return skillStep.calculation?.isSingleTurn === true
    || !skillStep.duration
    || skillStep.duration <= 1
}
```

如果 `duration` 为 `0` 或 `undefined`，认为是单回合效果。但 `duration: 0` 可能意味着"立即生效，无持续"——与"单回合持续"语义不同。

### 七、PassiveSkillManager：被动技能的 5 个具体问题

#### 7.1 `evaluateCondition` 的硬编码条件字符串

```typescript
// PassiveSkillManager.ts — evaluateCondition
switch (condition) {
  case 'target_has_buff':
    return target ? target.getBuffInstanceIds().length > 0 : false
  case 'source_has_buff':
    return source.getBuffInstanceIds().length > 0
  case 'target_low_hp':
    return target
      ? target.getAttribute('currentHealth') / Math.max(1, target.getAttribute('maxHealth')) < BATTLE_CONSTANTS.HEAL_THRESHOLD
      : false
  case 'target_has_poison':
    return target ? target.hasBuff('buff_poison') || target.hasBuff('buff_strong_poison') : false
  // ... 更多硬编码
  default:
    return true  // ← 未知条件默认通过！
}
```

- 条件字符串没有类型安全——拼写错误（如 `target_has_poision`）会走 `default` 分支，**静默返回 true**
- `target_has_poison` 硬编码了 `buff_poison` 和 `buff_strong_poison`——应该使用 `EffectTag.POISON` 标签
- `target_has_stun` 硬编码了 `buff_stun`——应该使用 `ControlType.STUN`

#### 7.2 `triggerPassives` 中 `triggerCount` 和 `lastTriggeredTurn` 的更新时机

```typescript
// PassiveSkillManager.ts — triggerPassives
// ponytail: 仅在确实执行了有效步骤后才累加冷却和计数
if (hasExecuted) {
  config.lastTriggeredTurn = (context?.currentTurn as number) || 0
  config.triggerCount = (config.triggerCount || 0) + 1
}
```

- `config` 是 `passives` Map 中的对象引用——修改它会影响后续触发
- 但如果 `executePassiveSkill` 中所有步骤都失败（`hasExecuted = false`），计数不增加——正确
- 问题：`config.lastTriggeredTurn` 使用 `context?.currentTurn || 0`——如果 `currentTurn` 为 `0`，`|| 0` 也是 `0`，正确。但如果 `currentTurn` 为 `undefined`，也是 `0`——可能不正确

#### 7.3 倒排索引与 `passives` Map 的同步风险

```typescript
// PassiveSkillManager.ts — registerPassive
registerPassive(characterId: string, config: PassiveSkillConfig): void {
  const list = this.passives.get(characterId) || []
  list.push(config)
  this.passives.set(characterId, list)
  // 同步更新倒排索引
  if (config.trigger) {
    const entries = this.indexByPhase.get(config.trigger) || []
    entries.push({ characterId, config })
    this.indexByPhase.set(config.trigger, entries)
  }
}
```

- 如果 `config.trigger` 为 `undefined`，不更新索引——但 `triggerPassives` 中 `if (config.trigger !== trigger) continue` 会跳过
- `removePassive` 和 `clearPassives` 也需要同步更新索引——代码中有处理
- 但 **没有防御性检查**：如果直接操作 `passives` Map（绕过 `registerPassive`），索引会不一致

#### 7.4 `triggerPassiveSkillsForAll` 的回退逻辑

```typescript
// PassiveSkillManager.ts — triggerPassiveSkillsForAll
const entries = this.indexByPhase.get(trigger)
if (entries && entries.length > 0) {
  for (const { characterId } of entries) {
    const entity = participants.get(characterId)
    if (!entity?.isAlive()) continue
    this.triggerPassives(trigger, entity, { ... })
  }
} else {
  // ponytail: 索引为空时回退全量扫描
  for (const participant of participants.values()) {
    this.triggerPassives(trigger, participant, { ... })
  }
}
```

回退全量扫描是为了兼容"未通过 `registerPassive` 注册的被动"。但这意味着 **索引为空时性能退化为 O(n×m)**。

#### 7.5 `executePassiveSkill` 不传 `token` 给 `executeStep`

```typescript
// PassiveSkillManager.ts — executePassiveSkill
executor.executeStep(step, action, source, target)
// ← 没有传 record 和 token
```

被动技能的伤害/治疗：
- 不写入 `CombatRecord`（无 `record`）
- 不使用延迟伤害令牌（无 `token`）——直接扣血/加血
- 不触发 `DAMAGE_ANIMATION` 事件（因为不经过 `BattleExecutor`）

### 八、target-resolver：目标解析的 3 个具体问题

#### 8.1 `FIRST` 策略的智能默认可能选错目标

```typescript
// target-resolver.ts — resolveSkillTargets
case TargetStrategy.FIRST:
default: {
  // 智能默认：如果技能含治疗/增益步骤，选最低血量；否则选第一个
  if (steps?.some((s) => s.type === SkillStepType.HEAL || s.type === SkillStepType.APPLY_BUFF)) {
    const target = candidates.reduce((min, p) =>
      p.getAttribute(ATTRIBUTE_CODE.currentHealth) /
      Math.max(p.getAttribute(ATTRIBUTE_CODE.maxHealth), 1) <
      min.getAttribute(ATTRIBUTE_CODE.currentHealth) /
      Math.max(min.getAttribute(ATTRIBUTE_CODE.maxHealth), 1)
        ? p : min,
    )
    return [target]
  }
  return take(candidates, selector.count === TargetStrategy.ALL ? candidates.length : (selector.count ?? 1))
}
```

- `APPLY_BUFF` 步骤不一定是增益——可能是 debuff（如 `buff_poison`）
- 如果技能同时有 `DEAL_DAMAGE` 和 `APPLY_BUFF`（debuff），智能默认会选最低血量的目标——**错误**
- 应该检查 `APPLY_BUFF` 的 `buffId` 是否为 debuff

#### 8.2 `ADJACENT` 策略依赖 `seatIndex`

```typescript
case TargetStrategy.ADJACENT: {
  const sourceSeat = source.seatIndex
  return candidates.filter(
    (p) => Math.abs(p.seatIndex - sourceSeat) === 1 && p.isAlive(),
  )
}
```

- `seatIndex` 由 `GameDataProcessor.enemyToParticipant` 设置为 `0`——**所有参与者的 seatIndex 都是 0**
- 这意味着 `ADJACENT` 策略 **永远返回空数组**（`Math.abs(0 - 0) === 0`，不等于 1）
- `RANDOM_ADJACENT` 同理

#### 8.3 `validateTargetAgainstSelector` 的 `FRONT`/`BACK` 验证

```typescript
case TargetStrategy.FRONT:
  return candidates.length > 0 && target.id === candidates[0].id
case TargetStrategy.BACK:
  return candidates.length > 0 && target.id === candidates[candidates.length - 1].id
```

`candidates` 的排序依赖于 `Array.from(participants.values()).filter(...)`——Map 的迭代顺序是插入顺序，不是 `seatIndex` 顺序。如果参与者插入顺序与 `seatIndex` 不一致，`FRONT`/`BACK` 验证会出错。

### 九、DeferredDamageToken：延迟伤害的 2 个具体问题

#### 9.1 `applyAll` 后 `entries` 被清空

```typescript
// DeferredDamageToken.ts — applyAll
applyAll(): void {
  if (this.applied) return
  this.applied = true
  // ...
  this.entries = []  // ← 清空
}
```

`applyAll` 后 `entries` 被清空，但 `totalDamageSnapshot` 和 `totalHealSnapshot` 保留了快照。`getTotalDamage` 和 `getTotalHeal` 在 `applyAll` 后返回快照值——正确。

但如果 `applyAll` 被调用两次（`applied` 标志防止），第二次不会重复扣血——正确。

#### 9.2 `record` 不检查 `target.isAlive()`

```typescript
// DeferredDamageToken.ts — record
record(target: BattleEntity, damage: number, heal: number = 0): void {
  this.entries.push({ target, damage, heal })
}
```

`record` 不检查目标是否存活。`applyAll` 中：

```typescript
for (const entry of this.entries) {
  if (!entry.target.isAlive()) continue  // ← 跳过死亡目标
  // ...
}
```

`applyAll` 跳过死亡目标——正确。但如果目标在 `record` 和 `applyAll` 之间死亡（如被另一个伤害杀死），伤害会被跳过——**可能导致伤害统计不准确**。
