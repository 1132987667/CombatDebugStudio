## 一、背景

封神榜已完成基础数值体系配置（玩家成长/系统预算/装备公式/属性定义/来源审计），但策划在实际工作中仍面临以下痛点：

1. **改参无预览**：调了数值不知道全局影响，容易改崩
2. **装备手填累**：每件装备都要手动配属性，效率低
3. **校验靠肉眼**：平衡性问题只能等实际测试才发现
4. **配置易出错**：没有约束，容易配出超标数据
5. **验证靠实测**：数值改完只能人工进战斗试打，缺「配置 → 自动推演 → 报告」的闭环（→ 由 3.11 战斗模拟验证台解决）

本规划旨在补齐这些能力，让封神榜成为策划的**数值控制中心**。

## 二、数值体系全链路分析

### 2.1 当前链路状态

```
① 度量衡      属性定义（SAP 价值倍数 / L1-L4 / 归属系统）
     ↓
② 玩家成长    玩家配置（初始 → 成长 → 自由点 → 转化 → 预览）
     ↓
③ 系统投放    等级 / 装备 / 流派 / 宠物 / 坐骑 / 天赋 / 法宝 / 神器
     ↓
④ 来源审计    属性 × 系统矩阵（只读）
     ↓
⑤ 公式结算    属性与公式（只读参考）
```

### 2.2 已有 vs 缺失

| 环节 | 已有 | 缺失 |
|------|------|------|
| ① 度量衡 | attributes 表（SAP/层级/归属） | 属性上限/下限约束、属性间依赖关系 |
| ② 玩家成长 | PlayerConfigView（六维配置+经验公式） | 转职/觉醒等特殊成长路径 |
| ③ 系统投放 | SystemBudget 权重（只读，等级 120 / 装备 240 / 其余 60） | **各系统实际属性值配置**、**装备词条数值范围**、**丹药/洗练/强化效果** |
| ④ 来源审计 | AuditView 矩阵 + data-insight.ts（敌人等级均值/词条频次/掉落归属，只读） | **一键校验**（实际投放 vs 预算偏差） |
| ⑤ 公式结算 | FormulasView（只读） | 实时预览（调参后立即看到战斗效果） |
| ⑥ 完整性校验 | HealthView + DataIntegrityService（引用断裂/命名重复/词条强约束，REFERENCE_RULES 注册表） | 数值级校验（区间/曲线/预算偏差）——已有面板可挂靠，见 5.5 |
| ⑦ 战斗验证 | 沙盒战斗引擎 BattleSystem + 单测级模拟先例（tests/unit/lianji-battle-sim.test.ts：装配 → 快进 N 回合 → 断言） | **面向策划的模拟推演视图**（TTK / 胜率 / 压制矩阵，见 3.11） |

> 关键判断：⑥⑦ 两行的已有基建是本规划的杠杆——数值级校验不需要新建面板（挂靠 HealthView），战斗验证不需要新引擎（复用 BattleSystem）。新增代码集中在**纯函数层**，视图层只做薄壳。

### 2.3 建设性方案（4 个扩展维度）

#### 方案 A：系统投放明细配置

**目标**：为每个养成系统配置「该系统能投放哪些属性、投放范围、投放规则」

```ts
interface SystemDistributionConfig {
  id: 'system_distribution'
  systems: Array<{
    system: string              // level / equipment / school / pet / mount / talent / artifact / relic（对齐 types.ts SystemBudgetEntry 8 系统）
    label: string
    distributions: Array<{
      attribute: string         // 属性代码（引用 attributes 表）
      mode: 'fixed' | 'range' | 'formula'  // 投放模式
      value?: number            // fixed 模式：固定值
      range?: { min: number; max: number }  // range 模式：随机区间
      formula?: string          // formula 模式：公式（如 'level * 2 + 10'）
      weight?: number           // 抽池权重（用于随机生成）
    }>
  }>
}
```

**视图**：`SystemDistributionView.vue`
- 顶部：选择系统（下拉）→ 该系统预算权重 + 已投放属性汇总
- 主体：属性投放配置表（属性/模式/值/范围/公式）
- 底部：一键校验（实际配置 vs 预算偏差）

#### 方案 B：装备词条数值范围控制

**目标**：统一控制词条数值的生成规则，而不是每个词条单独配 valueRange

```ts
interface AffixDistributionConfig {
  id: 'affix_distribution'
  /** 按稀有度定义词条数值范围倍率 */
  rarityMultiplier: Record<number, { min: number; max: number }>  // 1~5 稀有度 → 范围倍率
  /** 按品阶定义词条数值范围倍率 */
  tierMultiplier: Record<string, { min: number; max: number }>    // t1~t5 品阶 → 范围倍率
  /** 全局词条数值上下限 */
  globalClamp: { min: number; max: number }
  /** 词条数量规则（按装备稀有度/品阶决定可携带词条数） */
  affixCountRules: Array<{
    condition: { rarity?: number; tier?: string }
    count: { min: number; max: number }
  }>
}
```

**视图**：嵌入 `EquipmentView` 或独立视图
- 稀有度倍率表
- 品阶倍率表
- 词条数量规则
- 一键校验：扫描所有 equipment_affixes，检查 valueRange 是否在全局约束内

#### 方案 C：丹药/消耗品效果配置

**目标**：将丹药效果从硬编码转为可配置

```ts
interface PillEffectConfig {
  id: 'pill_effect'
  /** 丹药列表（每个丹药 = 一次属性点投放） */
  pills: Array<{
    id: string
    name: string
    /** 提供的属性点 */
    bonusPoints: number
    /** 使用等级门槛 */
    requiredLevel: number
    /** 获取来源（掉落/商店/任务） */
    source: string
    /** 稀有度 */
    rarity: number
  }>
  /** 丹药总上限（所有丹药提供的属性点总和不能超过此值） */
  totalCap: number
}
```

**视图**：`PillEffectView.vue` 或嵌入 PlayerConfigView
- 丹药列表（可增删改）
- 已使用属性点 / 剩余可用属性点
- 一键校验：丹药总属性点是否超过 pillBonusPoints

#### 方案 D：平衡性校验引擎

**目标**：一键校验整个数值体系的平衡性，输出报告

```ts
interface BalanceReport {
  /** 各系统实际投放 vs 预算偏差 */
  systemDeviations: Array<{
    system: string
    budgetWeight: number      // 预算权重（660 口径）
    actualSap: number         // 实际投放 SAP
    deviation: number         // 偏差百分比
    status: 'ok' | 'warn' | 'error'

  /** 属性覆盖检查：哪些属性没有主来源 */
  uncoveredAttributes: string[]
  /** 数值范围检查：装备词条是否超出全局约束 */
  outOfRangeAffixes: string[]
  /** 丹药检查：总属性点是否超过上限 */
  pillOverCap: boolean
  /** 总体平衡评分（0-100） */
  balanceScore: number
}
```

**视图**：`BalanceCheckView.vue`（独立视图或嵌入 AuditView）
- 雷达图：各系统投放占比
- 偏差条：实际 vs 预算
- 问题列表：点击跳转到对应配置修复

### 3.2 装备批量生成器（P0）

**场景**：策划需要批量生成装备来测试数值

**功能**：
- 按公式生成核心属性值（含浮动区间）
- 按词条池随机生成附加属性
- 输出完整装备 JSON（可直接导入 equipment 表）
- 批量生成 N 件同等级装备，统计数值分布

**输入**：装备等级 + 品阶 + 部位 + 数量

**输出**：
- 装备列表（JSON 格式）
- 数值分布统计（平均值/最大值/最小值）
- 一键导入封神榜

**价值**：策划不用手填装备数据，公式驱动自动生成

**数据结构**：
```ts
/** 生成请求（视图输入） */
interface EquipGenerateRequest {
  slot: string                  // weapon / armor / helmet / boots / charm / glove
  tier: string                  // t1~t5
  level: number                 // 装备等级（喂给 EquipFormulaConfig 公式）
  rarity: number                // 目标稀有度 1-5
  count: number                 // 生成数量（1~500）
  affixPool?: string[]          // 限定词条池（空 = 全部合法词条）
  seed?: number                 // 可复现随机种子（不填 = 时间戳，见 5.6）
}

/** 单件生成结果（对齐 types.ts EquipmentData，可直接导入 equipment 表） */
interface GeneratedEquipment extends Omit<EquipmentData, 'id'> {
  id: string                    // gen_ 前缀临时 id，导入时由存储层重排
}

/** 批量统计（数值分布，供策划判断浮动区间是否合理） */
interface EquipGenerateReport {
  items: GeneratedEquipment[]
  seed: number                  // 实际使用的种子（回填到 UI，可复现）
  stats: Record<string, {       // key = 属性代码
    min: number; max: number; mean: number; p50: number; p95: number
  }>
  sapPerItem: number[]          // 每件装备的 SAP 总量（对比 EquipTierWeight 区间）
}
```

生成口径约束：核心属性走已有 `EquipFormulaConfig` 公式；词条抽取受 3.2 方案 B 的稀有度/品阶倍率与 globalClamp 约束——**生成器是约束的消费端，不做第二套数值规则**。

### 3.3 属性上限约束器（P0）

**场景**：策划需要约束属性不要无限膨胀

**功能**：
- 每个属性的合理范围（min/max）配置
- 玩家满级属性是否超标检查
- 装备词条数值是否超标检查
- buff 叠加后是否超标检查
- 保存时自动拦截超标数据

**输入**：属性上下限配置

**输出**：
- 校验结果（超标列表）
- 保存拦截提示

**价值**：防止后期数值爆炸，保持游戏平衡

**数据结构**：
```ts
interface AttributeLimitConfig {
  id: 'attribute_limit'
  limits: Record<string, {
    min: number
    max: number
    /** 上限口径：base=终值钳制 / percent=百分比属性钳制（如暴击率 ≤ 75%） */
    kind: 'base' | 'percent'
    /** 违规处置：block=保存拦截 / clamp=自动钳制 / warn=仅提示 */
    onViolation: 'block' | 'clamp' | 'warn'
  }>
  /** 检查的快照口径：满级玩家 + 满强化 + 满词条叠加（最坏情况） */
  checkScopes: Array<'playerMax' | 'equipAffix' | 'buffStacked'>
}
```

与 5.5 校验分级体系的关系：本功能提供**约束数据**，校验执行统一走 5.5 的 ValidationRegistry，输出统一 ValidationIssue；`onViolation: 'clamp'` 的 quickFix 由校验结果一键触发。

### 3.5 敌人属性校验器（P1）

**场景**：策划配了一堆敌人，需要校验是否符合等级曲线

**功能**：
- 每个敌人的属性是否在合理区间（偏高/偏低）
- 掉落经验/金钱是否符合预期曲线
- 敌人 vs 同等级玩家的胜率估算
- 异常数据高亮（如 99999 血的 1 级怪）

**输入**：敌人列表 + 玩家等级曲线

**输出**：
- 校验报告（异常列表）
- 属性分布图
- 点击跳转修复

**价值**：防止策划配出"秒杀 boss"或"打不死的 1 级怪"

**校验规则明细**（每条输出一个 ValidationIssue，见 5.5）：

| 规则 | 判定 | 级别 |
|------|------|------|
| 等级-属性曲线偏离 | 敌人属性 vs `enemyMeanStatsByLevel`（data-insight.ts 已有）同等级均值偏离 > ±40% | warn；> ±100% 为 error |
| 秒杀/永动机 | TTK（见 3.11）< 1 回合 或 > 30 回合 | error |
| 经验/金钱曲线 | 掉落经验 vs enemy_reward_table 同级基准偏离 > ±30% | warn |
| 异常字面值 | 属性值 ≥ 10000 且等级 ≤ 10（"99999 血 1 级怪"类） | error |

均值参考线直接复用 `data-insight.ts` 的 `enemyMeanStatsByLevel()`——该函数已按等级聚合敌人六维均值，本功能不重复实现。

### 3.6 数值快照对比器（P1）

**场景**：策划改了一版数值，想对比"改前 vs 改后"的差异

**功能**：
- 玩家满级属性对比（六维数值 + SAP 总量）
- 各系统投放占比对比（雷达图）
- 装备生成数值对比（10级/30级/50级各品阶）
- 差异高亮（哪些属性变化超过 10%）

**输入**：两套配置（A/B）

**输出**：
- 属性对比表（差异列高亮）
- 雷达图对比
- 差异报告

**价值**：策划调参后立即看到全局影响，避免"改了一个数崩了整个体系"

**数据结构**：
```ts
interface ValueSnapshot {
  id: string                    // snap_<timestamp>
  label: string                 // 策划命名，如「9.15 平衡版」
  createdAt: number
  /** 参与对比的结构化表集合（params 域 key + 表数据深拷贝） */
  tables: Record<string, unknown>   // { player_config, system_budget, exp_table, equip_formula, ... }
}

interface SnapshotDiffResult {
  added: Array<{ table: string; key: string }>
  removed: Array<{ table: string; key: string }>
  changed: Array<{
    table: string; key: string; field: string
    before: number; after: number
    deltaPercent: number        // |Δ| > 10% 时 UI 高亮
    sapImpact?: number          // 换算成 SAP 的影响量（六维属性才换算）
  }>
}
```

存储与回滚：快照存 IndexedDB（复用 IPersistentStorage，量级估算见 5.7）；「回滚到快照」= 用 tables 覆盖当前对应表并写操作日志（OperationLogEntry 已有）；对比粒度为 表 → 行 → 字段 三级下钻。

### 3.7 经验曲线增补（P2，2026-09-08 评审收敛）

**输出**：带节点标注与累计经验序列的升级曲线图

### 3.10 战斗力估算器（P3）

**场景**：策划需要估算玩家在不同养成阶段的战斗力

> **修订（2026-09-08）**：本功能不再自建"战斗力公式"（任何静态战力公式都无法忠实反映回合制战斗的命中/先手/爆发节奏），而是**以 3.11 战斗模拟验证台的实际推演结果为口径**——"战斗力"即模拟胜率与 TTK 的加权读数。本功能退化为 3.11 输出之上的**汇总视图**（见 3.11 的养成瓶颈分析），不单独实现。

**功能**：
- 预估战斗力数值（= 模拟胜率 × 1000 归一化，口径随 3.11）

- 推荐挑战的关卡（胜率落在 60%~90% 区间的场景，即"有挑战但不挫败"）

**输入**：玩家等级 + 养成进度（装备/流派/宠物...）

**输出**：
- 战斗力数值
- 对比报告
- 养成建议

**价值**：策划从玩家角度审视数值体验

### 3.11 战斗模拟验证台（P1，2026-09-08 新增）

**场景**：策划改完数值（玩家成长/装备公式/敌人属性/buff），需要立刻知道"这样改，玩家打同级怪是什么体验"，而不是进游戏人工试打。

**这是本规划中杠杆最大的一项**：沙盒自带完整战斗引擎（`BattleSystem`），且已有单测级完整模拟先例（`tests/unit/lianji-battle-sim.test.ts`：DI 容器初始化 → 装配双方参与者 → mock RAF → 快进 50 回合 → 断言战斗结果）。3.11 把这条测试链路产品化：**测试里怎么跑的，视图里就怎么跑**，不写新的战斗逻辑。

**功能**：
- **TTK 曲线**（Time-to-Kill）：满配玩家 vs 各等级敌人均值装，期望击杀回合数折线。健康区间可配（默认 3~8 回合），区间外标红——秒杀怪 = 数值投放过量，打不死怪 = 投放不足
- **胜率蒙特卡洛**：同一装配模拟 N 场（默认 200，固定种子），输出胜率 + 回合数分布直方图。区分"必胜/碾压/胶着/翻车"四档
- **压制矩阵**：等级（1~50）× 品阶（t1~t5）网格，每格填 TTK/胜率热力色——一眼看出哪段曲线断档
- **A/B 对拼**：两套玩家配置互打 200 场，验证"流派 A vs 流派 B 是否克制失衡"
- **养成瓶颈分析**（3.10 的数据来源）：逐个移除某系统的投放再模拟，胜率跌幅最大的系统即当前瓶颈

**输入**：玩家配置（player_config 快照）+ 敌人选择（单只/按场景/按等级段）+ 模拟场数 + 种子

**输出**：
- TTK 折线 + 健康区间标注
- 胜率读数 + 回合分布直方图
- 压制矩阵热力图
- 异常清单（TTK 越界的等级点，点击跳转对应敌人/装备行）

**价值**：把"校验靠肉眼、验证靠实测"两个痛点一次解决——数值改完 3 秒出推演报告，且与实战同引擎，不存在"模拟器说平衡实际打起来不平衡"的第二真相源问题。

**数据结构**：
```ts
interface BattleSimulateRequest {
  playerConfig: PlayerGrowthConfig      // 复用 player-config.ts 装配链
  equippedSkills?: string[]             // 技能/被动 id（对齐 equippedPlayerSkills 注入结构）
  enemySelector:
    | { kind: 'single'; enemyId: string }
    | { kind: 'byScene'; sceneId: string }
    | { kind: 'byLevel'; from: number; to: number }
  runs: number                          // 蒙特卡洛场数（默认 200，上限 2000）
  maxRounds: number                     // 单场上限回合（默认 50）
  seed?: number
}

interface BattleSimulateReport {
  seed: number
  perLevel: Array<{
    level: number
    ttk: number                         // 期望击杀回合数
    winRate: number                     // 0~1
    roundsHistogram: Record<number, number>  // 回合数 → 场次
    status: 'stomp' | 'healthy' | 'close' | 'losing'  // 碾压/健康/胶着/翻车
  }>
  bottlenecks?: Array<{ system: string; winRateDrop: number }>  // 开启瓶颈分析时
}
```

**实现约束**：
- `domain/fengshen/battle-simulator.ts` 只做**编排**（装配 → 循环跑 → 聚合统计），战斗结算全部调用现有 `BattleSystem`，禁止复制结算公式
- **随机复用引擎已有机制**：请求种子经 `battleData.rng` 注入（第 i 场用 `seed + i` 派生，场间独立），不引入第二套随机源——确定性由 `seeded-battle-determinism.test.ts` 的引擎契约保证
- 浏览器侧单场模拟必须与单测同路径（同一 DI 装配流程），跑在 Web Worker 或分帧调度（每帧跑 10 场）避免卡 UI——量级核算见 5.7
- 敌人均值装引用 `data-insight.ts` 的 `enemyMeanStatsByLevel()`

## 四、优先级排序

按**实际价值 + 使用频率 + 实现成本**排序：

| 优先级 | 功能 | 覆盖环节 | 理由 |
|--------|------|----------|------|
| **P0** | 系统投放明细配置 | ③ 系统投放设计 | 核心缺失——目前只有权重没有实际投放量 |
| **P0** | 装备批量生成器 | ④ 装备数值设计 | 每次配装备都要用，无替代方案 |
| **P0** | 属性上限约束器 | ⑧ 平衡性校验 | 保存时自动拦截，防止数值爆炸 |
| **P1** | **战斗模拟验证台（3.11）** | ⑨ 实时预览 / ⑩ 版本管理 | **沙盒独有杠杆**——战斗引擎与模拟测试链路已存在，产品化边际成本低于任何自建公式；且是 3.9 校验、3.10 估算、3.5 敌人校验的**共用底座**（TTK/胜率口径） |
| **P1** | 消耗品效果配置 | ⑤ 消耗品设计 | 丹药/洗练/强化效果硬编码，策划无法调整 |
| **P1** | 平衡性校验引擎 | ⑧ 平衡性校验 | 一键校验整体平衡性，发现问题 |
| **P1** | 敌人属性校验器 | ⑥ 敌人设计 | 配敌人后检查一次，防止配置错误；TTK 规则依赖 3.11 先行 |
| **P1** | 数值快照对比器 | ⑩ 版本管理 | 改参时对比差异，防止改崩 |
| **P2** | 经验曲线增补（3.7，收敛） | ② 玩家成长设计 | 核心已被 ExpGoldView 覆盖，仅剩节点标注 + 累计经验增补（~0.5 天） |
| **P2** | 掉落模拟器 | ⑦ 经济系统 | 调掉落率时用，频率不高 |
| **P3** | 战斗力估算器 | ⑨ 实时预览 | 退化为 3.11 输出的汇总视图，随 3.11 白得 |

```
高频 + 无替代 → P0（系统投放配置、装备生成器、属性约束器）
中频 + 有价值 → P1（模拟验证台、消耗品配置、平衡性校验、敌人校验器、快照对比器）
低频 + 可替代 → P2（经验曲线、掉落模拟器）
依赖其他 + 锦上添花 → P3（战斗力估算器，依赖 3.11）
```

排序原则补充：**能成为其他功能底座的功能优先做**——3.11 的 TTK/胜率口径被 3.5（秒杀/永动机规则）、3.9（战斗体验校验）、3.10（战力读数）三处复用，故提到 P1 首位。

### 5.5 校验分级体系（统一所有校验的出口）

现状问题：本规划中「校验」散落在 3.3（属性上限）、3.5（敌人曲线）、3.9（平衡性）、方案 B（词条范围）、3.11（TTK 越界）五处，若各自实现输出格式与展示面板，会裂成五套「问题列表」。统一方案：

```ts
/** 数值级校验统一输出（与 DataIntegrityService 的引用级 issue 并列，不复用其 kind 枚举） */
interface ValidationIssue {
  ruleId: string                // 如 'enemy_curve_deviation' / 'ttk_out_of_range'
  severity: 'error' | 'warn' | 'info'
  table: string                 // 问题所在表（封神榜表名 / params 域 key）
  rowId: string                 // 问题行（可定位跳转）
  field?: string
  message: string               // 人话描述，含实际值与阈值
  /** 一键修复（可选）：把值钳回合法区间的操作描述 */
  quickFix?: { field: string; value: number; label: string }
}

/** 规则注册表：对齐 schema.ts REFERENCE_RULES 模式——新增校验 = 注册一条规则，不改执行器 */
interface ValidationRule {
  id: string
  severity: 'error' | 'warn' | 'info'
  /** 执行器：输入全量配置快照，输出该规则的 issue 列表（纯函数） */
  run: (ctx: ValidationContext) => ValidationIssue[]
}
```

分级语义与拦截策略：

| 级别 | 语义 | 保存拦截 | 展示 |
|------|------|----------|------|
| error | 数值级错误（99999 血 1 级怪 / TTK<1 回合 / 预算偏差>50%） | **拦截保存** | 红 |
| warn | 疑似问题（曲线偏离 ±40% / 词条接近上限） | 不拦截，保存后提示 | 黄 |
| info | 参考信息（无主来源属性 / 冷门词条） | 不拦截 | 灰 |

挂靠关系：**HealthView 即统一面板**——它已有「规则数 / 检查条目 / 问题分类卡片 / 过滤 / 列表」骨架，数值级 issue 作为新的分类（integrity / duplicate 之外新增 `numeric`）并入，severity 筛选与 quickFix 按钮为增量改动。执行时机：手动「全量校验」按钮 + 保存前仅跑 error 级规则（全量执行的性能预算见 5.7）。

### 5.6 Seeded RNG 基建（2026-09-08 评审收窄：仅配置生成侧）

随机分两个域，**已有机制不同，不强行统一**：

- **战斗内随机（已有，不在本节范围）**：战斗引擎内部已实现 seed → `battleData.rng`，命中/暴击/目标/AI/触发器全部走它而非 `Math.random`，并有确定性契约测试 `tests/unit/seeded-battle-determinism.test.ts` 锁定（同 seed 同行动序列 → 状态逐位一致）。3.11 蒙特卡洛的复现性由引擎层直接保障，见 3.11 实现约束。
- **配置生成随机（本节范围）**：3.2 装备生成（词条抽取/浮动区间）、3.8 掉落模拟。这两处若各自 `Math.random()` 会导致：结果不可复现、bug 无法回放、验收断言写不了。

```ts
// shared/utils/seeded-rng.ts（新建，零依赖）
export interface Rng {
  next(): number          // [0, 1)
  int(min: number, max: number): number
  pick<T>(arr: ReadonlyArray<T>): T
  weighted<T>(items: ReadonlyArray<{ item: T; weight: number }>): T
}
export function createRng(seed: number): Rng    // mulberry32 或 xoshiro，纯函数工厂
```

约定（仅约束配置生成侧）：
- 3.2 / 3.8 的纯函数接受可选 `seed`，不填则用 `Date.now()` 生成并把**实际使用的种子回填到报告**（EquipGenerateReport.seed / DropSimulateReport.seed 均已定义）——策划拿着种子可精确复现同一次生成/模拟
- 禁止在配置生成纯函数层直接调 `Math.random()`（可 lint 或 review 约束）
- 单测用固定种子断言确定性输出

### 5.7 性能预算（按真实配置量级核算）

当前配置量级：装备 158 件、敌人 124 只、物品 ~260 条、词条库 equipment-affixes.json 单文件。均为**千条以下**量级，纯函数全量扫描不构成性能风险：

| 操作 | 量级 | 预算 | 策略 |
|------|------|------|------|
| 全量数值校验（5.5 全规则） | 158 装备 × 词条 + 124 敌人 ≈ 数千字段 | < 50ms | 直接同步执行，无需 web worker |
| 保存前 error 级校验 | 只跑 error 规则子集 | < 10ms | 同步，无感 |
| 装备批量生成 | 500 件 | < 100ms | 同步（生成后统一算统计） |
| 掉落模拟 | 10 万次 | < 200ms | 同步 |
| **战斗蒙特卡洛** | 200 场 × ≤50 回合 | < 2s（目标 <1s） | **分帧调度**（每帧 10 场，进度条），后续可挪 Web Worker；单测同链路下 200 场实测为准，超标再优化 |
| 快照存储 | 单快照 = params 域各表深拷贝（估 < 1MB） | IndexedDB 无压力 | 保留最近 20 个命名快照 + 溢出提示 |

结论：除战斗蒙特卡洛需要分帧外，其余全部同步实现——**不要预先引入 Worker/流式等复杂度**（天花板：单场模拟 >5ms 时再来优化，先实测）。

## 七、风险与注意

| 风险 | 应对 |
|------|------|
| 系统投放配置可能与现有预算冲突 | 实时计算偏差，保存时拦截超标 |
| 装备生成器可能生成非法数据 | 复用 DataIntegrityService 校验，保存前拦截 |
| 消耗品配置可能超出属性上限 | 保存时自动校验，拦截超标数据 |
| 快照对比器需要保存历史版本 | 利用已有的 dataVersion 机制，每次保存前备份 |
| 属性上限可能与现有装备/词条冲突 | 提供"自动修正"功能，将超标值钳制到上限 |
| 掉落模拟需要随机数 | 使用固定种子，保证可复现 |
| **模拟结果与实战体验偏差**（3.11） | 与实战同一 BattleSystem 结算，天然同口径；装配链与单测同构并有单测锚定，防「模拟第二真相源」。剩余偏差主要来自玩家操作/走位类变量——本作回合制，影响可控 |
| **战斗模拟阻塞 UI**（3.11） | 分帧调度 + 进度条（5.7）；实测单场 > 5ms 再上 Web Worker，不预先优化 |
| **快照体积膨胀**（3.6） | 只深拷贝 params 域结构化表（<1MB/份），保留最近 20 份 + 溢出提示；不快照全量 xiyou/装备表（它们有 configs JSON 作为版本真相） |
| **公式表达式注入**（3.1 formula 模式） | 不做表达式解析器——formula 用「函数白名单」：预置 `linear(k, b)` / `poly(n)` 等有限模板，参数存结构化数据；策略拒绝 eval 字符串 |

## 八、验收标准

标注「自动」= 对应 vitest 断言，随功能落地一起交付（对齐石匠守则：非琐碎逻辑必须留可运行检查）；「人工」= 策划在浏览器实际操作验收。

| 功能 | 验收标准 | 验证方式 |
|------|----------|----------|
| 系统投放明细配置 | 选择"装备"系统，配置 3 条属性投放规则，实时显示偏差 | 人工 + 自动（偏差计算纯函数单测） |
| 装备批量生成器 | 固定种子生成 100 件 50 级仙品武器：核心属性在公式区间内；同种子二次生成结果逐字节一致 | 自动（Rng 确定性断言） |
| 属性上限约束器 | 构造超标属性 → error 级拦截保存且提示具体字段；quickFix 一键钳回区间 | 自动（校验规则单测） |
| 校验分级基建（5.5） | error/warn/info 三级各构造一条，HealthView 分类展示、过滤、跳转正确 | 人工（展示层）+ 自动（registry 聚合逻辑） |
| **战斗模拟验证台（3.11）** | 固定种子跑 200 场：TTK/胜率输出且分帧不卡 UI（>200ms/帧即不合格）；lianji-battle-sim 同配置在视图与单测中读数一致 | 自动（同链路读数一致断言）+ 人工（流畅度） |
| 消耗品效果配置 | 配置丹药提供 12 点属性，使用等级 50，总点数不超上限 | 自动（总Cap校验） |
| 平衡性校验引擎 | 一键校验后输出报告，偏差>15%的系统标红 | 自动（偏差分级断言） |
| 敌人属性校验器 | 能发现 99999 血的 1 级怪并标 error（复用现网数据构造用例） | 自动 |
| 数值快照对比器 | 对比两套配置，差异高亮准确无遗漏；回滚后各表与快照逐字段一致 | 自动（diff 与回滚往返断言） |
| 经验曲线增补（3.7） | ExpGoldView 曲线上正确出现转职/觉醒/满级节点标注与累计经验序列，与表数据一致 | 人工（展示层）+ 自动（累计求和复用已有纯函数，节点等级读取断言） |
| 掉落模拟器 | 固定种子模拟 1 万次掉落，统计结果与理论值偏差 < 5% | 自动（大数定律收敛断言，跑测试约 <1s） |
| 战斗力估算器 | 估算读数与 3.11 模拟胜率换算值一致（同一数据源，无第二公式） | 自动 |

**回归底线**：全量测试相对当前基线**无新增失败**（已知存量失败与 flaky 不计入；不写死文件数，随开发增长以基线对比为准）。

## 九、开放问题（待评审决策）

1. **formula 模式的表达力边界**（3.1）：预置模板（`linear`/`poly`）够不够？若策划需要「分段函数」（如 30 级前线性、之后指数），是加模板还是允许受限表达式 DSL？建议 Phase 1 先只上 `linear`，有真实需求再加。
2. **TTK 健康区间**（3.11）：默认 3~8 回合是否符合「变强→碾压→再变强」的爽感定位？碾压期（前 20 级）可能刻意要 <3 回合——建议区间按等级段可配，具体数值找策划要一版。
3. **压制矩阵的敌人取样**（3.11）：用「同等级均值怪」（data-insight 均值）还是「同等级 Boss」？两者曲线差异大，还是双轨都出？
4. **快照是否纳入 params 域以外的表**（3.6）：目前只快照 params 域；装备/敌人表改动频繁的话是否纳入？（体积与价值的取舍）
5. **模拟场数默认值**（3.11）：200 场胜率置信区间约 ±7%（95% 置信），够不够分辨「胶着 vs 翻车」？若要 ±3% 需 ~1000 场，耗时翻 5 倍——建议默认 200、矩阵视图 1000，让策划按需选。
6. **Phase 1 是否拆分**：校验基建（5.5/5.6）是三个 P0 的公共前置，可再拆出 Phase 0.5（2 天）先行，降低单阶段体量。
