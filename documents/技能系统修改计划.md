# 技能系统修改计划

> 基于对抗式评审输出的分层修改计划，2026-07-16

**说明**：本计划共含 8 项修改任务，按优先级分为 P0（功能性错误）、P1（设计缺陷）、P2（架构改进），每项含背景、方案、影响文件、边界案例、验证方式。

---

## P0 — 功能性错误，必须修复

---

### P0/AI-1：统一技能选择管道

**背景**：
`BattleExecutor.executeParticipantAction()` 有两条并行的技能选择路径——
- 有 AI：`aiInstance.makeDecision()` 通过 `AIPriorityStrategy` 权重选技能，同时也选了 `targetId`
- 无 AI：`availableSkills[Math.floor(Math.random() * availableSkills.length)]` 随机选

**两个核心问题**：
1. AI 路径选出的 `targetId` 在 `selectAndExecuteSkill` 中被 `resolveSkillTargets()` **完全丢弃并重算**，AI 的战术意图（集火/保护）丢失
2. 普攻路径（`selectAndExecuteAttack`）的目标选择是**纯随机**，AI 无法指定"打谁"

**方案**：

**1. 执行函数增加 `suggestedTargetId` 可选参数**

```typescript
// BattleExecutor.ts
async selectAndExecuteSkill(
  battle, source, skill,
  suggestedTargetId?: string,  // AI 建议，执行层验证后决定是否采纳
  context?,
): Promise<BattleAction>

async selectAndExecuteAttack(
  battle, source,
  suggestedTargetId?: string,  // 同上，支持普攻目标建议
): Promise<BattleAction>
```

**2. 目标采纳策略（验证后才采纳，无效则回退）**

| 场景 | 处理逻辑 |
|------|---------|
| **技能 + 有建议目标** | 用 `target-resolver.ts` 新增的 `validateTargetAgainstSelector(target, source, selector)` 检查目标是否满足技能 selector（阵营/存活/合法性）。满足 → 直接使用；不满足 → 走 `resolveSkillTargets` 重算 + 日志警告 |
| **技能 + 无建议目标** | 走 `resolveSkillTargets`，与现有逻辑一致 |
| **普攻 + 有建议目标** | 检查目标是否存活且为敌方。满足 → 使用；不满足 → 随机回退 + 日志警告 |
| **普攻 + 无建议目标** | 走现有 `selectTarget`（随机） |

**3. AI 路径调整**

`BattleAI.makeDecision()` 返回值不变，仍含 `skillId` + `targetId?`，但语义从"最终决定"变为"建议"。

```typescript
// BattleExecutor.executeParticipantAction()
const aiResult = aiInstance.makeDecision(...)
const suggestedTargetId = aiResult.targetId

if (aiResult.skillId) {
  const skill = this.skillManager.getSkillConfig(aiResult.skillId)
  if (skill) {
    await this.selectAndExecuteSkill(battle, participant, skill, suggestedTargetId, context)
  } else {
    await this.selectAndExecuteAttack(battle, participant, suggestedTargetId)
  }
} else {
  await this.selectAndExecuteAttack(battle, participant, suggestedTargetId)
}
```

**4. 控制模式三值枚举**

在 `BattleEntity` 或 `BattleData` 中新增 `controlMode` 字段：

```typescript
type ControlMode = 'AI'      // 使用 AI 实例 + AI 目标建议（敌人默认）
                 | 'AUTO'   // 使用默认权重策略选技能 + 策略建议的目标（自动战斗）
                 | 'MANUAL' // 完全由玩家输入驱动，跳过自动选技能（玩家手操）
```

**5. `AIPriorityStrategy` 新增方法**

```typescript
// AIPriorityStrategy.ts
selectBestSkill(
  skills: Skill[],
  participant: BattleEntity,
  battleState: BattleState,
): string | null  // 只返回技能ID，不附带目标建议（目标建议由 AI 的战术层决定）
```

**影响文件**：
- `src/domain/battle/service/BattleExecutor.ts` — `selectAndExecuteSkill` / `selectAndExecuteAttack` 增加 `suggestedTargetId` 参数；`executeParticipantAction` 重构，AI/非AI/手动三条路径统一调用
- `src/domain/battle/ai/BattleAI.ts` — `makeDecision` 返回类型不变，语义从"最终决定"改为"建议"
- `src/domain/battle/ai/AIPriorityStrategy.ts` — 新增 `selectBestSkill(skills, participant, battleState): string | null`
- `src/domain/battle/type/types.ts` — 新增 `ControlMode` 类型和字段
- `src/domain/skill/target-resolver.ts` — 新增 `validateTargetAgainstSelector(target, source, selector)` 验证函数

**边界案例**：
| 场景 | 处理方式 |
|------|---------|
| AI 建议的目标已被击杀 | 验证失败 → 走 `resolveSkillTargets` 或随机回退，记录日志 |
| AI 建议的目标是友军（但技能要求打敌人） | 验证失败 → 走 `resolveSkillTargets` 重算，记录日志 |
| `resolveSkillTargets` 返回空数组（无合法目标） | 降级为普攻（若能量足够）或跳过行动 + 日志警告 |
| 玩家手动控制（`controlMode: 'MANUAL'`） | 完全跳过 AI/自动策略，由 Store/UI 直接调用执行函数并传入玩家指定的目标 |
| 自动战斗但无 AI 实例（`controlMode: 'AUTO'`） | 走 `selectBestSkill` 选技能，目标由验证后采纳策略中的"无建议目标"分支处理 |

**验证**：
- `tests/unit/core/battle/AISkillSelection.test.ts` — 新建：验证 AI 建议的目标被正确验证/采纳/拒绝
- `tests/unit/core/battle/AttackTargetSelection.test.ts` — 新建：验证普攻场景下 AI 建议的目标被采纳，而非随机
- 现有技能测试绿灯 — 行为语义不变（无建议目标时走原有逻辑）

### P0/EXEC-1：deferDamage 改为请求令牌模式

**背景**：
`SkillManager.setDeferredDamageMode(bool)` 是全局可变 boolean。异常路径一旦漏关（有 6 处 `setDeferredDamageMode(true/false)` 分布在不同 try/catch/early-return 中），伤害链路永久断开。

**方案**：
用"请求令牌"替代全局 toggle——每次执行技能时创建一个 `DeferredDamageToken`，SkillExecutor.writeDamage 写到 token 上，调用方在动画完成后调用 `token.applyAll()` 统一应用。

```
class DeferredDamageToken {
  private entries: Array<{target, damage, heal}>
  private applied = false            // 防重复标志
  record(target, damage, heal): void
  applyAll(): void                   // 首次调用后锁定，后续调用无效果
  getTotalDamage(): number
  getTotalHeal(): number
}
```

`SkillExecutor.executeStep` 不再判断 `this.deferDamage`，改为接受 `token?: DeferredDamageToken`。调用方传 token 表示延迟模式，不传表示即时模式。

**影响文件**：
- `src/domain/skill/SkillExecutor.ts` — 删除 `deferDamage` 字段；`executeStep` / `executeDamage` / `executeHeal` 增加 `token?` 参数
- `src/domain/skill/SkillManager.ts` — 删除 `setDeferredDamageMode`；`executeSkill` 接受 `token?` 透传给 executor
- `src/domain/battle/service/BattleExecutor.ts` — `selectAndExecuteSkill` 中 new 一个 token，传进去，applyAll
- `src/domain/skill/PassiveSkillManager.ts` — `executePassiveSkill` 中删除 `save/restore` 模式，改传 token
- `src/shared/types/` — 新增 `DeferredDamageToken` 定义

**边界案例**：
- 动画播放中战斗结束了——token 不 apply，无伤害泄漏
- 同一个技能对多个目标——每个 target 独立记录后 applyAll
- passive 触发时 token 不传（被动不涉及动画编排）

**验证**：
- 现有技能测试绿灯（因为行为语义不变，只是调用方式变）
- 人工注入异常路径：token 不 apply → 伤害不生效但战斗不崩溃

### P0/AI-2：convertSkillConfigToSkill 汇总全部 steps 计算总伤害/治疗

**背景**：
`convertSkillConfigToSkill` 只读 `config.steps?.[0]?.calculation?.baseValue`。如果技能的第一个 step 是 APPLY_BUFF 或 CUSTOM，AI 认为该技能伤害=0、治疗=0，权重计算完全偏误。

**方案**：
遍历所有 steps：
- DEAL_DAMAGE / HEAL：累加所有 step 的 `calculation.baseValue`（含 extraValues）作为汇总值
- APPLY_BUFF：按 buffId 前缀标记 hasBuff / hasDebuff
- extraValues 引用 `maxHealth` / `currentHealth` 的动态伤害：标记 `hasDynamicDamage`，加载时不估算，AI 决策时实时算

`Skill` 接口变更：
- `damage` / `heal` 改为全部 steps 的汇总值
- 新增 `hasBuff` / `hasDebuff` / `hasDynamicDamage` 布尔字段
- 删除 `includeDamage / includeHeal / includeBuffId` 选项参数

**影响文件**：
- `src/domain/skill/types.ts` — `Skill` 接口新增 `hasBuff` / `hasDebuff` / `hasDynamicDamage`；`convertSkillConfigToSkill` 重写
- `src/domain/battle/ai/AIPriorityStrategy.ts` — `adjustWeightByBattleState` 和 `getBaseWeight` 中增加 `skill.hasBuff` 的判断

**边界案例**：
- 空 steps 数组 → 所有字段为 0/false
- calculation 缺失的 DEAL_DAMAGE step → damage 计为 0，不崩溃
- 多段伤害 → 所有段汇总

**验证**：
- `tests/unit/core/skill/convertSkillConfigToSkill.test.ts` — 新建：多步技能分别验证汇总结果

## P1 — 设计缺陷，应该修复

---

### P1/CTRL-1：技能可执行性检查单一路径

**背景**：
控制检查分散在三处：`SkillManager.isTargetStunned` 硬编码 `buff_stun`；`BuffSystem.isCharacterControlled` 统一入口；`BattleExecutor.isParticipantControlled` 包装前者。冷却检查也有两套——`SkillManager` 靠鸭子类型（`setSkillCooldown`），`PassiveSkillManager` 自管一套。

**方案**：
1. 在 `ParticipantSkills` 上暴露统一的 `canExecuteSkill(skillId, buffQuery: BuffQuery): SkillAvailability`，合并能量/冷却/控制状态，通过 `BuffQuery` 接口（而非具体 `BuffSystem` 类）解耦
2. `SkillManager.executeSkill` 入口调用此方法，不再自己做能量检查和控制检查
3. 删除 `SkillManager.isTargetStunned`，所有控制查询走 `BuffSystem.isCharacterControlled`
4. 给 `BattleEntity` 接口（或对应的参与者实现）增加 `canExecuteSkill` 方法签名，去掉鸭子类型

**影响文件**：
- `src/domain/battle/entity/ParticipantSkills.ts` — 新增 `canExecuteSkill(skillId, buffQuery: BuffQuery)` 方法
- `src/domain/skill/SkillManager.ts` — `executeSkill` 中能量/控制/冷却检查委托给 participant
- `src/domain/buff/BuffSystem.ts` — `canUseSkill` 已经是统一的，不需要改
- `src/domain/battle/type/types.ts` — `BattleEntity` 接口增加 `canExecuteSkill` 签名

**边界案例**：
- SILENCE 状态：`canUseSkill` 返回 false 但不阻止 `canAct`（普攻允许）
- 能量刚好等于消耗值：允许使用
- 冷却为 0 或 undefined：视为可用

**验证**：
- `tests/unit/core/battle/participant/ParticipantSkills.test.ts` — `canExecuteSkill` 对不同控制状态的响应

### P1/TAG-1：引入 EffectTag 系统替代硬编码 buff ID 列表

**背景**：
`HealCalculator.calculateDebuffEffect` 硬编码 `['buff_heal_reduction', 'buff_poison', 'buff_curse']`，`SkillExecutor.handleBurnDetonate` 硬编码 `includes('burn')`。新加一个减治疗的 buff 要改两个文件，且可能遗漏。

**方案**：
在 `BuffConfig` / `ScriptBuffConfig` 中增加 `tags?: string[]` 字段。查询点上通过 `BuffSystem.hasBuffWithTag(characterId, tag)` 替代硬编码 ID 列表。

标签使用 **TypeScript 枚举常量** 维护，如：

```typescript
export enum EffectTag {
  HEAL_REDUCTION = 'heal_reduction',
  BURN = 'burn',
  POISON = 'poison',
  STUN = 'stun',
  SILENCE = 'silence',
}
```

```typescript
// BuffSystem 新增
hasBuffWithTag(characterId: string, tag: string): boolean {
  for (const instance of this.getBuffInstances(characterId)) {
    const config = this.scriptRegistry.getBuffConfig(instance.buffId)
    if (config?.tags?.includes(tag)) return true
  }
  return false
}
```

**影响文件**：
- `src/shared/types/effect.ts` — 新增 `EffectTag` 枚举
- `src/domain/buff/types.ts` — `BuffConfig`、`ScriptBuffConfig`、`BuffConfigData` 增加 `tags?: string[]` 字段
  - ponytail: JSON 以 `as BuffConfigData` 断言加载，多余字段静默忽略，因此加字段不需要改加载逻辑
- `src/domain/buff/BuffSystem.ts` — 新增 `hasBuffWithTag` 和 `getBuffInstancesWithTag`
- `src/domain/skill/HealCalculator.ts` — `calculateDebuffEffect` 改为查标签 `EffectTag.HEAL_REDUCTION` 而非硬编码 ID
- `src/domain/skill/SkillExecutor.ts` — `handleBurnDetonate` 改为查标签 `EffectTag.BURN` 而非 `includes('burn')`
- `configs/buffs/` 目录下的 JSON 配置——逐个增加 `tags` 字段

**边界案例**：
- buff 无 tags 配置 → 等价于空数组，不匹配任何标签查询
- 一个 buff 可以有多个 tags（如 `['heal_reduction', 'debuff']`）
- 通过 addBuff 运行时创建的追踪 buff（`_track_passive_` 前缀）无 tags，不参与查询

**验证**：
- `tests/unit/core/buff/BuffSystem.test.ts` — 测试 `hasBuffWithTag`
- 现有减治疗/灼烧逻辑行为不变（因为配置加上对应 tag 即可）

### P1/PERF-1：comboStates 清理 + 被动技能按时机索引

**背景**：
- `SkillExecutor.comboStates` 在角色死亡后不清理，Map 持续膨胀
- `PassiveSkillManager.triggerPassiveSkillsForAll` 每次遍历所有参与者 × 所有被动，O(n*m)

**方案**：

1. **comboStates 绑定死亡事件**：在 `BattleExecutor` 检测到目标死亡时同步调用 `SkillExecutor.cleanupComboState(entityId)`。清理时机确定为**角色死亡时**而非回合结束时（已确认）。

2. **被动技能倒排索引**：`PassiveSkillManager` 内部增加按 `BattleTriggerPhase` 索引的倒排表：

```typescript
// registerPassive 时双写
private indexByPhase = new Map<string, Array<{characterId: string, config: PassiveSkillConfig}>>()

// triggerPassiveSkillsForAll 改为按 phase 查索引，只遍历有对应被动的角色
triggerPassiveSkillsForAll(trigger: BattleTriggerPhase, participants, context): void {
  const entries = this.indexByPhase.get(trigger) ?? []
  for (const { characterId, config } of entries) {
    const entity = participants.get(characterId)
    if (!entity?.isAlive()) continue
    this.triggerPassive(config, entity, context)
  }
}
```

**影响文件**：
- `src/domain/skill/SkillExecutor.ts` — 新增 `cleanupComboState(entityId)` 和 `clearAllComboStates()`，公开方法
- `src/domain/skill/PassiveSkillManager.ts` — `registerPassive` 重构为双写（character Map + 倒排索引）；`triggerPassiveSkillsForAll` 改为走索引；`removePassive` / `clearPassives` 同步更新索引
- `src/domain/battle/service/BattleExecutor.ts` — `handleHitAttack` / `selectAndExecuteSkill` 中检测到目标死亡后调用 `cleanupComboState`；战斗初始化时调用 `clearAllComboStates`

**边界案例**：
- 倒排索引必须与 `character` Map 保持同步——`removePassive` / `clearPassives` 修改倒排
- 同一角色在同一个 phase 上注册了多个被动（如 `BEFORE_ATTACK` × 2）——数组保留所有条目
- 角色退场后再注册——倒排索引未清理时，`isAlive()` 检查兜底

**验证**：
- `tests/unit/core/skill/SkillExecutor.test.ts` — 验证 `cleanupComboState` 后 comboStates 大小减 1
- `tests/unit/core/skill/PassiveSkillManager.test.ts` — 验证 `triggerPassiveSkillsForAll` 只调用了有对应 phase 的角色

## P2 — 架构改进，值得做但不紧急

### P2/ARCH-1：技能与 Buff 之间的双向通信接口

**背景**：
当前 Buff → 属性变更（单向通过 `ModifierStack`），但 Buff 无法操作技能系统（如"获得强化状态后技能冷却减 1"）。技能系统也无法查询自身携带的 Buff 是否会影响技能行为。

**方案**：
在 `BuffSystem` 上暴露一个 `SkillBuffBridge` 接口，持有弱引用：

```typescript
interface SkillBuffBridge {
  modifySkillCooldown(characterId: string, skillId: string, delta: number): void
  isSkillSilenced(characterId: string): boolean
  getSkillDamageModifier(characterId: string, skillId: string): number
}
```

`BuffSystem` 在构造时接收桥接口，Buff 脚本通过 `context.getBridge()` 访问。

**影响文件**：
- `src/domain/battle/service/SkillBuffBridge.ts` — 新建
- `src/domain/buff/BuffSystem.ts` — 构造函数增加桥接口参数；BuffContext 增加 `getBridge()`
- `src/domain/buff/BuffContext.ts` — 新增桥引用
- `src/domain/buff/scripts/base/BaseBuffScript.ts` — 模板 `onApply/onRefresh` 可调桥方法
- `src/domain/di/Container.ts` — 组装时传入桥实现

**延迟条件**：无功能需求驱动时可推迟到有具体 Buff 脚本需要调用桥时再做。

### P2/UI-1：技能描述模板化 + 不可用原因反馈

**背景**：
`Skill.description` 是静态字符串。技能伤害 50+attack×1.2 时描述只能手写。"技能不可用"只有布尔值，不暴露原因。

**方案**：

1. **描述模板**：`SkillConfig` 中支持描述模板语法 `{{damage}}` `{{heal}}` `{{extra.attack*ratio}}`，在加载时由 `GameDataProcessor` 替换为实际计算值。

2. **不可用原因**：`canExecuteSkill` 返回带原因的对象：

```typescript
export enum SkillBlockReason {
  COOLDOWN_X_TURNS = 'cooldown',
  ENERGY_SHORT = 'energy',
  STUNNED = 'stun',
  SILENCED = 'silence',
  DEAD = 'dead',
}

export interface SkillAvailability {
  can: boolean
  reason?: SkillBlockReason
  detail?: string  // 如 "还需 2 回合冷却"（格式约定：冷却用中文 + 数值，能量用 `current/max`，控制用状态名）
}
```

UI 层据此显示不同文案和图标提示。

**影响文件**：
- `src/domain/skill/types.ts` — 新增 `SkillBlockReason` 枚举和 `SkillAvailability` 接口；`SkillConfig.description` 支持模板语法
- `src/domain/battle/entity/ParticipantSkills.ts` — `canExecuteSkill` 返回 `SkillAvailability`
- `src/presentation/stores/battleStore.ts` 或新的 composable — 新增不可用原因的响应式状态
- `src/presentation/components/` — 技能面板组件展示不可用原因

## 修改顺序与依赖关系

```
P0/AI-2  (convertSkillConfigToSkill) ← 可独立进行，无依赖
P0/EXEC-1 (deferDamage token)        ← 可独立进行，无依赖
P0/AI-1  (统一技能选择管道)            ← 建议在 AI-2 之后，因为 AI 权重系统更准确后再统一管道
  └─ 依赖 P0/AI-2 完成后权重计算更准确

P1/TAG-1 (EffectTag 系统)            ← 推荐最先做 P1，因为后续 P1/CTRL-1 可能会用到
P1/CTRL-1 (统一控制检查)              ← 依赖 TAG-1 建成后可以用标签而非硬编码
P1/PERF-1 (性能优化)                 ← 可独立进行，不依赖其他

P2/ARCH-1 (SkillBuffBridge)         ← 可在任何时间插入，但建议等 P1 全部完成后
P2/UI-1 (描述模板+原因反馈)          ← 可独立进行
```

## 建议执行批次

| 批次 | 内容 | 预估改动文件数 |
|------|------|---------------|
| **批次 1**（核心修复） | P0/AI-2 → P0/EXEC-1 → P0/AI-1 | ~8 个 |
| **批次 2**（质量改进） | P1/TAG-1 → P1/CTRL-1 → P1/PERF-1 | ~10 个 |
| **批次 3**（架构演进） | P2/ARCH-1 + P2/UI-1（按需） | ~7 个 |
