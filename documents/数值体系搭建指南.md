# 数值体系搭建指南

> 面向对象：想掌握"从零搭一套支撑中小型游戏的数值体系"的开发者。
> 学习方式：本文结合当前 CombatDebugStudio 代码库的真实结构讲解，每一节都给出对应的代码位置，读完能动手、能改配置、能自己定曲线。

---

## 0. 这份文档解决什么

你手上有代码（属性、技能、伤害公式、Buff、配置），但不知道：
- 数值从哪来、往哪去；
- 属性为什么越加越多；
- "免疫眩晕""免疫灼烧"这类效果应该怎么表达；
- 敌人/角色的强度怎么随等级走曲线；
- 改完数值后靠什么验证没崩。

本文回答这些。读完你会得到一张"数值体系的完整地图"和一套可执行的搭建步骤。

## 1. 数值体系全景图

一套可维护的数值体系，由五层组成，从上到下：

```
┌─────────────────────────────────────────────┐
│ 5. 内容层    敌人 / 角色 / 技能 / Buff 配置   │  ← 策划改这里
├─────────────────────────────────────────────┤
│ 4. 平衡层    曲线公式 · TTK 模拟 · 校验脚本    │  ← 数值规则集中地
├─────────────────────────────────────────────┤
│ 3. 公式层    伤害公式 · 治疗公式 · 命中判定     │  ← 引擎逻辑
├─────────────────────────────────────────────┤
│ 2. 计算层    属性重算管线（四段式修饰符）       │  ← 引擎逻辑
├─────────────────────────────────────────────┤
│ 1. 属性层    属性 Schema（定义"有哪些属性"）    │  ← 元数据
└─────────────────────────────────────────────┘
```

搭建的关键认知：**越上层越应该是"数据"（改配置就能改游戏），越下层越应该是"代码"（稳定、少动）。**
谁该写代码、谁该写 JSON，是分层的首要决定。

## 2. 当前系统的数值骨架（可复用的部分）

CombatDebugStudio 的五层都已经存在，逐层看。

### 2.1 属性层 —— Schema 驱动

文件：`configs/attributes/attributes.json`

每个属性是一条 JSON：

```json
{
  "code": "critRate",
  "name": "暴击率",
  "displayName": "暴击率",
  "description": "攻击产生暴击的概率",
  "range": "0-100%",
  "impact": "提高暴击触发几率",
  "isPercentage": true,
  "defaultValue": 10
}
```

运行脚本 `npm run generate:attributes` 会把它生成为 TS 常量：
`src/domain/attribute/attribute-codes.generated.ts`（`ATTRIBUTE_CODE` 联合类型 + `AttributeMetaMap` 元数据表）。

```ts
// types.ts:194 从 generated 导入，业务代码只依赖类型，不依赖 JSON
import { ATTRIBUTE_CODE, AttributeMetaMap } from './attribute-codes.generated'
```

**关键点：属性是枚举（代码），不是运行时自由键。**
好处：
- 打错属性名 → 类型报错，不是运行时 undefined；
- 元数据（isPercentage / defaultValue / displayName）一处定义，UI 和公式共用；
- 增加属性 = 改 JSON + 跑生成脚本，不动战斗代码。

**注意**：`currentHealth`、`currentEnergy`、`shield` 标记了 `isRuntimeState: true`，这类属性由 `setAttributeValue` 直接维护，**不走公式重算**（见 `ParticipantStats.ts:145`）。

### 2.2 计算层 —— 四段式修饰符管线

文件：`src/domain/battle/entity/ParticipantStats.ts:141`

属性最终值 = 修饰符堆栈的累加结果，顺序是：

```
最终值 = (base + Σ加算) × (100 + Σ百分比) / 100
        × (100 + Σ独立乘) / 100 × (100 + Σ最终乘) / 100
```

四种修饰符类型（`types.ts:13`）：
| 类型 | 含义 | 例子 |
|---|---|---|
| `ADDITIVE` | 直接加减数值 | +10 攻击 |
| `PERCENTAGE` | 百分比修正 | +20% 攻击 |
| `MULTIPLICATIVE` | 独立乘区 | x1.5 最终伤害 |
| `FINAL` | 最终乘区 | x2 暴击伤害 |

`ParticipantStats` 用版本戳缓存：修饰符一变 → `invalidateCache()` 全局版本号 +1 → 下次读属性发现版本不匹配才重算。调试时能输出每一步拆解（`breakdown`），这是数值排查的地基。

**关键点：所有"加属性的东西"（Buff、装备、技能被动、阵型、地形）最终都变成一条 Modifier 塞进堆栈，计算层不区分来源。** 来源类型只是 `Modifier.sourceType` 的一个字段，用于 UI 展示。

### 2.3 公式层 —— 伤害公式

文件：`src/domain/skill/DamageCalculator.ts`

完整伤害流程（`calculateDamage`，顺序即代码顺序）：

```
1  命中判定    计算命中率 = hitValue/(hitValue+dodgeValue)×100%；实际命中 = clamp(计算命中率 + hit − dodge, 10, 95)（可关闭，enableDodge 门控）
2  暴击判定    critRate → critMultiplier = critDamage / 100
3  基础伤害    attack × (1 ± 15%) 浮动（无 calculation 时）
4  extraValues  附加 攻击力 × ratio 之类的加成
5  来源方加成  damageBoost / fireSkillDmgBonus / physicalSkillDmgBonus / damageToLowHp
6  捕获原始伤害 rawDamage（供反伤等使用）
7  暴击承伤减免 critDmgTakenReduction
8  防御        damage - defense（减法公式，真实伤害跳过）
9  攻击类型减免 normalAtkDmgReduction / skillDmgReduction
10 元素抗性    fireRes 等（ELEMENTAL 类型）
11 场地修正    fieldElementalModifier
12 伤害减免    damageReduction
13 易伤        damageTakenIncrease
14 目标修正    targetModifiers
15 阵营克制    elementMatrix（五行克制，缺省 1.0）
16 钳制        clamp[min=1, max=9999]
```

每个环节都有 `breakdown.steps` 记录 before/after，可逐行回放给玩家或调试器看。这就是"公式层可追溯"。

### 2.4 内容层 —— 全 JSON 配置

`configs/` 下按域分区：`enemies/`、`skills/`、`effects/`、`buffs/`、`params/`、`attributes/`。

技能示例（`configs/skills/skills.json`）：
```json
{
  "id": "skill_enemy_001_small",
  "name": "花粉迷雾",
  "cooldown": 2,
  "energyCost": 50,
  "steps": [
    {
      "type": "deal_damage",
      "attackType": "normal",
      "calculation": {
        "baseValue": 0,
        "extraValues": [{ "ratio": 0.8, "attribute": "attack" }]
      }
    },
    {
      "type": "apply_buff",
      "duration": 1,
      "effectId": "buff_hit_reduction",
      "calculation": { "baseValue": 0.3, "extraValues": [] }
    }
  ]
}
```

**关键点：技能的伤害不是写死的数值，而是"公式片段"**（`baseValue` + `extraValues` 里 `attribute × ratio`）。这样技能伤害会自动跟随攻击力成长，不会出现"技能倍率还停留在 1 级"的脱节问题。

### 2.5 平衡层 —— 已有工具

| 工具 | 文件 | 作用 |
|---|---|---|
| 属性生成 | `scripts/generate-attributes.cjs` | attributes.json → TS 类型 |
| 敌人重平衡 | `scripts/rebalance-enemies.cjs` | 按等级曲线批量重算敌人四维 |
| 战斗节奏验证 | `scripts/balance-check.cjs` | 模拟 TTK（回合数），断言 6~12 / 4~10 回合 |
| 技能配置校验 | `scripts/tools/validate_skills.cjs` | 检查技能 JSON 引用完整性 |

平衡目标写在 `balance-check.cjs` 头部注释里（这是本系统"数值验收标准"的雏形）：
- guardian 1v1 普攻 TTK ≈ 6~12 回合
- 我方 4v4 vs 场景 ≈ 4~10 回合分出胜负
- 任何敌方防御 < 我方最低攻击 × 0.85（杜绝破防卡 1 点）

## 3. 核心概念：tag 与免疫位图

这是你最关心的问题，单独开一大节。

### 3.1 问题起源：布尔属性爆炸

先看现状。`configs/attributes/attributes.json` 里躺着这么一批属性：

```json
{ "code": "slowImmune",       "range": "0-1", "impact": "非0时免疫减速" }
{ "code": "stunResist",       "range": "0-1", "impact": "非0时抵抗眩晕" }
{ "code": "knockbackResist",  "range": "0-1", "impact": "非0时抵抗击退" }
{ "code": "poisonResist",     "range": "0-1", "impact": "非0时抵抗中毒" }
{ "code": "bleedResist",      "range": "0-1", "impact": "非0时抵抗流血" }
{ "code": "burnImmune",       "range": "0-1", "impact": "非0时免疫灼烧" }
```

这是"每种效果一个布尔属性"的写法。问题：
1. **每加一种控制效果（冰冻/石化/恐惧…），就要加一个新属性**，属性表无限膨胀；
2. **角色配置要写一堆 0/1**，一个角色配 6 个免疫字段，可读性差；
3. **逻辑散落**：判断"是否免疫眩晕"在战斗代码里要 `getAttribute('stunResist')`，每处效果各自查各自的属性，没有统一入口；
4. **无法表达组合**：比如"毒系装备能防中毒+流血"，你没法用一个属性表达"这一组"。

解决方案有两个方向：**tag（标签）** 和 **免疫位图（bitmap）**。

### 3.2 Tag（标签）

**思想：不新增属性，而是给"效果"和"角色"打上字符串标签，按标签匹配。**

三个步骤：

**(1) 给效果打标签** —— 一个 Buff/技能声明自己属于哪些类别：

```json
{
  "id": "buff_poison",
  "tags": ["debuff", "dot", "poison"],
  "description": "中毒，每回合造成伤害"
}
```

**(2) 给角色声明免疫标签** —— 角色/装备/Buff 上写"我免疫这些标签"：

```json
{
  "id": "poison_immune",
  "immunities": ["poison"]
}
```

**(3) 施加效果时统一拦截** —— 检查目标是否免疫该效果的标签，免疫则施加失败：

```ts
// 伪代码：施加 Buff 前的统一闸门
function tryApplyBuff(target, buffConfig) {
  for (const tag of buffConfig.tags) {
    if (target.hasImmunity(tag)) return false   // 免疫，拦截
  }
  // ...正常施加
}
```

好处：
- 新增一种控制效果 = 新增一个 tag 字符串，**不动属性表、不动战斗代码**；
- "毒系装备防中毒+流血" = `immunities: ["poison", "bleed"]`；
- 可批量查询："这个角色有没有带 `dot` 标签的减益" → 驱散/净化逻辑统一；
- 可读性极好，策划一眼看懂。

### 3.3 免疫位图（Immunity Bitmap）

**思想：把一组"是/否"的免疫状态压缩进一个整数，用二进制位表示。**

```ts
// 约定每一位代表一种效果
const IMMUNITY = {
  POISON: 1 << 0,  // 1
  BURN:   1 << 1,  // 2
  STUN:   1 << 2,  // 4
  BLEED:  1 << 3,  // 8
  SLOW:   1 << 4,  // 16
  // ...
}
```

角色身上只有一个数字 `immunityMask`：
- 免疫中毒 + 灼烧 → `mask = POISON | BURN = 3`
- 判断是否免疫眩晕 → `(mask & STUN) !== 0`
- 合并两个来源的免疫 → `mask |= otherMask`
- 去重一个来源 → `mask &= ~otherMask`

优点：
- **一个 number 顶几十个布尔属性**，内存/网络传输极小；
- 位运算是 O(1)，快；
- 天然支持组合与合并。

缺点：
- **可读性差**：`0b1101` 不如 `["poison","burn","slow"]` 直观，调试要翻映射表；
- **上限固定**：32 位整数最多 32 种，64 位最多 64 种；
- **语义弱**：标签还能带"这是减速减益"，位图只有 0/1；
- 序列化对不上号时很难查。

### 3.4 对比与选型

| 维度 | 布尔属性（现状） | Tag 数组 | 免疫位图 |
|---|---|---|---|
| 新增效果成本 | 加属性+改代码 | 加字符串 | 加一位常量 |
| 可读性 | 中 | 高 | 低 |
| 组合免疫 | 差 | 好 | 好 |
| 容量上限 | 无 | 无 | 32/64 种 |
| 存储/传输 | 大 | 中 | 极小 |
| 批量查询/净化 | 差 | 好 | 好 |

**中小型游戏选型建议**：
- 效果种类 < 20、以人类可读和策划友好为优先 → **Tag 数组**；
- 状态位多（控制+Debuff 几十种）、对性能/包体敏感、需要网络同步 → **免疫位图**；
- 成熟做法是**两者结合**：业务逻辑用 tag，跨端同步用位图，配置层自动转换。

结合当前系统：战斗引擎本身是单机 TypeScript，没有网络传输压力，属性表已经 60+ 且有膨胀趋势 → **优先 Tag 数组**，位图作为未来若要做存档/回放压缩时的备选。

### 3.5 当前系统的落地情况（重要）

好消息：**tag 免疫机制在当前代码里已经有雏形了**，只差把属性表里那些布尔免疫属性迁移过来。

已存在的基础：

1. **Buff 配置已支持 tag 与免疫声明**（`src/domain/buff/types.ts:182`）：
```ts
tags?: string[]        // 效果标签
immunities?: string[]  // 免疫标签：拥有对应标签的角色免疫此 Buff
```

2. **Buff 查询已支持按 tag 查**（`src/domain/buff/types.ts:20`）：
```ts
hasBuffWithTag(characterId: string, tag: string): boolean
```

3. **Buff 类别已有 IMMUNITY 原子效果**（`src/domain/buff/atomic/types.ts:15`）：
```ts
IMMUNITY: 'immunity',  // 免疫
```

所以迁移路径很清晰（这是"属性收敛"，见 §4.4）：
- 把 `stunResist`/`burnImmune`/`poisonResist`… 这些 `range: "0-1"` 的布尔属性从 `attributes.json` 移除；
- 在 Buff/角色配置上用 `immunities: ["stun"]`、`immunities: ["burn"]` 声明；
- 施加控制/Debuff 前查 `hasBuffWithTag` 或 immunity 声明拦截。

## 4. 搭建一套数值体系的四步法

基于当前系统骨架，补齐三块 + 收敛一块。

### 4.1 曲线参数化（把写死在脚本里的公式提成配置）

✅ 已完成：`configs/params/curves.json` 已落地，`scripts/rebalance-enemies.cjs` 已改为读配置的纯执行器（曲线求值器 `evalCurve` 支持 `linear`，未知类型抛错）。

曲线配置（敌人）：

```json
{
  "enemy": {
    "hp":  { "base": 80,  "perLevel": 11, "type": "linear" },
    "atk": { "base": 10,  "perLevel": 2.0, "type": "linear" },
    "def": { "base": 1,   "perLevel": 0.9, "type": "linear" },
    "spd": { "base": 10,  "perLevel": 1.2, "type": "linear" }
  }
}
```

**曲线表 = 数值体系的中枢**，全游戏的强度增长由这一张表决定。数值策划改这张表，跑 `node scripts/rebalance-enemies.cjs` 即重算全部敌人。

曲线的三种常用形态：
- **线性**：`value = base + perLevel × (L-1)`（当前敌人用这个，低成长好控）
- **分段线性**：前期缓、后期陡（RPG 常用，防前期数值膨胀）
- **指数/幂**：`value = base × growth^(L-1)`（快节奏成长，注意上限）

### 4.2 模板化内容（职业模板 × 等级实例化）

现状问题：`configs/enemies/enemies.json` 里 80+ 个敌人，每个手写四维，改一轮曲线要跑脚本批量改（`rebalance-enemies.cjs` 就是这个补丁）。

**做法**：定义**职业/种族模板**，内容 = 模板 × 等级。

模板例子（guardian 五人组就是现成的五份模板，见 `balance-check.cjs:24`）：
```json
{
  "templates": {
    "guardian_fire":  { "hp": 350, "atk": 70, "def": 12, "spd": 35, "role": "输出" },
    "guardian_earth": { "hp": 520, "atk": 40, "def": 25, "spd": 16, "role": "坦克" }
  }
}
```

内容实例只需写 `{ "template": "guardian_fire", "level": 10 }`，属性由曲线 × 模板系数生成。**一次模板 = N 个内容**，新加一个等级不用手写。

### 4.3 平衡回路（TTK 模拟作为回归护栏）

现状：`balance-check.cjs` 已经做了 1v1 和 4v4 的 TTK 断言。

**做法**：把 TTK 模拟做成每次改数值后必须跑的"验收测试"，并扩展覆盖：
- 普攻 TTK（已有）
- 技能循环 TTK（加入能量/冷却约束）
- 暴击期望、元素克制场景
- 破防悬崖检查（已有）

工作流变成：
```
改 curves.json / templates → 跑 rebalance 脚本 → 跑 balance-check
→ TTK 不达标 → 回改 → 达标 → 提交
```

这就是数值体系的"测试"：**数值改动必须有可量化的验收标准，否则改完全靠手感**。

### 4.4 属性收敛（删掉布尔免疫属性）

见 §3.5。把 `attributes.json` 里 `range: "0-1"` 的免疫/抗性布尔属性迁到 tag 免疫体系，属性表从 60+ 收敛回核心维度。

建议保留的属性组：
- 战斗核心：`maxHealth/currentHealth/attack/defense/speed/currentEnergy/maxEnergy`
- 概率输出：`critRate/critDamage/hit/dodge`
- 伤害乘区：`damageBoost/damageReduction/damageTakenIncrease/trueDamageRate`
- 元素系统：`*Atk/*Res/fireSkillDmgBonus/physicalSkillDmgBonus`
- 上下文物：`damageDealt/damageTaken`（技能链输入）

其余"XX 免疫/抗性"的布尔属性一律收敛为 tag。

## 5. 术语表

| 术语 | 含义 |
|---|---|
| Attribute / 属性 | 角色的可量化维度（攻击/防御/暴击…），代码里是枚举 |
| Modifier / 修饰符 | 一条"对某属性加多少"的规则，来源可以是 Buff/装备/技能 |
| 乘区 | 属性计算中一段独立的乘法修正，互不干扰 |
| TTK / Time To Kill | 打死目标所需回合数，平衡的核心度量 |
| 破防悬崖 | 攻击 - 防御 ≤ 0 时伤害卡死为 1，导致某类角色完全打不动，属设计事故 |
| Tag / 标签 | 给效果或实体打的字符串标记，用于分类、批量匹配、免疫 |
| 免疫位图 / Bitmap | 用整数的二进制位表示一组免疫状态 |
| 曲线 / Curve | 属性随等级变化的公式 |
| Schema 驱动 | 由 JSON 定义类型/元数据，代码读取自动生成 |

## 7. 学习路径建议（怎么快速上手）

1. **先读 §2**，把五个层的代码各打开看一眼，形成"地图"。
2. **动手改一次敌人**：在 `enemies.json` 里加一个 5 级敌人，跑 `npm run dev` 看能不能出战。体会到"内容层 = 配置"。
3. **跑一次平衡验证**：`node scripts/balance-check.cjs`，理解 TTK 是什么。
4. **读一遍 attributes.json**：把里面"0-1 免疫属性"挑出来，对照 §3 思考它们该怎么收敛。
5. **试着把敌人的一条曲线改成配置**（§4.1），体会"曲线 = 中枢"。
6. **最后读 §3 的 tag/位图选型**，在你的新内容里用 tag 声明免疫，而不是加布尔属性。

---

## 8. 一句话总结

> **数值体系 = 属性 Schema 定边界 + 修饰符管线定计算 + 伤害公式定规则 + 曲线与模板定成长 + TTK 模拟定验收。**
> 免疫这类"是/否"效果，用 **tag**（人类可读、可组合）或**位图**（紧凑、O(1)）表达，而不是一个效果一个布尔属性——否则属性表会膨胀到无法维护。
