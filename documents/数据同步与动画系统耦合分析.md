# 数据同步与动画系统耦合分析

## 背景

直觉上，"伤害数字、HP 条、技能特效都依赖 syncTeams()"——同步时机是回合粒度，动画需要帧粒度，两者是否应该分开？

代码调查后发现，实际耦合情况比直觉推测的更松、更局部化。

---

## 当前数据流（实际）

```
领域层                            表现层

action 开始
  ├─ triggerMissAnimation   → eventBus → Watch → 闪避动画 (GSAP/CSS)
  ├─ triggerSkillEffect     → eventBus → Watch → 技能动画 (GSAP/VFX)
  ├─ damageToken.applyAll() → 直接改 entity.currentHealth
  │                               └─ shallowReactive → HP 条即时更新
  ├─ triggerDamageAnimation → eventBus → Watch → 飘字动画
action 结束

回合结束
  └─ BattleLifecycleManager 发射 TEAM_DATA_CHANGED
       └─ syncTeams() → 全量一致性刷新（创建新 proxy）
```

### 各元素的真实驱动源

| 元素 | 驱动方式 | 更新粒度 | 是否依赖 syncTeams |
|------|---------|---------|-------------------|
| 伤害数字/治疗数字 | eventBus `DAMAGE_ANIMATION` → Watch handler → `showDamageNum()` / `addDamageNumber()` | 每个 action | **否** |
| 技能特效（光弹/命中/蓄力） | eventBus `SKILL_EFFECT` → Watch handler → GSAP / `playAttackSequence()` | 每个 action | **否** |
| 闪避/Buff 特效 | eventBus `MISS_ANIMATION` / `BUFF_EFFECT` | 每个 action | **否** |
| HP 条 | `shallowReactive` proxy 追踪 `entity.currentHealth` → computed `hpPercent` | 每个 action（`damageToken.applyAll()` 直接改字段） | **否**（但仍受 syncTeams 副作用影响） |
| 能量条 | 同上 | 同上 | **否** |
| 全量状态一致性 | syncTeams 重建 proxy 数组 | 回合边界 | **是** |

### 关键发现

**动画和数据同步已经在不同的管道里了：**

- 动画走事件总线（`eventBus.emit` → `battleStore` Watch handler → 表现层执行）
- HP/能量数据走响应式（`shallowReactive` → Vue computed 自动追踪）
- syncTeams 只在回合边界做一次全量校对

这不是"回合 vs 帧"的粒度冲突——回合内的每个 action 已经能独立触发动画和数据更新。

## 实际存在的三个问题

### 问题 ①：syncTeams 全量重建 proxy → 多余重渲染

**位置**：`src/presentation/stores/battleStore.ts:151-171`

**当前行为**：
```ts
this.allyTeam = data.allyTeam.map(p => shallowReactive(p))
```

每次 syncTeams 为所有参与者创建全新的 `shallowReactive` 包装，导致 `ParticipantCard` 的 `props.participant` 引用变化，触发整张卡片无差别重渲染——即使该参与者本轮没有任何变化。

**修法**：原地 patch，不换引用。
```ts
// 只写不存在的字段，保持引用不变
for (let i = 0; i < data.allyTeam.length; i++) {
  Object.assign(this.allyTeam[i], data.allyTeam[i])
}
```

**改动量**：1 行。
**效果**：消除每回合整卡无差别重渲染。

---

### 问题 ②：动画时长用固定 timer 而非 GSAP 实际完成回调

**位置**：`BattleAnimationManager.processAnimationQueue()`

**当前行为**：
```ts
rafTimer.setTimeout(resolve, animation.duration)  // 固定毫秒数
```

而 GSAP 动画受 `battleSpeed` 影响，实际时长 ≠ `animation.duration`。领域层假设动画会在 `duration` 毫秒内完成，GSAP 可能在更快或更慢的时间结束——两者没有同步机制。

**修法**：动画管理器不设固定超时，改为等 GSAP 完成回调。
```ts
gsap.to(...).then(resolve)  // 或 eventCallback: onComplete
```

**前提**：需要领域层的 `waitForAnimation()` 等待的是表现层实际的 GSAP 完成信号，而非固定计时器。这需要在事件总线上加入回执通道（animation-complete callback），改动量中等。

**效果**：动画与数据更新时序精确同步，`battleSpeed` 调节时不会出现"动画已完但数据未到"或反之。

---

### 问题 ③：两套独立的飘字系统并存

**位置**：
- `src/presentation/components/ParticipantCard.vue` — `addDamageNumber()` / `damageNumbers`（CSS `@keyframes float-up`）
- `src/presentation/components/BattleVisualEffects.vue` — `showDamageNum()` / `showHealNum()`（DOM 飘字）

**当前行为**：同一个伤害事件同时触发两套飘字：
1. `BattleField.vue` 的 `animationState.damage` Watch handler 中调用 `visualEffectsRef.showDamageNum()`
2. 同一 handler 调用 `cardRef.addDamageNumber()`

两套都渲染到 DOM，导致数字重复显示（除非某一套被 CSS 隐藏或 `v-if` 禁用）。

**修法**：选一套保留，删另一套。

| 维度 | ParticipantCard 飘字 | BattleVisualEffects 飘字 |
|------|-------------------|------------------------|
| 实现 | CSS `@keyframes float-up` | 响应式数组 → DOM 渲染 |
| 区分度 | 仅数字 + 颜色 | 有暴击/治疗/闪避区分 |
| 定位 | 卡片局部 | 战场全局坐标定位 |

建议保留 `BattleVisualEffects`（功能更完整），移除 `ParticipantCard` 中的 `addDamageNumber()`、`damageNumbers` ref 及相关模板。

**改动量**：小。删一个方法 + 模板片段 + CSS。
**效果**：消除伤害数字视觉重复。

## 分层架构评估

从四层架构（表现层/应用层/领域层/基础设施层）角度看当前的设计：

```
表现层 ─── GSAP 动画 ─── Vue 响应式 ─── 组件渲染
   ↑ eventBus Watch       ↑ shallowReactive
应用层 ─── BattleFacade ───
   ↑                          ↑
领域层 ─── BattleExecutor ─── BattleSystem
           trigger*Animation   damageToken.applyAll()
              │                    │
           eventBus.emit       直接改 entity 字段
```

**动画管道**（eventBus）和**数据管道**（shallowReactive）从领域层就已经分叉。这是正确的分层——表现层关注点在事件监听和响应式同步之间是正交的。

三个问题都是**局部实现缺陷**，不是架构级问题。不需要做"拆分动画和同步"这样的大重构。

---

## 推荐修复顺序

| 优先级 | 问题 | 改动量 | 风险 | 收益 |
|--------|------|--------|------|------|
| P0 | ③ 两套飘字删一套 | 小 | 低 | 消除视觉重复 bug |
| P1 | ① syncTeams 原地 patch | 1 行 | 低 | 消除多余重渲染 |
| P2 | ② GSAP 完成回调同步 | 中 | 中 | 精确时序同步 |

P0/P1 可以先做，P2 评估后再决定是否值得。
