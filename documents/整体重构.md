# 战斗系统架构设计方案（95分版·彻底重构）

> 本方案在上一版基础上，**彻底放弃命名兼容策略**，采用一次性重构方案。核心原则：**新架构即唯一架构，旧代码直接迁移，不设兼容层**。

---

## 第一部分：设计原则与约束

### 1.1 核心原则

| 原则 | 说明 |
|------|------|
| **彻底重构，不兼容** | 所有代码一次性移动到新结构，旧路径全量失效，不保留兼容层 |
| **领域驱动设计（DDD）** | 以领域模型为核心，所有业务逻辑围绕领域聚合组织 |
| **六边形架构（端口-适配器）** | 领域层通过端口定义依赖，基础设施层提供适配器实现 |
| **按特性划分模块** | DI模块按业务特性（Battle、Buff、Skill）划分，避免分层导致的循环依赖 |
| **脚本即领域** | Buff脚本是领域逻辑的核心，纳入`domain/buff/scripts/`闭环 |
| **类型单一来源** | 领域类型在`domain/`定义，DTO在`application/dto/`定义，共享类型在`shared/types/`定义，三者各司其职 |
| **内核共享** | `domain/kernel/`作为领域内核，承载跨聚合的值对象和异常 |

### 1.2 版本号与破坏性变更

```
版本: 3.0.0 (breaking change)
迁移方式: 全量文件移动 + import路径批量替换
不保留: core/, utils/, services/, scripts/ (顶层)
```

## 第三部分：核心类型归属规则

### 3.1 类型三层分类表

| 层次 | 目录 | 内容 | 示例 |
|------|------|------|------|
| **领域类型** | `domain/kernel/value-objects/` | 值对象（不可变） | `Health`, `Energy`, `Side` |
| **领域类型** | `domain/kernel/exceptions/` | 领域异常 | `BattleException`, `SkillException` |
| **领域接口** | `domain/**/interfaces/` | 领域层接口 | `IStrategyManager`, `IBuffSystem` |
| **应用DTO** | `application/dto/` | 数据传输对象 | `ParticipantDto`, `BattleStateDto` |
| **共享类型** | `shared/types/` | 纯数据结构 | `battle-dto.ts`, `config-types.ts` |

### 3.2 映射规则

```
领域聚合根 (Battle)        →  domain/battle/aggregate/Battle.ts
领域实体 (Participant)     →  domain/battle/entity/Participant.ts
值对象 (Health)           →  domain/kernel/value-objects/Health.ts
领域异常 (BattleError)     →  domain/kernel/exceptions/BattleException.ts
领域端口 (ILogger)        →  domain/port/logging/ILogger.ts
应用DTO (BattleStateDto)  →  application/dto/BattleStateDto.ts
共享类型 (config schema)   →  shared/types/config-types.ts
工具函数 (Counter)        →  shared/utils/Counter.ts
```

### 3.3 禁止事项

| ❌ 禁止 | ✅ 正确 |
|--------|--------|
| `domain/battle/` 中定义DTO | DTO放在 `application/dto/` |
| `shared/types/` 中定义领域实体 | 领域实体在 `domain/` |
| `domain/port/` 中定义UI相关接口 | UI端口在 `application/port/` |
| `infrastructure/` 直接依赖 `presentation/` | 依赖方向：表现层→应用层→领域层←基础设施层 |

```typescript
  }
```

# 执行重构方案所需掌握的核心信息与设计细节

> 本文档是重构方案的"操作手册"，旨在将所有设计思想、约束规则、编码规范完整传达给执行团队，确保重构不偏离设计初衷。

---

## 第一部分：核心设计思想

### 1.1 为什么选择六边形架构 + DDD？

```
┌──────────────────────────────────────────────────────────────┐
│  传统分层（单向依赖）          六边形架构（依赖倒置）         │
│  ┌──────────┐                 ┌──────────┐                  │
│  │  表现层   │ ──依赖──→      │  表现层   │ ──依赖──→        │
│  └──────────┘                 └──────────┘                  │
│       ↓                              ↓                      │
│  ┌──────────┐                 ┌──────────┐                  │
│  │  应用层   │ ──依赖──→      │  应用层   │ ──依赖──→        │
│  └──────────┘                 └──────────┘                  │
│       ↓                              ↓                      │
│  ┌──────────┐                 ┌──────────┐                  │
│  │  领域层   │                 │  领域层   │ ←─── 接口定义    │
│  └──────────┘                 └──────────┘                  │
│       ↓                              ↑                      │
│  ┌──────────┐                 ┌──────────┐                  │
│  │基础设施层  │                 │基础设施层 │ ─── 实现接口    │
│  └──────────┘                 └──────────┘                  │
└──────────────────────────────────────────────────────────────┘
```

**关键区别**：
- **传统分层**：依赖方向向下，领域层被基础设施层"污染"
- **六边形架构**：领域层定义接口（端口），基础设施层实现接口（适配器），依赖方向**指向领域层**

**设计决策**：
1. 所有业务逻辑必须写在 `domain/` 中，基础设施层只做"翻译"（适配）
2. 领域层**不导入**任何基础设施层的代码（`infrastructure/` 不可见）
3. 领域层通过端口接口（`domain/port/`）声明需要什么，由基础设施层提供

---

## 第二部分：目录职责边界（严格执行）

### 2.1 `domain/` — 领域层（业务逻辑核心）

**身份标识**：这是系统的"大脑"，所有业务规则都写在这里。

**放入什么**：
- 聚合根（Aggregate Root）：`Battle` 是唯一的聚合根
- 实体（Entity）：`Participant` 是实体，有唯一标识和生命周期
- 值对象（Value Object）：`Health`, `Energy`, `Side`, `Speed`, `TurnNumber`, `BattleId`
- 领域服务（Domain Service）：跨聚合的业务逻辑，如 `BattleDomainService`
- 领域事件（Domain Event）：`BattleStarted`, `BattleEnded`, `TurnExecuted`
- 领域异常（Domain Exception）：`BattleException`, `SkillException`
- 端口接口（Port）：`ILogger`, `IStorage`, `IDomainEventBus`
- 仓储接口（Repository）：`IBattleRepository`
- 领域工厂：`BattleFactory`, `ParticipantFactory`

**禁止放入**：
- ❌ Vue 组件或任何 UI 相关代码
- ❌ HTTP 请求、数据库操作（这些应该在 `infrastructure/`）
- ❌ 日志具体实现（只能依赖 `ILogger` 接口）
- ❌ 框架相关代码（Vue、Pinia、mitt）

**正确示例**：
```typescript
// domain/battle/aggregate/Battle.ts
import { ILogger } from '@/domain/port/logging/ILogger'  // ✅ 依赖接口
// import { BattleLogManager } from '@/infrastructure/...'  // ❌ 禁止！
```

### 2.2 `application/` — 应用层（用例协调）

**身份标识**：这是系统的"调度中心"，负责编排领域对象完成用户用例。

**放入什么**：
- 门面（Facade）：`BattleFacade` — 对外统一入口
- 命令（Command）：`StartBattleCommand`, `ExecuteTurnCommand` — 写操作
- 命令处理器（Command Handler）：`StartBattleHandler` — 执行写操作
- 查询（Query）：`GetBattleStateQuery` — 读操作
- 查询处理器（Query Handler）：`GetBattleStateHandler` — 执行读操作
- DTO（Data Transfer Object）：`BattleStateDto`, `ParticipantDto`
- DTO映射器（Mapper）：`ParticipantMapper`, `BattleStateMapper`
- 应用事件（Application Event）：`BattleStartedEvent`, `TurnExecutedEvent` — 通知UI

**禁止放入**：
- ❌ 业务规则（应该在 `domain/`）
- ❌ 基础设施具体实现（应该在 `infrastructure/`）
- ❌ 值对象和实体（应该在 `domain/`）

```typescript

    // 4. 不包含业务规则判断
  }

```

## 第三部分：类型系统规则（防止类型混淆）

### 3.1 类型三层分类

| 类型层级 | 位置 | 特征 | 示例 |
|---------|------|------|------|
| **领域类型** | `domain/kernel/value-objects/` | 不可变，有业务行为 | `Health`, `Energy`, `Side` |
| **领域实体** | `domain/**/entity/` | 有标识，可变 | `Participant` |
| **领域接口** | `domain/**/interfaces/` | 领域层定义 | `IStrategyManager` |
| **应用DTO** | `application/dto/` | 扁平结构，仅数据传输 | `ParticipantDto` |
| **共享类型** | `shared/types/` | 纯数据结构，无行为 | `ConfigSchema`, `EventTypes` |

### 3.2 转换关系图

```
┌─────────────────────────────────────────────────────────────────┐
│ 外部输入（JSON/UI）                                            │
│   ↓ 反序列化                                                   │
│ shared/types/ConfigSchema  (原始数据)                         │
│   ↓ Mapper                                                     │
│ domain/kernel/value-objects/Health  (领域值对象)              │
│   ↓ 业务逻辑处理                                               │
│ domain/battle/aggregate/Battle  (聚合根)                      │
│   ↓ Mapper                                                     │
│ application/dto/BattleStateDto  (输出给UI)                    │
│   ↓ 序列化                                                     │
│ 外部输出（JSON/UI）                                            │
└─────────────────────────────────────────────────────────────────┘
```

### 3.3 禁止混用的规则

| ❌ 错误做法 | ✅ 正确做法 |
|------------|------------|
| `domain/battle/` 直接返回 `shared/types/` 中的类型 | 领域方法返回领域类型，在应用层转换为DTO |
| `application/dto/` 中定义业务方法 | DTO只包含数据，业务方法在领域层 |
| `presentation/` 直接使用 `domain/kernel/value-objects/` | 通过 `application/dto/` 获取数据 |
| `infrastructure/` 直接使用领域值对象 | 适配器内部转换，对外只使用基础类型 |

### 4.2 聚合根设计原则

1. **唯一入口**：对 `Battle` 内部状态的修改必须通过 `Battle` 的方法
2. **不变性**：状态变更返回新的 `BattleState`，不修改原有状态
3. **事务边界**：一次方法调用代表一个完整的事务
4. **引用完整性**：外部不能持有 `Participant` 的引用，必须通过 `Battle` 获取

```typescript
// ✅ 正确：通过聚合根方法修改状态
const battle = Battle.start(allies, enemies)
const result = battle.executeTurn()  // 内部修改状态
const state = battle.getState()

// ❌ 错误：外部直接修改参与者
const participant = battle.getParticipant('p1')
participant.health = Health.of(50)  // 不允许！
```

## 第五部分：值对象设计规则

### 5.1 值对象 vs 实体

| 特征 | 值对象 | 实体 |
|------|--------|------|
| 标识 | 无独立标识，由值决定 | 有唯一标识（ID） |
| 可变性 | 不可变 | 可变 |
| 相等性 | 所有属性相等即相等 | 标识相等即相等 |
| 生命周期 | 依附于实体 | 独立生命周期 |

### 5.2 值对象模板

```typescript
// domain/kernel/value-objects/Health.ts
export class Health {
  // 1. 私有构造函数
  private constructor(private readonly _value: number) {
    // 2. 不变量验证
    if (_value < 0) throw new DomainException('Health cannot be negative')
    if (!Number.isFinite(_value)) throw new DomainException('Health must be finite')
  }

  // 3. 工厂方法
  static of(value: number): Health {
    return new Health(Math.max(0, value))
  }

  static zero(): Health {
    return new Health(0)
  }

  // 4. Getter（只读）
  get value(): number { return this._value }

  // 5. 操作方法（返回新实例）
  add(amount: number): Health {
    return new Health(this._value + amount)
  }

  subtract(amount: number): Health {
    return new Health(Math.max(0, this._value - amount))
  }

  // 6. 判断方法
  isZero(): boolean { return this._value === 0 }
  isLessThan(other: Health): boolean { return this._value < other._value }
  isGreaterThan(other: Health): boolean { return this._value > other._value }

  // 7. 相等性
  equals(other: Health): boolean {
    return this._value === other._value
  }

  // 8. 序列化
  toNumber(): number { return this._value }
}
```

### 5.3 值对象使用规则

```typescript
// ✅ 正确：使用工厂方法创建
const health = Health.of(100)
const newHealth = health.subtract(30)

// ✅ 正确：通过聚合根方法传递值对象
battle.takeDamage(participantId, Damage.of(50))

// ❌ 错误：直接 new
const health = new Health(100)  // 构造函数是私有的

// ❌ 错误：修改值对象
health._value = 80  // 不可变，没有setter
```

### 6.2 事件发布规则

### 10.1 新聚合根模板

```typescript

import { IAggregateRoot } from '@/domain/kernel/interfaces/IAggregateRoot'
import { BattleId } from '@/domain/kernel/value-objects/BattleId'
import { ILogger } from '@/domain/port/logging/ILogger'
import { IDomainEventBus } from '@/domain/port/event/IDomainEventBus'

export class Battle implements IAggregateRoot {
  // 1. 私有只读属性（值对象）
  private readonly _id: BattleId

  // 2. 可变状态（由聚合根管理）
  private _state: BattleState

  // 3. 依赖（通过构造函数注入）
  private readonly _logger: ILogger
  private readonly _eventBus: IDomainEventBus

  // 4. 私有构造函数
  private constructor(
    id: BattleId,
    initialState: BattleState,

    eventBus: IDomainEventBus

    this._id = id
    this._state = initialState

  static start(

    enemies: Participant[],
    rules: BattleRules,
    logger: ILogger,
    eventBus: IDomainEventBus
  ): Battle {

    const id = BattleId.generate()
    const state = BattleState.create(id, allies, enemies, rules)

    const battle = new Battle(id, state, logger, eventBus)

    // 发布领域事件
    battle._eventBus.publish(new BattleStartedEvent(id))

    return battle
  }

  // 6. 公共方法（修改状态）
  executeTurn(): TurnResult {
    // 业务逻辑
    // ...
  }

  // 7. Getter（只读访问）
  get id(): BattleId { return this._id }
  get state(): BattleState { return this._state }
  get status(): BattleStatus { return this._state.status }

  // 8. 私有方法（内部辅助）
  private validateState(): void {
    // ...
  }
}
```
