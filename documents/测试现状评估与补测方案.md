### 缺口（按风险排序）

1. **SkillExecutor 覆盖极薄** — `SkillExecutor.test.ts` 仅 2 个 gainEnergy 用例。该类有 15 个步骤分支 + 10 个 customType 分支（`src/domain/skill/SkillExecutor.ts:112-160,555-624`），其中大量"消耗型语义"与"状态机"逻辑零测试：必中/必暴标记消耗、引爆换算、轮转下标推进、净化计数语义、弹射概率合成。这是引擎里状态最多的一层，回归风险最高。
2. **投影层零测试** — `BattleProjection.ts` / `participantMapper.ts` / `UIParticipantSnapshot` 在 tests/ 全文检索零命中。组件统一从快照读数据，映射错一个字段（如 perStack 透传、除零守卫）就是全 UI 显示错误，且无人报警。
3. **skills→buffs 引用一致性无回归锁** — 实测脚本验证：8 个技能 JSON 中 60 处 `"buffId"` 引用 + SkillExecutor 硬编码常量，去重共 44 个 buffId，**当前全部存在于 `configs/buffs/buffs.json`（142 条），零断链**。但这个状态没有任何测试保护，改配置时随时可能引入断链（引擎侧 `executeBuff` 对未知 buffId 的行为依赖 `addBuff` 合并链，坏数据会静默或运行期抛错）。
4. **Buff 叠加边界未穷尽** — 现有测试覆盖了三种 stackRule 主干，但未覆盖：LIMITED 满层刷新分支（`BuffSystem.ts:564-588`，含 `_stacks` 变量同步与 effectPlan 校准）、旧版多实例清理（`:560-562`）、INDEPENDENT 默认上限 10（`:623`）、免疫返回 `''`（`:522-544`）——最后这个尤其关键，SkillExecutor 的 shield/control/overflow_shield 都有 `instanceId 为空` 的 WARN 分支在等它。
5. 杂项：根目录有游离 `tmp-closed-loop.test.ts`，不在 vitest include（`vite.config.ts:31-36` 只收 `tests/**`）范围内，属遗留垃圾，建议确认后删除。

## 二、补测方案（按风险×成本排序）

落地方式全部使用现有 Vitest（`npm run test`），参与者构造复用 `tests/factories/ParticipantFactory.ts` 与 `tests/fixtures/loadTestData.ts`，不引入新框架、不新增依赖。

### T1（P0）configs 引用一致性校验测试

**目标**：把"44/44 引用零断链"的现状锁进回归测试，配置改坏时 CI 报警。

**落地**：新建 `tests/unit/config-cross-refs.test.ts`（fs 读 configs/ 目录，非 fixture 快照——直接校验入库数据）。

**用例设计**：
- 正常：skills/*.json 全部 steps 的 `buffId`/`effectId`、`parameters.buffIds[]`、customParams 的 `applyBuffId` ∈ buffs.json id 集合。
- 正常：buffs.json 内部交叉引用（effects/triggers 参数里出现的 buffId）也已注册。
- 正常：SkillExecutor/`KNOWN_BUFF_IDS` 硬编码的 buff 常量（`buff_tianwang`/`buff_fengzhu`/`buff_liejia`/`buff_suijia`/`buff_fengsuo`/`buff_shield` 等，`SkillExecutor.ts:761-792,818,921,1007`）逐个存在于 buffs.json——代码引用的 id 断链比 JSON 断链更隐蔽。
- 边界：同一 id 多处引用去重后只报一条错误（校验器输出可读性）。
- 异常：内存构造缺引用的技能对象，断言校验函数报出"引用 X 不存在"（校验逻辑本身要有负例，不然它永远不会红）。

### T2（P0）SkillExecutor 步骤执行覆盖

**目标**：覆盖有状态分支与消耗语义，异常路径抛错行为锁定。

**落地**：扩展 `tests/unit/core/skill/SkillExecutor.test.ts`，按步骤组拆 2-3 个文件（executor-steps / executor-custom）。damage/heal 主干已由 T 已有测试覆盖，本项聚焦 executor 自身的编排逻辑。

**用例设计**（每条对源码行号）：
- **必中/必暴消耗**：命中带 `GUARANTEED_CRIT` 的来源打完 deal_damage 步骤后实例被移除（`SkillExecutor.ts:216-225`）；多步技能第二步不再必暴；`GUARANTEED_HIT` 首个伤害步骤后消耗（`:227-234`）。
- **cleanse / remove_debuff 计数语义**：remove_debuff 缺省只移除 1 个且仅 polarity=negative；cleanse 缺省移除全部（count=999）；polarity 缺失的 buff 不算减益不被 remove_debuff 命中（`:461-475`）。
- **轮转施加**：`buffIds=[A,B]` 三连发依次 A→B→A；目标免疫（addBuff 返回 ''）时下标照样前进；`stacks=3` 时首层走管线 + 补 2 次 LIMITED 叠层；空 buffIds 静默返回（`:640-681`）。
- **引爆三连**：fengshi N 层 → `round(attack×0.1×N)` + `floor(N/2)` 层裂甲转化 + 全部风势消耗；无层数时只产 STATUS 提示；风痕段数上限 `fenghenMaxSegments`（`:809-901`）。liejia 同构，`maxSegments=8` 封顶真实伤害段数（`:911-974`）。burn_detonate：full 变体 ×2 倍率且移除灼烧，非 full 只结算不移除（`:1050-1097`）。
- **fengsuo_bounce 概率合成**：速度差每 10 点 +5%；天网 +20% 且伤害 ×1.3、上限随之抬升到 `maxProbability+0.2`；风逐概率翻倍并消耗 1 层；rng 注入固定种子验证触发/不触发两侧（`:742-800`）。
- **异常路径**：未知 `step.type` 抛 `[SkillExecutor] 未实现的技能步骤类型`；未知 customType 抛对应错误（`:154-159,619-623`）——这两条 throw 是数据校验之外的最后防线。
- **状态卫生**：`clearAllRotatingStates`/`clearAllComboStates` 后轮转从下标 0 重来、连击计数清零（跨局战斗不残留，`:86-103`）。
- **延迟模式**：`context.token` 存在时不直接 `applyDamage`，伤害记入 token 且 `action.damage` 累加（`:186-198`）。

### T3（P1）投影层快照一致性

**目标**：participantMapper 纯函数语义 + BattleProjection 批处理/版本语义零回归。

**落地**：新建 `tests/unit/core/projection/participantMapper.test.ts` 与 `battle-projection.test.ts`（store 用裸 `Map` mock 即可，无 Vue 依赖，environment 保持 node）。

**用例设计**：
- participantMapper：`maxHp=0` → `healthPercent=0` 非 NaN（`participantMapper.ts:60`）；shield 读 `buffSystem.getShieldValue`；实例已被 BuffSystem 移除但 `getBuffInstanceIds` 残留 → 跳过不崩（`:96-97`）；`perStack=false` 修饰符透传到 attributes（`:119-121`）。
- BattleProjection：同一 tick 多次 `markDirty` → microtask 合并只 flush 一次；`statsVersion` 未变 → 跳过写入（`BattleProjection.ts:143`）；首次写入走 `set`、后续 `Object.assign` 就地更新保持引用（reactive 契约，`:151-157`）；mapper 抛错被 try/catch 吞掉且不影响其余参与者（`:158-160`）。
- 端到端一致性（与 BuffSystem 真实例）：施加 3 层 LIMITED buff → 快照 `buffs[].currentStacks===3`、`remainingTurns` 与 BuffSystem 实值一致——这是"UI 显示 = 引擎真值"的核心契约。

### T4（P1）Buff 叠加/过期边界补穷尽

**目标**：补现有 BuffSystem 测试未覆盖的分支。**先读 `BuffSystem.test.ts`/`BuffSystemLifecycle.test.ts` 现有用例标题去重，只做增量。**

**落地**：扩展 `tests/unit/core/buff/` 现有文件。

**用例设计**（对应 `BuffSystem.ts` 行号）：
- LIMITED 满层：`currentStacks==maxStacks` 时 addBuff → 层数不变、持续时间刷新、`context.variables._stacks` 同步为 maxStacks、effectPlan `onStackChange` 被以满层值调用（`:564-588`）。
- LIMITED 旧版多实例清理：手工塞 2 个同 buffId 实例再 addBuff → 只剩 1 个实例且层数+1（`:559-562`）。
- INDEPENDENT 达上限返回 `''` 且不新增实例；`maxStacks:0` 不被 falsy 回退吞掉（`??` 语义，`:620-627`）。
- 免疫三通道：controlType 免疫 / buffId 免疫 / tag 免疫各自返回 `''`（`:522-544`）；串联验证 SkillExecutor.executeShield 拿到空 id 时不产 effect（跨层契约）。
- 过期时序：`duration>0 且 remainingTurns 从 1 → 0` 精确移除一次（不双减）；`duration=-1` 永久不递减（`:1086-1087`）。

### T5（P2）e2e 全战斗冒烟

**目标**：真实 configs 全量数据跑完整战斗不抛错，兜住单测盲区（步骤组合序列）。

**落地**：扩展 `tests/e2e/BattleE2E.test.ts` 或新增 smoke 文件。

**用例设计**：
- 正常：注入完整 xiyou 技能/buff 配置，固定种子 rng 跑 ≥20 回合，断言无异常、每步 `damageBreakdown.steps` 的 before→after 链自洽（复用 DamageCalculator.test 已有的链校验思路）。
- 边界：同种子两次回放结果逐位一致（确定性契约——rng 注入点回归）。
- 异常：配置引用断链时（内存注入）引擎抛错信息可定位（与 T1 双保险）。
