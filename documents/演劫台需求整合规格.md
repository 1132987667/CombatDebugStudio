## 1. 整合前提与原则

### 1.1 已拍板决策

| 决策 | 结论 | 含义 |
| --- | --- | --- |
| 整合性质 | **需求/设计层面** | 吸收系统设计，不迁移 SOLO-DEMO 代码 |
| 题材与战斗形态 | **以封神榜为主** | 五行 5 元素、4v4 队伍+阵型；SOLO-DEMO 的 8 元素/单人回合制**不沿用** |
| 数值框架 | **沿用已拍板框架** | 五行攻击归并、五行抗性保留、独立乘区连乘、无等级压制、乘区注册表等 |

### 1.2 整合原则

1. **引擎不重建**：战斗公式/技能/AI/元素矩阵/Buff 在 CombatDebugStudio 已完整实现，SOLO-DEMO 的战斗类需求只做"验证与补齐"，不做二次开发。
2. **数据域复用**：敌人/场景/阵型/技能/Buff/材料/装备已入封神榜数据域（IndexedDB 14 store），演劫台只消费，不重复建模。
3. **新增集中在"成长与经营"**：演劫台真正要新建的是 SOLO-DEMO 已验证的成长循环、养成、剧情、内容系统。
4. **吸收教训**：SOLO-DEMO 最大的失败是"数据先行、链路断裂"——每张需求单强制带验收标准，杜绝同款事故。
5. **归一而非照搬**：SOLO-DEMO 的单人/8 元素/六属性模型全部归一化到封神榜的 4v4/五行/扁平属性体系。

### 1.3 每张需求单的字段说明

每条演劫台需求含：**所属模块 / SOLO-DEMO 现状差距（含文件证据）/ 演劫台落地方案 / 涉及现有资产 / 验收标准 / 依赖 / 优先级**。
优先级：P0（断链必做）/ P1（数值对齐）/ P2（系统完善）/ P3（内容扩展）。

## 3. 成长模块需求逐条

### R01 轮回/飞升/天赋悬空调用修复

- **所属模块**：成长循环（store 层）
- **SOLO-DEMO 现状差距**：十余处 dispatch/commit 指向不存在的 mutation/action——
  - `reincarnation.js:350` → `player/resetPlayer`（不存在）；
  - `ascension.js:368-394` → `player/resetPlayerForAscension`、`combat/resetBattleRecords`、`cultivation/resetCultivation`、`homebase/resetHomebase`、`reincarnation/resetReincarnationForAscension`（均不存在）；
  - `ReincarnationView.vue:187-202` → `reincarnation/INCREMENT_COUNT`、`player/RESET_PLAYER`（均不存在）；
  - `AscensionView.vue:153-168` → `ascension/INCREMENT_COUNT`、`player/RESET_PLAYER_FOR_ASCENSION`（均不存在）；
  - `talent.js:196-198` → `ADD_TALENT_POINT`（不存在）；视图读 `talentPoints/totalTalentPoints` 字段恒 undefined。
  - 后果：任何一次轮回/飞升/天赋操作都会抛 Vuex 错误，功能不可用。
- **演劫台落地方案**：演劫台从零设计成长 store（DDD 应用层用例编排），**不复制 SOLO-DEMO 的实现**，但在设计阶段就把"重置"抽象为领域服务（`ReincarnationService`/`AscensionService`），统一处理"保留什么/重置什么"，杜绝悬空调用。重置边界按数值框架 D4 子系统占比定义。
- **涉及现有资产**：无直接复用；参考封神榜数据域（灵蕴之魂/本源之魂资源）。
- **验收标准**：演劫台执行"轮回/飞升"不报错；重置后队伍等级回退、保留资源按配置；`npm run typecheck` 通过、无未定义 action 引用。
- **依赖**：无。
- **优先级**：P0。

### R20 境界突破奖励对齐

- **所属模块**：成长循环（境界）
- **SOLO-DEMO 现状差距**：`player.js:383-399` `ADVANCE_REALM` 每境界只给体魄/根骨/灵蕴各 +5，与 `player_attribute_plan.md:49-68` 要求的递增奖励表（15/15/15/20/20/20/25/25/25/30/30/30/35/35/35，高境界含神识/机敏）完全不符。
- **演劫台落地方案**：演劫台境界归一到封神榜 5 阶 10 境界（数值框架 §2.2），奖励表存封神榜 `params` 数据域（`realm_rewards`），每境界奖励 = 指定角色基础属性点 + 解锁内容（技能/洞天建筑/地图）。数值表重定（见 §13 Q2）。
- **涉及现有资产**：`src/domain/character/types.ts`（角色）、`configs/params/`。
- **验收标准**：境界推进按奖励表真实发放；奖励配置在封神榜可编辑，改配置不重启生效。
- **依赖**：封神榜 params 域已就绪。
- **优先级**：P1。

### R21 命数突破消耗宝物

- **所属模块**：成长循环（境界/命数）
- **SOLO-DEMO 现状差距**：`player.js:473-484` 只检查 `level >= maxLevel` 即突破，无"对应宝物"校验（代码注释自认简化）；突破后 `保留所有属性`（`:325-327`），与"重置"语义矛盾。
- **演劫台落地方案**：**演劫台将命数并入境界**（不单设命数，避免双重置叠加）。境界突破需要：等级达标 + 消耗宝物（天道之气/混沌本源，来自封神榜 materials 域）+ 完成突破条件。突破后按配置重置/保留属性。
- **涉及现有资产**：`configs/materials/materials.json`（天道之气/混沌本源待补）、`src/domain/character/types.ts`。
- **验收标准**：突破按钮在资源不足时禁用；突破后资源真实扣除、属性按配置处理。
- **依赖**：R20（境界结构）。
- **优先级**：P1。

### R27 逆轮溯真奖励对齐

- **所属模块**：成长循环（轮回）
- **SOLO-DEMO 现状差距**：视图公式 `(count+currentFloor)*pow(1.1,level)` 引用不存在的字段 → 计算结果 `NaN`；全属性加成硬编码 5%（策划为 1%）；等级属性增幅 +4% 未实现；传家宝 `availableItems` 从未填充。
- **演劫台落地方案**：归一为"**小队轮回**"（作用于整个队伍而非单人）。灵蕴公式数据化到 `params` 域（`(轮回次数+最高关卡)×1.1^轮回等级×难度系数`）；全队全属性 +1% 与等级增幅 +4% 作为持久 modifier 注入（复用 ParticipantStats 修饰符管线）；传家宝系统（带 1 件装备跨世，等级重置词条保留）纳入装备模块。
- **涉及现有资产**：`ParticipantStats`（修饰符注入）、`configs/params/`、封神榜装备域。
- **验收标准**：轮回后全队属性出现 +1% 修饰符且可溯源；传家宝装备跨世保留词条。
- **依赖**：R01（重置服务）、R05（装备穿戴）。
- **优先级**：P2。

### R28 万象归墟效果落地

- **所属模块**：成长循环（飞升）
- **SOLO-DEMO 现状差距**：`attributeConversion:1.0`、`itemDropRate:2.0` 定义但全项目无使用；继承 reset 调用全部悬空。
- **演劫台落地方案**：归一为"**飞升**"——保留洞天/功法/轮回材料，队伍基础属性按配置转为核心属性倍率提升、物品获取翻倍。属性转化作为持久 modifier，掉落倍率进战斗规则参数（`params` 域）。
- **涉及现有资产**：`DamageCalculator`（掉落/参数消费点）、`configs/params/`、`application/projection/`。
- **验收标准**：飞升后属性转化/掉落翻倍真实生效；昊天镜能追溯飞升前的快照。
- **依赖**：R01。
- **优先级**：P2。

### R29 天赋点数机制 + 效果接线

- **所属模块**：成长循环（天赋）
- **SOLO-DEMO 现状差距**：`ADD_TALENT_POINT` mutation 不存在；视图读 `talentPoints/totalTalentPoints` 恒 undefined；天赋学习消耗 `reincarnationPoints`（错误货币）；`core_attribute_bonus`（气血/攻击+10%）类型天赋无消费方——player.js 只应用了 `attribute_bonus`。
- **演劫台落地方案**：每角色天赋盘，天赋点来自等级/任务（封神榜配置）；天赋效果分两类——`attribute_bonus`（基础属性）与 `core_attribute_bonus`（核心属性 %，走独立乘区）。天赋效果经 ParticipantStats 修饰符管线统一生效，天赋前置检查（prerequisites）在应用层校验。
- **涉及现有资产**：`ParticipantStats`、`ModifierType`（独立乘区连乘已拍板）、`src/domain/attribute/types.ts`。
- **验收标准**：天赋点可获取、可消耗；两类天赋效果作用于属性计算并可追溯；前置天赋未学时不可学。
- **依赖**：R01。
- **优先级**：P2。

### R31 角色属性分配 UI

- **所属模块**：成长循环（角色）
- **SOLO-DEMO 现状差距**：`CharacterView.vue:376-379` "属性分配"按钮仅 `console.log`，自由属性点无法分配；`ALLOCATE_ATTRIBUTE_POINT`（`player.js:355-361`）有 mutation 但无 UI 入口。
- **演劫台落地方案**：演劫台角色面板提供"自由属性点分配"，分配到基础属性（走扁平属性体系，非六基础属性模型）。分配即调用应用层用例，实时触发属性重算（ParticipantStats 版本戳机制）。
- **涉及现有资产**：`ParticipantStats`、`presentation/modules/huanling/components/CharacterEditor.vue`（参照）。
- **验收标准**：可分配/回收自由属性点，核心属性实时变化并可见。
- **依赖**：无。
- **优先级**：P2。

### R32 队伍系统（多角色出战）

- **所属模块**：成长循环（队伍）
- **SOLO-DEMO 现状差距**：`TeamView.vue:115-200` 硬编码 2 人（主角+剑灵），与 store 无关联；`maxMembers:5` 但与战斗无衔接；战斗全程单人 player 模块。
- **演劫台落地方案**：**演劫台复用 CombatDebugStudio 现有 4v4 队伍体系**——`configs/formations`（阵型）+ `configs/lineups`（预设阵容）+ `enemyToParticipant` 转换。队伍养成 = 每个上阵角色独立等级/属性/装备（guardian 五人组原型）。SOLO-DEMO 的"多角色独立养成"需求已由现有阵容体系覆盖，演劫台只需补"养成界面"与"战斗结算联动"。
- **涉及现有资产**：`configs/formations`、`configs/lineups`、`GameDataProcessor.enemyToParticipant`、`application/projection/participantMapper`。
- **验收标准**：可编成 4 人阵容上阵；战斗按阵容全员行动；战后全员获得经验；角色独立成长。
- **依赖**：无（引擎已就绪）。
- **优先级**：P2。

## 4. 装备模块需求逐条

### R05 装备穿戴链路闭合 + 槽位数据对齐

- **所属模块**：装备
- **SOLO-DEMO 现状差距**：
  - `inventory.js:548-594` `EQUIP_ITEM` 唯一调用方是开发者面板（`DeveloperPanel.vue:1188`），正常 UI 无法穿戴装备；
  - `items.json` 的 slot（gloves/belt/necklace/ring）与 6 槽位定义（weapon/armor/helmet/boots/charm/ring）互不匹配；
  - `InventoryView.vue` 无"穿戴"按钮，玩家正常流程无法穿装备。
- **演劫台落地方案**：基于封神榜 equipment 域（已从材料剥离，含 slot/stats/requiredLevel）。槽位为 6 类：武器 / 衣服 / 头盔 / 靴子 / 护符 / 戒指，另法宝、神器为独立类型（不占槽位）。装备穿戴 = 将装备 stats 转 Modifier（`sourceType: 'equipment'`）并入角色属性堆栈（复用 Buff 合并管线），脱换即增删修饰符。槽位以封神榜 equipment 域为准。
- **涉及现有资产**：封神榜 equipment store、`ParticipantStats`、`ModifierSourceType.EQUIPMENT`、`CharacterEditor.vue`（参照）。
- **验收标准**：背包对可穿戴物品显示"穿戴"，穿卸属性实时重算；槽位与装备数据 slot 一致。
- **依赖**：封神榜 equipment 域已剥离。
- **优先级**：P0。

### R13 装备品质系统 8 阶 + 属性范围 40%-120%

- **所属模块**：装备
- **SOLO-DEMO 现状差距**：`equipmentGenerator.js:15-21` 仅 5 阶（普通/魔法/稀有/史诗/传说），无白绿蓝紫橙红金彩；`quality` 字段不参与 `calculateBaseStats`（`equipmentGenerator.js:255-292`），同等级白装与橙装基础属性相同；策划要求的 40%-120% 属性范围完全缺席。
- **演劫台落地方案**：封神榜 equipment 域补 `quality`（1-8）字段；品质影响基础属性乘区（40%~120%，每阶 +~10-20%）与词条数量。品质范围由 schema 校验（封神榜数值范围约束）。
- **涉及现有资产**：封神榜 equipment store + FieldSchema、`configs/params/`。
- **验收标准**：同等级不同品质基础属性不同；品质 8 阶生成；越界品质被 schema 拒绝。
- **依赖**：R05。
- **优先级**：P1。

### R14 词条库对齐策划案 §4.3

- **所属模块**：装备

## 12. 开发路线与验收

| 阶段 | 内容 | 吸收需求 | 验收（闭环） |

3. 数值一处定义——境界/轮回/洗练奖励全走封神榜配置，不写死在组件；
4. 数据引用完整性——所有新增域走健康检查，杜绝乱码 id。

## 一句话总结

> **演劫台 = CombatDebugStudio 引擎（4v4/五行/已拍板数值）× 封神榜数据域（消费）× SOLO-DEMO 系统设计（成长/装备/经营/剧情四层玩法，40 需求逐条归一）。**
> 不迁移 SOLO-DEMO 代码；吸收系统设计、玩法结构与"链路断裂"教训；每张需求单带验收标准，逐阶段闭环落地。
