## §0 背景：一场没有赢家的辩论

团队就"调试系统与回放系统谁包含谁"展开辩论，双方论据如下：

| | 正方（调试包含回放） | 反方（回放包含调试） |
|---|---|---|
| **最强论据** | 调试日志有因果链（`steps`、`correlationId`），回放只有结果 | 回放有快照/种子/校验，是完整的可执行存档 |
| **致命伤** | 没有根——缺快照，跳转要重放全程；缺种子，无法重建随机 | 没有核——`events` 只有最终状态，追问「为什么」时哑口无言 |
| **本质** | 追求「可解释性」 | 追求「可重建性」 |

**裁决结论：不选边。** 双方都抓住了对方的致命弱点，正说明辩题是伪命题——两个能力都重要、都缺一不可，而当前实现却在**同一个战斗实例上维护两套完全不同的事件格式**。正确做法不是"谁包含谁"，而是**合并为一套结构化领域事件（Unified Battle Event Stream），作为唯一事实来源**；回放与调试是同一数据源的两个视图（Projection），正如 `BattleProjection` 之于领域实体。

## §1 现状盘点（事实）

### 1.1 同一场战斗，两份事件序列

`RecordedBattle`（`BattleRecorder.ts:48`）是当前唯一存档，同时装着两套事件：

```
RecordedBattle
├── events: ReplayBattleEvent[]   ← 轻量，只有结果，供回放（BattleReplay.vue 自带播放循环）
├── rounds, initialState, randomSeed, checksum  ← 回放核心资产
└── traceEvents?: TraceEvent[]    ← 重量，有因果链，仅供导出序列化（无消费方，见 §1.2 注记②）
```

> **v1.1 现状注记**：`RecordedBattle` 定义于 `BattleRecorder.ts:48-103`（v1.0 未注明位置，修订明确）。`rounds` 数组实际从不被 push（`BattleRecorder.ts:216-226` 的写入分支因无 `rounds.push` 而不生效），`recording.initialState` 与 `BattleReplay.initialState`（`BattleStateSnapshot`）形状不一致且均零读取方——见 §1.4 事实 4。

同一动作的两副面孔：

```ts
// ReplayBattleEvent（types.ts:876）—— 有结果，无过程
{ eventId: 'event_...', type: 'action', turn: 3, roundNumber: 2, timestamp: Date.now(),
  data: { action: { damage: 85 }, category: 'damage', severity: 'low' } }

// TraceEvent（trace-event.ts:70）—— 有过程，无快照锚点
{ id: 'evt_N', correlationId: 'corr_3_5', phase: 'damage_calculation',
  payload: { steps: [{ stepName: 'base', before: 0, after: 100 },
                     { stepName: 'defense', before: 100, after: 85 }] },
  summary: '伤害计算 剑士→史莱姆 100→85' }
```

### 1.2 双格式的四个具体不一致

| # | 不一致 | 位置 | 后果 |
|---|--------|------|------|
| 1 | **两套枚举并行**：`ReplayBattleEvent.type`（`BattleEventType`）与 `TraceEvent.phase`（`TracePhase`）都描述"发生了什么"，语义重叠但各自演化 | `types.ts:858` / `trace-event.ts:12` | 一个事件类型要改两处，迟早分叉 |
| 2 | **两套时基**：`ReplayBattleEvent.timestamp = Date.now()`（绝对），`TraceEvent.timestamp = performance.now()`（战斗内相对） | `BattleRecorder.ts:530` / `trace-event.ts:127` | 无法直接对齐两份序列 |
| 3 | **派生逻辑重复**：`category`/`severity` 在录制时由 `deriveCategory/deriveSeverity` 从 `action.type` 猜出，而 `TraceEvent.level/phase` 已携带同义语义 | `BattleRecorder.ts:552-592` | 同一语义两个来源，改一处漏一处 |
| 4 | **消费割裂**：`ReplayEngine` 明确不消费 `traceEvents`（`ReplayEngine.ts:91` 注释）；回放面板只读 `events`，调试面板只读 `traceEvents` | — | 一个存档两套读取路径，少维护一处就静默失效 |

> **v1.1 现状注记**：上表行号经逐条核对（2026-08-01）全部精确。第 4 行需补充两点事实：① `ReplayEngine`/`BattleReplayManager`/`BattleFacade.startReplay` 整条链路**无任何调用方**（死代码），真实回放面板 `BattleReplay.vue` 自带播放循环直接消费 `RecordedBattle.events`；② 存档 `traceEvents` 字段（`BattleRecorder.ts:89`）由 `BattleSystem.endBattle`（`BattleSystem.ts:1196-1199`）写入，但**全仓库零读取方**——调试面板 `DebugLogDialog` 消费的是 `TraceEventCollector` 内存而非存档字段。因此"割裂"比 v1.0 描述的更严重：`traceEvents` 写入后即闲置，只有导出调试文件时才随 `RecordedBattle` 一起序列化。

### 1.3 已具备的合并基础

- `TraceEvent` 已携带 `id / correlationId / parentId / phase / battleId / turn / sourceId / targetId / timestamp / payload / summary / level`——**信息量最大的结构已经存在**，回放需要的只是补两个字段。
- `TracePhase` 已覆盖全部领域阶段（战斗生命周期、回合流转、行动执行、伤害/治疗计算、属性重算、Buff 生命周期/触发、被动触发、AI 决策、配置加载/校验），**足以承担事件类型语义**。
- 战斗结束时 `BattleSystem.endBattle` 已将 `traceEvents` 写入 `RecordedBattle`（`BattleSystem.ts:1196`）——统一存档的方向已有雏形。
- 调试日志改造文档 §7 P2 已规划"`TraceEvent[]` 写入 `RecordedBattle.traceEvents`"——本次方案将该方向推到底。

> **v1.1 现状注记**：① `TracePhase.BATTLE_LIFECYCLE` 虽已定义（`trace-event.ts:14`），但 **`battle_start` / `battle_end` 的 TraceEvent 尚不存在**——`BattleRecorder.startRecording`（`:180-189`）与 `endRecording`（`:368-377`）产生的仍是 `ReplayBattleEvent`（`type: 'battle_start'/'battle_end'`）。方案 P0 需新增这两个根事件的发射（见 §4.4 时基约定）。② `action_execution` 的 TraceEvent 目前仅携带 `{ controlMode }` 等极简 payload（`BattleExecutor.ts:205-218`），**不含伤害/治疗数值**——回放 UI 的"详情"展示需以 `damage_calculation` 子事件或 `summary` 为准（§5.1 已按此设计）。

## §2 目标与非目标

### 目标

1. **单一事实来源**：一套事件格式同时服务回放与调试，删除 `ReplayBattleEvent` 及其双格式同步负担。
2. **回放能力不降级**：快照跳转（事件级锚点）、随机种子（确定性重演）、校验和、版本兼容全部保留。
3. **调试能力不降级**：因果链（`correlationId`）、树状嵌套（`parentId`）、计算过程（`steps`）、五维过滤全部保留。
4. **一份文件两种能力**：用户下载一份存档，回放面板按时间轴播放，调试面板按因果树展开。

> **v1.1 现状注记（目标 2）**："快照跳转/随机种子/校验和"能力目前**只存在于死代码 `ReplayEngine` 中**（§1.4 事实 2），真实面板 `BattleReplay.vue` 只有事件级播放/帧跳转，无状态快照跳转。因此"能力不降级"的实际含义是：**不在本次改造中移除这些存档资产**（`initialState`/`rounds.startSnapshot`/`randomSeed`/`checksum` 保留在 `RecordedBattle`，§4.5），而非保障 `BattleReplay.vue` 具备完整快照跳转——后者是回放面板 v2 增强（§5.1 事件树项）。

### 非目标（YAGNI）

- **不做"回放时真正重演计算"**：现状回放消费端（`BattleReplay.vue` 自带播放循环；`ReplayEngine` 为死代码，见 §1.4 事实 2）只播放事件序列不执行计算，`randomSeed` 仅为存档资产。本方案保持该语义——`randomSeed` 字段保留在存档与根事件中，供未来真重演（`SeededRandom`）或跨战斗对比使用，但不重构回放为模拟器。
- **不新增第三套事件枚举 `type`**：用 `TracePhase` 承担事件类型语义（见 §4.2 决策 D2），消灭双枚举而非再造一个。
- **不做事件压缩/懒加载**：沿调试日志改造文档 §7 P3 后置，不并入本次。

## §3 目标架构

```
                     ┌─────────────────────────────────────────┐
                     │        RecordedBattle（唯一存档）         │
                     │  version / checksum / randomSeed        │
                     │  initialState / rounds（快照锚点）        │
                     │  combatRecords / result（战报）           │
                     │  events: TraceEvent[]  ★统一事件流        │
                     └──────────────────┬──────────────────────┘
                                        │
              ┌─────────────────────────┴─────────────────────────┐
              │                                                   │
   ┌──────────▼──────────┐                          ┌─────────────▼───────────┐
   │   回放面板（Projection 1）│                          │  调试面板（Projection 2）  │
   │ 按 timestamp 播放     │                          │ 按 correlationId 建树    │
   │ 按 snapshot 跳转      │                          │ 展开 payload.steps      │
   │ 按 phase 分类显示      │                          │ 按 phase/actor/level 过滤 │
   └─────────────────────┘                          └─────────────────────────┘
```

**两个面板消费同一份 `TraceEvent[]`，不再维护第二份事件序列。** 如同 `BattleProjection` 之于领域实体：领域实体是唯一事实来源，UI 各取所需的投影。

## §4 数据模型设计

### 4.1 以 TraceEvent 为基座扩展（决策 D1）

**不新建 `UnifiedBattleEvent` 接口**，而是扩展现有 `TraceEvent`。理由：

- `TraceEvent` 已具备因果链、树、payload、级别、战斗隔离等全部调试字段，信息量最大；
- 补两个字段即覆盖回放需求；新建第三套类型等于再造一份真相，重蹈双格式覆辙；
- 与调试日志改造文档的方向一致，无架构转向成本。

```ts
// src/shared/types/trace-event.ts（扩展后）

export interface TraceEvent {
  id: string
  /** 因果链 ID — 同一次行动的根（调试视图建树依据） */
  correlationId: string
  /** 父事件 ID — 树状嵌套 */
  parentId?: string
  /** 领域阶段 — 唯一事件类型语义（替代 ReplayBattleEvent.type） */
  phase: TracePhase
  battleId?: string
  turn?: number
  sourceId?: string
  targetId?: string
  /** 战斗内单调时基（performance.now()），battle_start 根事件为相对零点 */
  timestamp: number
  /** 结构化 payload — 按 phase 不同而不同（含计算 steps） */
  payload: Record<string, unknown>
  /** 人类可读摘要（仅扫读，不作程序输入） */
  summary: string
  level: TraceLevel

  // ---- ★ 本次新增：回放锚点 ----
  /** 事件发生后的状态增量（回放跳转锚点，仅关键节点携带） */
  snapshot?: StateDelta
  /** 随机种子（仅 battle_start 根事件携带，确定性重演用） */
  randomSeed?: string
}
```

### 4.2 不新增 type 字段（决策 D2）

裁决草案中的 `type: 'action' | 'turn_start' | 'buff_apply'` 语义**已由 `TracePhase` 全覆盖**，不另设枚举：

| 裁决草案 type 语义 | TracePhase 承担者 |
|---|---|
| `action` | `action_execution`（行动执行） |
| `turn_start` / `turn_end` | `turn_flow`（回合流转，payload.action 区分 start/end） |
| `buff_apply` / `buff_remove` / `buff_update` | `buff_lifecycle`（payload.action 区分施加/移除/刷新） |
| `battle_start` / `battle_end` | `battle_lifecycle` |
| 伤害/治疗详情 | `damage_calculation` / `heal_calculation`（作为行动节点的子节点） |

回放 UI 的图标、分类、过滤一律按 `phase` 派生（映射表见 §5.2）。`BattleEventType` 停止在新事件上使用，仅保留给旧数据兼容与 `addBattleLog` 战斗文本。

### 4.3 StateDelta：事件级增量快照（决策 D4）

```ts
/** 状态增量 — 只记录"本事件改变了什么"，全量由 initialState / rounds 快照兜底 */
export interface StateDelta {
  turn: number
  /** 变更参与者（仅列出发生变化的字段） */
  participants: Array<{
    id: string
    hp?: number            // 变更后的当前气血
    energy?: number        // 变更后的当前能量
    buffs?: Array<{ buffId: string; instanceId: string; stacks: number; remainingTurns: number }>
    stats?: Record<string, number>   // 关键属性快照（攻击/防御等，按需）
  }>
}
```

**锚点分层（跳转能力的分级保障）**：

| 层级 | 锚点 | 粒度 | 来源 |
|---|---|---|---|
| 全量锚点 | `initialState` + `rounds.startSnapshot/endSnapshot` | 回合级 | 既有机制，**保留不动** |
| 增量锚点 | 事件级 `snapshot?: StateDelta` | 行动级 | 本次新增，**可选字段**，关键节点（行动结算根事件）携带 |

跳转算法不变（`ReplayEngine` 现有"最近全量锚点 + 重放增量事件"模式——该算法目前仅存在于死代码 `ReplayEngine`，§1.4 事实 2；若 P2 删除死代码，此算法描述作为目标行为迁移到 `BattleReplay.vue` 或 v2 快照跳转）：事件级增量锚点只用于**提高跳转精度**，缺省时回退到回合级全量锚点，功能不降级。

### 4.4 时基统一（决策 D3）

- 事件流内统一 `performance.now()`（战斗内单调、可比、可排序）；
- 约定 **`battle_start` 根事件的 `timestamp` 为相对零点（0）**，后续事件为其毫秒偏移；
- 存档层保留 `RecordedBattle.startTime`（`Date.now()`）作为绝对时间基准，仅用于 UI 显示"战斗开始于几点几分"；
- 旧 `ReplayBattleEvent` 的 `Date.now()` 时基随其退役，不再处理。

> **v1.1 现状注记**：`createTraceEvent`（`trace-event.ts:121-129`）目前强制 `timestamp: performance.now()`，**无覆盖参数**。实现零点约定需在 P0 为 `TraceEventInput` 增加可选 `timestamp?` 字段（`battle_start` 传 `0`），或发射后改写。回放 UI 的 `formatTime`（`BattleReplay.vue:422-425`）当前用 `new Date(timestamp)` 格式化绝对时间，改造后需改为相对时基显示（如 `0:00.000` 格式）。

### 4.5 统一后的 RecordedBattle

```ts
export interface RecordedBattle {
  battleId: string
  replayId: string
  version: string               // ★ 版本号 +1
  randomSeed: string            // 权威字段（同时冗余写入 battle_start 根事件）
  startTime: number
  endTime?: number
  winner?: ParticipantSide
  /** ★ 唯一事件序列 — TraceEvent[]（原 events: ReplayBattleEvent[] 删除，traceEvents? 合并于此） */
  events: TraceEvent[]
  /** 初始状态快照（全量锚点，保留） */
  initialState: { participants: Array<BattleEntity> }
  /** 回合数据（startSnapshot/endSnapshot 保留；rounds.events 删除） */
  rounds: BattleRound[]
  /** 战报（统计用，与事件流无关，保留） */
  combatRecords: CombatRecord[]
  result?: BattleResult
  checksum?: string
  saveKey?: string
  reviveEvents?: ...
}
```

字段处置汇总：

| 字段 | 处置 | 理由 |
|---|---|---|
| `events: ReplayBattleEvent[]` | **删除**，替换为 `events: TraceEvent[]` | 统一事件流是唯一序列 |
| `traceEvents?: TraceEvent[]` | **合并入 `events`**（删除可选字段） | 两字段同类型并存即双真相 |
| `rounds.events` | **删除** | 事件序列唯一来源是 `events`，回合内事件由 `turn` 字段归属 |
| `rounds.startSnapshot/endSnapshot` | **保留** | 回合级全量快照锚点（§4.3） |
| `initialState` / `randomSeed` / `checksum` / `version` | **保留** | 回放核心资产 |
| `combatRecords` / `result` / `reviveEvents` | **保留** | 战报统计，独立于事件流 |

### 5.1 回放面板（BattleReplay.vue）

## §6 兼容与迁移策略

1. **版本号**：`BATTLE_REPLAY_VERSION`（`types.ts:696`，现为 `'1.0.0'`）+1 → `'2.0.0'`，新格式以版本号区分。

## §8 风险与权衡

| 风险 | 影响 | 缓解 |
|---|---|---|
| 事件流体积大于旧 `ReplayBattleEvent`（payload + steps） | 存档变大 | 增量 `snapshot` 可选；事件压缩/采样已后置 P3（调试日志改造文档） |
| `performance.now()` 时基无法跨战斗对齐 | 跨战斗对比只有相对时间 | 存档层保留 `startTime`（Date.now()）作绝对基准；对比场景本就是"按 correlationId 对齐"，不依赖时基 |
| 旧数据兼容路径长期残留 | 维护双分支 | 单仓库同步升级，一个迭代后按需删除兼容分支 |
| 回放 UI 分类表（§5.2）成为新维护点 | 一张表 vs 两套枚举 | 净收益：单点维护，且与调试面板共用 `TracePhase` 语义 |
| **（v1.1 新增）`ReplayEngine`/`BattleReplayManager` 死代码链处置** | 若保留不处理，`ReplayBattleEvent` 类型无法删除，双枚举残留 | §1.4 事实 2 已确认无调用方；P2 随死代码清扫删除（或标记废弃），`BattleReplay.vue` 是唯一消费端，无用户可见行为损失 |
| **（v1.1 新增）`action_execution` TraceEvent 缺伤害数值** | 回放详情展示空洞 | §5.1 已改以 `damage_calculation` 子事件/`summary` 为详情来源；若需行动级数值，实施时在 `BattleExecutor` 的 `action_execution` 发射处（`BattleExecutor.ts:205-218`）补 payload |

## 一句话总结

**调试日志不是回放的注释，回放数据也不是调试的存档——它们是同一场战斗在镜子里的两个面。** 以 `TraceEvent` 为唯一事件类型，补 `snapshot` 与 `randomSeed` 两个字段，让 `RecordedBattle.events` 成为唯一事实来源：回放按时间轴消费它，调试按因果树消费它，一份文件两种能力，再无"两份真相"。
