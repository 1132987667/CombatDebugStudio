## 1. 战斗总览

### 1.1 参与方

- 一场战斗由「我方阵营（ALLY）」与「敌方阵营（ENEMY）」的参战单位构成，单位统一建模为 `BattleEntity`（我方角色 / 敌方敌人 / 召唤物）。
- 阵型（`FormationManager`）提供站位（`seatIndex` 前/后排）与阵型增益；前排保护规则作用于目标选择。

### 1.2 核心资源

| 资源 | 默认值 | 说明 |
| --- | --- | --- |
| 气血 HP | 按角色/敌人配置 | `currentHealth` / `maxHealth`，0 及以下死亡 |
| 能量 EP | 上限 200，初始 30 | 回合开始恢复 `energyGainPerTurn`（默认 15）；受击获得 `energyGainOnHit`（默认 12，每回合最多 3 次）；技能消耗 |
| 技能冷却 | 按技能配置 | 每回合开始 `reduceSkillCooldowns()` 递减，执行成功后立即置冷却 |

### 1.3 战斗宏观流程

```
BATTLE_START（初始化）
   │
   ▼
┌──────────────────────────────────────────────┐
│  回合循环（currentTurn = 1, 2, 3 …）           │
│  TURN_START → 逐个行动 → TURN_END → 回合递增   │
│  （每行动后与回合末各检查一次结束条件）          │
└──────────────────────────────────────────────┘
   │  一方全灭 / 回合数达上限
   ▼
BATTLE_END（判胜、trace 收尾、战报）
```

## 2. 战斗状态机（回合全流程）

> 实现位置：`BattleSystem.processTurnInternal()`。这是回合的唯一推进器，所有阶段顺序不可调换。

### 2.1 回合级状态

| 阶段 | 顺序 | 内容 | 实现位置 |
| --- | --- | --- | --- |
| TURN_START | 1 | 发 `TURN_START` 触发器事件 → 回合开始被动 → 复活冷却递减 → 场地周期（turn_start）→ 技能冷却递减 → 重置受击能量计数 → 发放回合能量 → `recalcAll()` 属性重算 → `createTurnOrder()` 出手排序 | `BattleSystem.ts:944-1055` |
| 行动循环 | 2 | 按出手顺序逐个 `executeParticipantAction()`；行动后发 `ACTION_END`；**每次行动后执行结束条件检查** | `BattleSystem.ts:1074-1131` |
| TURN_END | 3 | `updatePerTurn()` 回合末统一 Buff 结算（DOT/HOT/持续效果/时长递减）→ **结束条件检查**（dot 致死及时判胜）→ 发 `TURN_END` 触发器事件 → 回合末被动 → 场地周期（turn_end）+ 场地递减 + 仇恨衰减 → 消费额外行动（extra_action，每回合上限 3）→ 回合态势快照 → 回合递增 | `BattleSystem.ts:1140-1248` |

### 2.2 战斗级状态

`BattleStatus`：`IDLE → ACTIVE → PAUSED(暂停可恢复) → END`；`RoundStatus`：`START → END`。

### 2.3 关键时序规则（📌 决策）

1. **回合末是唯一「全局统一 Buff 结算点」**。DOT/HOT、时长递减、护盾续期全部在 `updatePerTurn`（TURN_END 阶段）执行，不在回合开始执行。
2. **结束条件在「每次行动后」与「回合末」两个时点检查**，保证一行动击倒最后一人立即判胜、DOT 致死不拖入下一回合。
3. **死亡不即时结算被动**。伤害扣血后只入 `pendingDeaths` 队列，由 `runEndConditionCheck()` 统一确认：仍死亡则触发 `ON_DEATH`（死者）/ `ON_KILL`（击杀者）；已被复活者跳过死亡被动（兼容复活机制）。
4. **额外行动（时之沙）**在 TURN_END 后、回合递增前消费，每回合上限 3 次防死循环。

## 3. 行动级流程（行动状态机）

> 实现位置：`BattleExecutor.executeParticipantAction()`。

```
进入行动
  │
  ├─ 被控制？ → 记录「被控制，无法行动」日志，跳过行动（不决策、不执行）   [⚠️ 见 §6.4]
  │
  ├─ 决策：controlMode 三路径
  │    ├─ AI    → BattleAI.makeDecision（技能/普攻/跳过）
  │    ├─ AUTO  → 权重策略选技能，否则普攻
  │    └─ MANUAL→ 由 Store/UI 直接驱动
  │
  ├─ 执行：技能走 SkillManager.executeSkill，普攻走 selectAndExecuteAttack
  │
  ├─ afterAction()
  └─ ACTION_END 触发器事件 →（回到主循环）结束条件检查
```

- 技能可执行性三级检查（`canExecuteSkill`）：**控制 → 冷却 → 能量**，任一不过返回 `can: false` 并携带 `SkillBlockReason`；失败不消耗能量、不触发冷却。
- 普攻（普通攻击技能 `isNormalAttackSkill`）在决策处拦截，强制走普攻路径（与技能路径日志口径一致）。
- 玩家手动操作（MANUAL）由 UI 层驱动，引擎不主动决策。

## 4. 胜负判定

> 实现位置：`BattleRuleManager.checkBattleEndCondition()` + `BattleSystem.runEndConditionCheck()`。

### 4.1 判定规则（📌 决策）

| 场景 | 规则 | 现状 |
| --- | --- | --- |
| 一方全灭 | 存活单位数为 0 即判负，对方获胜 | ✅ |
| 多个单位同时死亡 | 按 `pendingDeaths` 入队顺序逐个确认；死亡被动可能复活（复活者跳过死亡被动），最终以「确认仍死亡」后的存活数判定 | ✅ |
| **同归于尽**（我方全灭且敌方全灭） | **先检查「我方全灭」→ 判玩家失败**。判定顺序：`aliveCharacters === 0` 优先返回 `ENEMY` 胜。即同归于尽 = 玩家战败 | ✅（顺序见 §4.3） |
| 持续伤害（DOT）致死 | **算战败**。`updatePerTurn` 回合末结算后立即 `runEndConditionCheck`，我方因 DOT 全灭即判负 | ✅ |
| 回合开始因中毒死亡 | **不会发生**。DOT 在回合末（TURN_END）结算，不在回合开始；上一回合末已确认的死亡会在下一回合 `turnOrder` 生成前被排除，不进入行动 | ✅ |
| 超过最大回合（默认 99） | 按双方存活单位的**气血比例之和**（`currentHealth/maxHealth` 累加）比大小，我方 ≥ 敌方判我方胜 | ✅ |
| 召唤物 | **不计入胜负判定**（胜负只看非召唤参战单位）；召唤物死亡不触发 ON_DEATH（防无限连锁） | 🚧 召唤本身未实现，规则先行 |

### 4.2 结束判定时点

1. 每个参战者行动之后；
2. 回合末 `updatePerTurn` 之后（覆盖 DOT/HOT 致死）；
3. 两处都走同一 `runEndConditionCheck`（先结算 pendingDeaths → 触发死亡被动 → 再查结束条件）。

### 4.3 同归于尽判定顺序（📌 决策）

```
if (我方存活 === 0)        → 敌方胜   ← 同归于尽时命中这里，玩家失败
if (敌方存活 === 0)        → 我方胜
if (currentTurn >= maxTurns) → 按气血比例判胜
```

> 该顺序是硬性约定，写测试时锁定：`{ally: 0, enemy: 0}` 必须判定为 ENEMY 胜。

## 5. 行动顺序、速度与位移

### 5.1 行动顺序（✅）

- **当前引擎无「行动条」机制**。采用「每回合按速度重新排序」模型：`TurnManager.createTurnOrder()` 每回合开始时按 `effectiveSpeed` 降序排列，同速走确定性 rng 随机（`speedFirst` 开关可关闭，关闭则按注册顺序）。
- 速度在每回合 `recalcAll()` 后读取，保证 Buff 速度修正（如减速）即时生效于下一回合排序。

### 5.2 击退 / 拉扯（🚧 未实现 + 📌 决策）

- 现状：`STATUS_CODE.KNOCKBACK` / `PULL` 仅有元数据定义（`status-meta.ts`），**无执行链路**；`knockbackResist` 属性有定义未消费。
- **决策：击退不改变速度、不延迟回合**。击退 = 阵型座次后移一位（`seatIndex + 1`，已在最后排无效）；拉扯 = 前移一位。击退不造成伤害，可触发位置相关被动，可被 `knockbackResist` 免疫。行动顺序仍由速度决定，与座次无关（除非阵型规则另行声明）。
- 「延迟一回合」与「速度临时降低」两种玩家猜测均**不采用**，避免与既有速度模型冲突。

### 5.3 召唤物参与行动排序（🚧 + 📌 决策）

- 现状：`summonUnit` 触发器仅有占位实现（`BuffSystem.requestSummon` → 回调仅记日志，`TODO(P2)` 完整召唤管道）。
- **决策**：召唤物创建后并入 `participants` 同阵营，**参与下一回合的 `createTurnOrder` 速度排序**；有存活回合限制（到期自动移除）；死亡不触发 `ON_DEATH`；不计入胜负判定。花妖 / 蜘蛛等召唤物的行动逻辑沿用普通单位的 AI 决策路径。

## 6. 控制状态体系

> 状态元数据：`src/shared/types/status-meta.ts`；控制查询：`BuffSystem.getHighestPriorityControlEffect()` / `isCharacterControlled()` / `canUseSkill()`。
> 控制类型全集：`ControlType`（`stun / silence / freeze / sleep / bind / confusion / fear / charm / taunt / petrify / immobilize / disarm / polymorph / imprison / guixu`）。

### 6.1 控制优先级模型

- 同目标多个控制共存时，**最高 `controlPriority` 的控制生效**（`getHighestPriorityControlEffect`）。
- 优先级：归墟 200 > 眩晕 100 > 石化 95 > 冰冻 90 > 变形 85 > 睡眠 80 > 魅惑 75 > 束缚 70 > 禁锢 65 > 恐惧 60 > 沉默 50 > 缴械 45 > 混乱 40 > 嘲讽 35 > 定身 25。

### 6.2 核心控制状态速查表

| 状态 | 代号 | 可否普攻 | 可否技能 | 可否行动 | 受击是否解除 | 可净化 | 可驱散 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 眩晕 stun | 100 | ✗ | ✗ | ✗（完全跳过） | 不解除 | ✓ | ✓ |
| 沉默 silence | 50 | **✓（设计意图）** | ✗ | ✓（行动但不放技能） | — | ✓ | ✓ |
| 束缚 bind | 70 | ✗ | ✗ | ✗ | 不解除 | ✓ | ✓ |
| 冰冻 freeze | 90 | ✗ | ✗ | ✗ | **解除**（设计意图） | ✓ | ✓ |
| 睡眠 sleep | 80 | ✗ | ✗ | ✗ | **解除并 +20% 受伤**（设计意图） | ✓ | ✓ |
| 石化 petrify | 95 | ✗ | ✗ | ✗ | 不解除（附 50% 减伤） | ✓ | ✓ |
| 混乱 confusion | 40 | ✓ | ✓ | ✓（目标随机化） | — | ✓ | ✓ |
| 嘲讽 taunt | 35 | ✓ | ✓ | ✓（只能打施法者） | — | ✓ | ✓ |
| 禁锢 imprison | 65 | ✗ | ✗ | ✗（且不可被选为目标） | 不解除 | ✓ | ✓ |
| 归墟 guixu | 200 | ✓ | ✓ | ✓（不可被他人选中） | — | ✗ | ✗ |

### 6.3 束缚 / 冰冻 / 睡眠 / 眩晕的区别（📌 决策）

| 对比维度 | 眩晕 | 束缚 | 冰冻 | 睡眠 |
| --- | --- | --- | --- | --- |
| 是否跳过行动 | 是 | 是 | 是 | 是 |
| 受击是否唤醒 | 否 | 否 | **是** | **是** |
| 受击附带效果 | 无 | 无 | 无 | 额外承伤 +20%（乘算） |
| 优先级 | 100 | 70 | 90 | 80 |

> 「麻痹」无独立类型，统一用眩晕类（stun）表达；若要区分「麻痹只禁行动不禁技能」的语义，应使用沉默 + 眩晕组合或新增类型。

### 6.4 代码现状与设计意图的差距（⚠️ 待对齐）

| 项 | 设计意图（status-meta / 本文档） | 代码现状 | 处置 |
| --- | --- | --- | --- |
| 沉默可普攻 | 沉默 `blocksAction=false`，应可普攻 | `BuffSystem.isCharacterControlled()` 把**任何** `controlType !== none`（含 silence）判为被控 → `executeParticipantAction` 直接「无法行动」跳过 | **对齐方案**：`isCharacterControlled()` 只对 `blocksAction=true` 的控制返回 true；`canUseSkill()` 只对 `blocksSkill=true` 返回 false。即由 `status-meta` 的 `blocksAction / blocksSkill` 双标志驱动行动判定 |
| 冰冻 / 睡眠受击唤醒 | freeze/sleep 受击解除（睡眠附带 +20% 承伤） | `ControlEffect` 为空操作，无受击唤醒监听 | **对齐方案**：`settleDamage` 对持有 freeze/sleep 的目标触发唤醒（移除该控制 Buff）；睡眠唤醒时该次伤害 ×1.2 |

### 6.5 控制状态下使用丹药（📌 决策）

- 现状：**战斗中物品（丹药）使用链路未实现**（仅有 `BattleAction` 的 `item` 类型与日志类别，无 `executeItem`）。
- **决策**：物品使用视为「不消耗行动轮的额外动作」（未来实现时的占用规则另定）。**完全控制状态（`blocksAction=true`，眩晕/束缚/冰冻/睡眠/石化/禁锢）不可使用任何物品**；**沉默（只禁技能）可正常使用物品**。丹药施加的临时增益 Buff 与被控无关，可叠加于控制解除后继续生效。

## 7. 命中 / 闪避 / 暴击公式

> 实现位置：`DamageCalculator.calculateDamage()`。

### 7.1 命中判定（✅）

```
闪避门控：enableDodge 开关（默认 false）
实际命中率 = hitRate − dodgeRate（下限 0）
if (rng()×100 > 实际命中率) → 闪避（isMiss=true，伤害直接为 0）
```

- 属性默认（`attributes.json`）：`hit = 90`、`dodge = 10`，故无修正时实际命中率 = 90 − 10 = **80%**。
- 必暴标记 `buff_guaranteed_crit`：**必中 + 必暴**，跳过命中判定。

### 7.2 暴击判定（✅）

```
暴击率 = source.critRate
if (必暴 || (enableCrit && rng()×100 < critRate)) → 暴击
暴击伤害 = floor(基础伤害 × (critDamage / 100))
```

- 属性默认（`attributes.json`）：`critRate = 10`、`critDamage = 125`；`BattleRuleManager.damage.critical.defaultRate=0.05` 仅为规则兜底，实际以角色属性为准。
- 暴击在「基础伤害 + extraValues 加成」之后计算，早于防御减免（先暴击放大、后减免）。

### 7.3 概率硬上限（📌 决策，来自《数值框架设计》§1.4）

| 属性 | 上限 |
| --- | --- |
| 暴击率 | 100% |
| 命中率 | 100% |
| 闪避率 | 75%（保留 25% 必中空间） |
| 免伤率 | 90% |
| 元素抗性 | 80% |

## 8. 伤害结算管线

> 实现位置：`DamageCalculator`（完整链路）+ `BattleExecutor.settleDamage`（扣血/事件/仇恨/死亡）。

### 8.1 技能伤害链路顺序（✅）

```
1. 基础伤害 calculateBaseDamage（有 calculation → baseValue；无 → attack + level×2）
2. + extraValues（Σ attribute×ratio，属性从 source 或 target 读取）
3. 暴击判定与暴击倍率（floor）
4. 来源方加成（damageBoost / 火系加成 / 物理加成 / 低血量加成）
5. 捕获 rawDamage（减免前）
6. 暴击承伤减免
7. 防御减免（减法：damage − defense；TRUE 类型跳过）
8. 普攻/技能减免（TRUE 跳过）
9. 元素抗性 + 场地元素修正（仅 ELEMENTAL）
10. 通用减免（TRUE 跳过）
11. 易伤 damageTakenIncrease
12. 目标修正 targetModifiers
13. 阵营元素克制 elementMatrix
14. 阈值钳制 [minDamageThreshold, maxDamageThreshold]（默认 [1, 9999]）
```

### 8.2 扣血与护盾（✅）

```
伤害先扣护盾（shieldValues 聚合值，ShieldEffect 累加/ShieldBuff 覆盖，见 §11.6）
→ 护盾耗尽后剩余伤害扣气血
→ 触发 DAMAGE_TAKEN / ON_HIT / 仇恨
→ 死亡入 pendingDeaths（延迟结算）
```

### 8.3 反伤 / 受击回能（✅）

- 反伤走触发器（`reflect_damage` / `reflect_fire_damage`），支持 `basis='raw'|'final'` 双模型，深度计数器（上限 3）防递归。
- 受击回能：每回合受击能量计数重置（上限 3 次），命中获得 `energyGainOnHit`。

## 9. 治疗与持续效果

### 9.1 治疗结算（✅）

- `HealCalculator`：治疗量**不超过 `maxHealth − currentHealth`**，溢出单独记录 `overflow`（可供 `overflow_shield` 转盾）。
- 减治疗效果（`heal_reduction` tag）：每层 20%，上限 80%。
- HOT 在回合末 `updatePerTurn` 结算（`HotEffect`），可叠层（value × stacks）。

### 9.2 持续伤害 DOT（✅）

| Buff | damageType | 机制 | 层数上限 |
| --- | --- | --- | --- |
| 中毒 `buff_poison` | 脚本（PoisonDebuff） | 每回合伤害随回合递增（baseDamage × multiplier^stacks），减速 20% | 3 |
| 剧毒 `buff_strong_poison` | 脚本（StrongPoisonDebuff） | 同中毒，数值更高 | 3 |
| 灼烧 `buff_burn` | effectPlan dot | 每回合 3% 最大生命 × 层数 | 3 |
| 流血 `buff_bleed` | effectPlan dot | 每回合 3% 最大生命 × 层数 | 3 |

- DOT 在**回合末**统一结算，走 `requestDamage(origin='dot')`（计入承伤/HP，不计命中/暴击/技能）。
- 中毒 / 剧毒 / 灼烧 / 流血 **互不排斥、可同时存在**（不同 buffId 独立实例，独立结算）。📌 决策。

## 10. Buff / Debuff 规则

### 10.1 叠加模型（✅，`BuffSystem.addBuff` + `StackRule`）

| 叠加规则 | 行为 | 备注 |
| --- | --- | --- |
| `LIMITED`（默认） | 已有同类 Buff → 层数 +1；**达到 `maxStacks` → 刷新持续时间，不增加层数** | 层数驱动 `_stacks`，修饰符随层数缩放（`perStack`） |
| `REFRESH` | 移除旧实例，重新施加（重置持续时间） | 典型：狂暴类 Buff |
| `INDEPENDENT` | 每个实例独立计算效果 | 上限默认 10（`maxStacks` 控制） |

### 10.2 同类 Buff 是否叠加（📌 决策）

- **可叠加与否由单个 Buff 的 `maxStacks` 决定，不设全局默认**：
  - `buff_atk_up`（攻击+10%）：`maxStacks: 1` → **不可叠层**，再次施加走 LIMITED 满层刷新时间。
  - 中毒/灼烧/流血：`maxStacks: 3` → **可叠 3 层**，满层刷新时间。
- 举例「攻击上升 +10% 叠加两层」：默认配置下**不允许**（`maxStacks=1`）；需要两层就在配置里把 `maxStacks` 调为 2。

### 10.3 同类 Debuff：刷新还是叠层（📌 决策）

- 默认按 `LIMITED`：**再次施加 → 叠一层**（伤害随层数递增），满层后刷新持续时间。
- 若某 Debuff 设计为「只刷新不叠层」，配置 `stackRule: 'refresh'` 或 `maxStacks: 1`。

### 10.4 最大叠层与 UI 展示（✅）

- `currentStacks` / `maxStacks` 即真实层数，参与效果计算与 UI 显示。
- 修饰符效果文案由 `ModifierEffect.getEffectLines` 生成：`perStack` 为真且层数 >1 时显示 `×N`。
- DOT 效果文案由脚本/`DotEffect` 输出（`每回合失去 X 生命`）。📌 决策：UI 必须同时展示「层数」与「剩余回合」，层数用角标、剩余回合用 `remainingTurns`。

### 10.5 免疫机制（✅）

- `characterImmunities` 在 `addBuff` 时阻断施加：按 `controlType` / buffId / `tags` 三种维度匹配免疫。
- 已知天花板：**「免疫阻止施加」与「净化移除已存在」未分离**——目标先中 debuff、后获得免疫时，旧 debuff 不会自动移除（见《Buff 系统架构能力评估》§6）。

### 10.6 护盾叠加与持续（📌 决策）

| 项 | 规则 | 现状 |
| --- | --- | --- |
| 多个护盾叠加 | **数值相加**（`ShieldEffect.onApply` 累加到 `BuffSystem.shieldValues`） | ✅（PATH B） |
| 护盾覆盖 vs 相加 | PATH A 脚本 `ShieldBuff` 为**设置值**（多个会覆盖），PATH B 原语为**累加**。**统一规则：护盾按来源累加**，避免两路径语义分叉 | ⚠️ 需统一 |
| 护盾持续递减 | 护盾 Buff 的 `remainingTurns` 在**回合末 `updatePerTurn` 递减**；到期 `onRemove` 回收剩余护盾（PATH B 回收自身量；PATH A 清零） | ✅ |
| 护盾可否治疗 | 不可被治疗，只能吸收伤害或随持续结束消失 | ✅ |

### 10.7 净化（cleanse）与驱散（dispel）

| 操作 | 规则 | 现状 |
| --- | --- | --- |
| 净化（cleanse） | **现状**：移除目标**全部** Buff 实例（不区分正负/极性）；`remove_debuff` 步骤才按极性过滤（默认移除 1 个减益） | ⚠️ 与 status-meta「只移除负面状态」不一致，**以现状为准**：cleanse = 全清，remove_debuff = 定点清除，二者需在技能配置中按需选用 |
| 驱散（dispel） | 移除敌方 `dispellable=true` 的正面状态（增益/护盾/反射等） | ✅（`removeDispellableBuffs`） |
| 控制可否被净化 | **可以**。控制类 `cleanseable/dispellable = true`（除归墟 `false`）→ 眩晕/沉默/束缚/冰冻/睡眠可被净化/丹药移除 | ✅ 元数据 + 机制 |
| 丹药能否解控 | 战斗中丹药未实现；**决策：解控丹药存在，视为净化**（走 cleanse/remove_debuff 语义） | 🚧 链路未实现 |

### 10.8 临时 Buff 与永久 Buff 分层（📌 决策）

| 来源 | 语义 | 持续 | 底层实现 |
| --- | --- | --- | --- |
| 装备词条 | 常驻，随穿戴增删 | 永久（脱装移除） | `ModifierSourceType.EQUIPMENT` |
| 技能 Buff | 战斗中施加 | 按 `duration` | effectPlan / 脚本 |
| 丹药 Buff | 战斗中服用 | 临时（如 3 回合） | 与技能 Buff 同管线，`sourceType` 标记来源 |
| 永久 Buff | `duration=-1` / `isPermanent` | 整场战斗 | 不随回合递减 |

- 分层目的：UI 区分来源（装备/技能/丹药），驱散/净化的作用范围后续可按来源过滤（`excludeTags` / 来源过滤为演进项，见 §14）。

## 11. 战斗中物品（丹药）使用（🚧）

- 现状：`BattleAction` 支持 `item` 动作类型，日志系统有物品类别，`KeybindManager` 有「使用物品」键位，**但无 `executeItem` 执行链路**。
- 已建模数据：`configs/materials/`（疗伤丹药回血、元气丹回能、攻击/防御/速度丹药 +20% 持续 3 回合、全属性丹药等）。
- **决策（先行规则，落地时遵循）**：
  1. 使用丹药不占用行动轮（作为行动外动作）或占用一行动轮 —— **占用行动轮**，避免与普攻/技能节奏失衡；
  2. 眩晕/束缚/冰冻/睡眠/石化/禁锢等完全控制状态**不可使用**；沉默**可用**；
  3. 丹药效果走标准 Buff 管线（`sourceType` 标记丹药来源），遵循 §10.8 分层与叠加规则；
  4. AI 策略需加入丹药决策（低血用药、有 debuff 用解控药），见 §12。

## 12. AI 决策规则（补完）

> 实现位置：`AISystem` / `AIPriorityStrategy`（Aggressive / Defensive / Balanced）。已有：冷却与能量校验、技能权重（终结技/小技能/被动 + 战场形势 + 角色状态）、确定性 rng。

补充策略（📌 决策）：

```
IF 自身气血 < 30% AND 有疗伤丹药        → 使用疗伤丹药
IF 自身有可净化的 debuff AND 有解控手段  → 净化/解控
IF 能量 >= 大招消耗 AND 大招可用          → 释放大招
IF 能量 >= 小技能消耗 AND 小技能可用      → 释放小技能（避开有护盾/免伤的敌人）
IF 目标处于低血量                      → 优先高爆发技能
ELSE                                   → 普攻
```
