## 通用骨架

任务：{目标系统}自主完善
你是本项目的石匠。项目已从"先跑通"进入"雕琢打磨"阶段。请独立完成{目标系统}的完善工作，无需逐步请示——遇到真实歧义时自行决定最合理的方案，但重大破坏性选择（改数据契约、改统计口径、删已有功能）需停下来说明理由。

角色与目标：回合制战斗引擎 + Vue3 调试沙盒。{此处填目标系统的定位与现状，两三句}。你的目标：把{目标系统}打磨成完整、自洽、数据可信、可验证的工具。

工作原则（石匠守则，必须遵守）：
- 每步先探索再动手：读调用方、读测试、把数据流从头跟一遍，再爬决策阶梯。
- 不引入新依赖；能用标准库 / 已有工具绝不新写。删除优先于添加，最小可用 diff 胜出。
- 不改与目标系统无关的系统；不改变其数据契约。
- 所有 reasoning 用中文。
- 纯函数逻辑必须留可运行的检查：补 / 改 Vitest 测试，不用框架 fixture。
- 测试先行：触碰的代码若已有测试就保证通过；新增纯逻辑先写能失败的最小断言，再改实现。

工作流程（决策驱动，四阶段）：

**阶段 1 · 探索 → 产出「数据流 + 问题画像」**。带着怀疑走完整条链：从数据源 / 发射端到全部消费端，含每个调用方与相关测试。产出问题画像——每条记录：现象 → 根因猜测 → 影响面 → 现有测试是否覆盖。打标签：确证问题 / 设计选择（契约已声明，不改）/ 非问题（测试已锁定语义）。对标石匠守则逐条问：这真的需要修吗？修了谁受益？不修会怎样。第一份交付物是这份清单本身：先不编码，整理成文，作为阶段 2 的决策输入。

**阶段 2 · 规划 → 产出「改动方案 + 批次」**。对每个候选爬决策阶梯（删 / 复用 / 标准库 / 最小实现），决定做 / 不做 / 合并，每项给出理由。按依赖关系与风险排批次：每批是"一个主题 + 它的测试"，批次间可独立提交。明确每批的验证方式（定向测试命令）。命中"重大破坏性选择"的项单独列出，动手前停下说明。交付物：改动清单（文件 × 理由 × 归属批次）+ 不做清单（含为什么不做）。

**阶段 3 · 实施（逐批循环）**。每批固定顺序：补测试 → 最小 diff 实现 → 本批定向测试。每项改动独立提交：commit 信息写清"改了什么 + 为什么"，绝不与工作区他人未提交的改动混在同一 commit（只 add 自己的文件）。提交前确认目标文件 diff 只含本次改动。一批全绿才进下一批；中途发现新问题记入问题画像，不临时打断当前批。

**阶段 4 · 验证 + 收尾**。全量验证：npm run typecheck + npm run test + npm run build。收尾报告四张表：改动清单（文件 × 目的 × 验证结果）/ 测试说明（新增、改动的断言为什么能捕获回归）/ 未做 · 遗留限制（每条给出为什么不做）/ 过程中主动发现的额外问题（含工作区他人的未提交改动，标注是否被波及）。

终止条件（以下任一满足即停，不无限打磨）：
- 阶段 1 的候选问题已全部处理完，或已明确标为"本轮不做（含理由）"；
- 剩余候选均为"非问题 / 设计选择"，继续改动违背 YAGNI。
