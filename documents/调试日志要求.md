# 调试日志要求

> **文档性质**：战斗引擎调试日志体系的**验收要求**——§2 完整保留原始要求清单（完整性依据），§3 将清单逐条对照 CombatDebugStudio 的实现机制（验收依据），§8 为 UI 设计要求（三栏式布局）。
> **关联文档**：`documents/需求文档/调试日志改造.md`（设计愿景 + 数据模型 + 编码规范，本文档的要求以此为准）、`documents/日志管理.md`（日志系统原始需求规格，面向展示层）。

## 设计原则

> **每一次状态变化都有来源，每一次行动顺序都有依据，每一次伤害结算都有公式，每一次随机判定都有凭证，任何战斗结果都可以被复现、解释和证伪。**

## 1. 概述

一款成熟的回合制战斗引擎，其核心能力不仅体现在战斗逻辑的正确实现上，更体现在战斗过程是否可观察、可追踪、可验证。CombatDebugStudio 通过结构化调试日志体系（`TraceEvent` + `TracePhase` + `correlationId`）完整记录战斗初始化、行动顺序、状态变化、伤害结算、随机判定与事件因果链：每一次攻击的命中与闪避、每一次暴击的触发、每一项伤害数值的构成，以及每一个 Buff / Debuff 的产生与消失，都保留清晰的计算依据和随机凭证。

日志不仅要回答"发生了什么"，更要回答"为什么发生"。在相同输入与相同随机种子下，战斗结果必须能够被复现；任何异常结果也必须能够通过日志回溯到具体逻辑节点。这样的可追溯性与可证伪性，是战斗引擎进行平衡调整、问题定位、自动化测试与长期演进的基石。

## 2. 完整覆盖清单（原始要求）

> 以下为调试日志体系必须覆盖的记录范围清单，完整保留每一项原始要求，作为 §3 逐条对照的索引。新功能上线时对照本清单检查是否存在未覆盖的记录点。

### 2.1 战斗初始化信息

- 战斗唯一标识
- 随机种子
- 参战单位列表
- 单位初始属性快照
- 技能、装备、被动、Buff、地形等初始条件

### 2.2 行动顺序与回合流程

- 每个回合的开始与结束
- 行动条、速度值、出手顺序的计算过程
- 单位行动权判定依据
- 行动阶段划分，例如：回合开始、行动前、技能选择、目标选择、结算、回合结束
- 每一次行动触发的时序记录

### 2.3 状态变化记录

- Buff / Debuff 的添加、移除、刷新、叠加、衰减
- 状态变化前后的数值对比
- 状态来源，例如技能、装备、被动、地形、效果链
- 状态触发条件与持续时间
- 属性变更的详细原因

### 2.4 伤害与治疗结算过程

- 伤害类型，例如物理、魔法、真实伤害、持续伤害等
- 基础值来源
- 攻击力、防御力、抗性、暴击、暴击伤害、增伤、减伤、穿透、格挡等每一项修正值
- 伤害公式的输入参数与中间计算结果
- 最终伤害或治疗量
- 目标生命值变化前后数值

### 2.5 随机判定记录

- 命中、闪避、暴击、格挡、效果触发概率等随机事件的判定过程
- 随机种子或随机数序列
- 判定阈值
- 实际随机结果
- 判定成功或失败的原因
- 所有概率事件必须具备可复现性

### 2.6 事件因果链

- 每个战斗事件都应有唯一事件 ID
- 记录事件触发来源、触发目标、触发时机
- 支持从一个最终结果反推出完整的事件链路
- 能够说明"为什么该单位在此时行动"
- 能够说明"为什么该次伤害是这个数值"
- 能够说明"为什么该次攻击命中、闪避、暴击或未暴击"

### 2.7 可证伪与可复现能力

- 在相同输入、相同配置、相同随机种子下，战斗结果必须可复现
- 日志应足以支撑离线重算或回放验证
- 任何一个异常结果都能够通过日志定位到具体计算步骤
- 日志不仅用于观察结果，更用于证明结果产生的依据

> 因此，优秀的回合制战斗引擎调试日志，不应只是简单的运行记录，而应是一套完整的**战斗事实证据链**。它能够让开发者清楚地看到战斗中的每一次状态变化、每一个行动顺序、每一项伤害组成以及每一次随机判定的来源与过程。只有当战斗结果可以被解释、被追踪、被验证、被证伪时，战斗引擎才具备真正可靠的工程基础。

## 3. 机制落地对照

> 将 §2 清单逐条对照本项目的实现机制。括号内为验收口径：每一项都必须能在现有（或应新增的）trace 事件中找到对应记录。

| 原始要求（§2） | 落地载体 |
| --- | --- |
| 战斗唯一标识 | `TraceEvent.battleId`（隔离多场战斗） |
| 随机种子 | `BattleRecorder.randomSeed`（`SeededRandom`，LCG 确定性随机） |
| 参战单位列表 | `RecordedBattle.initialState.participants` |
| 单位初始属性快照 | `initialState`（阵营、HP/能量等基础属性） |
| 技能、装备、被动、Buff、地形等初始条件 | `CONFIG_LOAD` / `CONFIG_VALIDATION`；场地效果由 `FieldEffectManager` 管理（`TraceTriggerSource.FIELD_EFFECT`） |
| 每个回合的开始与结束 | `TURN_FLOW`（`TURN_START` / `TURN_END`） |
| 行动条、速度值、出手顺序的计算过程 | `TurnManager` 按有效速度排序（`speedFirst` 规则；项目未实装行动条机制，出手顺序为回合内速度优先），结果记入 `TURN_FLOW.payload.turnOrder` |
| 单位行动权判定依据 | 有效速度值排序依据随回合事件保留 |
| 行动阶段划分（回合开始、行动前、技能选择、目标选择、结算、回合结束） | 以 `ACTION_EXECUTION` 为因果树根，`AI_DECISION`（技能选择）→ 技能执行（目标选择、结算）挂在子树节点 |
| 每一次行动触发的时序记录 | `correlationId`（一次行动一个 scope）+ `timestamp` |
| Buff / Debuff 的添加、移除、刷新、叠加、衰减 | `BUFF_LIFECYCLE`（action: `APPLY` / `REMOVE` / `UPDATE` / `MODIFIER`） |
| 状态变化前后的数值对比 | payload 的 before / after |
| 状态来源（技能、装备、被动、地形、效果链） | payload.path（`A` = 脚本 / `B` = effectPlan / `D` = 纯标记）；装备 / 地形作为属性来源类型参与（`EQUIPMENT` / `TERRAIN`） |
| 状态触发条件与持续时间 | payload.stackRule、stacks、maxStacks、duration |
| 属性变更的详细原因 | `ATTRIBUTE_RECALC`（triggeredBy + before/after 的 `CalculationBreakdown`；幂等重算不产生事件） |
| 伤害类型（物理、魔法、真实伤害、持续伤害等） | payload.category（如 physical） |
| 基础值来源 | steps 首步（base） |
| 攻击力、防御力、抗性、暴击、暴击伤害、增伤、减伤、穿透、格挡等每一项修正值 | steps 逐步 before → after 记录（只记录实际发生数值变换的环节，无变换节点不落盘，值在 payload 顶层） |
| 伤害公式的输入参数与中间计算结果 | `DAMAGE_CALCULATION.payload.steps` 直接复用 `DamageBreakdown.steps`（`DamageStep[]`） |
| 最终伤害或治疗量 | payload.raw / payload.final；治疗走 `HEAL_CALCULATION` |
| 目标生命值变化前后数值 | 结算环节记录 HP before → after |
| 命中、闪避、暴击、格挡、效果触发概率等随机事件的判定过程 | 对应 phase 的 payload 记录 checks（required / roll / passed）；命中/闪避判定在 `DAMAGE_CALCULATION`（hitRate、dodgeRate） |
| 随机种子或随机数序列 | `BattleRecorder.randomSeed` |
| 判定阈值 | checks.probability.required、crit.rate 等 |
| 实际随机结果 | roll |
| 判定成功或失败的原因 | verdict / passed / skipReason |
| 所有概率事件必须具备可复现性 | `SeededRandom` 的确定性保证 |
| 每个战斗事件都应有唯一事件 ID | `TraceEvent.id` |
| 记录事件触发来源、触发目标、触发时机 | sourceId / targetId / phase / timestamp |
| 支持从一个最终结果反推出完整的事件链路 | `correlationId`（同一条因果链共享）+ `parentId`（树状嵌套）构成因果树 |
| 能够说明"为什么该单位在此时行动" | `TURN_FLOW.turnOrder` + `AI_DECISION` 的权重 breakdown（逐项贡献） |
| 能够说明"为什么该次伤害是这个数值" | `DAMAGE_CALCULATION.steps` 全变换链 |
| 能够说明"为什么该次攻击命中、闪避、暴击或未暴击" | 随机判定 checks + roll |
| 在相同输入、相同配置、相同随机种子下，战斗结果必须可复现 | `BattleRecorder` 录制 randomSeed、事件序列、回合快照、combatRecords、traceEvents 与 checksum |
| 日志应足以支撑离线重算或回放验证 | `ReplayEngine` 回放；`DebugLogDialog` 导出 `TraceEvent[]` JSON，导出数据天然可 diff |
| 任何一个异常结果都能够通过日志定位到具体计算步骤 | 因果树按 phase / actor（sourceId、targetId）/ turn 过滤 |
| 日志不仅用于观察结果，更用于证明结果产生的依据 | 结构化 payload 存事实与数字，`summary` 只作人类快速扫读，不作为程序逻辑输入 |

## 4. 本日志体系必须能够证明

| 证明点 | 落地载体 |
| --- | --- |
| 本次攻击由哪个单位发起 | `TraceEvent.sourceId`（或 payload 内实体 ID） |
| 攻击目标是谁 | `TraceEvent.targetId` |
| 使用了哪个技能 | `ACTION_EXECUTION` / `AI_DECISION` 的 payload（skillId / skillName） |
| 是否命中，以及命中的随机依据 | `DAMAGE_CALCULATION` 命中/闪避判定（hitRate、dodgeRate、roll、verdict） |
| 是否暴击，以及暴击的随机依据 | `DAMAGE_CALCULATION` payload.crit（rate、roll、multiplier、triggered） |
| 伤害由哪些数值组成 | `DAMAGE_CALCULATION` payload.steps（`DamageStep[]`） |
| 每一项加成或减免如何参与计算 | steps 逐步 before → after，每步带原因 |
| 最终伤害为何是该数值 | payload.raw / payload.final + steps 全变换链 |
| 目标生命值如何变化 | 结算记录 HP before → after |

## 6. 验收基准（30 秒调试会话）

以下四个调试会话均应在 30 秒内完成，作为调试日志体系的验收基准（详见 `调试日志改造.md` §8）：

- **故事 A · 伤害取证**："第 3 回合剑士对史莱姆的伤害为什么是 85？"——过滤 `phase=damage_calculation` + 角色 → 点开因果链 → 看到 `steps[]` 逐步 before → after。
- **故事 B · 决策取证**："为什么 AI 这回合选了治疗？"——过滤 `phase=ai_decision` → 看到候选权重与 breakdown（如"低血量队友 +40"）。
- **故事 C · 被动取证**："荆棘反甲为什么没触发？"——过滤 `phase=passive_trigger` + 展开 trace 级 → 看到 `verdict: SKIPPED, skipReason: COOLDOWN`。
- **故事 D · 跨战斗对比**："同一个技能，为什么第 2 场比第 1 场伤害高？"——分别导出两场战斗的 `TraceEvent[]` → 按 correlationId 对齐 → diff 两条 `steps[]`。

## 7. 当前实现状态

- **已落地**：三层架构（LogCollector → LogParser → LogRenderer）；`TraceEvent` 树状因果链（correlationId + parentId）；`BattleRecorder` 录制（randomSeed / initialState / traceEvents / checksum）；`ReplayEngine` 回放；`DebugLogDialog` 树状视图、按 phase/角色/回合过滤与 JSON 导出；`PASSIVE_TRIGGER` 的 SKIPPED 记录；trace 级默认隐藏。
- **持续要求**：命中/闪避判定的随机依据（hitRate、dodgeRate、roll）纳入 `DAMAGE_CALCULATION` payload；所有概率事件保持"required / roll / passed"三要素；新增 phase 发射点时对照 `调试日志改造.md` §5 示例与 §6 规范。

## 8. UI 设计要求（三栏式布局）

> 调试日志"层级深、数据密集、因果关系复杂"，单一列表或纯 JSON 视图在复杂战斗下难以快速定位问题。
> 方向：把 `DebugLogDialog` 从 "Tabs 三视图"（树状 / 实时流 / 日志）升级为**单屏三栏联动**——左侧宏观结构、中间逻辑卡片、右侧底层数据，一次点击完成"定位 → 拆解 → 取证"。
> 标注：【已有】= 当前实现已具备；【新增】= 本设计引入的 UI 能力；【优化】= 结合项目现有机制的落地调整。
> 配套示例：`documents/调试日志UI示例.html`——自包含 HTML（无框架、无依赖），浏览器直接打开即可查看三栏布局、卡片联动与检视器三区的**最终形态**。示例为纯设计展示（数据为示意：单位 A/B/C、HP 3200、`Final_DMG = (ATK × Skill_Multiplier − DEF) × Crit_Multiplier × (1 + DMG_Bonus)`、roll 0.642 > 0.35 未暴击），不绑定任何实现机制。

### 8.1 布局架构

| 栏 | 宽度 | 职责 | 数据源（现有机制） |
| --- | --- | --- | --- |
| 左栏 · 结构树 | 20% | 战斗宏观骨架（初始化 / 回合 / 行动 / 结算），支持折叠展开 | `TraceLogTree`（`TraceEventNode[]`，correlationId + parentId 因果树）【已有】 |
| 中栏 · 事件流卡片 | 40% | 选中行动下的逻辑步骤，垂直卡片 | 按 `TracePhase` 分组的子事件流【新增】 |
| 右栏 · 数据检视 | 40% | 选中卡片的底层数据：公式 / 随机凭证 / 属性快照 | `TracePayloadViewer` 升级为语义化三区【优化】 |

> 与现有视图的关系：三栏联动是"树状"Tab 的升级形态；"实时流 / 日志"Tab 保留（扁平扫读与错误通道不丢失）。弹窗宽度由 80vw 建议调至 92vw 以容纳三栏。

### 8.2 左栏：全局导航与时间线（结构树）

- **严格时序层级**：战斗实例 → 初始化阶段 → 第 N 回合 → 回合开始 [阶段] / 行动 [行动] / 回合结束 [阶段] → 战斗结算。【新增】
- **阶段与行动界限**：回合开始/结束标记为 `[阶段]`，单位操作标记为 `[行动]`，避免"回合开始块出现两次"的歧义（TURN_FLOW 事件与 ACTION_EXECUTION 子树在树形结构上天然区分）。【新增】
- **行动排序可视化**：行动节点旁直接显示有效速度与出手序号，让"为什么该单位此时行动"（§2.2）在树上一目了然——数据来自 `TURN_FLOW.payload.turnOrder` 与速度排序依据。【优化】
- **状态标记**：单位死亡节点灰化/删除线；暴击 / 闪避 / 跳过（SKIPPED）加矢量徽章（遵守 AGENTS.md：UI 禁止 emoji，用 SVG/矢量字符）。【新增】
- **trace 级降噪**：trace 级子事件默认折叠、SKIPPED 默认隐藏，勾选后展开（沿用现有 TraceLevel 门控）。【已有】

### 8.3 中栏：事件流卡片（Event Stream Cards）

- **卡片模板按 TracePhase 注册，而非硬编码四步**：每张卡片 = 一个 phase 的渲染器，新增 phase 只需注册渲染器，与 `TracePhase` 枚举一一对应。【优化】
  - `AI_DECISION` 卡片：候选技能权重与 breakdown（逐项贡献）。
  - `DAMAGE_CALCULATION` 卡片：`steps[]` 逐步 before → after + 顶层 raw / final / crit，展开即 §2.4 全变换链。
  - `PASSIVE_TRIGGER` 卡片：verdict（TRIGGERED / SKIPPED）+ skipReason + checks（required / roll / passed）。
  - `BUFF_LIFECYCLE` 卡片：action / path / stacks / duration / modifiers。
  - `ATTRIBUTE_RECALC` 卡片：before / after 数值对比。
  - `TURN_FLOW` 卡片：回合开始/结束、turnOrder、能量获取。
- 用户方案的"卡片 1~4"（行动前置检查 → 目标选择与命中判定 → 伤害/效果结算 → 后置效果与状态施加）映射到上述 phase 组：命中判定在 `DAMAGE_CALCULATION`（hitRate / dodgeRate / roll / verdict），后置效果是 `BUFF_LIFECYCLE` / `PASSIVE_TRIGGER` 子事件。【优化】
- 卡片垂直排列、同级缩进对齐因果树深度；点击卡片 → 右栏联动。【新增】

### 8.4 右栏：深度详情检视（Inspector Panel）

- **区域 A · 公式与计算过程**：将 `payload.steps`（`DamageStep[]`）渲染为公式链，逐步高亮 before → after 与原因，顶层显示 raw / final。示例：`base 100 → crit ×1.25 (roll 0.18 < 0.32 暴击) → damageBoost ×1.10 → defense −80 → final 85`。【优化】
- **区域 B · 随机数凭证（RNG Proof）**：显示判定消耗的随机值、阈值与结论，如 `roll 0.642 > critRate 0.35 → 未暴击`；`roll 0.42 ≤ 1.0 → 被动触发`。【新增】
  - 数据侧配套（见 §8.6）：为概率判定附加 **rngSeq（随机数序列索引）**，与 `BattleRecorder.randomSeed` 对齐后可逐次核对随机消耗——"所有概率事件可复现性"（§2.5）的 UI 凭证。
- **区域 C · 属性快照对比（State Diff）**：渲染 payload 的 before / after（`CalculationBreakdown`、HP before → after），增减值绿/红高亮（`HP: 3200 → 1985 (−1215)`）。数据已由 `ATTRIBUTE_RECALC` / 结算记录提供，无需额外打点。【优化】

### 8.5 高级交互与辅助功能

1. **全局过滤与搜索**：勾选"仅暴击 / 仅 DOT / 仅单位 A"，按 level / phase / actor / 文本过滤——把现有 `filteredStream` 五维过滤能力上浮到三栏。【已有 → 上浮】
2. **分支对比（Branch Comparison）**：加载两份导出的 `TraceEvent[]`，按 correlationId 对齐同名因果链后 diff `steps[]`（验收故事 D 的 UI 化）。【新增】
3. **异常高亮与断点**：error / warn 级事件（伤害为负、随机异常、配置校验失败）在左树与卡片自动标红；断点 = 暂停日志流并定位到具体事件。level 配色体系已具备。【已有 → 加强】
4. **战斗回放同步**：左下角可选 2D 战场缩略图，随左树滚动同步高亮单位（依赖 `BattleReplay` 播放器）。P2，视需要实现。【新增】

### 8.6 数据侧配套要求

- 【新增】概率判定 payload 附加 `rngSeq`（本场第 N 个随机数）与判定来源，配合 `randomSeed` 形成完整随机凭证链——区域 B 的数据前提。
- 【已有】`steps` 只记录实际变换环节、幂等重算不产生事件——保证中栏卡片"每张都有信息量"。
- 【已有】错误/警告走 `addDebugLog` 错误通道、不伪造 phase——异常高亮（§8.5.3）的数据来源。

### 8.7 落地优先级

- **P0（三栏骨架）**：左树复用 `TraceLogTree` 数据；中栏 phase 卡片渲染器（先 `DAMAGE_CALCULATION` / `AI_DECISION`）；右栏区域 C State Diff。
- **P1**：区域 B RNG 凭证 + `rngSeq` 打点；全局过滤上浮三栏；SKIPPED 徽章与 trace 折叠。
- **P2**：分支对比 UI、异常断点、回放缩略图同步。

> 性能约束：单场战斗日志 ≤ 1000 条（`MAX_EVENT_LOG`），三栏中左树与中栏卡片列表需虚拟滚动；所有交互不引入额外 `await`、不改变随机种子（遵循"零成本关闭"原则，见 `调试日志改造.md` §2 原则三）。
