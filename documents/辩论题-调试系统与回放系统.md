# 辩论题：调试系统与回放系统，谁包含谁？

> 用途：团队架构辩论素材。事实依据为当前代码实现（2026-07）。
> 相关文件：`documents/需求文档/调试日志改造.md`、`documents/战斗回放系统.md`、`src/domain/battle/service/BattleRecorder.ts`、`src/presentation/views/BattleReplay.vue`、`src/presentation/views/components/DebugLogDialog.vue`

## 一、辩题

> **正方命题：调试系统应当包含回放系统——调试日志是唯一存档，回放只是调试日志的一种可视化消费方式。**
> **反方命题：回放系统应当包含调试系统——回放数据是唯一存档，调试只是回放数据的一种解释视图。**

（注：辩题是"应然"之争，不是"实然"描述。当前实现是"回放包含调试"，正方要论证的是这个关系应该反过来。）

## 二、背景事实（双方共用的前提）

一场战斗结束后，系统里只有**一份**数据存档：`RecordedBattle`。它同时装着回放需要的一切（随机种子 `randomSeed`、初始状态快照 `initialState`、事件序列 `events`、回合数据 `rounds`、校验和 `checksum`）和调试需要的一切（结构化追踪事件 `traceEvents`，即调试日志）。`traceEvents` 是这份存档的**可选字段**——缺了它，回放照常工作；而调试日志单独导出时，既不能跳转、也不能重放。

**争的不是"现在谁包含谁"，而是"这个包含关系是合理的，还是颠倒的"。**

## 三、正方立论：调试系统包含回放系统

1. **信息量论**：调试日志是"领域事件的完整结构化投影"（调试日志改造文档原则一）。一条 `DAMAGE_CALCULATION` 事件带着完整的 `steps[]`（base → crit → damageBoost → defense → final 每一步 before → after）和因果链（`correlationId` + `parentId`）。回放需要的"状态怎么变"只是这个投影的子集——**调试日志含"为什么"，回放数据只有"是什么"**。信息量大的容器应该包住信息量小的。
2. **语义主权论**：回放的本质是"把发生过的事再演一遍"，而"发生过的事"的权威记录就是调试日志。回放器只是调试日志的播放器；反过来，回放数据解释不了任何"为什么"。一个系统冠以"调试"之名，天然涵盖回放；冠以"回放"之名，涵盖不了调试。
3. **维护成本论**：现在同一场战斗维护两套并行格式（`ReplayBattleEvent[]` + `TraceEvent[]`），两个数据源就会有两份真相、两类不同步的 bug。若调试日志是唯一事实来源，回放数据降级为它的投影（像 `BattleProjection` 之于领域实体），少一套数据结构就少一类 bug。
4. **演进论**：项目北极星是"因果树"，回放只是这棵树在时间维度上的播放；跨战斗对比（导出两份日志、按 `correlationId` 对齐 diff `steps[]`）本质上就是"并排回放"。调试视角天然覆盖回放视角，反之不成立。

## 四、反方立论：回放系统包含调试系统

1. **完整性论**：回放数据有快照（`initialState`、回合快照）——任意时刻跳转不需要重放全程；有随机种子——用 `SeededRandom` 确定性重演；有校验和——文件损坏可检出。**调试日志一样都没有。** 回放是"存档"，调试是"注释"——档案袋必须包住说明书，说明书包不住档案袋。注释丢了还能回放，存档丢了注释毫无意义。
2. **现实现证论**：数据结构已经裁决了——`traceEvents` 是 `RecordedBattle` 的**可选字段**（`traceEvents?: TraceEvent[]`），战斗结束才注入，缺省系统完好。字段依赖容器而存在，容器不依赖字段，谁包含谁一目了然。
3. **可执行性论**：调试日志记录的是**已经发生的随机结果**（`roll: 0.42`），回放要求的是**用同一个种子重新演算**（`randomSeed`）。一个是观察记录，一个是可执行剧本。只有剧本没有注释，能演；只有注释没有剧本，演不了。能重建战斗的一方，才是主体。
4. **产品形态论**：用户下载的 `battle_debug_*.json` 是**一份文件、两种能力**——回放面板和调试面板都消费这份 `RecordedBattle`。以"回放数据"为壳（存档格式），调试面板只是壳上的一个视图。壳稳定，视图随便加；反过来让调试日志当壳，它装不下快照和种子。

## 五、预判交锋（质询与回应）

- **正方质询**：你的 `events` 里每条事件只有结果没有过程——跳到第 3 回合，你解释得清"为什么是 85 不是 100"吗？没有调试日志的回放，和录像有什么区别？
  **反方回应**：这正是调试日志的价值，但它作为字段嵌在回放数据里，恰好证明它是被包含者。
- **反方质询**：你说调试日志补上种子和快照就能回放——那你补的这部分正是回放系统的核心资产（种子、快照、版本、校验）。补完之后那个"调试日志"已经不是日志，**是回放存档换了身马甲**。
  **正方回应**：这不叫换马甲，叫"唯一存档"——谁当壳不重要，重要的是别维护两份真相。
- **事实交锋**：调试面板现在就能单独导出纯 `trace-events-*.json`——这份文件能回放吗？不能。而 `battle_debug_*.json` 能。**用户手里那份"既能调试又能回放"的文件，叫回放数据。**
- **裁决式交锋**：决定包含关系的不是命名，是"谁的缺失会瘫痪"。删掉 `traceEvents`：回放照常、调试面板空转。删掉 `events` / `initialState` / `randomSeed`：回放瘫痪，只剩一堆无依无靠的 trace。谁缺了谁瘫痪，谁就是被包含的那个。

## 六、评判标准建议

1. **结构性**：谁的数据结构是容器、谁是字段？（当前实现：回放是容器）
2. **完整性**：去掉哪一部分，另一部分仍可独立工作？
3. **信息量**：谁解释"为什么"，谁只记录"是什么"？
4. **可执行性**：谁的文件能重建一场战斗（种子 + 快照），谁的文件只能旁观？
5. **演进性**：哪个方向未来维护成本更低（单一事实来源 vs 双格式同步）？

## 七、结辩参考

**正方**：调试系统不是"顺便打的 print"，它是战斗引擎在镜子里的完整投影——每个数字有来历，每个决策有理由。回放只是让这面镜子动起来。我们要的不是两个系统，而是一个以调试日志为唯一事实来源的系统，回放是它的播放键。

**反方**：存档是根基，解释是装饰。快照、种子、校验让一场战斗能被完整重建，这是回放系统的资产；调试日志是这份存档的说明书。说明书永远放在档案袋里，而不是档案袋放在说明书里。
