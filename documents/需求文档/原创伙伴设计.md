# 原创伙伴设计 · 拾烬

> 状态：设计稿，待实现
> 日期：2026-09-18
> 范围：伙伴（mate）战斗技能接入的首个验证角色 + 共享施工口径

---

## 一、背景：问题不在"几个角色"，在"伙伴不会放技能"

前期讨论过 1v4 / 4v4 / 10 角色全规格三条路线。核对代码后，这个选择题的前提不成立：

| 事实 | 位置 |
| --- | --- |
| 4v4 编成早已在跑：主角 + 至多 3 名上阵伙伴 | `src/presentation/modules/yanjie/xiyou/battle.ts:51` `buildPlayerParty()` |
| 上阵上限是一个常量，退回 1v4 成本 = 改一行 | 同文件 `:27` `MAX_ACTIVE_MATES = 3` |
| `mate.json` 现有 6 名伙伴，3 名 `active: true` | `configs/xiyou/mate.json` |
| **伙伴固定空技能，引擎普攻兜底** | `battle.ts:477` |
| **伙伴 schema 无技能字段**，只有 `name/role/rarity/level/stars/active/desc/stats` | `configs/xiyou/mate.json` |

所以当前 3 个伙伴的实际形态是 3 根数值柱子。战斗显得单调的原因是"伙伴不会放技能"，把它减到 1v4 不解决这个问题，只是把 3 根柱子换成 0 根。

**结论：唯一该做的第一步是给伙伴接技能，且从 1 个开始验证。**

---

## 二、根因：配置里放的是给人看的描述，不是引擎能执行的东西

同一个缺口在四个系统上重复出现：

| 系统 | 数据现状 | 战斗接入 |
| --- | --- | --- |
| 伙伴 | `configs/xiyou/mate.json` | `battle.ts:477` 写死空技能 |
| 法宝 | `configs/xiyou/equip.json` treasures 5 条 | 无消费者 |
| 坐骑 | 同上 mounts 4 条 | 无消费者 |
| 宠物 | 同上 / `mate.json` pets 长度 0 | 无消费者 |

法宝条目的 `"skill": "每次攻击后提升 3% 攻击，可叠 5 层"`、筋斗云的 `"skill": "首回合必定先手"` 是**中文描述文本，引擎不解析**。全仓唯一读取伙伴/宠物 `.active` 的战斗侧代码是 `debugActions.ts:670`，且那是扫荡 prep 的展示口径。

这四套系统的**数据表、面板 UI、存档槽、数值预算归属都已建成**（`save-schema.ts:70` 八槽含法宝神器；`domain/fengshen/` 有 `system_budget` 八系统枚举与 `budget-deviation` 校验器；规划文档给宠物/坐骑/法宝/神器各 60 属性点 = 各 9.09%）。缺的只有"进战斗"这一层。准确说法是：**已列预算、已建面板、未接战斗**。

**共享修法**：给 `mates` / `treasures` / `mounts` 统一加 `skillId` 引用 `configs/skills/*`，在 `xiyouToEnemy` 一处按单位类型取技能。一次施工，四系统受益。本文档负责把这条路的第一个实例做穿。

## 三、角色：拾烬

### 世界观依据

`configs/enemies/enemies.json` 的命名口吻给了明确线索——大量「旧花妖」「金蝉残影·净坛」「九齿残魂·朱刚鬣」「河伯·沧浪·千年执念」。神佛妖魔在这个世界里都已经是**灰烬与执念的残影**。那么原创伙伴不该是另一个现成神话人物，该是活在灰烬里的下一代。

### 设定

- **名字**：拾烬。动词 + 名词，与主角「降妖者」同构（`shared/constants/player.ts:3`）。
- **身份**：旧战场的拾灰人，提一盏灯笼收殓散落的余温。不收香火，只收没烧完的东西。
- **与主角的关系**：降妖者负责把执念打散，拾烬负责接住散下来的东西再还给主角。**打与收**，天然对应战斗里 DPS 与辅助的分工，不需要额外解释他为什么跟着你。
- **机制合法性**：因为敌人是"执念/妖气"（关卡有 `node.amp` 妖气增幅，见 `buildEnemyRoster`），"熄火"即驱散敌方增益，在这个世界里有叙事根据，不是硬凑的机制。

### 定位：控场放大器，明确不抢伤害

这是有意的设计约束。伙伴接技能后会真的开始输出，若伤害过高会破坏"玩家养的是主角"的体验。拾烬 Lv5 攻击只有 19，但他让**主角**的伤害变高。他的爽点应该是"上了他之后主角数字涨了"，而不是"他也砍得挺狠"。

## 五、数值决策与理由

| 项 | 值 | 理由 |
| --- | --- | --- |
| Lv1 基准 attack | 12 | 约为孙小圣（22）的 55%。辅助位有意压伤害，保证主角是团队最高输出 |
| Lv5 实战 | 416 / 19 / 11 / 22 | `mateToCombatant` 每级 +15%（`battle.ts:32`） |
| 单体技 80% / 大招 45% | 均低于普攻 100% | 他的输出不该是重点，裂甲才是 |
| 大招 `energyCost: 80` | 不可照抄主角的 150 | 伙伴 `maxEnergy: 100` 且 0 能量起步（`battle.ts:41-42`），每回合回能 15、受击 12。150 上限的 `golden_fury` 搬到伙伴身上会**永远放不出大招**；80 = 第 6 回合稳定可用 |
| 速度 22 > 主角 15 | 先手敲壳 | 顺序必须是"帮手先手把壳敲裂 → 主角后手打脆皮"，不能反过来 |
| 裂甲叠满节奏 | 约 4 回合 | 满层 −20% 防御，收益归全队，所以 AOE 挂层比单体挂层值钱 |

## 六、三个已核实的技术坑（实现前必读）

1. **被动触发点必须用 `AFTER_ATTACK`，不能用 `ON_ATTACK`。**
   `src/domain/battle/type/types.ts:774` 把旧名 `ON_ATTACK` 归一化为 `BEFORE_ATTACK`。用 `ON_ATTACK` 会让效果在本次攻击结算前生效，伤害与叠层口径全错。

2. **下列 Buff 是未接线的空壳，不能当设计素材：**

   | id | 症状 |
   | --- | --- |
   | `buff_baolu`（暴露） | 自述"受暴击率提升待属性落地" |
   | `buff_fengzhu`（风逐） | `executionMode: "marker"`，"段数+1 待连击引擎消费" |
   | `buff_jingji_stack`（荆棘） | `executionMode: "marker"`，"反伤比例动态提升待接线" |

   它们在面板上看起来可用，实际不产生任何战斗效果。设计前需先排除 `executionMode: "marker"` 一类条目。

3. **伙伴能量起点与引擎默认不一致。**
   `mateToCombatant` 硬编码 `energy: 0`，而引擎默认 `DEFAULT_INITIAL_ENERGY: 30`（`types.ts:122`）。要么让伙伴同样初始 30，要么明确"伙伴靠普攻与受击攒能"。这决定第几回合能放大招，实现时需与主角口径对齐后确认。

## 八、验证方案

用 `QuickBattleSim` 无头模拟跑同一场景两次：**带拾烬 / 不带拾烬**。

对比指标是**主角的伤害数字**，不是拾烬自己的。

- 战斗文本应出现「敲灯」「一盏照夜」；
- 敌方防御应逐回合下降（裂甲层数可见）；
- 主角同技能伤害应明显高于基线。

判定：主角伤害没明显上涨 → 这套辅助设计没成立，退回"让帮手直接当第二个打手"的路线；上涨且节奏可感 → 复制这套形状到其余伙伴，纯配置工作。

## 九、后续路线

每一步都是完整可玩状态，不存在烂尾中间态：

```
现在：拾烬 1 人接技能（本文档），主角为验证指标
  ↓ 成立
把 3 个已建成系统接进战斗：其余伙伴 + 法宝 + 坐骑（纯配置，同一处 xiyouToEnemy）
  ↓ 还想投
10 角色全规格 + 宠物独立数据表
```

宠物 / 坐骑 / 神器 / 法宝**不砍**——它们已占 `system_budget` 各 60 点额度、面板与存档齐备，属于"已列预算未施工"。等伙伴技能这条路验证通过，它们走同一处改动即可接入。
