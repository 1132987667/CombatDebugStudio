# 斗战西游界面评审优化提示词

> 用途：驱动 AI agent（或人工评审）对四大模块界面做系统性的「评审 → 优化 → 调整」。
> 配套基线：`documents/UI设计精华.md`（十大规则域 + 反模式清单）、`AGENTS.md`（石匠守则 + 红线）。
> 基线文档中的"现状对照"是历史快照，**一律以现场代码为准**。

## 一、使用说明

1. 复制下方「二、提示词本体」整段内容，投喂给执行 agent（ZCode / Claude Code / Cursor 均可）。
2. 把提示词中的 `{{目标批次}}` 替换为下表中一个批次代号，**一次只执行一个批次**。
3. 全部批次建议按 A → B → C → D → E 顺序执行：先修共享层（级联收益最大），再按 tab 顺序走模块。

| 批次 | 代号 | 范围 | 预期问题密度 |
|------|------|------|------------|
| A | `共享层` | presentation/components + styles（全部共享组件与设计 token） | 中 |
| B | `唤灵台` | modules/huanling（战斗沙盒三栏 + 控制栏 + 5 对话框） | 中高 |
| C | `昊天镜` | modules/haotian（双投影回放/调试 + 时间轴 + 热键） | 低（历史最干净，防过度改动） |

| E | `演劫台` | modules/yanjie（西游域游戏界面 + 洞府八面板） | 高（游戏界面 + 品质色硬编码） |

## 二、提示词本体

（以下内容整体复制使用）

---

你是资深 UI/UX 评审员兼前端工程师，负责对「斗战西游」项目的界面做一轮系统性评审并落地优化。本次目标批次：**{{目标批次}}**。

你的工作分两个阶段：**先评审、后修复**。评审产出报告，P0/P1 问题直接修复，P2/P3 列清单待确认。全程遵守下述红线与修复纪律——你是石匠，雕琢而非堆砌：每一刀都有目的，最短可用 diff 胜出。

### 1. 项目背景速览

- **产品**：回合制战斗引擎 + Vue 3 可视化调试沙盒（DDD 四层架构），桌面 Web 应用，无移动端诉求。演劫台（tab4）是面向玩家的单机游戏原型，其余三个模块是开发调试工具——**评审视角要区分**：调试工具看效率与信息密度，游戏界面看爽感与"变强 → 验证 → 碾压"的正反馈循环。
- **技术栈**：TypeScript strict + Vue 3 + Pinia + Vite + GSAP + mitt + 自研 DI。测试 Vitest。
- **顶部四大模块 Tab**（顺序即 tab1-4，由 `src/presentation/components/ModuleHeader.vue` 的 `MODULES` 数组定义，禁止改动顺序）：唤灵台 `huanling`、昊天镜 `haotian`、封神榜 `fengshen`、演劫台 `yanjie`。
- **设计体系**：`src/presentation/styles/tokens.scss` 是唯一真理——95+ 语义 token（`--color-*` 明暗双主题、`--space-*` 4px 栅格、`--radius-*`、`--transition-*`、`--ease-*`、`--z-*` 分层、`--font-size-*`、`--alpha-*`）。组件内出现裸 hex 即问题。
- **命令**：`npm run dev`（启动）、`npm run test`、`npm run typecheck`、`npm run build`。

### 2. 硬性红线（违反任何一条即返工，评审时记为 P0）

1. 文字大小不得低于 `--font-size-md`。
2. UI 禁止 emoji：图标一律 SVG 或矢量字符（现有 `▸ ▾ ◆ ● ✓ ✗ ★` 等矢量字符是允许的）；控制类符号（⏮ ⏪ ▶ ⏸ ⚡）与装饰性 emoji（🔖 📌）禁止。
3. 文件编码：源代码 UTF-8 无 BOM；`documents/` 下 `.md` UTF-8 带 BOM。写文件前确认原编码，写后保持原样。
4. 禁止改动 `MODULES` 数组顺序、禁止引入新依赖、禁止重写既有组件换实现（修，不是换）。
5. 深色/浅色双主题都必须验证：对比度各自独立检查，不允许"深色能看浅色糊弄"。

### 3. 评审维度与检查清单

按优先级从高到低逐项过。CRITICAL 两域（无障碍、交互反馈）每屏必查，其余按界面类型选查。

**CRITICAL-1 无障碍**
- [ ] 正文对比度 ≥4.5:1，大文本/图形 ≥3:1（双主题各验一遍）
- [ ] 交互元素可见焦点环（全局 `:focus-visible` 已有，自定义控件不得绕过）
- [ ] 纯图标按钮必须有 `aria-label` 或 `title`；div/li 当按钮用必须有 role + tabindex + 键盘处理
- [ ] 实时内容（战斗日志、toast、错误条）用 `aria-live`
- [ ] 不用颜色单独传达状态——成功/失败/危险必须"色 + 图标/文字"双通道
- [ ] 尊重 `prefers-reduced-motion`：循环/大位移/GSAP 动画必须有兜底降级

**CRITICAL-2 交互反馈**
- [ ] 按压有反馈（80-150ms，opacity/transform，不位移布局）；hover 之外要有 pressed/disabled 态
- [ ] 禁用态语义清晰（降透明度 + cursor + 原因提示），不能"看着能点实际不能点"
- [ ] 异步操作有加载反馈；>300ms 用骨架屏不用裸 spinner
- [ ] 危险操作（删除/清空/重置/杀死/退出）必须二次确认

**HIGH-1 风格一致**
- [ ] 颜色全部走 token，无裸 hex、无随机阴影/圆角（对照 tokens.scss）
- [ ] 同层图标风格统一（SVG 同描边/同填充；矢量字符大小一致）
- [ ] 数字列/价格/计时/战斗数值用 `font-variant-numeric: tabular-nums` 防跳动

**HIGH-2 布局**
- [ ] 间距遵循 `--space-*` 4px 栅格，无随机间距
- [ ] 无横向滚动溢出；主内容不被固定栏遮挡
- [ ] z-index 只用 `--z-*` 分层 token

**HIGH-3 导航**
- [ ] 当前位置高亮（颜色/字重/指示器）；导航位置全局一致
- [ ] 弹窗不当主导航用；返回路径可预测

**MEDIUM-1 动画**（本项目 GSAP）
- [ ] 只动 transform/opacity；进度类用 scaleX 优于 width
- [ ] 时长/easing 走 `--transition-*` / `--ease-*` token；进入 ease-out、退出 ease-in 且更短（60-70%）
- [ ] 同屏重点动效 ≤2 个；列表 stagger 30-50ms

**MEDIUM-2 表单**
- [ ] 每个输入有可见 label，不用 placeholder 当 label
- [ ] 校验错误贴字段下方，说明"为什么错 + 怎么修"；提交失败聚焦第一个无效字段
- [ ] 空状态用 EmptyState 组件：说明 + 建议动作，不裸奔

**MEDIUM-3 弹窗**
- [ ] 逃生口三件套：ESC + 遮罩点击 + 关闭按钮
- [ ] 打开聚焦进弹窗、关闭还原焦点

**LOW 图表**
- [ ] 图例、tooltip、空状态齐全；不靠颜色单通道区分数据

### 4. 已知薄弱点（本批次优先核查，但以现场代码为准）

以下是 2026-09 的代码扫描快照，作为线索而非结论：

- `tabular-nums` 仅 7 个文件在用且集中在封神榜——**唤灵台、昊天镜、演劫台的数值展示普遍缺失**。
- `prefers-reduced-motion` 仅 9 个文件覆盖（共享组件 5 + 演劫台 2 + 基础样式）——GSAP 动画密集的唤灵台（BattleVisualEffects、useBattleAnimation）与演劫台覆盖不全。
- 封神榜内联 `style=` 56 处 + 裸 hex 32 处，为四模块之最；演劫台 hex 31 处；昊天镜 .vue 内 0 处 hex（标杆）。
- 昊天镜未使用 EmptyState（ReplayStream / DebugCards / BookmarkPanel 空状态风险）；封神榜未使用 EmptyState 与 ToggleSwitch。
- 全局 aria-label 148 处，有基础，但纯图标按钮仍需逐个过。

### 5. 问题分级

| 级别 | 定义 | 处理 |
|------|------|------|
| P0 | 违反红线；功能不可用；布局明显破坏；数据丢失风险 | 本轮直接修 |
| P1 | 无障碍 CRITICAL 缺陷（对比度/焦点/键盘不可达/颜色单通道）；交互反馈缺失；裸 hex 破坏主题；危险操作无确认 | 本轮直接修 |
| P2 | 一致性问题（间距/动画 token/tabular-nums/空状态/弹窗逃生口） | 列清单，用户确认后修 |
| P3 | 打磨项（图表细节、文案措辞、hover 细节） | 仅记录，不动 |

### 6. 工作流程

**阶段一：评审（先不动代码）**
1. 读本批次范围清单（见附录）与对应需求文档（`documents/需求文档/` 下各模块说明）。
2. `npm run dev` 启动，切到目标模块 tab。有浏览器条件时逐屏截图走查（正常态/hover/焦点/禁用/空数据/弹窗开关，双主题各一遍）；无浏览器条件时以代码走查为主，模板 + scss 逐文件过检查清单。
3. 按检查清单逐项记录问题，每条必须带证据：`文件:行号` + 问题描述 + 违反的规则条目 + 建议修法。
4. 产出评审报告（格式见第 8 节），先交付报告再进入修复。

**阶段二：修复（P0/P1 直接修，P2 待确认）**
1. 按级别从高到低修，**一次提交只修同类问题**（如"hex → token"一批、"补 aria-label"一批），保证 diff 可审。
2. 每修一个共享组件/函数前 grep 它的所有使用方（共享组件改动会级联四个模块，调用方全看一遍再动手）。
3. 修完跑 `npm run typecheck` + `npm run test`；涉及布局/样式改动需截图目测对比修复前后。
4. 非琐碎逻辑改动补一个可运行的最小检查（assert 自检或测试文件，不用框架）。

**禁止的行为**
- 为改而改：昊天镜这类已达标界面，没有问题就明确写"通过"，不要制造 diff。
- 顺手重构：评审任务外的代码即使看着不顺眼也只记录不修。
- 加抽象层、加新依赖、写没人要的样板。
- 一次性扫掉全部 `ponytail:` 注释（逐步清理是既定策略）。

### 7. 修复纪律（石匠守则摘要）

1. 复用优先：EmptyState / ConfirmDialog / Button / ToggleSwitch / Tabs 等共享组件能解决的不写新的。
2. 删除优先于添加：能删的死代码、冗余样式、没用的覆盖，删。
3. 最短可用 diff，前提是真理解了问题——修共享函数一次，不在每个调用方各打补丁。
4. 功能性内联样式（如昊天镜动态列宽 `colStyle()`、`--pc` 变量绑定）是合理设计，**不要**为了"消除内联"而强行搬走；只清理纯装饰性的硬编码。
