## §1 问题定性

### 1.1 现状：五个互不相识的碎片

当前调试日志并非"一个系统"，而是五条独立管道各自为政：

| # | 碎片 | 位置 | 覆盖范围 | 缺陷 |
|---|------|------|----------|------|
| 1 | `BattleLogManager.addDebugLog()` | `infrastructure/adapters/logging/` | 全局自由文本 | 无结构、无关联、无 battleId 绑定；调用点 domain 60+ 处 + presentation 15 处，错误路径约占 20 处但几乎全部默认 `INFO` 级（`BattleLogManager.ts:234`） |
| 2 | `TraceLogCollector` + `TraceDamageLogger` | `domain/battle/logs/` | 收集器本身是通用索引器（turn/stepName 查询、树重建齐备），但**数据来源只有三处**：伤害链路、Buff 生命周期、被动触发（仅触发时） | 不覆盖 AI 决策、属性重算、回合流转、被动"没触发" |
| 3 | `BuffTraceLogger` | `domain/battle/logs/` | 仅 Buff 施加/移除/层数/修饰符 | 纯静态方法；traceId 命名自成一系（`buff_apply_N`），与伤害链路（`trace_dmg_N`）、被动（`pas_N`）不共享命名空间，无 correlationId |
| 4 | `console.log` / `console.error` 散布 | 全领域层（`BattleSystem.ts:387/890/1058`、`BattleAI.ts:144/149/159`、`BuffContext.ts:61-97` 等 **38 处**） | 随机 | 绕过日志系统，无法收集、过滤、持久化 |
| 5 | `RecordedBattle.traceLogs` | `domain/battle/service/BattleRecorder.ts:245` | 战斗结束时由 `TraceLogCollector` 导出 | **无消费者**——`ReplayEngine.ts:91` 注释明确：ReplayEngine 只处理 BattleReplay（events/rounds），不处理 RecordedBattle（combatRecords/traceLogs） |

> **v1 勘误**：v1 表格中的 `BattleRecorder.generateLogMessage()`（旧 :430-450）已删除，不再是碎片之一。

### 1.2 根因：数据契约缺失

与项目中已识别的 20 处"启发式猜测"反模式同源——**数据生产者未显式声明语义，迫使下游消费者猜测**：

- `addDebugLog(message: string)` 的 `message` 是自由文本，下游只能做字符串匹配
- 一次技能执行涉及伤害计算、Buff 施加、被动触发、属性重算，但这些事件之间**没有 `correlationId`** 将它们串联为因果链
- `TraceLogEntry` 有 `traceId` / `parentTraceId`，但三个写入方（`TraceDamageLogger` / `BuffTraceLogger` / `PassiveSkillManager:273`）**不共享 traceId 命名空间**：`trace_dmg_N` / `buff_apply_N` / `pas_N` 各说各话
- `LogLevel` 枚举存在（`ERROR/WARN/INFO/DEBUG/TRACE`），但 `addDebugLog` 的调用方几乎全部使用默认 `INFO`，级别语义形同虚设
- 调试日志不绑定 `battleId`，`BattleDataGenerator` 批量生成 50 场战斗时日志混在一起

### 1.3 影响量化

| 维度 | 当前 | 目标 |
|------|------|------|
| 追踪覆盖率 | 伤害链路 + Buff 变更 + 被动触发（约 35% 运行时事件） | 全部关键运行时事件（AI 决策、技能执行、伤害/治疗计算、Buff 生命周期、被动触发/跳过、属性重算、回合流转） |
| 因果链关联 | 无（三个写入方命名空间互不相识） | 同一 `correlationId` 串起一次行动的完整因果链 |
| 结构化程度 | 自由文本为主（DMG_SUM 等文本行 + 孤立树节点） | 结构化 `payload` + 人类可读 `summary` |
| 战斗隔离 | 无 | 按 `battleId` 分桶 |
| 生产环境开销 | `console.log` 始终执行 | 运行时 `isEnabled` 门控（P0）+ 编译期消除（P3） |
| 死数据 | `RecordedBattle.traceLogs` 无人消费 | 转为 `RecordedBattle.traceEvents`（P3）或明确移除 |

## §2 指导原则

### 原则一：调试日志是领域事件的投影，不是副作用

调试日志不是"顺便打一行 `console.log`"，而是领域运行时状态的**结构化投影**。

每一次伤害计算、每一次 AI 决策、每一次属性重算**本身就是一条领域事件**（有输入、有输出、有中间步骤）。调试日志系统的工作不是"在业务代码中插入打印语句"，而是**让这些已经存在的领域事件被结构化地捕获、关联、存储、查询**。

### 原则二：结构化优先，文本是最后手段

任何需要下游解析才能提取信息的日志格式，都是设计失败。

```
❌ addDebugLog("DMG_SUM 剑士→史莱姆 | base=100 final=85 crit=false defRed=15%")
✅ tracePort.emit({ phase: 'damage_calculation', payload: { base: 100, final: 85, crit: false, defenseReduction: 0.15 } })
```

文本 `summary` 仅用于人类快速扫读，**不作为任何程序逻辑的输入**。

### 原则三：零成本关闭，按需开启

- **未开启时**：日志发射点不执行任何序列化、不分配任何对象、不产生任何 I/O（发射点先查 `isEnabled` 再构建 payload）
- **开启时**：完整捕获，但不影响战斗时序、不改变随机种子、不引入额外 `await`
- **实现手段（分两步）**：P0 先做运行时 `isEnabled` 门控；编译期消除（`import.meta.env.DEV` 守卫）后置 P3，且注意 `import.meta.env` 对领域层的侵入要在 adapter 层收敛

### 原则四：记录"没发生"与记录"发生"同等重要

被动没触发，必须留下痕迹：是概率 roll 失败？冷却未就绪？条件不满足？目标已死亡？当前 `PassiveSkillManager.shouldTriggerPassive()` 返回 `false` 时什么都不说（且 `PassiveSkillManager.ts:274` 只在 `hasExecuted` 时写 trace）——这是调试被动技能最大的黑洞。

## §4 数据模型

### 4.1 追踪阶段枚举

> **边界声明**：`TracePhase` 只描述"正在发生的领域阶段"。**错误/警告不属于任何 phase**——catch 块不是阶段而是事件，走 §4.6 的错误通道，禁止为错误编造 phase。

### 4.2 结构化追踪事件

```typescript
export interface TraceEvent {
  /** 事件唯一 ID（自动生成） */
  id: string
  /** 关联 ID — 同一因果链的所有事件共享此 ID */
  correlationId: string
  /** 父事件 ID — 构成树状嵌套 */
  parentId?: string
  /** 追踪阶段 */
  phase: TracePhase
  /** 战斗实例 ID — 隔离多场战斗 */
  battleId?: string
  /** 回合号 */
  turn?: number
  /** 来源实体 ID（供 actorId 过滤索引） */
  sourceId?: string
  /** 目标实体 ID（供 actorId 过滤索引） */
  targetId?: string
  /** 时间戳（performance.now()，非 Date.now()） */
  timestamp: number
  /** 结构化 payload — 按 phase 不同而不同 */
  payload: Record<string, unknown>
  /** 人类可读摘要（仅用于快速扫读，不作为程序输入） */
  summary: string
  /** 级别（字符串级联常量 TraceLevel，与数值型 LogLevel 独立） */
  level: TraceLevel
}
```

### 4.4 TraceScope —— correlationId 作用域

v1 只定义了 `beginScope()` 签名，没有返回类型，也没回答"scope 生命周期"。v2 补全：

```typescript
// src/shared/types/trace-event.ts（与 TraceEvent 同文件）

export interface TraceScopeMeta {
  battleId?: string
  turn?: number
}

export interface TraceScope {
  readonly correlationId: string
  readonly phase: TracePhase
  /** 本 scope 事件的挂载点（根 scope 为 undefined；供 emit 时作 parentId） */
  readonly parentId?: string
  readonly meta?: TraceScopeMeta
  /** 派生子 scope：correlationId/meta 不变，phase 与 parentId 可覆盖 */
  child(phase: TracePhase, parentId?: string): TraceScope
}

// 端口接口（src/domain/port/IDebugTracePort.ts）
export interface IDebugTracePort {
  /** 发射事件，返回事件 id（供子事件挂 parentId） */
  emit(event: TraceEvent): string
  isEnabled(phase: TracePhase): boolean
  beginScope(correlationId: string, phase: TracePhase, meta?: TraceScopeMeta, parentId?: string): TraceScope
}
```

**关键设计：`correlationId` 在整条因果链上保持不变，树的嵌套关系由每个事件的 `parentId` 表达。** 与 `TraceLogEntry.traceId/parentTraceId` 同构，但命名空间统一（§4.5）。

### 4.5 correlationId 生命周期与流动机制（v1 最大空白，细化）

#### 4.5.1 根 scope 的创建点

**`BattleExecutor.executeParticipantAction()`（`BattleExecutor.ts:186`）——每"一次行动"一个 scope**，覆盖从 AI 决策到结算的完整因果链：

```
executeParticipantAction(battle, participant)                // BattleExecutor.ts:186
  │  const base = tracePort.beginScope(`corr_${turn}_${++seq}`, ACTION_EXECUTION, {battleId, turn})
  │  const execId = tracePort.emit(createTraceEvent({ phase: ACTION_EXECUTION, parentId: base.parentId, ... }))
  │  const actionScope = base.child(ACTION_EXECUTION, execId)   // 子事件 parentId = ACTION_EXECUTION 事件 id
  │
  ├─ aiInstance.makeDecision(battleState, participant, base)  // BattleAI.ts:39 接口新增可选第 3 参
  │     └─ emit(AI_DECISION, base)                            // 决策挂根（parentId=undefined）
 │     └─ skillManager.executeSkill(..., ctx)                 // ctx.trace = scope（StepExecutionContext）
 │           └─ SkillExecutor.executeStep(skillStep, action, source, target, context)
 │                 ├─ emit(ACTION_EXECUTION, context.trace)
 │                 ├─ DamageCalculator.calculateDamage(..., context)   // DamageCalculator.ts:105
 │                 │     └─ emit(DAMAGE_CALCULATION, context.trace, { steps })  // payload.steps 直接复用
 │                 ├─ HealCalculator.calculateHeal(..., context)       // HealCalculator.ts:34
 │                 └─ BuffSystem.addBuff(..., context)      // addBuff 第 5 参已是 context（BuffSystem.ts:405）
 │                       └─ emit(BUFF_LIFECYCLE, context.trace)
 │                       ※ removeBuff（:840）/ refreshBuff（:927）无 context 参，
 │                          需扩展可选 trace 参数（仅这两个方法，向后兼容）
 │
 └─ 被动触发链（BEFORE_ATTACK / DAMAGE_TAKEN …）
       └─ createPassiveContext(phase, battle, { trace: scope })         // types.ts:943 扩展
             └─ emit(PASSIVE_TRIGGER, context.trace)
```

#### 4.5.2 贯穿载体：`StepExecutionContext.trace`（零新增参数）

**现状**：`SkillExecutor`（8 个方法）、`DamageCalculator`（:105/:607）、`HealCalculator`（:34）、`BuffSystem`（:405）**已经全部接收 `context?: StepExecutionContext`**；`createStepContext(record, token, fromPassive, damage)` 工厂已有 4 个调用点（`BattleExecutor.ts:1284`、`SkillManager.ts:375`、`PassiveSkillManager.ts:363`）。

**变更**（每个都是向后兼容的可选参数）：

1. `StepExecutionContext` 增加 `readonly trace?: TraceScope`（`types.ts:917`）
2. `createStepContext(record, token, fromPassive, damage, trace?)` 增加可选参数（`types.ts:961`），调用点按需传入
3. `BattleAI.makeDecision(battleState, participant, trace?)` 增加可选参数——接口（`BattleAI.ts:39`）与实现（`BattleAI.ts:127`、`AISystem.ts:99` 包装）同步加；**不传则 AI_DECISION 退化为独立事件（correlationId 自生成），不破坏现有调用**

**为什么不需要新增参数穿过整个调用链**：scope 搭在已有 context 上流动，发射点从 `context.trace` 取即可。这是 v2 相对 v1 最重要的机制澄清——v1 只写了"correlationId 由 BattleExecutor 传入"，没有回答怎么传到 `DamageCalculator`（距离 4 层调用、跨 3 个文件）。

#### 4.5.3 命名空间统一

| 现在 | 之后 |
|------|------|
| `trace_dmg_1`（TraceDamageLogger） | `corr_3_17`（correlationId，战斗内自增） |
| `buff_apply_1`（BuffTraceLogger） | 同上（同一因果链共享） |
| `pas_1_${Date.now()}`（PassiveSkillManager:277） | 同上 |

`TraceEvent.id` 才是每个事件的唯一 ID（`evt_${seq}`，createTraceEvent 生成），correlationId 只表关联。

#### 4.5.4 并发安全：为什么显式传参，不用隐式全局

`BattleDataGenerator` 批量生成 50 场战斗时多场战斗可能交错执行；隐式"当前 scope"（AsyncLocalStorage / 全局变量）在 `async/await` 边界会串场。**显式参数传递无此问题——scope 是值对象，随调用链流动，天然隔离。**

#### 4.5.5 作用域结束

无需显式 close。scope 是纯数据（correlationId + meta + child()），emit 时读取，`executeParticipantAction` 返回即自然消亡。

### 4.6 错误日志通道与双端口边界（v1 空白，细化）

#### 4.6.1 决策

**错误/警告不属于"领域事件投影"，不进入 TracePhase 体系。** 理由：`TracePhase` 描述"正在发生的领域阶段"，catch 块里的错误不是阶段；给错误编 phase 会变成"错误种类 × 阶段"的组合爆炸。

| | `IDebugTracePort`（新增） | `IBattleLogManager`（现有） |
|---|---|---|
| 语义 | 领域事件的结构化投影（正在发生什么） | 面向人的日志（出错了 / 系统消息） |
| 数据形态 | `TraceEvent`（phase + payload + correlationId） | `LogEntry`（level + message + context/error） |
| 消费者 | `TraceEventCollector` → 因果链视图 | `DebugLogDialog` 扁平列表、战斗文本 |
| 级别 | trace / debug / info | warn / error |
| 错误转发 | 无 | ERROR 级转发 `console.error`（`BattleLogManager.ts:236-238`） |
| 持久化 | 战斗结束 → `RecordedBattle.traceEvents`（P3） | 内存分桶 + 导出 |
| 失败语义 | emit 永不抛异常 | 同左 |

#### 4.6.2 addDebugLog 调用点三分法（v1 遗漏的最大工作量）

domain 层 `addDebugLog` 调用点 **60+ 处**，v1 的删除清单没有覆盖它们。分类处置：

| 类别 | 数量级 | 处置 | 示例 |
|---|---|---|---|
| **错误/警告路径** | ~20 处 | **保留** `addDebugLog`，强制显式 `level: WARN/ERROR` + 附 error/context（现状大量默认 INFO） | 保存/加载战斗记录失败（`BattleRecorder.ts:427/477`）、Buff 错误（`BuffErrorBoundary.ts:58-70`）、AI catch（`BattleAI.ts:149-163`）、自动战斗 catch（`AutoBattleManager.ts:88-159`） |
| **调试信息路径** | ~30 处 | 迁移到 `tracePort.emit`（phase 有对应）或**直接删除**（无对应且无价值） | `执行技能 X`（`SkillManager.ts:363`）、`回合 N 执行完成`（`BattleSystem.ts:1429`）、`注册BUFF脚本`（`BuffScriptRegistry.ts:300`） |
| **战斗叙事文本** | 少数 | **不动**——那是 `addBattleLog` 的领域（`BattleExecutor.ts:205-222` 即 addBattleLog），不在调试日志范围 | `角色[名] 被控制，无法行动` |

#### 4.6.3 LoggerProvider 处置修订

v1 主张"消灭 `LoggerProvider` 静态服务定位器"。核查后修订为**保留**：

- 它已在 `domain/port/` 下、面向 `IBattleLogManager` 端口（`LoggerProvider.ts:17-33`），**不是反向依赖**，是"静态"问题
- 错误通道（4.6.2 第 1 类）仍需要访问日志器，`IDebugTracePort` 通过 DI/setter 注入（与 `BattleSystem.ts:189` 构造注入、`BattleExecutor.ts:134` setter 注入的现有模式一致）
- 迁移优先级低于 tracePort 本身；当错误通道调用点收敛后（全部改构造注入）再议删除

## §6 编码规范

### 6.1 发射点写法

```typescript
// ✅ 先查开关，再构建 payload（热路径零开销）
if (tracePort.isEnabled(TracePhase.DAMAGE_CALCULATION)) {
  tracePort.emit({ ..., payload: buildDamagePayload(breakdown) })
}

// ✅ payload 里放事实和数字，不放形容词
payload: { probability: 0.6, roll: 0.73, passed: false }

// ✅ summary 用固定模板，便于扫读和文本搜索
summary: `伤害计算 ${source}→${target} ${base}→${final}${crit ? ' ★暴击' : ''}`

// ✅ 子事件带 parentId，构成树
parentId: context.trace.parentId

// ✅ trace 一律从 context.trace / scope 取，禁止自行 newTraceId
correlationId: context.trace.correlationId
```

### 6.2 禁止写法

```typescript
// ❌ 字符串插值承载语义（下游只能正则）
emit({ summary: `概率 ${0.6 * 100}%，roll 了 ${roll}，没通过` })

// ❌ 形容词代替事实
emit({ summary: '伤害被大幅削减' })

// ❌ 无开关检查的昂贵构建
emit({ payload: serializeEntireBattleState() })

// ❌ 孤立事件（无 correlationId / parentId）——自造 traceId 命名空间（trace_dmg_N / buff_apply_N / pas_N）同样禁止
emit({ phase: TracePhase.DAMAGE_CALCULATION })

// ❌ 领域层直接 console.log
console.log('初始化战斗数据', battleData)   // BattleSystem.ts:387
console.log(`${participant.name} chose skill`, skillId)  // BattleAI.ts:144
```

### 6.3 级别约定（v2 统一口径）

| 级别 | 语义 | 默认 | 示例 |
|------|------|------|------|
| `error` | 不该发生的事发生了 | 开 | 配置错误、脚本异常、递归超限（走 §4.6 错误通道，`addDebugLog` + level） |
| `warn` | 可恢复的异常 | 开 | 技能降级为普攻、目标失效回退（同上） |
| `info` | 关键状态迁移 | 开 | 战斗开始/结束、回合切换（TURN_FLOW） |
| `debug` | 完整因果链节点 | 开 | 伤害计算、AI 决策、**Buff 施加/移除/刷新（BUFF_LIFECYCLE）**、被动触发 |
| `trace` | 高频细节与"跳过"记录 | **关** | 属性重算（ATTRIBUTE_RECALC）、被动跳过、监听器分发明细 |

> **v2 修订**：v1 的表格与此处示例 4 有冲突（示例 4 的 BUFF_LIFECYCLE 是 debug 级，但现状 BuffTraceLogger 全部输出 TRACE 级，trace 默认关会让 Buff 生命周期不可见）。v2 明确：**迁移时 Buff 生命周期定级 debug**，trace 只留给属性重算与"跳过"记录。

| 发射点 | 文件 | TracePhase | scope 来源 |

## §8 验收标准

系统完成，当且仅当以下四个调试会话**都能在 30 秒内完成**：

### 故事 A · 伤害取证

> "第 3 回合剑士对史莱姆的伤害为什么是 85？"

操作：过滤 `phase=damage_calculation` + `actor=剑士` → 点开因果链 → 看到 `steps[]` 逐步 `before→after`。

**不需要打开任何源码。**

### 故事 B · 决策取证

> "为什么 AI 这回合选了治疗？"

操作：过滤 `phase=ai_decision` → 看到三个候选的权重数字与 breakdown → 看到 `hasLowHealthAlly: true` 贡献了 +40。

**不需要在 `AIPriorityStrategy` 里加 `console.log`。**

### 故事 C · 被动取证

> "荆棘反甲为什么没触发？"

操作：过滤 `phase=passive_trigger` + `owner=史莱姆` + 展开 trace 级 → 看到 `verdict: SKIPPED, skipReason: COOLDOWN, remaining: 1`。

**不需要猜测，不需要复现。**

### 故事 D · 跨战斗对比

> "同一个技能，为什么第 2 场比第 1 场伤害高？"

操作：分别导出两场战斗的 `TraceEvent[]` → 按 `correlationId` 对齐同名因果链 → diff 两条 `steps[]` → 看到差异在 `damageBoost` 一步。

**面板提供导出功能，导出的 JSON 天然可 diff（对比 UI 降级，见 §7 P2）。**

## 附录 A：与 20 处反模式的关系

调试日志系统的重构与已识别的 20 处"启发式猜测"反模式**共享同一个根因**：

> 数据生产者未显式声明语义，迫使下游消费者猜测。

在调试日志领域，这个根因表现为：

| 反模式表现 | 涉及 # | 修复方式 |
|------------|--------|----------|
| 领域层产出自由文本，下游正则解析 | #1, #14 | `payload` 结构化，`summary` 仅供扫读 |
| 事件之间无关联 ID，下游靠时间戳猜关联 | #9, #12 | `correlationId` 显式串联（§4.5） |
| 事件无结构化 payload，下游 `JSON.stringify` + 字符串搜索 | #5, #11 | `payload: Record<string, unknown>` |
| 被动"没触发"无记录，调试者只能猜 | #13 | `verdict: SKIPPED` + `skipReason` 枚举 |
| 录制时生成数据，回放时从不消费 | #14 | **v2 勘误**：`generateLogMessage()` 已删；剩余对象是 `RecordedBattle.traceLogs`（`BattleRecorder.ts:245`），P3 以 `traceEvents` 替换或明确移除 |
| 双时序模型并存（主系统 vs 回放引擎） | #19 | 与本次重构无直接关系，`TraceEvent.timestamp` 使用 `performance.now()` 统一时基；回放引擎不执行计算（`ReplayEngine.ts:91`），**不产生 tracePort 事件，无需接入** |

## 附录 B：实施约束（v2 修订）

1. **不改变运行时行为。** 每一层修复前后，**战斗结果、战斗文本日志（`addBattleLog` 输出）、动画时序**必须完全一致。修复的是"谁负责决定语义"，不是"语义是什么"。**调试日志内容允许结构化变化**——这正是重构目的（v2 修订，消除与 B.4 的矛盾）。

2. **删除优先于添加。** 每新增一个 `emit` 调用，必须同步删除对应的 `console.log` / 旧的 `TraceDamageLogger.log` / `BuffTraceLogger.onXxx` / 调试信息类 `addDebugLog`。不允许"新通道加了，旧通道也留着做兼容"——兼容期不超过一个迭代。

3. **单一事实来源。** 每个语义只在一个位置决定：

   | 语义 | 唯一来源 |
   |------|----------|
   | 伤害计算步骤 | `DamageCalculator` → `DamageBreakdown.steps` |
   | AI 权重 | `AIPriorityStrategy.calculateSkillWeights()` |
   | 被动触发/跳过 | `PassiveSkillManager.shouldTriggerPassive()` |
   | Buff 生命周期 | `BuffSystem.addBuff/removeBuff/refreshBuff` |
   | 属性重算 | `ParticipantStats.recalcAttribute()` |
   | 回合流转 | `BattleSystem.processTurnInternal()` |
   | **correlationId** | **`BattleExecutor.executeParticipantAction()`（根 scope，§4.5）** |

4. **测试守护。** 每删除一处旧日志调用，对应的行为由现有测试守护（`tests/unit/TraceEventCollector.test.ts`，含树重建 / phase / battleId / actorId 查询 / **空维度匹配返回空** / beginScope 共享 correlationId / emit 容错用例，全量 183 用例）。**不为旧日志格式本身写测试**——旧格式是要被删除的，不是要被固化的。

## 一句话总结

**调试日志不是"开发时顺便打的 print"，而是领域运行时状态的结构化投影。重构的核心不是"加更多日志"，而是"让已经存在的领域事件被正确地捕获、关联、存储"。** 一个 `correlationId` 串起一条因果链（根在 `BattleExecutor`，沿已有的 `StepExecutionContext` 零成本贯穿），一个 `TracePhase` 标明一个运行时节点，一个结构化 `payload` 消灭所有正则解析，一个独立错误通道承接 catch 块。调试日志系统的完成度，就是领域层可观测性的完成度。
