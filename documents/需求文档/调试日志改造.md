## §2 指导原则

### 原则一：调试日志是领域事件的投影，不是副作用

调试日志不是"顺便打一行 `console.log`"，而是领域运行时状态的**结构化投影**。

每一次伤害计算、每一次 AI 决策、每一次属性重算**本身就是一条领域事件**（有输入、有输出、有中间步骤）。调试日志系统的工作不是"在业务代码中插入打印语句"，而是**让这些已经存在的领域事件被结构化地捕获、关联、存储、查询**。

### 原则二：结构化优先，文本是最后手段

任何需要下游解析才能提取信息的日志格式，都是设计失败。

```
❌ addDebugLog("DMG_SUM 剑士→史莱姆 | base=100 final=85 crit=false defRed=15%")
✅ tracePort.emit({ phase: 'damage_calculation', payload: { base: 100, final: 85, crit: false, defenseReduction: 0.15 } })
```

文本 `summary` 仅用于人类快速扫读，**不作为任何程序逻辑的输入**。

### 原则三：零成本关闭，按需开启

- **未开启时**：日志发射点不执行任何序列化、不分配任何对象、不产生任何 I/O（发射点先查 `isEnabled` 再构建 payload）
- **开启时**：完整捕获，但不影响战斗时序、不改变随机种子、不引入额外 `await`
- **实现手段**：运行时 `isEnabled` 门控（发射点先查开关）；如需编译期消除（`import.meta.env.DEV` 守卫），注意对领域层的侵入要在 adapter 层收敛

### 原则四：记录"没发生"与记录"发生"同等重要

被动没触发，必须留下痕迹：是概率 roll 失败？冷却未就绪？条件不满足？目标已死亡？**调试"为什么没触发"与"为什么触发"同等重要**——`SKIPPED` 事件带原因码（`COOLDOWN | PROBABILITY | CONDITION | MAX_TRIGGERS | DEAD | PHASE_MISMATCH`），trace 级、默认隐藏，需要时展开查看。

## §3 完成态愿景

### 3.1 北极星图景

打开调试面板，选中第 3 回合，看到的不再是散落的文本行，而是一棵**因果树**——每个数字都有来历，每个决策都有理由，每个状态变化都有源头：

```
▼ [回合 3] AI_DECISION · 剑士 选择 【烈焰斩】                    ⏱ 0.4ms
│   weights: 烈焰斩=142 ▸ 防御姿态=65 ▸ 普通攻击=50
│   选中理由: 基础50 + 伤害技能30 + 高威胁目标30 + 能量充足(85≥40)
│
└─▼ ACTION_EXECUTION · 剑士 → 史莱姆 执行【烈焰斩】              ⏱ 11.2ms
  │   energy: 85 → 45 · targets: [史莱姆]
  │
  ├─▼ PASSIVE_TRIGGER · BEFORE_ATTACK · [剑士] 先发制人           ✓ 已触发
  │   │   probability: 100% · roll: 0.42 · cooldown: 就绪
  │   └─ BUFF_LIFECYCLE · 施加【先发制人】→ 剑士
  │         modifier: damageBoost +25% · duration: 1回合 · stacks: 1
  │
  ├─▼ DAMAGE_CALCULATION · 剑士 → 史莱姆 · 100 ──▶ 85            ★ crit
  │   │   base          0 → 100    基础威力 100
  │   │   extra       100 → 130    attack 150 × 0.2
  │   │   crit        130 → 162    ×1.25 (暴击率32%, roll 0.18)
  │   │   damageBoost 162 → 178    伤害提升 +10%
  │   │   ── rawDamage = 178 ──
  │   │   defense     178 →  98    防御 80 减法减免
  │   │   skillDmgRed  98 →  88    技能减免 10%
  │   │   damageRed    88 →  85    免伤率 3%
  │   │   clamp        85 →  85    阈值 [1, 9999]
  │   └─ final: 85 · raw: 178 · category: physical
  │
  ├─▼ SETTLE · 史莱姆 承受 85                                     HP 240 → 155
  │   ├─ THREAT · 剑士 仇恨 +85 (累计 340)
  │   ├─ TRIGGER_EVENT · DAMAGE_TAKEN 广播 → 2 个监听器
  │   └─▼ PASSIVE_TRIGGER · DAMAGE_TAKEN · [史莱姆] 荆棘反甲      ✓ 已触发
  │       └─▼ DAMAGE_CALCULATION · 反伤 史莱姆 → 剑士 · 25
  │
  ├─ BUFF_LIFECYCLE · 【先发制人】到期移除 → 剑士
  └─ ATTRIBUTE_RECALC · 剑士 damageBoost: 25% → 0%
```

> **与北极星愿景的差异（演进中的设计决策，§3.4 原内容）**：
> - `rawDamage` / `clamp 85→85` 不出现——**无变换节点不记录**，值在 payload 顶层 `raw`/`final`
> - `SETTLE` / `THREAT` / `TRIGGER_EVENT` 阶段不存在（不在 `TracePhase` 枚举，见 §4.1）
> - `ATTRIBUTE_RECALC` 只记录值实际变化的属性——幂等重算（值未变）不产生事件
> - 树状视图载体：`src/presentation/modules/haotian/views/DebugTimeline.vue`（消费 `unified-debug-tree.deriveDebugTree` 派生的 `DebugTreeEntry`，非直接消费 `TraceEventCollector` 树）

## §4 数据模型

### 4.1 追踪阶段枚举

```typescript
// src/shared/types/trace-event.ts

export const TracePhase = {
  // 战斗流程
  BATTLE_LIFECYCLE:  'battle_lifecycle',
  TURN_FLOW:         'turn_flow',
  ACTION_EXECUTION:  'action_execution',

  // 计算链路
  DAMAGE_CALCULATION: 'damage_calculation',
  HEAL_CALCULATION:   'heal_calculation',
  ATTRIBUTE_RECALC:   'attribute_recalc',

  // Buff 系统
  BUFF_LIFECYCLE:    'buff_lifecycle',
  BUFF_TRIGGER:      'buff_trigger',
  PASSIVE_TRIGGER:   'passive_trigger',

  // AI 决策
  AI_DECISION:       'ai_decision',

  // 配置与校验
  CONFIG_LOAD:       'config_load',
  CONFIG_VALIDATION: 'config_validation',
} as const

export type TracePhase = (typeof TracePhase)[keyof typeof TracePhase]
```

> **边界声明**：`TracePhase` 只描述"正在发生的领域阶段"。**错误/警告不属于任何 phase**——catch 块不是阶段而是事件，走错误通道（`addDebugLog` + 显式 level），禁止为错误编造 phase。

### 4.2 结构化追踪事件

```typescript
export interface TraceEvent {
  /** 事件唯一 ID（自动生成） */
  id: string
  /** 关联 ID — 同一因果链的所有事件共享此 ID */
  correlationId: string
  /** 父事件 ID — 构成树状嵌套 */
  parentId?: string
  /** 追踪阶段 */
  phase: TracePhase
  /** 战斗实例 ID — 隔离多场战斗 */
  battleId?: string
  /** 回合号 */
  turn?: number
  /** 来源实体 ID（供 actorId 过滤索引） */
  sourceId?: string
  /** 目标实体 ID（供 actorId 过滤索引） */
  targetId?: string
  /** 时间戳（performance.now()，非 Date.now()） */
  timestamp: number
  /** 结构化 payload — 按 phase 不同而不同 */
  payload: Record<string, unknown>
  /** 人类可读摘要（仅用于快速扫读，不作为程序输入） */
  summary: string
  /** 级别（字符串级联常量 TraceLevel，与数值型 LogLevel 独立） */
  level: TraceLevel
}
```

### 4.3 与现有类型的关系

| 现有类型 | 处置 |
|----------|------|
| `DamageBreakdown` / `DamageStep`（`domain/battle/combat-record.ts`） | **保留**。`DAMAGE_CALCULATION` 事件的 `payload.steps` 直接引用，不重复定义。**steps 只记录实际发生数值变换的环节**——无变换节点（快照/跳过）不记录，值在 payload 顶层 |
| `CalculationBreakdown`（`domain/attribute/types.ts`） | **保留**。`ATTRIBUTE_RECALC` 事件的 `payload.before/after` 直接引用；**幂等重算（值未变）不产生事件** |
| `SkillWeight`（`domain/battle/ai/AIPriorityStrategy.ts`） | **保留**。`breakdown: WeightBreakdownItem[]`（`{ label, value }` 逐项贡献，如 `{ label: '低血量队友', value: 40 }`），`reason` 由 breakdown 生成（`+40 低血量队友`） |
| `StepExecutionContext`（`domain/battle/type/types.ts`） | **扩展**：`readonly trace?: TraceScope`——贯穿载体，全链路已有 context 参数，**零新增参数**（§4.5.2） |
| `PassiveTriggerContext`（`domain/battle/type/types.ts`） | **对齐**：从 `TraceScope` 统一取值 |

### 4.4 TraceScope —— correlationId 作用域

```typescript
// src/shared/types/trace-event.ts

export interface TraceScopeMeta {
  battleId?: string
  turn?: number
}

export interface TraceScope {
  readonly correlationId: string
  readonly phase: TracePhase
  /** 本 scope 事件的挂载点（根 scope 为 undefined；供 emit 时作 parentId） */
  readonly parentId?: string
  readonly meta?: TraceScopeMeta
  /** 派生子 scope：correlationId/meta 不变，phase 与 parentId 可覆盖 */
  child(phase: TracePhase, parentId?: string): TraceScope
}

// 端口接口（src/domain/port/IDebugTracePort.ts）
export interface IDebugTracePort {
  /** 发射事件，返回事件 id（供子事件挂 parentId） */
  emit(event: TraceEvent): string
  isEnabled(phase: TracePhase): boolean
  beginScope(correlationId: string, phase: TracePhase, meta?: TraceScopeMeta, parentId?: string): TraceScope
}
```

**关键设计：`correlationId` 在整条因果链上保持不变，树的嵌套关系由每个事件的 `parentId` 表达。**

### 4.5 correlationId 生命周期与流动机制

#### 4.5.1 根 scope 的创建点

**`BattleExecutor.executeParticipantAction()` —— 每"一次行动"一个 scope**，覆盖从 AI 决策到结算的完整因果链：

```
executeParticipantAction(battle, participant)
  │  const base = tracePort.beginScope(`corr_${turn}_${++seq}`, ACTION_EXECUTION, {battleId, turn})
  │  const execId = tracePort.emit(createTraceEvent({ phase: ACTION_EXECUTION, parentId: base.parentId, ... }))
  │  const actionScope = base.child(ACTION_EXECUTION, execId)   // 子事件 parentId = ACTION_EXECUTION 事件 id
  │
  ├─ aiInstance.makeDecision(battleState, participant, base)
  │     └─ emit(AI_DECISION, base)                              // 决策挂根（parentId=undefined）
  │     └─ skillManager.executeSkill(..., ctx)                  // ctx.trace = scope（StepExecutionContext）
  │           └─ SkillExecutor.executeStep(skillStep, action, source, target, context)
  │                 ├─ emit(ACTION_EXECUTION, context.trace)
  │                 ├─ DamageCalculator.calculateDamage(..., context)
  │                 │     └─ emit(DAMAGE_CALCULATION, context.trace, { steps })  // payload.steps 直接复用
  │                 ├─ HealCalculator.calculateHeal(..., context)
  │                 └─ BuffSystem.addBuff(..., context)
  │                       └─ emit(BUFF_LIFECYCLE, context.trace)
  │
  └─ 被动触发链（BEFORE_ATTACK / DAMAGE_TAKEN …）
        └─ createPassiveContext(phase, battle, { trace: scope })
              └─ emit(PASSIVE_TRIGGER, context.trace)
```

#### 4.5.2 贯穿载体：`StepExecutionContext.trace`（零新增参数）

scope 搭在已有 context 上流动：`SkillExecutor`、`DamageCalculator`、`HealCalculator`、`BuffSystem` **已经全部接收 `context?: StepExecutionContext`**；发射点从 `context.trace` 取即可——**不需要为 trace 新增参数穿过调用链**。

#### 4.5.3 命名空间统一

`correlationId` 是战斗内自增的关联键（`corr_${turn}_${seq}`），同一因果链共享；**`TraceEvent.id` 才是每个事件的唯一 ID**（`evt_${seq}`，createTraceEvent 生成）。禁止自造独立命名空间（`trace_dmg_N` / `buff_apply_N` / `pas_N`）。

#### 4.5.4 并发安全

`BattleDataGenerator` 批量生成多场战斗时多场战斗可能交错执行；隐式"当前 scope"（AsyncLocalStorage / 全局变量）在 `async/await` 边界会串场。**显式参数传递无此问题——scope 是值对象，随调用链流动，天然隔离。**

#### 4.5.5 作用域结束

无需显式 close。scope 是纯数据（correlationId + meta + child()），emit 时读取，`executeParticipantAction` 返回即自然消亡。

### 4.6 双端口边界

| | `IDebugTracePort` | `IBattleLogManager` |
|---|---|---|
| 语义 | 领域事件的结构化投影（正在发生什么） | 面向人的日志（出错了 / 系统消息） |
| 数据形态 | `TraceEvent`（phase + payload + correlationId） | `LogEntry`（level + message + context/error） |
| 消费者 | `TraceEventCollector` → 因果链视图 | `DebugLogDialog` 扁平列表、战斗文本 |
| 级别 | trace / debug / info | warn / error |
| 错误转发 | 无 | ERROR 级转发 `console.error` |
| 持久化 | 战斗结束 → `RecordedBattle.traceEvents` | 内存分桶 + 导出 |
| 失败语义 | emit 永不抛异常 | 同左 |

**addDebugLog 调用点三分法**：

| 类别 | 处置 | 示例 |
|---|---|---|
| **错误/警告路径** | **保留** `addDebugLog`，强制显式 `level: WARN/ERROR` + 附 error/context | 保存/加载战斗记录失败、Buff 错误、AI catch、自动战斗 catch |
| **调试信息路径** | 迁移到 `tracePort.emit`（phase 有对应）或**直接删除**（无对应且无价值） | `执行技能 X`、`回合 N 执行完成`、`注册BUFF脚本` |
| **战斗叙事文本** | **不动**——那是 `addBattleLog` 的领域，不在调试日志范围 | `角色[名] 被控制，无法行动` |

### 示例 3 · 被动因果取证（"为什么没触发"）

**调试问题**："荆棘反甲明明 100% 触发，为什么这次没反应？"

```typescript
// ✓ 触发
tracePort.emit({
  phase: TracePhase.PASSIVE_TRIGGER,
  correlationId, parentId: context.trace.parentId,
  level: 'debug',
  summary: `被动触发 [${entity.name}] ${config.name} (${config.trigger})`,
  payload: {
    passiveId: config.skillId, owner: entity.name, trigger: config.trigger,
    verdict: 'TRIGGERED',
    checks: {
      phaseMatch: true,
      cooldown: { ready: true, remaining: 0 },
      probability: { required: 1.0, roll: 0.42, passed: true },
      maxTriggers: { limit: -1, used: 3 },
      condition: { expr: config.condition, passed: true },
      targetAlive: true,
    },
  },
})

// ✗ 跳过 — 用 trace 级，默认折叠（UI 勾选「trace 细节」后可见）
tracePort.emit({
  phase: TracePhase.PASSIVE_TRIGGER,
  correlationId,
  level: 'trace',             // ← 跳过用 trace 级，默认隐藏
  summary: `被动跳过 [${entity.name}] ${config.name}：冷却中(剩1回合)`,
  payload: {
    passiveId: config.skillId, owner: entity.name, trigger: config.trigger,
    verdict: 'SKIPPED',
    skipReason: 'COOLDOWN',   // ← 枚举：COOLDOWN | PROBABILITY | CONDITION | MAX_TRIGGERS | DEAD | PHASE_MISMATCH
    checks: {
      phaseMatch: true,
      cooldown: { ready: false, remaining: 1, lastTriggeredTurn: 2 },
    },
  },
})
```

### 示例 5 · 回合流程

```typescript
// 发射点：BattleSystem.processTurnInternal() 的回合开始/结束位置
// 回合事件没有"行动 scope"（回合先于行动存在），correlationId 自生成或复用 battleId 派生
tracePort.emit({
  phase: TracePhase.TURN_FLOW,
  battleId, turn,
  level: 'info',
  summary: `回合 ${turn} 开始 · 行动顺序: ${turnOrder.map(id => names[id]).join(' → ')}`,
  payload: {
    action: 'TURN_START',
    turnOrder,
    aliveCount: { ally: 2, enemy: 1 },
    energyGain: 15,
    passiveTriggers: { fired: 2, skipped: 1 },
  },
})
```

## §6 编码规范

### 6.1 发射点写法

```typescript
// ✅ 先查开关，再构建 payload（热路径零开销）
if (tracePort.isEnabled(TracePhase.DAMAGE_CALCULATION)) {
  tracePort.emit({ ..., payload: buildDamagePayload(breakdown) })
}

// ✅ payload 里放事实和数字，不放形容词
payload: { probability: 0.6, roll: 0.73, passed: false }

// ✅ summary 用固定模板，便于扫读和文本搜索
summary: `伤害计算 ${source}→${target} ${base}→${final}${crit ? ' ★暴击' : ''}`

// ✅ 子事件带 parentId，构成树
parentId: context.trace.parentId

// ✅ trace 一律从 context.trace / scope 取，禁止自行 newTraceId
correlationId: context.trace.correlationId
```

### 6.2 禁止写法

```typescript
// ❌ 字符串插值承载语义（下游只能正则）
emit({ summary: `概率 ${0.6 * 100}%，roll 了 ${roll}，没通过` })

// ❌ 形容词代替事实
emit({ summary: '伤害被大幅削减' })

// ❌ 无开关检查的昂贵构建
emit({ payload: serializeEntireBattleState() })

// ❌ 孤立事件（无 correlationId / parentId）——自造 traceId 命名空间（trace_dmg_N / buff_apply_N / pas_N）同样禁止
emit({ phase: TracePhase.DAMAGE_CALCULATION })

// ❌ 领域层直接 console.log
console.log('初始化战斗数据', battleData)
console.log(`${participant.name} chose skill`, skillId)

// ❌ 记录"值没变"的幂等事件（快照/跳过/重算无变化）——无变换不记录
steps.push({ stepName: 'rawDamage', before: x, after: x })   // 值在 payload 顶层，不重复打点
```

### 6.3 级别约定

| 级别 | 语义 | 默认 | 示例 |
|------|------|------|------|
| `error` | 不该发生的事发生了 | 开 | 配置错误、脚本异常、递归超限（走错误通道，`addDebugLog` + level） |
| `warn` | 可恢复的异常 | 开 | 技能降级为普攻、目标失效回退（同上） |
| `info` | 关键状态迁移 | 开 | 战斗开始/结束、回合切换（TURN_FLOW） |
| `debug` | 完整因果链节点 | 开 | 伤害计算、AI 决策、Buff 施加/移除/刷新（BUFF_LIFECYCLE）、被动触发 |
| `trace` | 高频细节与"跳过"记录 | **关（UI 默认隐藏）** | 属性重算（ATTRIBUTE_RECALC，仅值变化时）、被动跳过、监听器分发明细 |

## §8 典型调试场景（验收基准）

系统设计的目标：以下四个调试会话**都能在 30 秒内完成**。开发新功能时对照这些场景是否仍然成立：

### 故事 A · 伤害取证

> "第 3 回合剑士对史莱姆的伤害为什么是 85？"

操作：过滤 `phase=damage_calculation` + `actor=剑士` → 点开因果链 → 看到 `steps[]` 逐步 `before→after`。

**不需要打开任何源码。**

### 故事 B · 决策取证

> "为什么 AI 这回合选了治疗？"

操作：过滤 `phase=ai_decision` → 看到三个候选的权重数字与 breakdown → 看到 `hasLowHealthAlly: true` 贡献了 +40。

**不需要在 `AIPriorityStrategy` 里加 `console.log`。**

### 故事 C · 被动取证

> "荆棘反甲为什么没触发？"

操作：过滤 `phase=passive_trigger` + `owner=史莱姆` + 展开 trace 级 → 看到 `verdict: SKIPPED, skipReason: COOLDOWN, remaining: 1`。

**不需要猜测，不需要复现。**

### 故事 D · 跨战斗对比

> "同一个技能，为什么第 2 场比第 1 场伤害高？"

操作：分别导出两场战斗的 `TraceEvent[]` → 按 `correlationId` 对齐同名因果链 → diff 两条 `steps[]` → 看到差异在 `damageBoost` 一步。

**面板提供导出功能，导出的 JSON 天然可 diff。**

## 一句话总结

**调试日志不是"开发时顺便打的 print"，而是领域运行时状态的结构化投影。** 一个 `correlationId` 串起一条因果链（根在 `BattleExecutor`，沿已有的 `StepExecutionContext` 零成本贯穿），一个 `TracePhase` 标明一个运行时节点，一个结构化 `payload` 消灭所有正则解析，一个独立错误通道承接 catch 块。**只记录"发生了变换"的事实**——值没变的快照/跳过/幂等重算不产生事件，让调试者看到的每一条都有信息量。
